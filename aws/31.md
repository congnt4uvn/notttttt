## 2. What Is Amazon SQS?

Amazon Simple Queue Service (Amazon SQS) is a fully managed message queuing service. It allows application components to communicate asynchronously without requiring them to be available at the same time.

A producer sends a message to a queue. A consumer receives and processes that message.

```text
+------------------+       +------------------+       +------------------+
| Spring Boot API  | ----> |    SQS Queue     | ----> | Worker / Lambda  |
|    Producer      |       |    Messages      |       |    Consumer      |
+------------------+       +------------------+       +------------------+
```

Example: an e-commerce API accepts an order. Instead of sending an email, generating an invoice, and updating analytics before returning the HTTP response, it can save the order and enqueue work for background processing.

### Why use a queue?

- **Decoupling:** the producer does not need to know how the consumer works.
- **Buffering:** messages can wait while consumers are busy or temporarily unavailable.
- **Load leveling:** consumers process work at a controlled rate.
- **Resilience:** temporary consumer failures do not necessarily lose queued work.
- **Asynchronous processing:** the API can respond without waiting for every downstream task.

A queue does not automatically make every workflow reliable. The application still needs durable state, retries, monitoring, and duplicate-safe processing.

## 3. Core SQS Concepts

| Term | Meaning |
|---|---|
| Queue | A named destination that stores messages |
| Producer | Application or service that sends messages |
| Consumer | Application or service that receives and processes messages |
| Message body | Payload containing the application data |
| Message ID | Identifier assigned to a message by SQS |
| Receipt handle | Token returned when a message is received; used to delete or change its visibility |
| Visibility timeout | Period during which a received message is hidden from other consumers |
| Dead-letter queue | Separate queue for messages that repeatedly fail processing |
| Long polling | Receive operation that waits briefly for messages instead of returning immediately |

### Example message

A producer might send this JSON body:

```json
{
  "eventId": "evt-10001",
  "eventType": "ORDER_CREATED",
  "orderId": "O501",
  "customerId": "C1001",
  "createdAt": "2026-11-04T09:30:00Z"
}
```

Keep messages reasonably small. SQS message size has a service limit; for large files or documents, store the payload in Amazon S3 and send a reference in the message.

## 4. Standard Queue vs. FIFO Queue

SQS offers Standard and FIFO queue types.

| Feature | Standard queue | FIFO queue |
|---|---|---|
| Throughput | Very high, scales automatically | Supports high throughput when configured appropriately |
| Delivery | At-least-once; duplicates are possible | Exactly-once processing is not guaranteed for arbitrary consumer side effects; deduplication reduces duplicate sends |
| Ordering | Best-effort ordering | Preserves order within a message group |
| Message group ID | Not used | Required for messages sent to FIFO queues |
| Deduplication ID | Not used | Supports deduplication for a configured interval |
| Typical use | Independent background jobs | Workflows that require ordered processing per group |

### Important: FIFO does not make external side effects exactly once

FIFO queues provide ordering within a message group and producer-side deduplication features. A consumer can still perform an action and fail before deleting the message. The message may be delivered again after visibility expires.

Therefore, consumers should still be idempotent.

### Choosing a queue

Choose Standard when:

- High throughput matters.
- Messages can be processed independently.
- Occasional duplicates and out-of-order delivery can be handled by the application.

Choose FIFO when:

- Order matters within a business entity or workflow.
- You can define a useful message group, such as `ORDER#O501`.
- The throughput and grouping model fits the application.

## 5. How Message Consumption Works

The basic SQS consumer flow:

```text
1. Producer sends message
          |
          v
2. SQS stores message
          |
          v
3. Consumer receives message
          |
          v
4. Message becomes invisible
   during visibility timeout
          |
          v
5. Consumer processes message
          |
          v
6. Consumer deletes message
          |
          v
7. Message is removed from the queue
```

If the consumer does not delete the message before the visibility timeout expires, SQS can make it visible again for another receive attempt.

### At-least-once delivery

For Standard queues, a message can be delivered more than once. Design processing so that repeated delivery does not repeat an irreversible business action.

Example: before charging a payment, check a durable idempotency record keyed by the event or order ID.

## 6. Visibility Timeout

Visibility timeout is the period during which a received message is hidden from other consumers.

Example:

```text
Queue contains message M1
        |
Consumer A receives M1
        |
M1 becomes invisible for 60 seconds
        |
Consumer A processes M1
        |
+-----------------------------+
| If successful: delete M1    |
| If not deleted: it can      |
| become visible again        |
+-----------------------------+
```

### How should you choose the timeout?

- Set it longer than the normal processing time.
- Include enough time for expected variability.
- Avoid setting it extremely high if failed messages need to be retried promptly.
- For long-running jobs, extend visibility while processing with `ChangeMessageVisibility`.
- Configure the function or worker timeout consistently with the queue's visibility timeout.

A common starting point is to set visibility timeout to several times the expected processing duration, then validate with actual workload measurements. For Lambda event source mappings, follow the documented relationship between function timeout, batching, and queue visibility timeout.

### Change visibility with AWS CLI

```bash
aws sqs change-message-visibility \
  --queue-url "$QUEUE_URL" \
  --receipt-handle "$RECEIPT_HANDLE" \
  --visibility-timeout 120 \
  --region ap-southeast-1
```

The receipt handle must come from the latest receive response for that message.

## 7. Message Retention, Delay, and Long Polling

### 7.1 Message retention

SQS retains messages for a configured period. The retention period can be configured from 1 minute up to 14 days.

Choose a period based on how long the system can be unavailable and how long delayed processing remains useful.

### 7.2 Delay queues

A delay queue postpones delivery of new messages for a configured period.

Use cases:

- Schedule a short delay before a task becomes available.
- Avoid immediate processing during a controlled workflow.
- Implement simple delayed work.

SQS delay queues are not a replacement for a full scheduling system for complex calendar-based workflows.

### 7.3 Short polling vs. long polling

| Short polling | Long polling |
|---|---|
| Returns immediately based on sampled servers | Waits for a message or the wait period to end |
| Can return empty responses when messages exist elsewhere | Reduces empty receives |
| May increase request volume | Often reduces cost and unnecessary requests |

Enable long polling by setting `ReceiveMessageWaitTimeSeconds` or using `WaitTimeSeconds` on receive calls. The maximum long-poll wait is 20 seconds.

Example:

```bash
aws sqs receive-message \
  --queue-url "$QUEUE_URL" \
  --wait-time-seconds 20 \
  --max-number-of-messages 10 \
  --region ap-southeast-1
```

## 8. Dead-Letter Queues (DLQs)

A dead-letter queue stores messages that could not be processed successfully after a configured number of receives.

```text
                 Main Queue
                     |
                     v
                Consumer
                     |
          +----------+----------+
          |                     |
          v                     v
      Success                Repeated failure
          |                     |
          v                     v
      Delete message        Redrive to DLQ
                                |
                                v
                         Investigate / replay
```

### Why use a DLQ?

- Isolate poison messages that always fail.
- Prevent repeated failures from consuming worker capacity forever.
- Preserve failed messages for investigation.
- Support controlled redrive after the underlying problem is fixed.

### Configure a redrive policy

The main queue's redrive policy identifies the DLQ ARN and the maximum receive count. The DLQ must be the same queue type as the source queue (Standard with Standard, FIFO with FIFO).

Example policy JSON:

```json
{
  "deadLetterTargetArn": "arn:aws:sqs:ap-southeast-1:123456789012:Orders-DLQ",
  "maxReceiveCount": 5
}
```

A message is moved to the DLQ after it exceeds the configured receive count according to the queue's redrive behavior.

### DLQ operational practices

1. Monitor the number of visible messages in the DLQ.
2. Inspect the error and message payload safely.
3. Identify whether the failure is caused by bad data, a code bug, or a dependency outage.
4. Fix the cause before redriving.
5. Replay messages in a controlled way.
6. Keep sensitive data out of logs and diagnostic output.

## 9. AWS CLI: Create and Use SQS Queues

The examples use Region `ap-southeast-1`. Queue URLs and ARNs are account- and Region-specific; capture them from command output rather than guessing.

### 9.1 Check your identity and Region

```bash
aws sts get-caller-identity
aws configure get region
```

### 9.2 Create a Standard queue

```bash
aws sqs create-queue \
  --queue-name Orders \
  --attributes '{
    "VisibilityTimeout": "60",
    "MessageRetentionPeriod": "345600",
    "ReceiveMessageWaitTimeSeconds": "20"
  }' \
  --region ap-southeast-1
```

The retention value above is four days, expressed in seconds.

Capture the returned `QueueUrl`:

```bash
QUEUE_URL="PASTE_QUEUE_URL_FROM_CREATE_QUEUE_OUTPUT"
```

### 9.3 Get the queue ARN

```bash
aws sqs get-queue-attributes \
  --queue-url "$QUEUE_URL" \
  --attribute-names QueueArn All \
  --region ap-southeast-1
```

### 9.4 Send a message

```bash
aws sqs send-message \
  --queue-url "$QUEUE_URL" \
  --message-body '{
    "eventId": "evt-10001",
    "eventType": "ORDER_CREATED",
    "orderId": "O501"
  }' \
  --region ap-southeast-1
```

### 9.5 Receive a message

```bash
aws sqs receive-message \
  --queue-url "$QUEUE_URL" \
  --max-number-of-messages 5 \
  --wait-time-seconds 20 \
  --attribute-names All \
  --message-attribute-names All \
  --region ap-southeast-1
```

The response includes a receipt handle. Save the latest receipt handle for the message you intend to delete.

### 9.6 Delete a message

```bash
aws sqs delete-message \
  --queue-url "$QUEUE_URL" \
  --receipt-handle "$RECEIPT_HANDLE" \
  --region ap-southeast-1
```

Deleting with a receipt handle acknowledges successful processing. Do not delete a message before the business operation has safely completed.

### 9.7 Create a DLQ

```bash
aws sqs create-queue \
  --queue-name Orders-DLQ \
  --region ap-southeast-1
```

Retrieve its ARN using `get-queue-attributes`, then configure the main queue's redrive policy. Example:

```bash
aws sqs set-queue-attributes \
  --queue-url "$QUEUE_URL" \
  --attributes '{
    "RedrivePolicy": "{\"deadLetterTargetArn\":\"PASTE_DLQ_ARN\",\"maxReceiveCount\":\"5\"}"
  }' \
  --region ap-southeast-1
```

### 9.8 Create a FIFO queue

FIFO queue names must end with `.fifo`.

```bash
aws sqs create-queue \
  --queue-name Orders.fifo \
  --attributes '{
    "FifoQueue": "true",
    "ContentBasedDeduplication": "true",
    "VisibilityTimeout": "60",
    "ReceiveMessageWaitTimeSeconds": "20"
  }' \
  --region ap-southeast-1
```

Send a FIFO message with a group ID:

```bash
aws sqs send-message \
  --queue-url "$FIFO_QUEUE_URL" \
  --message-body '{"orderId":"O501","status":"CREATED"}' \
  --message-group-id "ORDER#O501" \
  --region ap-southeast-1
```

When content-based deduplication is disabled, provide a `MessageDeduplicationId` on each send. Content-based deduplication uses a hash of the message body; message attributes are not part of that hash.

### 9.9 Delete a queue after the lab

```bash
aws sqs delete-queue \
  --queue-url "$QUEUE_URL" \
  --region ap-southeast-1
```

**Cost and safety note:** SQS is billed based on requests and applicable data transfer or related features. Review current regional pricing. Do not delete production queues or queues containing data you still need.

## 10. Spring Boot Integration with AWS SDK for Java 2.x

This section shows a simple producer and consumer using the low-level `SqsClient`.

### 10.1 Maven dependencies

Use the AWS SDK for Java 2.x BOM and set `${aws.sdk.version}` to an approved current version.

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>software.amazon.awssdk</groupId>
            <artifactId>bom</artifactId>
            <version>${aws.sdk.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>sqs</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
</dependencies>
```

### 10.2 Configuration

```yaml
app:
  aws:
    region: ap-southeast-1
  sqs:
    orders-queue-url: ${ORDERS_QUEUE_URL}
```

```java
@Configuration
public class SqsConfiguration {

    @Bean
    SqsClient sqsClient(
            @Value("${app.aws.region}") String region) {

        return SqsClient.builder()
                .region(Region.of(region))
                .credentialsProvider(
                    DefaultCredentialsProvider.create()
                )
                .build();
    }
}
```

Use an IAM role when the application runs on AWS. Do not put long-lived access keys in `application.yml`.

### 10.3 Message DTO

```java
public record OrderCreatedEvent(
        String eventId,
        String eventType,
        String orderId,
        String customerId
) {}
```

### 10.4 Producer service

```java
@Service
public class OrderMessageProducer {

    private final SqsClient sqsClient;
    private final ObjectMapper objectMapper;
    private final String queueUrl;

    public OrderMessageProducer(
            SqsClient sqsClient,
            ObjectMapper objectMapper,
            @Value("${app.sqs.orders-queue-url}") String queueUrl) {
        this.sqsClient = sqsClient;
        this.objectMapper = objectMapper;
        this.queueUrl = queueUrl;
    }

    public void publish(OrderCreatedEvent event) {
        try {
            String body = objectMapper.writeValueAsString(event);

            SendMessageRequest request =
                SendMessageRequest.builder()
                    .queueUrl(queueUrl)
                    .messageBody(body)
                    .build();

            sqsClient.sendMessage(request);
        } catch (JsonProcessingException e) {
            throw new IllegalArgumentException(
                "Could not serialize order event", e
            );
        }
    }
}
```

### 10.5 Consumer service

The following method illustrates receiving one batch. In production, run a managed polling loop or use an event-driven integration such as Lambda. Do not start an unmanaged infinite loop inside a web request thread.

```java
@Service
public class OrderMessageConsumer {

    private final SqsClient sqsClient;
    private final ObjectMapper objectMapper;
    private final String queueUrl;

    public OrderMessageConsumer(
            SqsClient sqsClient,
            ObjectMapper objectMapper,
            @Value("${app.sqs.orders-queue-url}") String queueUrl) {
        this.sqsClient = sqsClient;
        this.objectMapper = objectMapper;
        this.queueUrl = queueUrl;
    }

    public void pollOnce() {
        ReceiveMessageResponse response =
            sqsClient.receiveMessage(
                ReceiveMessageRequest.builder()
                    .queueUrl(queueUrl)
                    .maxNumberOfMessages(5)
                    .waitTimeSeconds(20)
                    .build()
            );

        for (Message message : response.messages()) {
            try {
                OrderCreatedEvent event =
                    objectMapper.readValue(
                        message.body(),
                        OrderCreatedEvent.class
                    );

                processIdempotently(event);

                sqsClient.deleteMessage(
                    DeleteMessageRequest.builder()
                        .queueUrl(queueUrl)
                        .receiptHandle(message.receiptHandle())
                        .build()
                );
            } catch (Exception e) {
                // Log a safe error summary. Do not delete the message.
                // It can become visible again after the visibility timeout.
                // Configure a DLQ to isolate repeatedly failing messages.
            }
        }
    }

    private void processIdempotently(OrderCreatedEvent event) {
        // Check/store eventId in a durable idempotency store.
        // Perform the business action only once for that event.
    }
}
```

This is a teaching skeleton, not a complete production consumer. In particular, implement durable idempotency, structured error handling, bounded concurrency, shutdown handling, and metrics. Ensure a failed message is not accidentally acknowledged.

### 10.6 Controller example

```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderMessageProducer producer;

    public OrderController(OrderMessageProducer producer) {
        this.producer = producer;
    }

    @PostMapping("/{orderId}/events")
    public ResponseEntity<Void> publishOrderCreated(
            @PathVariable String orderId) {

        OrderCreatedEvent event = new OrderCreatedEvent(
            UUID.randomUUID().toString(),
            "ORDER_CREATED",
            orderId,
            "C1001"
        );

        producer.publish(event);

        return ResponseEntity.accepted().build();
    }
}
```

HTTP `202 Accepted` communicates that the request has been accepted for asynchronous processing. It does not mean the background task has completed.

## 11. Reliable Messaging Patterns

### 11.1 The delete-after-success rule

A consumer should delete a message only after the required business operation has completed successfully.

```text
Receive message
      |
      v
Validate payload
      |
      v
Check idempotency key
      |
      v
Perform business action
      |
      v
Persist successful result
      |
      v
Delete SQS message
```

If the consumer crashes after the business action but before deletion, the message may be delivered again. Idempotency is what prevents the repeated delivery from duplicating the business action.

### 11.2 Idempotency

Use a stable event ID or business operation ID.

Example:

```text
eventId = evt-10001

Before processing:
    Has evt-10001 already completed?

If yes:
    Do not repeat the business side effect.
    Acknowledge the message.

If no:
    Perform the operation.
    Record evt-10001 as completed.
    Acknowledge the message.
```

The idempotency record and business update should be coordinated carefully. If they are stored in separate systems, consider failure windows and use a transactional or outbox/inbox design where appropriate.

### 11.3 Retry strategy

- Let transient failures retry.
- Use bounded retry policies in the consumer.
- Configure a DLQ and a sensible maximum receive count.
- Avoid tight application retry loops that amplify outages.
- Use exponential backoff with jitter for downstream APIs.
- Alert when DLQ depth or message age increases.

### 11.4 Transactional outbox pattern

A common reliability problem occurs when an application saves an order in a database but fails before publishing the event.

The transactional outbox pattern writes the business record and an outbox record in the same database transaction. A separate publisher sends outbox events to SQS and marks them as published.

```text
Spring Boot API
      |
      v
Database transaction
   +------------------+
   | Save Order       |
   | Save Outbox Event|
   +------------------+
      |
      v
Outbox Publisher
      |
      v
     SQS
      |
      v
   Consumer
```

The publisher may send an event more than once, so consumers still need idempotency. For DynamoDB-backed applications, DynamoDB transactions and Streams can be used to implement related event-publication designs.

## 12. Security Best Practices

1. Use IAM roles for producers and consumers running on AWS.
2. Grant only required actions, such as `sqs:SendMessage` to a producer and receive/delete permissions to a consumer.
3. Use queue policies to control cross-account access where needed.
4. Use server-side encryption for messages when required by your security policy.
5. Use TLS for requests in transit.
6. Avoid putting secrets, payment card data, or unnecessary personal data in message bodies.
7. Restrict who can read from DLQs because they may contain sensitive payloads.
8. Monitor queue policy changes and access.
9. Use VPC endpoints for private access from supported VPC workloads where appropriate.
10. Rotate and review permissions as services change.

Example IAM policy concept for a producer (replace account ID and queue name):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "sqs:SendMessage"
      ],
      "Resource": "arn:aws:sqs:ap-southeast-1:123456789012:Orders"
    }
  ]
}
```

A consumer needs additional permissions such as `sqs:ReceiveMessage`, `sqs:DeleteMessage`, and `sqs:GetQueueAttributes`. Keep producer and consumer roles separate when practical.

## 13. Monitoring and Operations

Important CloudWatch metrics include:

| Metric | What it tells you |
|---|---|
| `ApproximateNumberOfMessagesVisible` | Approximate number of messages ready to be received |
| `ApproximateNumberOfMessagesNotVisible` | Approximate number currently in flight |
| `ApproximateNumberOfMessagesDelayed` | Approximate number delayed |
| `ApproximateAgeOfOldestMessage` | Approximate age of the oldest available message |
| `NumberOfMessagesSent` | Messages sent |
| `NumberOfMessagesReceived` | Messages received |
| `NumberOfMessagesDeleted` | Messages deleted |

Metric names and availability can vary by queue type and monitoring context. SQS queue counts are approximate, not exact transactional counters.

### Useful alarms

- DLQ visible-message count greater than zero.
- Oldest message age exceeds the business processing target.
- Visible message count grows continuously.
- In-flight message count remains high.
- Consumer errors or downstream failures increase.

### Operational questions

- Is the producer sending messages faster than consumers process them?
- Are consumers failing on a particular message type?
- Is visibility timeout shorter than processing duration?
- Is a downstream service throttling the consumer?
- Is the DLQ growing?
- Is the queue retaining messages longer than the business process needs?

## 15. Troubleshooting

| Symptom or error | Possible cause | What to check |
|---|---|---|
| `AccessDenied` | IAM role or queue policy does not allow the operation | Queue ARN, IAM action, resource policy |
| `QueueDoesNotExist` | Incorrect queue URL, Region, or account | Use the URL returned by `create-queue` |
| Message appears more than once | Standard queue delivery behavior or consumer did not delete it | Idempotency and delete-after-success logic |
| Message repeatedly reappears | Consumer crashes, fails, or visibility timeout expires | Consumer logs and visibility timeout |
| Messages move to DLQ too quickly | Receive count too low or transient errors | Redrive policy and processing reliability |
| Queue depth keeps increasing | Producers outpace consumers | Worker concurrency, downstream capacity, message age |
| Consumer processes the same message concurrently | Visibility timeout too short or duplicate delivery | Processing duration, timeout, idempotency |
| FIFO send fails | Missing group ID or required deduplication ID | Queue type and send parameters |
| Long poll returns no messages | Queue may be empty or messages may be invisible | Queue depth, visibility, correct queue URL |
| Consumer cannot delete a message | Wrong or stale receipt handle | Use the receipt handle from the latest receive |

## 16. Practical Exercises with Answers

### Exercise 1 — What problem does SQS solve?

**Answer:** SQS decouples producers and consumers. It buffers messages so components can operate asynchronously and tolerate temporary differences in availability or processing speed.

### Exercise 2 — Standard or FIFO?

An application processes independent image-resize jobs. High throughput matters, and job order does not matter.

**Answer:** A Standard queue is usually a suitable choice. The consumer must still handle possible duplicate delivery.

### Exercise 3 — Which queue type?

A payment workflow must process events in order for each individual account.

**Answer:** Consider a FIFO queue with `MessageGroupId` set to an account identifier. Design the consumer for retries and idempotency as well.

### Exercise 4 — What happens when visibility timeout expires?

**Answer:** If the message has not been deleted, it can become visible and be received again by another consumer.

### Exercise 5 — Why use long polling?

**Answer:** Long polling waits for messages for a configured period and can reduce empty receive responses and unnecessary request volume.

### Exercise 6 — What is a DLQ?

**Answer:** A dead-letter queue stores messages that exceed the source queue's configured receive threshold, allowing investigation and controlled replay.

### Exercise 7 — Should a consumer delete a message before processing?

**Answer:** No. It should delete only after the required processing has completed successfully. Otherwise, a failure can cause message loss from the application's perspective.

### Exercise 8 — Does FIFO guarantee an external payment is charged exactly once?

**Answer:** No. FIFO ordering and deduplication do not guarantee exactly-once side effects in an external payment system. Use an idempotency key with the payment provider and durable application state.

### Exercise 9 — What is the transactional outbox pattern?

**Answer:** It saves the business change and an event record in the same database transaction. A separate publisher sends the event to the queue, reducing the risk of committing data but losing the corresponding message.

### Exercise 10 — What should you monitor?

**Answer:** Monitor visible messages, in-flight messages, oldest message age, send/receive/delete counts, consumer errors, and DLQ depth.

### Question 1: What is Amazon SQS?

**Model answer:**

Amazon SQS is a managed message queue service. It allows different application components to communicate asynchronously. A producer sends messages to a queue, and a consumer processes them later.

### Question 2: What is the difference between Standard and FIFO queues?

**Model answer:**

A Standard queue supports very high throughput, but messages can be delivered more than once and ordering is not guaranteed. A FIFO queue preserves message order within a message group and supports deduplication features.

### Question 3: What is visibility timeout?

**Model answer:**

Visibility timeout is the period when a message becomes invisible after a consumer receives it. If the consumer does not delete the message before the timeout expires, the message can become visible again.

### Question 4: Why do we need a dead-letter queue?

**Model answer:**

A dead-letter queue stores messages that repeatedly fail processing. It helps us isolate problematic messages, investigate errors, and replay them after fixing the problem.

### Question 5: Why should a consumer be idempotent?

**Model answer:**

A message can be delivered more than once. An idempotent consumer can process the same event again without repeating the business action or creating duplicate records.

## 19. AWS Interview Questions and Answers

**Q1. What is Amazon SQS?**

Amazon SQS is a fully managed message queuing service used to decouple distributed application components.

**Q2. What is the difference between a producer and a consumer?**

A producer sends messages to a queue. A consumer receives and processes messages from that queue.

**Q3. What is at-least-once delivery?**

It means a message is delivered one or more times. Consumers must be able to handle duplicate delivery safely.

**Q4. What is visibility timeout?**

It is the period during which a received message is hidden from other consumers while the current consumer processes it.

**Q5. What happens if a consumer does not delete a message?**

After its visibility timeout expires, the message can become visible and be received again.

**Q6. What is the difference between Standard and FIFO queues?**

Standard queues prioritize very high throughput and provide at-least-once delivery with best-effort ordering. FIFO queues preserve order within message groups and support deduplication features.

**Q7. Does FIFO guarantee exactly-once business processing?**

No. Consumer failures can still lead to repeated processing attempts. External side effects require application-level idempotency.

**Q8. What is a DLQ?**

A dead-letter queue receives messages that exceed the configured receive threshold on the source queue.

**Q9. What is long polling?**

Long polling waits for messages for up to the configured wait time, reducing empty receive responses.

**Q10. What is a receipt handle?**

It is a token returned when a message is received. The consumer uses the latest receipt handle to delete the message or change its visibility.

**Q11. How do you prevent duplicate order processing?**

Use a stable event or order ID as an idempotency key and persist processing state so repeated deliveries do not repeat the business action.

**Q12. What is the transactional outbox pattern?**

It stores a business change and its event in one database transaction. A separate publisher sends the event to SQS.
