## 2. Why Auto Scaling?

An application rarely receives exactly the same amount of traffic all day.

- During quiet periods, two application instances may be enough.
- During a campaign, traffic may increase several times.
- If an instance fails, the application should recover automatically.
- When demand decreases, unnecessary instances should be removed to reduce cost.

**Amazon EC2 Auto Scaling** helps maintain the desired number of EC2 instances and can adjust capacity according to demand.

### Example architecture

```text
                         Internet
                            |
                       Route 53
                            |
                    Application Load
                       Balancer
                      /         \
                 AZ-a             AZ-b
                  |                 |
             Target Group      Target Group
                  |                 |
              EC2 Instance      EC2 Instance
              Spring Boot       Spring Boot
                  \                 /
                   \               /
                    Shared Database
```

The Auto Scaling Group manages the EC2 instances. The load balancer distributes incoming requests to healthy registered targets.

### Main benefits

| Benefit | Explanation |
|---|---|
| High availability | Instances can run in multiple Availability Zones |
| Elasticity | Capacity can increase or decrease with demand |
| Fault recovery | Unhealthy instances can be replaced |
| Cost optimization | Scale in when demand is lower |
| Integration | Works with Elastic Load Balancing and CloudWatch |

Important: Auto Scaling does not make application code automatically resilient. Your application should still handle retries, shared state, database failures, and graceful shutdown.

## 3. Launch Templates

A **Launch Template** defines how EC2 instances should be launched.

It can contain:

- Amazon Machine Image (AMI)
- Instance type
- Key pair
- Security groups
- IAM instance profile
- Storage and block device mappings
- User data
- Network interface settings
- Metadata options
- Instance purchasing options

Launch Templates are preferred over the older Launch Configurations because they support versioning and more launch options.

### 3.1 Example Launch Template configuration

```text
Launch Template: spring-boot-template

AMI: Amazon Linux
Instance type: t3.small
Key pair: my-key
Security group: spring-boot-sg
IAM instance profile: ec2-ssm-and-app-role
Root volume: 20 GiB gp3
User data: install Java and start the application
Metadata: IMDSv2 required
```

Use an IAM instance profile instead of storing AWS access keys on the EC2 instance.

### 3.2 Launch Template versions

A Launch Template can have multiple versions.

```text
Launch Template
    |
    +-- Version 1: application release 1
    |
    +-- Version 2: updated Java configuration
    |
    +-- Version 3: new AMI and application release
```

An Auto Scaling Group can reference a specific version, the default version, or the latest version using the supported version selector.

For production deployments, explicitly controlling the version is often safer than unintentionally following a changing latest version.

### 3.3 Create a Launch Template with AWS CLI

The following is an illustrative command. Replace the AMI, security group, key pair, and IAM profile with resources in your account.

```bash
aws ec2 create-launch-template \
  --region ap-southeast-1 \
  --launch-template-name spring-boot-template \
  --version-description "Initial Spring Boot template" \
  --launch-template-data '{
    "ImageId": "ami-REPLACE_ME",
    "InstanceType": "t3.small",
    "KeyName": "my-key",
    "SecurityGroupIds": ["sg-REPLACE_ME"],
    "IamInstanceProfile": {
      "Name": "ec2-ssm-and-app-role"
    },
    "MetadataOptions": {
      "HttpTokens": "required"
    },
    "BlockDeviceMappings": [{
      "DeviceName": "/dev/xvda",
      "Ebs": {
        "VolumeSize": 20,
        "VolumeType": "gp3",
        "DeleteOnTermination": true
      }
    }]
  }'
```

Inspect the template:

```bash
aws ec2 describe-launch-templates \
  --region ap-southeast-1 \
  --launch-template-names spring-boot-template
```

Inspect versions:

```bash
aws ec2 describe-launch-template-versions \
  --region ap-southeast-1 \
  --launch-template-name spring-boot-template
```

Do not copy an AMI ID from an unrelated region. AMI IDs are region-specific.

## 4. EC2 User Data and Instance Bootstrapping

**User data** is commonly used to run initialization commands when an EC2 instance launches.

Typical tasks include:

- Install Java.
- Download an application artifact.
- Configure environment variables.
- Create directories.
- Start a service.
- Send initialization logs to a known location.

### 4.1 Example User Data for Amazon Linux

This example assumes the application JAR is stored in an S3 bucket and the instance role is authorized to read it. Confirm the package manager and Java package name for the AMI you select.

```bash
#!/bin/bash
set -euxo pipefail

exec > >(tee /var/log/user-data.log | logger -t user-data -s 2>/dev/console) 2>&1

dnf install -y java-17-amazon-corretto-headless awscli

mkdir -p /opt/myapp
aws s3 cp s3://MY-APP-BUCKET/releases/app.jar /opt/myapp/app.jar

cat > /etc/systemd/system/myapp.service <<'EOF'
[Unit]
Description=Spring Boot Application
After=network-online.target
Wants=network-online.target

[Service]
User=root
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/java -jar /opt/myapp/app.jar
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable myapp
systemctl start myapp
```

### 4.2 User Data best practices

1. Make scripts robust and as idempotent as possible.
2. Log output so boot failures can be diagnosed.
3. Do not put passwords, API keys, or long-lived credentials in user data.
4. Use an IAM role to access S3, Systems Manager, and other AWS services.
5. Prefer baking stable dependencies into a tested AMI when startup time matters.
6. Test the script on a single instance before using it in an ASG.
7. Ensure the application becomes healthy before the load balancer sends it production traffic.

User data is not a secrets-management system. Access to instance metadata and instance configuration should be carefully controlled.

## 5. Auto Scaling Groups

An **Auto Scaling Group (ASG)** is a logical group of EC2 instances that Amazon EC2 Auto Scaling manages together.

### 5.1 Capacity settings

An ASG has three important capacity values:

| Setting | Meaning | Example |
|---|---|---:|
| Minimum capacity | Lowest desired number of instances | 2 |
| Desired capacity | Current target capacity | 2 |
| Maximum capacity | Highest allowed number of instances | 6 |

Example:

```text
Minimum: 2
Desired: 2
Maximum: 6
```

The ASG attempts to maintain desired capacity, subject to its configuration and available capacity. Scaling policies can change desired capacity within the minimum and maximum bounds.

### 5.2 Availability Zones

Choose subnets in multiple Availability Zones.

```text
                 Auto Scaling Group
                 Min: 2 / Max: 6
                         |
             +-----------+-----------+
             |                       |
          AZ-a                    AZ-b
             |                       |
       Private subnet          Private subnet
             |                       |
         EC2 instances          EC2 instances
```

Using multiple AZs improves resilience to an AZ-level problem. It does not guarantee that every failure scenario will be handled without interruption.

### 5.3 Create an Auto Scaling Group

First, create or identify:

- A Launch Template.
- Two private subnets in different AZs.
- An ALB target group, if using a load balancer.
- A suitable IAM role and security groups.

Example:

```bash
aws autoscaling create-auto-scaling-group \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg \
  --launch-template "LaunchTemplateName=spring-boot-template,Version=1" \
  --min-size 2 \
  --max-size 6 \
  --desired-capacity 2 \
  --vpc-zone-identifier "subnet-AAA,subnet-BBB" \
  --target-group-arns "arn:aws:elasticloadbalancing:ap-southeast-1:123456789012:targetgroup/my-targets/abcdef1234567890" \
  --health-check-type ELB \
  --health-check-grace-period 180
```

The ARN and subnet IDs above are placeholders. Use real values from your account.

Inspect the ASG:

```bash
aws autoscaling describe-auto-scaling-groups \
  --region ap-southeast-1 \
  --auto-scaling-group-names spring-boot-asg
```

Inspect scaling activities:

```bash
aws autoscaling describe-scaling-activities \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg
```

Scaling activities are particularly useful when an instance cannot launch or the group cannot reach its desired capacity.

## 6. Health Checks: EC2 vs. ELB

Auto Scaling can use different health signals.

| Health check | What it checks | Example failure |
|---|---|---|
| EC2 status checks | Instance and underlying system status | Instance or host system impairment |
| ELB health checks | Target health reported by the load balancer | Application does not respond on the health-check path |

When an ASG uses ELB health checks, it can replace an instance that the load balancer reports as unhealthy, subject to the ASG's health-check behavior and configuration.

### 6.1 Health-check grace period

A new instance may need time to:

- Boot the operating system.
- Install or configure software.
- Download the application.
- Start the JVM.
- Establish connections.
- Become ready to serve requests.

The health-check grace period gives a newly launched instance time to initialize before certain health-check failures can cause replacement.

Do not set it arbitrarily high. A very long grace period can delay recovery from a genuinely failed launch.

### 6.2 Application readiness

For Spring Boot, expose a health endpoint suitable for the load balancer.

For example, with Spring Boot Actuator:

```text
GET /actuator/health
```

Consider separating:

- **Liveness:** Is the application process alive?
- **Readiness:** Is the application ready to receive traffic?

A process can be alive but not ready. Configure the ALB health-check path and success codes to match the endpoint's actual behavior.

## 7. Attach an Auto Scaling Group to a Target Group

An ASG can register launched instances with an Elastic Load Balancing target group and deregister instances when they leave the group.

```text
Client
  |
  v
Application Load Balancer
  |
  v
Target Group
  |
  +------ EC2 instance A
  |
  +------ EC2 instance B
  |
  +------ EC2 instance C

Auto Scaling Group controls instance capacity.
```

Important considerations:

- The instance security group should allow application traffic from the ALB security group.
- The target group port and protocol must match the application listener.
- The health-check path must return an accepted response.
- Instances should be in the correct VPC.
- Deregistration delay gives existing requests time to finish during target removal.

### 7.1 Deregistration and graceful shutdown

When an instance is terminating, the load balancer can stop sending it new requests and allow in-flight requests to complete during the configured deregistration delay.

Your application should also shut down gracefully:

- Stop accepting new work.
- Complete or safely cancel in-flight work.
- Close database connections.
- Flush important buffers.
- Exit within the termination time budget.

Do not assume the load balancer's deregistration delay alone guarantees graceful application shutdown.

## 8. Scaling Policies

Scaling policies determine when and how the ASG changes capacity.

### 8.1 Target tracking scaling

Target tracking tries to maintain a selected metric near a target value.

Examples:

- Average CPU utilization: 50%.
- ALB requests per target: a chosen requests-per-minute target.
- A custom CloudWatch metric representing queue depth or workload.

Concept:

```text
Metric rises above target
          |
          v
Auto Scaling increases capacity
          |
          v
Load is distributed across more instances
          |
          v
Metric moves toward target
```

Target tracking is often a good starting point for applications with a metric that correlates well with required capacity.

### 8.2 Step scaling

Step scaling adjusts capacity by different amounts depending on how far a CloudWatch alarm metric moves beyond thresholds.

Illustrative policy:

| CPU utilization | Example adjustment |
|---|---:|
| 60%–70% | Add 1 instance |
| 70%–85% | Add 2 instances |
| Above 85% | Add 3 instances |

The actual alarm thresholds and adjustment ranges must be designed and tested for the workload.

### 8.3 Scheduled scaling

Scheduled scaling changes capacity at known times.

Example:

```text
08:00 — Increase desired capacity to 4
18:00 — Reduce desired capacity to 2
```

This can help with predictable business-hour traffic.

### 8.4 Predictive scaling

Predictive scaling uses historical load patterns to forecast future capacity needs. It is most useful when traffic has recurring patterns and sufficient history.

It should not replace reactive scaling for unexpected spikes.

### 8.5 Compare scaling approaches

| Policy | Best fit | Main idea |
|---|---|---|
| Target tracking | Metric-driven demand | Maintain a metric near a target |
| Step scaling | Alarm thresholds and severity | Apply different capacity changes |
| Scheduled scaling | Predictable timetable | Change capacity at set times |
| Predictive scaling | Recurring demand patterns | Forecast capacity needs |

Simple scaling is an older policy type. For many new designs, target tracking or step scaling is more flexible.

### 8.6 Configure target tracking with AWS CLI

Example: maintain average ASG CPU utilization near 50%.

```bash
aws autoscaling put-scaling-policy \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg \
  --policy-name cpu-target-tracking \
  --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{
    "PredefinedMetricSpecification": {
      "PredefinedMetricType": "ASGAverageCPUUtilization"
    },
    "TargetValue": 50.0
  }'
```

The command returns a policy ARN. Inspect policies with:

```bash
aws autoscaling describe-policies \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg
```

A CPU target is only an example. Some applications are constrained by memory, request concurrency, queue depth, database capacity, or another metric.

## 9. Warmup, Cooldown, and Scaling Behavior

These terms are related but not interchangeable.

- **Default instance warmup:** Helps Auto Scaling account for newly launched instances while evaluating scaling metrics and policy behavior.
- **Health-check grace period:** Gives a new instance time before certain health-check failures can trigger replacement.
- **Cooldown:** A stabilization period associated with certain scaling policy behaviors, particularly older simple scaling patterns.
- **Lifecycle hook timeout:** The time available for a custom lifecycle action before the hook's timeout behavior applies.

Avoid treating all of these as one universal delay. Configure each according to its purpose and the behavior of the scaling policy in use.

## 10. Lifecycle Hooks

Lifecycle hooks allow you to run custom actions when an instance is entering or leaving an Auto Scaling Group.

Common transition points:

```text
Launch:
Pending
   |
   v
Pending:Wait  <-- Launch lifecycle hook
   |
   v
Pending:Proceed
   |
   v
InService

Terminate:
InService
   |
   v
Terminating:Wait  <-- Termination lifecycle hook
   |
   v
Terminating:Proceed
   |
   v
Terminated
```

### 10.1 Launch lifecycle hook use cases

- Register the instance in an internal inventory.
- Fetch configuration from a trusted service.
- Perform a controlled initialization step.
- Wait for an external provisioning workflow.

### 10.2 Termination lifecycle hook use cases

- Drain a custom work queue.
- Export application diagnostics.
- Deregister from an internal service.
- Complete a controlled cleanup action.

Lifecycle hooks have a timeout and a default result. A workflow should send heartbeats when supported and needed, and should complete the lifecycle action when its work is finished.

### 10.3 Create a lifecycle hook

Illustrative command:

```bash
aws autoscaling put-lifecycle-hook \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg \
  --lifecycle-hook-name app-termination-hook \
  --lifecycle-transition autoscaling:EC2_INSTANCE_TERMINATING \
  --heartbeat-timeout 300 \
  --default-result CONTINUE
```

Inspect hooks:

```bash
aws autoscaling describe-lifecycle-hooks \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg
```

A worker can complete a lifecycle action using the relevant instance ID and lifecycle action token or supported identifiers:

```bash
aws autoscaling complete-lifecycle-action \
  --region ap-southeast-1 \
  --lifecycle-hook-name app-termination-hook \
  --auto-scaling-group-name spring-boot-asg \
  --instance-id i-REPLACE_ME \
  --lifecycle-action-result CONTINUE
```

Do not leave instances waiting indefinitely. Monitor hook outcomes and design a safe timeout path.

## 11. Instance Refresh

**Instance Refresh** is an Auto Scaling feature for replacing instances in an ASG, commonly after changing the Launch Template or application image.

Typical use cases:

- Deploy a new AMI.
- Roll out a new Launch Template version.
- Replace instances after a security update.
- Gradually replace old application instances.

### 11.1 Conceptual process

```text
ASG currently runs:
Instance A — old version
Instance B — old version
Instance C — old version
Instance D — old version

          Start Instance Refresh
                    |
                    v
          Launch replacement capacity
                    |
                    v
          Wait for healthy capacity
                    |
                    v
          Terminate selected old instances
                    |
                    v
          Continue in batches
                    |
                    v
          ASG runs new version
```

The precise replacement order and capacity behavior depend on the refresh preferences and ASG configuration.

### 11.2 Refresh preferences

Depending on the current feature configuration, preferences can control aspects such as:

- Minimum healthy percentage.
- Maximum healthy percentage.
- Instance warmup.
- Checkpoints and pauses.
- Skip matching instances.
- Auto rollback, where supported and configured.

Review current AWS documentation before relying on a particular option or default in production.

### 11.3 Start an Instance Refresh

First update the ASG to use the intended Launch Template version. Example:

```bash
aws autoscaling update-auto-scaling-group \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg \
  --launch-template "LaunchTemplateName=spring-boot-template,Version=2"
```

Then start the refresh:

```bash
aws autoscaling start-instance-refresh \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg \
  --preferences '{
    "MinHealthyPercentage": 90,
    "InstanceWarmup": 180
  }'
```

Inspect the refresh:

```bash
aws autoscaling describe-instance-refreshes \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg
```

Do not run a production refresh without checking spare capacity, health checks, launch quotas, subnet IP capacity, and application compatibility.

## 12. Deployment Strategies

A deployment strategy determines how a new application version replaces or coexists with the old version.

### 12.1 Rolling deployment

Replace instances gradually.

```text
Stage 1: [OLD] [OLD] [OLD] [OLD]
Stage 2: [NEW] [OLD] [OLD] [OLD]
Stage 3: [NEW] [NEW] [OLD] [OLD]
Stage 4: [NEW] [NEW] [NEW] [NEW]
```

**Advantages**
- Can use existing infrastructure.
- Incremental rollout limits the number of instances changing at once.
- Instance Refresh can help roll out Launch Template changes.

**Disadvantages**
- Old and new versions coexist temporarily.
- Database and API changes must remain compatible during the transition.
- A bad release can affect users before the rollout is stopped.

### 12.2 Blue/green deployment

Maintain two environments:

- Blue: current production version.
- Green: new version.

```text
                  Load Balancer
                        |
                 Traffic routing
                   /         \
             Blue (old)     Green (new)
             Production     Candidate
```

Test Green, then shift traffic to it.

**Advantages**
- Clear separation between old and new environments.
- Fast traffic switch when the new environment is ready.
- Rollback can be a traffic switch if the old environment remains healthy.

**Disadvantages**
- Requires additional capacity during the deployment.
- Data changes can complicate rollback.
- Both environments must be kept secure and monitored.

### 12.3 Canary deployment

Send a small portion of traffic to the new version first.

```text
                 Load Balancer
                       |
              +--------+--------+
              |                 |
          95% traffic        5% traffic
              |                 |
          Stable v1          Canary v2
```

Observe error rates, latency, and business metrics. Increase traffic only when the canary behaves correctly.

### 12.4 Compare strategies

| Strategy | Traffic movement | Main strength | Main risk |
|---|---|---|---|
| Rolling | Instances replaced in batches | Lower extra capacity | Versions coexist |
| Blue/green | Traffic switches between environments | Clear separation and rollback path | Higher temporary cost |
| Canary | Small percentage first, then increase | Early feedback from real traffic | Requires reliable traffic control and monitoring |

An ASG and Instance Refresh can support rolling replacement. Blue/green and canary traffic management often require additional deployment and routing capabilities, such as CodeDeploy, load-balancer weighted forwarding, or another traffic-management system. An ASG alone does not automatically implement every deployment strategy.

## 13. Systems Manager for Instance Operations

AWS Systems Manager helps operate EC2 instances without relying on SSH access as the primary management path.

Useful capabilities include:

| Capability | Purpose |
|---|---|
| Session Manager | Open a managed shell session |
| Run Command | Execute commands on managed instances |
| Patch Manager | Coordinate patching workflows |
| State Manager | Maintain a desired instance configuration |
| Parameter Store | Store configuration parameters and supported secret values |

For Session Manager, check that:

1. SSM Agent is installed and running.
2. The EC2 instance has an appropriate instance profile.
3. The instance can reach the required Systems Manager endpoints, through internet egress or configured VPC endpoints.
4. The operator has permission to start and manage sessions.

Session Manager can reduce the need to expose inbound SSH to the internet. It does not remove the need for IAM controls, logging, and network connectivity.

## 14. Spring Boot Production Architecture

A practical architecture:

```text
                         Users
                           |
                        Route 53
                           |
                    Application Load
                       Balancer
                           |
                     Target Group
                           |
             +-------------+-------------+
             |                           |
          AZ-a                         AZ-b
             |                           |
       Private subnet              Private subnet
             |                           |
        EC2 / Spring Boot           EC2 / Spring Boot
             |                           |
             +-------------+-------------+
                           |
                 RDS / Shared Services
                           |
                    CloudWatch Logs
```

### 14.1 Application design considerations

**Keep application instances stateless where practical.**

Avoid storing important user session state only in local instance memory. If sessions must be shared, use an appropriate shared session store or token-based design.

**Store uploaded files outside the instance.**

Use S3 or another durable shared storage service rather than relying on an EC2 instance's local disk.

**Plan database connections.**

If every instance opens a large connection pool, scaling from two to six instances can multiply database connection demand. Set pool sizes based on database capacity and expected maximum ASG size.

**Use graceful shutdown.**

Configure Spring Boot and the service manager to stop accepting new work and finish in-flight requests within the termination budget.

**Separate readiness from liveness.**

A readiness endpoint should reflect whether the application can serve requests. Avoid making a temporary dependency issue cause unnecessary instance replacement unless that is the intended policy.

### 14.2 Security group relationship

```text
Internet
   |
   v
ALB Security Group
Inbound: HTTPS from approved client ranges
Outbound: application port to EC2 SG
   |
   v
EC2 Security Group
Inbound: application port from ALB SG only
Outbound: required database and service destinations
   |
   v
Database Security Group
Inbound: database port from EC2 SG only
```

Prefer security-group references over broad source CIDR rules for internal service-to-service access when appropriate.

## 15. Monitoring and Troubleshooting

Monitor both infrastructure and application behavior.

Useful signals include:

- ASG desired, actual, minimum, and maximum capacity.
- EC2 launch failures and status checks.
- ALB healthy and unhealthy host counts.
- Target response time and HTTP error counts.
- CPU utilization and relevant application metrics.
- Scaling activities and lifecycle hook outcomes.
- Application logs and deployment version.

### 15.1 Common problems

| Symptom | Possible cause | What to inspect |
|---|---|---|
| ASG cannot launch instances | Invalid AMI, IAM profile, quota, subnet IP shortage | Scaling activities and EC2 launch errors |
| Targets are unhealthy | Wrong port/path, security group, app not ready | Target health reason and application logs |
| Instances repeatedly replaced | Health check failure or bootstrap failure | ASG activity history and user-data logs |
| Scaling does not happen | Metric, alarm, policy, or limits are wrong | CloudWatch alarms and scaling policies |
| CPU is high but no scale-out | Policy not attached or metric unsuitable | Policy configuration and scaling activities |
| Lifecycle hook waits too long | Worker did not complete the action | Hook status, timeout, worker logs |
| Instance Refresh fails | New version unhealthy or capacity unavailable | Refresh status, ASG activities, target health |
| Application starts slowly | Dependency downloads or slow bootstrap | User-data log and boot duration |

### 15.2 Useful commands

```bash
# List Auto Scaling Groups
aws autoscaling describe-auto-scaling-groups \
  --region ap-southeast-1

# Show instances in one group
aws autoscaling describe-auto-scaling-groups \
  --region ap-southeast-1 \
  --auto-scaling-group-names spring-boot-asg \
  --query "AutoScalingGroups[0].Instances"

# Show recent scaling activities
aws autoscaling describe-scaling-activities \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg

# Show policies
aws autoscaling describe-policies \
  --region ap-southeast-1 \
  --auto-scaling-group-name spring-boot-asg

# Show EC2 instances
aws ec2 describe-instances \
  --region ap-southeast-1 \
  --filters "Name=tag:aws:autoscaling:groupName,Values=spring-boot-asg"
```

For an instance you can access, inspect:

```bash
sudo cat /var/log/cloud-init-output.log
sudo cat /var/log/user-data.log
sudo systemctl status myapp
sudo journalctl -u myapp --no-pager -n 100
```

Log locations vary by AMI and initialization system.

## 16. Hands-on Lab — Deploy a Spring Boot App with ALB and Auto Scaling

### Goal

Build a small deployment with:

- One Application Load Balancer.
- One target group.
- One Launch Template.
- One Auto Scaling Group.
- Two private subnets in different AZs.
- Minimum 2, desired 2, maximum 6 instances.
- ELB health checks.
- A target-tracking scaling policy.

### Step 1 — Prepare the network

1. Select a VPC with at least two Availability Zones.
2. Create or select public subnets for the ALB.
3. Create or select private subnets for EC2 instances.
4. Ensure private instances can retrieve required packages and artifacts through a suitable egress design or VPC endpoints.

### Step 2 — Prepare security groups

ALB security group:
- Allow HTTPS from approved client ranges.
- Allow outbound application traffic to the EC2 security group.

EC2 security group:
- Allow the application port only from the ALB security group.
- Allow only required outbound connections.

### Step 3 — Create a target group

Configure:
- Target type: Instances.
- Protocol and port: match the Spring Boot service.
- Health-check path: `/actuator/health` or a dedicated readiness path.
- Success codes: match the application's response.

### Step 4 — Create an ALB

1. Use at least two public subnets in different AZs.
2. Attach the ALB security group.
3. Create an HTTPS listener using an ACM certificate for production.
4. Forward requests to the target group.

### Step 5 — Create the Launch Template

Configure:
- A tested AMI.
- A suitable instance type.
- EC2 security group.
- IAM instance profile.
- IMDSv2 required.
- User data to install or start the application.

### Step 6 — Create the ASG

Set:

```text
Minimum capacity: 2
Desired capacity: 2
Maximum capacity: 6
Subnets: private subnet in AZ-a and AZ-b
Target group: Spring Boot target group
Health check type: ELB
Grace period: appropriate for application startup
```

### Step 7 — Verify the deployment

- Confirm that two instances launch.
- Confirm that both register in the target group.
- Confirm that both become healthy.
- Send requests through the ALB DNS name.
- Confirm that application logs are available.

### Step 8 — Configure scaling

Create a target-tracking policy using a metric that reflects application load. CPU utilization is a simple lab metric.

For a safe lab test, generate a controlled workload and observe scaling activities. Do not create uncontrolled load against a production system.

### Step 9 — Test recovery

In a disposable lab, terminate one ASG-managed instance through the EC2 console or CLI and observe whether the group launches a replacement.

Do not terminate production instances as an experiment.

### Step 10 — Test a new version

1. Create a new Launch Template version.
2. Update the ASG to reference it.
3. Start an Instance Refresh.
4. Watch target health and refresh status.
5. Confirm that the new version serves requests.

### Cleanup

To avoid ongoing charges, remove lab resources when finished, in dependency order. Review whether the ALB, NAT Gateway, EC2 instances, EBS volumes, public IPv4 addresses, and CloudWatch logs are still present. Some resources incur charges even when idle.

## 17. Exercises with Answers

### Exercise 1 — Capacity

An ASG has:
- Minimum: 2
- Desired: 3
- Maximum: 8

A scaling policy requests 10 instances. What is the maximum capacity the group may target?

**Answer:** 8. The maximum capacity is the upper bound.

### Exercise 2 — Multi-AZ

Why should an ASG use subnets in more than one Availability Zone?

**Answer:** It distributes capacity across AZs and improves resilience if one AZ has a problem. The application and its dependencies must also be designed for multi-AZ operation.

### Exercise 3 — Health checks

An EC2 instance passes EC2 status checks but the ALB reports it unhealthy. Give two possible reasons.

**Answer:**
1. The application is not listening on the target port.
2. The health-check path returns an unexpected status code or is blocked by a security group.

Other possibilities include slow startup, wrong protocol, or an incorrect target-group configuration.

### Exercise 4 — Scaling policies

Traffic is predictably high every weekday from 9 a.m. to 5 p.m. Which scaling approach could help prepare capacity in advance?

**Answer:** Scheduled scaling is suitable for a predictable timetable. Predictive scaling may also help when recurring patterns can be forecast from sufficient history.

### Exercise 5 — Deployment

You want to send 5% of production traffic to a new application version before increasing the percentage. Which deployment strategy is this?

**Answer:** Canary deployment.

### Exercise 6 — Secrets

Why should an AWS access key not be placed in EC2 user data?

**Answer:** User data is not a secure secrets store and may be accessible through instance or API mechanisms to principals with sufficient permissions. Use an IAM instance profile and a managed secret store when needed.

### Exercise 7 — Instance Refresh

What should you verify before starting an Instance Refresh?

**Answer:** Verify the new AMI and Launch Template, application startup, target health, spare capacity, subnet IP capacity, service quotas, database compatibility, and rollback plan.

### Exercise 8 — Lifecycle hook

A termination lifecycle hook is waiting. What should the worker do after its cleanup task completes?

**Answer:** Complete the lifecycle action with the appropriate result. If the work needs more time, use heartbeats where supported and remain within the hook's timeout behavior.

### Exercise 9 — Spring Boot state

Why is storing user sessions only in local memory risky in an ASG?

**Answer:** Requests from one user can reach different instances, and an instance can be replaced. Use stateless authentication or a shared session store.

### Exercise 10 — Database capacity

An application scales from 2 to 6 instances. Each instance has a connection pool maximum of 40. What is the theoretical maximum number of application database connections?

**Answer:** 6 × 40 = 240 connections, excluding other clients and services. The database must be sized and protected against this load.

## 19. English Speaking Practice

Read each question aloud, then practice the model answer.

### Q1. What is Amazon EC2 Auto Scaling?

**Model answer:**

Amazon EC2 Auto Scaling helps maintain the required number of EC2 instances. It can add instances when demand increases and remove instances when demand decreases. It can also replace unhealthy instances.

### Q2. What is a Launch Template?

**Model answer:**

A Launch Template defines the configuration used to launch EC2 instances. It can include the AMI, instance type, security groups, IAM instance profile, storage, and user data.

### Q3. What is the difference between minimum, desired, and maximum capacity?

**Model answer:**

Minimum capacity is the lowest capacity the group should maintain. Desired capacity is the target number of instances. Maximum capacity is the upper limit.

### Q4. What is target tracking scaling?

**Model answer:**

Target tracking scaling adjusts the number of instances to keep a metric near a target value. For example, I can configure it to maintain average CPU utilization around fifty percent.

### Q5. What is an Instance Refresh?

**Model answer:**

An Instance Refresh gradually replaces instances in an Auto Scaling Group. I can use it to deploy a new AMI or a new Launch Template version.

### Q6. What is the difference between rolling and blue/green deployment?

**Model answer:**

A rolling deployment replaces instances in batches. A blue/green deployment uses two environments and shifts traffic from the old environment to the new one after testing.

### Q7. Why should a Spring Boot application be stateless?

**Model answer:**

An Auto Scaling Group can add, remove, or replace instances. If user sessions are stored only in local memory, users may lose their sessions when requests reach another instance. A stateless design makes scaling easier.

### Q8. How do you troubleshoot an unhealthy target?

**Model answer:**

First, I check the target health reason. Then I verify the application port, health-check path, security groups, application logs, and startup time. I also check whether the application is ready to receive traffic.

## 20. AWS Interview Questions and Answers

### 1. What is the difference between an AMI and a Launch Template?

**Answer:** An AMI is an image used to create an instance, containing the operating system and possibly preinstalled software. A Launch Template defines the broader EC2 launch configuration and references an AMI.

### 2. What is an Auto Scaling Group?

**Answer:** It is a group of EC2 instances managed together to maintain desired capacity and apply scaling and health-management behavior.

### 3. Can an ASG span multiple Availability Zones?

**Answer:** Yes. It can use subnets in multiple AZs within the same VPC, allowing capacity to be distributed across them.

### 4. What happens when an ASG-managed instance becomes unhealthy?

**Answer:** Depending on the configured health checks and ASG behavior, Auto Scaling can mark it unhealthy and replace it to maintain capacity.

### 5. What is the difference between EC2 health checks and ELB health checks?

**Answer:** EC2 status checks assess instance and underlying system status. ELB health checks assess whether a registered target responds correctly to the load balancer's health-check requests.

### 6. What is target tracking scaling?

**Answer:** It adjusts ASG capacity to keep a selected metric near a configured target value.

### 7. When would you use scheduled scaling?

**Answer:** When demand follows a predictable schedule, such as a business application that receives more traffic during working hours.

### 8. What is a lifecycle hook?

**Answer:** A lifecycle hook pauses an instance at a launch or termination transition so a custom workflow can perform additional work before the transition continues.

### 9. What is Instance Refresh?

**Answer:** It is a feature for gradually replacing instances in an ASG, often to roll out a new Launch Template version or AMI.

### 10. Does Auto Scaling automatically provide blue/green deployment?

**Answer:** No. Auto Scaling manages instance capacity. Blue/green deployment also requires separate environments and a traffic-shifting mechanism, such as load-balancer routing or a deployment service.

### 11. Why should secrets not be stored in user data?

**Answer:** User data is not designed as a secure secret store. Use IAM roles and managed secret services with least-privilege access.

### 12. How can you reduce SSH exposure for EC2 administration?

**Answer:** Use Systems Manager Session Manager where supported, with the required agent, IAM permissions, and network connectivity.
