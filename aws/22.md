## 2. What Is Load Balancing?

A load balancer distributes incoming requests across multiple targets, such as EC2 instances, containers, or IP addresses.

Without a load balancer, users may connect directly to one application server.

```text
             Users
               |
               v
        Single EC2 Instance
          Spring Boot
```

This creates a potential bottleneck and a single point of failure.

With a load balancer:

```text
                  Users
                    |
                    v
             Load Balancer
                    |
          +---------+---------+
          |         |         |
          v         v         v
        EC2 A     EC2 B     EC2 C
       App 1     App 2     App 3
```

The load balancer sends requests to healthy targets according to its configuration and load-balancing behavior.

### Why use a load balancer?

1. Distribute traffic across multiple targets.
2. Improve application availability.
3. Support horizontal scaling.
4. Perform health checks.
5. Help avoid sending traffic to unhealthy targets.
6. Terminate TLS at a supported load-balancer listener.
7. Route requests based on hostnames, paths, or other supported conditions.
8. Provide a stable entry point for clients.

A load balancer does not automatically make an application highly available. The targets, Availability Zones, database, dependencies, and deployment process must also be designed for resilience.

## 3. Elastic Load Balancing (ELB)

**Elastic Load Balancing** is an AWS service that automatically distributes incoming traffic across registered targets.

AWS offers several load balancer types for different traffic patterns.

### Main load balancer types

| Type | Main purpose | Typical use |
|---|---|---|
| Application Load Balancer (ALB) | Layer 7 HTTP/HTTPS routing | Web applications, REST APIs, microservices |
| Network Load Balancer (NLB) | Layer 4 TCP, UDP, and supported protocols | High-performance network traffic, static IP requirements |
| Gateway Load Balancer (GWLB) | Deploy and scale virtual network appliances | Firewall and inspection appliances |
| Classic Load Balancer (CLB) | Previous-generation load balancer | Legacy architectures |

For new application designs, evaluate ALB or NLB based on the application protocol and requirements. Classic Load Balancer is a previous-generation option.

### OSI layer reminder

| Layer | Name | Example |
|---:|---|---|
| 7 | Application | HTTP, HTTPS |
| 4 | Transport | TCP, UDP |
| 3 | Network | IP |

ALB operates at Layer 7. NLB operates at Layer 4. GWLB supports transparent deployment of virtual network appliances and operates at Layer 3 for its load-balancing function.

## 4. Application Load Balancer (ALB)

An **Application Load Balancer** is designed for HTTP and HTTPS traffic.

It can route requests based on supported Layer 7 information, such as:

- Hostname.
- URL path.
- HTTP headers.
- HTTP methods.
- Query strings.
- Source IP address.

### Example: Path-based routing

```text
                       Internet
                           |
                           v
                    Application ALB
                           |
              +------------+------------+
              |                         |
              v                         v
        /api/orders/*              /api/products/*
              |                         |
              v                         v
       Order Target Group       Product Target Group
              |                         |
          +---+---+                 +---+---+
          |       |                 |       |
          v       v                 v       v
        App A   App B             App C   App D
```

The ALB evaluates listener rules and forwards requests to the matching target group.

### Example: Host-based routing

```text
api.example.com       ---> API Target Group
admin.example.com     ---> Admin Target Group
shop.example.com      ---> Storefront Target Group
```

This allows multiple application services to share an ALB while using separate target groups and routing rules.

### ALB use cases

- Spring Boot REST APIs.
- Web applications.
- Microservices.
- Host-based routing.
- Path-based routing.
- HTTP-to-HTTPS redirection.
- Integration with supported authentication and web-protection features.

### ALB and Availability Zones

An ALB is configured with subnets in multiple Availability Zones. Its targets should also be distributed across suitable Availability Zones for resilience.

## 5. Network Load Balancer (NLB)

A **Network Load Balancer** operates at Layer 4 and handles supported network traffic such as TCP and UDP.

It is useful when an application needs network-level load balancing rather than HTTP-aware routing.

### Architecture

```text
             TCP / UDP Clients
                    |
                    v
              Network NLB
                    |
          +---------+---------+
          |                   |
          v                   v
       Target A             Target B
       Service              Service
```

### Common NLB characteristics

- Layer 4 load balancing.
- Supports TCP and UDP, along with other supported listener configurations.
- Designed for high-performance network traffic.
- Can provide static IP addresses per enabled Availability Zone.
- Supports preserving client IP in supported target configurations.
- Supports TLS listeners and other protocol-specific capabilities.

Check the current service documentation for exact listener, target-type, and feature support before choosing an NLB design.

### When might you choose NLB?

- TCP or UDP workloads.
- Applications requiring Layer 4 routing.
- Workloads with static IP requirements.
- Network services where HTTP-aware routing is not needed.
- High-performance connection handling.

## 6. Gateway Load Balancer (GWLB)

A **Gateway Load Balancer** helps deploy, scale, and manage virtual network appliances such as:

- Third-party firewalls.
- Intrusion detection systems.
- Intrusion prevention systems.
- Deep packet inspection appliances.

### Architecture

```text
                 Application Traffic
                         |
                         v
                Gateway Load Balancer
                         |
                 +-------+-------+
                 |               |
                 v               v
             Firewall A      Firewall B
                 |               |
                 +-------+-------+
                         |
                         v
                  Destination Network
```

GWLB uses the GENEVE protocol for traffic between the Gateway Load Balancer and its appliance targets.

### When should you evaluate GWLB?

Use it when you need to insert and scale virtual network appliances in a network traffic path.

It is not a normal replacement for ALB in a Spring Boot web application.

---

## 7. ALB vs NLB vs GWLB

| Feature | ALB | NLB | GWLB |
|---|---|---|---|
| Primary layer | Layer 7 | Layer 4 | Layer 3 appliance insertion |
| Main traffic | HTTP / HTTPS | TCP / UDP and supported protocols | Network traffic through appliances |
| Routing logic | Host, path, headers, and other HTTP conditions | Network-level connection handling | Appliance traffic distribution |
| Typical target | Instances, IPs, Lambda, containers where supported | Instances, IPs, and supported target types | Virtual network appliances |
| Typical use | Web apps and APIs | Network services | Firewall and inspection appliances |
| HTTP path routing | Yes | No | No |

### Selection guide

```text
What kind of traffic do you need to load balance?
                    |
          +---------+----------+
          |                    |
          v                    v
      HTTP / HTTPS         TCP / UDP
          |                    |
          v                    v
         ALB                  NLB

Need to distribute traffic across virtual
network security appliances?
                    |
                    v
                   GWLB
```

## 8. Listeners

A **listener** checks for connection requests on a configured protocol and port.

Examples:

- HTTP on port 80.
- HTTPS on port 443.
- TCP on port 5432 for a suitable NLB use case.

An ALB listener commonly uses HTTP or HTTPS.

### Example ALB listeners

| Listener | Default action |
|---|---|
| HTTP :80 | Redirect to HTTPS :443 |
| HTTPS :443 | Forward to web target group |

### HTTP to HTTPS redirection

A common web architecture redirects HTTP requests to HTTPS.

```text
Client
  |
  | HTTP :80
  v
ALB Listener :80
  |
  | Redirect
  v
Client retries HTTPS :443
  |
  v
ALB Listener :443
  |
  v
Application Target Group
```

TLS certificates for ALB HTTPS listeners are commonly managed using AWS Certificate Manager (ACM).

### Listener rules

An ALB listener can have rules with conditions and actions.

Example:

| Priority | Condition | Action |
|---:|---|---|
| 10 | Path is `/api/orders/*` | Forward to orders target group |
| 20 | Path is `/api/products/*` | Forward to products target group |
| Default | No rule matches | Forward to default target group |

Rules are evaluated by priority. The default action is used when no applicable rule matches.

## 9. Target Groups

A **target group** is a logical group of targets that receives traffic from a load balancer.

Depending on the load balancer and target-group configuration, targets can include:

- EC2 instances.
- Private IP addresses.
- Containers registered through supported integrations.
- Lambda functions for supported ALB configurations.

### Example

```text
                 ALB Listener :443
                         |
                         v
                  Orders Target Group
                    /           \
                   v             v
                EC2 A          EC2 B
             Spring Boot    Spring Boot
```

### Target types

Common ALB target types include:

| Target type | Description |
|---|---|
| Instance | Targets are registered by EC2 instance ID |
| IP | Targets are registered by IP address |
| Lambda | A Lambda function is registered as a target for supported ALB use cases |

NLB and GWLB support their own target-group configurations. Always check target-type compatibility with the chosen load balancer.

### Target registration

Targets must be registered with the target group and pass health checks before they are considered healthy for normal traffic routing.

## 10. Health Checks

A health check helps the load balancer determine whether a target can receive traffic.

For an ALB target group, health-check settings can include:

- Protocol.
- Port.
- Path.
- Interval.
- Timeout.
- Healthy threshold.
- Unhealthy threshold.
- Success codes (matcher).

### Example Spring Boot health endpoint

A Spring Boot application using Spring Boot Actuator may expose a health endpoint such as:

```text
/actuator/health
```

Example configuration:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      show-details: never
```

The endpoint must be reachable by the load balancer and return an expected successful response.

Do not expose sensitive health details publicly. Use appropriate access controls and health-check design.

### Health-check example

| Setting | Example |
|---|---|
| Protocol | HTTP |
| Port | Traffic port |
| Path | `/actuator/health` |
| Interval | 30 seconds |
| Timeout | 5 seconds |
| Healthy threshold | 2 |
| Unhealthy threshold | 3 |
| Success codes | `200` |

These are illustrative values. Tune them based on application startup time, response behavior, and operational requirements.

### Target health states

Common target states include:

- `initial`
- `healthy`
- `unhealthy`
- `unused`
- `draining`
- `unavailable`

The exact states and meanings depend on the load-balancer type and target-group configuration.

### Why can a target become unhealthy?

- Application process is stopped.
- Health-check path is incorrect.
- Health-check port is incorrect.
- Security Group blocks ALB-to-target traffic.
- NACL blocks request or return traffic.
- Application returns a response code outside the configured matcher.
- Application takes too long to respond.
- Target is not registered or is in an unsuitable state.

## 11. Cross-Zone Load Balancing and Availability

Load balancing across Availability Zones can improve resilience.

### Concept

```text
                 Application Load Balancer
                         |
             +-----------+-----------+
             |                       |
             v                       v
            AZ A                    AZ B
        +----------+             +----------+
        | App A1   |             | App B1   |
        | App A2   |             | App B2   |
        +----------+             +----------+
```

Cross-zone load balancing behavior and configuration vary by load-balancer type and target group.

For ALB, load is distributed across enabled Availability Zones and healthy targets according to the service's behavior.

For NLB and other types, cross-zone behavior has its own configuration and considerations. Review the relevant service behavior rather than assuming all load balancers work identically.

### Resilience checklist

- Enable the load balancer in multiple Availability Zones where appropriate.
- Run targets in multiple Availability Zones.
- Configure health checks.
- Use Auto Scaling or an appropriate orchestration platform to replace failed targets.
- Ensure the database and other dependencies are resilient.
- Test behavior when one target or one Availability Zone becomes unavailable.

## 12. TLS and HTTPS

TLS encrypts data between a client and a server or between supported network endpoints.

A common ALB design terminates client TLS at the ALB:

```text
Client
  |
  | HTTPS
  v
ALB HTTPS Listener
  |
  | HTTP or HTTPS to target, by design
  v
Spring Boot Target
```

You can also configure encrypted communication from the load balancer to targets when required.

### AWS Certificate Manager

AWS Certificate Manager (ACM) can provide and manage certificates for supported AWS integrations, including ALB HTTPS listeners.

A typical process:

1. Request or import a certificate.
2. Validate domain ownership as required.
3. Ensure the certificate is available in the appropriate Region for the ALB.
4. Configure an HTTPS listener.
5. Select the certificate.
6. Configure the listener's forwarding or redirect rules.

### Security considerations

- Use HTTPS for public application traffic.
- Choose a suitable TLS security policy.
- Renew and monitor certificates.
- Avoid sending sensitive data over unencrypted links.
- Decide whether traffic from ALB to application targets also requires TLS.

## 13. Spring Boot Behind an Application Load Balancer

Consider an e-commerce API deployed on two EC2 instances.

### Architecture

```text
                    Internet
                       |
                       v
                 Application ALB
                  HTTPS :443
                       |
              +--------+--------+
              |                 |
              v                 v
         Target Group      Health Checks
              |
        +-----+-----+
        |           |
        v           v
      EC2 A       EC2 B
    Spring Boot Spring Boot
        |           |
        +-----+-----+
              |
              v
          Amazon RDS
```

### Security Group design

| Security Group | Inbound rule | Source |
|---|---|---|
| ALB SG | TCP 443 | Intended client sources |
| App SG | TCP 8080 | ALB SG |
| DB SG | TCP 5432 | App SG |

The database port is an example for PostgreSQL. Adjust it to the actual database engine.

### Spring Boot application

A simple controller:

```java
package com.example.demo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    @GetMapping("/api/hello")
    public String hello() {
        return "Hello from Spring Boot behind AWS ALB!";
    }
}
```

Example application port:

```yaml
server:
  port: 8080
```

### Health endpoint

Add Spring Boot Actuator as a dependency and configure a suitable health endpoint.

For Maven:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

Configure:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      show-details: never
```

The target group can use `/actuator/health` if the endpoint is available and reachable.

### Important application considerations

- Do not store sessions only in local memory if requests can reach different instances.
- Use a shared session store or stateless authentication where appropriate.
- Store uploaded files in shared storage such as S3 rather than on one EC2 instance's local disk.
- Ensure database connection pools are sized across all instances.
- Handle graceful shutdown so deployments do not interrupt active requests.
- Configure forwarded-header handling correctly when TLS terminates at the ALB.
- Ensure health checks do not report healthy before the application is ready.

## 14. AWS CLI: Inspect Load Balancers

The examples below are for inspection. Replace placeholders with actual resource identifiers.

Set Region and check identity:

```bash
aws configure set region ap-southeast-1
aws sts get-caller-identity
```

### 14.1 List load balancers

For Application and Network Load Balancers:

```bash
aws elbv2 describe-load-balancers \
  --query "LoadBalancers[].[LoadBalancerName,Type,State.Code,DNSName,VpcId]" \
  --output table
```

### 14.2 Describe one load balancer

```bash
aws elbv2 describe-load-balancers \
  --load-balancer-arns arn:aws:elasticloadbalancing:REGION:ACCOUNT_ID:loadbalancer/app/NAME/ID
```

### 14.3 List listeners

```bash
aws elbv2 describe-listeners \
  --load-balancer-arn LOAD_BALANCER_ARN
```

### 14.4 List target groups

```bash
aws elbv2 describe-target-groups \
  --query "TargetGroups[].[TargetGroupName,TargetType,Protocol,Port,VpcId]" \
  --output table
```

### 14.5 Describe target health

```bash
aws elbv2 describe-target-health \
  --target-group-arn TARGET_GROUP_ARN
```

### 14.6 Describe listener rules

```bash
aws elbv2 describe-rules \
  --listener-arn LISTENER_ARN
```

### 14.7 Inspect load-balancer attributes

```bash
aws elbv2 describe-load-balancer-attributes \
  --load-balancer-arn LOAD_BALANCER_ARN
```

### 14.8 Inspect target-group attributes

```bash
aws elbv2 describe-target-group-attributes \
  --target-group-arn TARGET_GROUP_ARN
```

### CLI safety notes

- Use the correct Region and account.
- Replace placeholders with real ARNs.
- Ensure the IAM identity has permission to inspect the resources.
- These commands do not create or modify load balancers.
- Creating a load balancer, NAT Gateway, or other network resource may incur charges.

## 15. Hands-on Lab — Design an ALB for Spring Boot

### Lab objective

Design a public HTTPS entry point for a Spring Boot application running on two EC2 instances in private subnets.

### Requirements

- One VPC.
- Two Availability Zones.
- Public subnets for the ALB.
- Private application subnets for EC2 instances.
- One ALB.
- One target group.
- HTTPS listener on port 443.
- Optional HTTP listener on port 80 that redirects to HTTPS.
- Health check at `/actuator/health`.
- Application port 8080.
- Database is private and accepts traffic only from the application Security Group.

### Step 1 — Network plan

| Component | Example CIDR |
|---|---|
| VPC | `10.80.0.0/16` |
| Public subnet AZ A | `10.80.1.0/24` |
| Public subnet AZ B | `10.80.2.0/24` |
| App subnet AZ A | `10.80.11.0/24` |
| App subnet AZ B | `10.80.12.0/24` |
| Database subnet AZ A | `10.80.21.0/24` |
| Database subnet AZ B | `10.80.22.0/24` |

These are sample ranges. Verify that they do not overlap with existing networks.

### Step 2 — Security Groups

**ALB Security Group**

- Inbound TCP 443 from approved client CIDRs.
- Outbound TCP 8080 to the application Security Group.

**Application Security Group**

- Inbound TCP 8080 from the ALB Security Group.
- Outbound database traffic to the database Security Group.
- Other outbound traffic only as required.

**Database Security Group**

- Inbound database port from the application Security Group.
- No public inbound rule.

### Step 3 — Target group design

| Setting | Value |
|---|---|
| Target type | Instance |
| Protocol | HTTP |
| Port | 8080 |
| Health-check protocol | HTTP |
| Health-check path | `/actuator/health` |
| Success matcher | 200 |

Use settings appropriate to the actual application and security requirements.

### Step 4 — Listener design

| Listener | Action |
|---|---|
| HTTP :80 | Redirect to HTTPS :443 |
| HTTPS :443 | Forward to Spring Boot target group |

Attach a suitable ACM certificate to the HTTPS listener.

### Step 5 — Register targets

Register the two EC2 instances with the target group.

Confirm:

- Both instances are running.
- The application listens on port 8080.
- The application Security Group allows traffic from the ALB Security Group.
- The health-check endpoint returns the expected response.

### Step 6 — Test the application

From an authorized client:

```bash
curl -I https://YOUR_DOMAIN
```

Test the API:

```bash
curl https://YOUR_DOMAIN/api/hello
```

Test the health endpoint only if it is intentionally exposed through the ALB:

```bash
curl https://YOUR_DOMAIN/actuator/health
```

Do not expose detailed health information or sensitive management endpoints to the public.

### Step 7 — Simulate an unhealthy target

In a test environment:

1. Stop one application instance or make its health endpoint fail.
2. Inspect target health.
3. Confirm the load balancer stops routing normal traffic to the unhealthy target according to its health behavior.
4. Restore the application.
5. Confirm that the target becomes healthy again.

Do not perform this test on production without an approved test plan.

### Step 8 — Review resilience

- Are targets distributed across Availability Zones?
- Does Auto Scaling replace failed instances?
- Is the database resilient?
- Are application sessions shared or stateless?
- Are logs and metrics available?
- Is there a rollback strategy for deployments?

## 16. Common Load Balancer Problems

| Symptom | Possible causes | What to check |
|---|---|---|
| ALB returns 503 | No healthy targets or no usable target | Target health, registration, health checks |
| ALB returns 502 | Target closed connection, invalid response, protocol mismatch | App logs, target protocol, application port |
| ALB returns 504 | Target response timeout | App performance, dependencies, timeout settings |
| Target is unhealthy | Wrong health path or port, SG/NACL block, app not ready | Health-check configuration and network controls |
| HTTPS listener fails | Certificate, listener, TLS configuration | ACM certificate, listener protocol, domain |
| HTTP does not redirect | Missing redirect rule | Listener default action and rule priorities |
| Some API paths fail | Incorrect listener rules or application routes | Path conditions and target-group mapping |
| Requests lose session | Session stored locally on one instance | Shared session storage or stateless design |

### 503 vs 502 vs 504

| Code | General meaning |
|---|---|
| 502 Bad Gateway | The load balancer received an invalid response or encountered a target-side connection problem |
| 503 Service Unavailable | No suitable healthy target may be available, or the service cannot currently handle the request |
| 504 Gateway Timeout | The target did not respond within the applicable timeout |

The exact cause depends on the architecture and logs. Use load-balancer access logs, target health details, and application logs to investigate.

## 17. Practical Exercises

### Exercise 1 — Load balancing

**Question:** What is the main purpose of a load balancer?

**Answer:** To distribute incoming traffic across multiple targets and improve availability, scalability, and traffic management.

### Exercise 2 — ELB

**Question:** What does Elastic Load Balancing do?

**Answer:** It distributes incoming traffic across registered targets according to the selected load-balancer type and configuration.

**Question:** Which load balancer should you evaluate for a Spring Boot REST API using HTTP and HTTPS path-based routing?

**Answer:** Application Load Balancer (ALB).

### Exercise 4 — NLB

**Question:** Which load balancer should you evaluate for a TCP service that needs Layer 4 load balancing?

**Answer:** Network Load Balancer (NLB).

### Exercise 5 — GWLB

**Question:** What is Gateway Load Balancer commonly used for?

**Answer:** Deploying and scaling virtual network appliances such as firewalls and inspection systems.

### Exercise 6 — Listener

**Question:** What is a listener?

**Answer:** A listener checks for connection requests on a configured protocol and port and applies its configured rules or default action.

### Exercise 7 — Target Group

**Question:** What is a target group?

**Answer:** A logical group of targets that receives traffic forwarded by a load balancer.

### Exercise 8 — Health Check

**Question:** Why does an ALB use health checks?

**Answer:** To determine whether registered targets are healthy enough to receive traffic.

### Exercise 9 — HTTPS

**Question:** What is a common way to enable HTTPS on an ALB?

**Answer:** Configure an HTTPS listener and attach a suitable certificate, commonly managed through AWS Certificate Manager.

### Exercise 10 — Multi-AZ

**Question:** Why deploy targets across multiple Availability Zones?

**Answer:** To improve resilience if a target or an Availability Zone becomes unavailable.

### Exercise 11 — 503

**Question:** What should you inspect when an ALB returns 503?

**Answer:** Target registration, target health, health-check configuration, and whether healthy targets are available.

### Exercise 12 — Spring Boot

**Question:** Which Spring Boot endpoint could be used as an ALB health check?

**Answer:** A suitable health endpoint such as `/actuator/health`, provided it is enabled, reachable, and returns an expected status.

**Answer:** Requests may be sent to different application instances, and each instance has separate memory. Use stateless authentication or shared session storage where appropriate.

### Exercise 14 — Architecture

**Question:** Describe a basic secure architecture for a Spring Boot API on AWS.

**Answer:** Use an ALB in public subnets, Spring Boot targets in private subnets across Availability Zones, and a private database. Allow application traffic only from the ALB Security Group and database traffic only from the application Security Group.

### Question 1: What is a load balancer?

Model answer:

> A load balancer distributes incoming traffic across multiple application targets. It can improve availability and scalability. It also performs health checks so that traffic can be sent to healthy targets according to its configuration.

### Question 2: What is the difference between ALB and NLB?

Model answer:

> An Application Load Balancer operates at Layer 7 and is designed for HTTP and HTTPS traffic. It supports routing based on hostnames and URL paths. A Network Load Balancer operates at Layer 4 and is designed for network traffic such as TCP and UDP.

### Question 3: What is a target group?

Model answer:

> A target group is a logical group of targets that receives traffic from a load balancer. The targets can be EC2 instances, IP addresses, or other supported target types. The target group also defines health-check settings.

### Question 4: What is a health check?

Model answer:

> A health check helps the load balancer determine whether an application target is healthy. For a Spring Boot application, I can use a suitable Actuator health endpoint. I need to make sure the path, port, security rules, and expected response are correct.

### Question 5: How would you deploy Spring Boot behind an ALB?

Model answer:

> I would create an ALB in public subnets and deploy Spring Boot instances in private subnets across multiple Availability Zones. I would create a target group, register the instances, configure health checks, and add an HTTPS listener with a certificate. The application Security Group would accept traffic only from the ALB Security Group.

### Question 6: Why should an application not store all sessions locally?

Model answer:

> A load balancer can send requests to different application instances. If each instance stores sessions only in local memory, the next request may reach another instance that does not have the session. I would use stateless authentication or shared session storage.

## 20. AWS Interview Questions and Answers

### Q1. What is Elastic Load Balancing?

Elastic Load Balancing automatically distributes incoming traffic across registered targets according to the selected load-balancer type and configuration.

### Q2. What are the main AWS load balancer types?

Application Load Balancer, Network Load Balancer, Gateway Load Balancer, and the previous-generation Classic Load Balancer.

### Q3. What is the difference between ALB and NLB?

ALB operates at Layer 7 and supports HTTP-aware routing. NLB operates at Layer 4 and handles supported network protocols such as TCP and UDP.

### Q4. What is Gateway Load Balancer used for?

It helps deploy and scale virtual network appliances, such as firewalls and traffic-inspection systems.

### Q5. What is a listener?

A listener checks for connection requests on a configured protocol and port and applies its rules or default action.

### Q6. What is a target group?

A target group is a logical collection of targets that receives traffic forwarded by a load balancer.

### Q7. What is a health check?

A health check evaluates whether a registered target is responding as expected. Unhealthy targets are handled according to the load balancer's health behavior.

### Q8. What is path-based routing?

Path-based routing forwards requests to different target groups based on URL paths, such as `/api/orders/*` and `/api/products/*`.

### Q9. What is host-based routing?

Host-based routing forwards requests based on the hostname, such as `api.example.com` or `admin.example.com`.

### Q10. How can you enable HTTPS on an ALB?

Create an HTTPS listener, attach a suitable TLS certificate such as one managed by ACM, and configure its forwarding or redirect actions.

### Q11. Why deploy an ALB across multiple Availability Zones?

To improve resilience and allow the load balancer to route traffic to targets in multiple Availability Zones.

### Q12. What does an unhealthy target mean?

The target is failing its configured health checks or is otherwise not considered healthy for normal traffic routing.

### Q13. Why might an ALB return 503?

There may be no suitable healthy targets available, or the service may be unable to handle the request. Inspect target health and load-balancer logs.

### Q14. What can cause an ALB 502 response?

A target-side connection problem or invalid response can cause a 502. Inspect application behavior, target protocol, connection handling, and logs.

### Q15. What can cause an ALB 504 response?

A target may not respond within the applicable timeout. Investigate application latency, downstream dependencies, and timeout settings.

### Q16. How do you configure a Spring Boot health check?

Enable a suitable health endpoint, for example through Spring Boot Actuator, and configure the target group's health-check path, port, protocol, and expected response.

### Q17. What is TLS termination?

TLS termination is where encrypted client traffic is decrypted at a network endpoint, such as an ALB HTTPS listener. Traffic from the ALB to targets can be configured separately.

### Q18. What are sticky sessions?

Sticky sessions direct a user's requests to the same target for a configured period where supported. They can be useful for some applications, but shared session storage or stateless designs are often more resilient.

### Q19. Does an ALB automatically scale the application?

No. The ALB distributes traffic, but application capacity must be managed separately, for example with Auto Scaling or an orchestration platform.

### Q20. How would you troubleshoot an unhealthy target?

Check the health-check path and port, application process, response code, Security Groups, NACLs, route tables, host firewall, and application logs.
