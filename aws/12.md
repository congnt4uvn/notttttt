## 2. Why Advanced IAM Concepts Matter

In simple examples, an identity-based policy grants an action on a resource. In real AWS environments, several policy types and service controls can affect the same request.

For example, an EC2 application might have an identity policy that allows S3 access, but:
- A permissions boundary may limit the role.
- An SCP may restrict the account.
- A bucket policy may explicitly deny the request.
- A VPC endpoint policy may restrict traffic through a private endpoint.
- A KMS key policy may prevent decryption of an encrypted object.

Therefore, an `Allow` statement in one policy does not guarantee that the request will succeed.

### Example architecture

```text
Spring Boot Application
        |
        v
EC2 Instance Role
        |
        +--> Identity-based policy
        |
        +--> Permissions boundary
        |
        +--> Organization SCP
        |
        v
Amazon S3 Request
        |
        +--> Bucket policy
        |
        +--> VPC endpoint policy (if request uses that endpoint)
        |
        +--> KMS key policy (if object uses SSE-KMS)
        |
        v
Authorization decision
```

This is a conceptual view. The exact policy evaluation path depends on the principal, resource, service, and request.

## 3. Policy Types: A Review

| Policy or control | Main purpose | Example |
|---|---|---|
| Identity-based policy | Defines permissions for an IAM identity | Role can read S3 objects |
| Resource-based policy | Defines access at a supported resource | Bucket trusts a role |
| Trust policy | Defines who can assume a role | EC2 service can assume a role |
| Permissions boundary | Sets the maximum permissions an identity-based policy can grant | Developer role cannot exceed an approved permission set |
| SCP | Sets maximum available permissions for principals in affected organization accounts | Production accounts cannot disable selected security services |
| Session policy | Further limits permissions for a particular role session | Temporary session can access only one prefix |
| VPC endpoint policy | Controls access through a particular VPC endpoint | Endpoint permits access only to approved S3 resources |

Important: these controls do not all grant permissions. Some only restrict permissions.

## 4. Permissions Boundaries

A permissions boundary is an advanced IAM feature that sets the maximum permissions an identity-based policy can grant to an IAM user or role.

A boundary does not grant permissions by itself.

Think of it as a ceiling:

- Identity policy: what the identity is allowed to request.
- Permissions boundary: the maximum permission set the identity can receive through identity-based policies.
- Effective access: still depends on other applicable policy types and service rules.

### 4.1 Example scenario

A company lets developers create IAM roles for development workloads. The company wants to ensure those roles cannot receive permissions beyond an approved set.

An administrator can attach a permissions boundary to the developer-created roles.

### 4.2 Example boundary policy

This illustrative boundary allows a limited set of S3 actions on a particular bucket. It is a permissions ceiling, not a grant.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BoundaryForInvoiceBucket",
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::company-invoices"
    },
    {
      "Sid": "BoundaryForInvoiceObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::company-invoices/invoices/*"
    }
  ]
}
```

If the role's identity policy allows `s3:DeleteObject`, but the boundary does not allow that action, the boundary prevents that identity-based permission from becoming effective.

### 4.3 Attach a boundary using AWS CLI

```bash
aws iam put-role-permissions-boundary \
  --role-name InvoiceApplicationRole \
  --permissions-boundary arn:aws:iam::111122223333:policy/InvoiceRoleBoundary
```

Replace the example account ID and policy name.

Inspect the role:

```bash
aws iam get-role \
  --role-name InvoiceApplicationRole
```

The returned role details include the permissions boundary when one is attached.

Remove a boundary only through an approved change process:

```bash
aws iam delete-role-permissions-boundary \
  --role-name InvoiceApplicationRole
```

### 4.4 Important limitations

- A boundary does not grant access.
- It limits permissions granted through identity-based policies.
- Resource-based policy behavior depends on the principal form and AWS authorization rules; do not assume a boundary is a universal filter for every resource-policy grant.
- Other controls, such as SCPs and explicit Deny statements, may still restrict access.

## 5. Service Control Policies (SCPs)

Service Control Policies are used with AWS Organizations. They define the maximum permissions available to principals in affected member accounts.

An SCP does not grant permissions. An identity or resource policy must still grant the requested access where required.

### 5.1 Organization structure

```text
AWS Organization
       |
       +-- Management Account
       |
       +-- Organizational Unit: Development
       |       |
       |       +-- Dev Account A
       |       +-- Dev Account B
       |
       +-- Organizational Unit: Production
               |
               +-- Prod Account A
               +-- Prod Account B
```

SCPs can be attached to the organization root, organizational units, or accounts. The effective restrictions depend on the policies inherited through the organization structure and the applicable policy type.

### 5.2 Example use cases

- Restrict which AWS Regions workloads can use.
- Prevent member accounts from disabling selected security services.
- Prevent use of certain high-risk services or actions.
- Establish organization-wide guardrails.

### 5.3 Example SCP: deny selected actions

Illustrative example:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyDisablingSecurityLogging",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail"
      ],
      "Resource": "*"
    }
  ]
}
```

This is a simplified example. Validate the operational impact before attaching it. A guardrail can affect legitimate administration and automation.

### 5.4 SCP vs IAM policy

| Topic | IAM policy | SCP |
|---|---|---|
| Main purpose | Grants or denies permissions to identities/resources | Sets maximum available permissions for affected organization principals |
| Scope | Specific identities or resources | Organization root, OU, or account |
| Grants access? | An Allow can grant access, subject to other controls | No |
| Typical owner | IAM/security administrators | Organization administrators |
| Example | Role can read S3 objects | Member accounts cannot stop selected CloudTrail operations |

### 5.5 Important notes

- SCPs apply to member accounts, not the AWS Organizations management account in the same way.
- SCPs do not grant permissions.
- SCPs do not restrict service-linked roles in the same way they restrict ordinary IAM principals.
- The exact effective permission depends on the organization hierarchy and policy evaluation rules.
- Test changes in a non-production organizational unit before broad deployment.

## 6. STS Session Policies

When a principal assumes a role, the resulting session receives the role's permissions, subject to applicable restrictions.

A session policy can further restrict the permissions of that particular session.

It cannot grant permissions beyond the role's permissions.

### 6.1 Example scenario

A role normally reads objects from a reports bucket. A particular session should access only the `monthly/` prefix.

The caller can pass a session policy during `AssumeRole` that narrows the session.

### 6.2 Example session policy

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadMonthlyReportsOnly",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::company-reports/monthly/*"
    }
  ]
}
```

The role itself must already have compatible permissions. The session policy narrows the session; it does not add permissions.

### 6.3 Assume a role with a session policy

Save the JSON policy as `session-policy.json`, then use:

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::111122223333:role/ReportsReadRole \
  --role-session-name MonthlyReportsSession \
  --policy file://session-policy.json
```

The response contains temporary credentials. Protect them as secrets.

### 6.4 Session policy vs permissions boundary

| Topic | Permissions boundary | Session policy |
|---|---|---|
| Applies to | IAM user or role identity | A particular role session |
| Purpose | Maximum permissions identity-based policies can grant | Further restricts session permissions |
| Duration | Remains attached until changed | Applies to the session |
| Grants permissions? | No | No |

## 7. Resource-Based Policies

A resource-based policy is attached to a supported AWS resource and identifies which principals can access it.

Examples include:
- S3 bucket policies.
- SQS queue policies.
- SNS topic policies.
- KMS key policies.
- Secrets Manager resource policies.

### 7.1 Example S3 bucket policy

Allow a specific role to read objects:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowReportsRoleRead",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/ReportsApplicationRole"
      },
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::company-reports/*"
    }
  ]
}
```

This is a resource-based permission. The principal, account configuration, and other applicable policies still matter.

### 7.2 Explicit Deny example

A bucket policy can explicitly deny access under a condition. For example, an organization might require secure transport.

Illustrative S3 policy statement:

```json
{
  "Sid": "DenyInsecureTransport",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::company-reports",
    "arn:aws:s3:::company-reports/*"
  ],
  "Condition": {
    "Bool": {
      "aws:SecureTransport": "false"
    }
  }
}
```

This denies requests made without secure transport. Review the full bucket policy and test integrations before deployment.

### 7.3 Bucket policy vs role policy

| Role identity policy | Bucket policy |
|---|---|
| Attached to the role | Attached to the S3 bucket |
| Defines what the role is allowed to do | Defines which principals can access the bucket |
| Often used to grant application permissions | Often used to share or restrict bucket access |

## 8. VPC Endpoint Policies

A VPC endpoint policy controls which principals and resources can be accessed through a particular VPC endpoint.

It does not replace IAM policies or resource policies. It adds another layer of control for traffic that uses that endpoint.

### 8.1 Example

A private application subnet uses an S3 gateway endpoint. The endpoint policy should allow access only to the approved bucket.

Illustrative endpoint policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCompanyReportsBucket",
      "Effect": "Allow",
      "Principal": "*",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::company-reports",
        "arn:aws:s3:::company-reports/*"
      ]
    }
  ]
}
```

This is an endpoint-level filter, not a grant to every principal. IAM and S3 authorization must also allow the request.

### 8.2 When is it useful?

- Restrict private network access to approved S3 buckets.
- Reduce the chance that workloads use a VPC endpoint to access unrelated resources.
- Add a network-path-specific policy layer.

### 8.3 Important distinction

| Control | What it controls |
|---|---|
| Security group | Network traffic to and from supported network interfaces/resources |
| Network ACL | Subnet-level network traffic rules |
| IAM policy | AWS API permissions for an identity |
| Resource policy | Access permissions on a resource |
| VPC endpoint policy | Access through a particular VPC endpoint |

A security group does not grant `s3:GetObject`. IAM does not open a TCP port. These controls solve different problems.

## 9. IAM Policy Simulator and Access Analyzer

### 9.1 IAM Policy Simulator

The IAM Policy Simulator can help test how policies evaluate for selected identities, actions, and resources.

It is useful for:
- Testing whether an action is allowed or denied.
- Identifying policy statements that affect a simulated decision.
- Reviewing the impact of policy changes.

It does not fully reproduce every live service request, resource-policy behavior, service-specific condition, or organization configuration. Treat simulation as one part of testing.

### 9.2 IAM Access Analyzer policy validation

Use Access Analyzer validation to identify policy syntax problems and security findings.

A good review workflow:

1. Draft the policy.
2. Validate the policy.
3. Review findings.
4. Simulate relevant permissions.
5. Deploy to a test environment.
6. Run the real application workflow.
7. Monitor CloudTrail and application logs.
8. Refine the policy.

### 9.3 Example CLI validation

The AWS CLI includes Access Analyzer validation commands in supported versions:

```bash
aws accessanalyzer validate-policy \
  --policy-type IDENTITY_POLICY \
  --policy-document file://invoice-policy.json
```

For a resource policy, use the appropriate policy type supported by the command and service. Check the CLI help and current AWS documentation for supported values and parameters.

## 10. Hands-on Lab: Build a Restricted S3 Role

### Lab scenario

You will create a role for a Spring Boot application that runs on EC2.

Requirements:
- EC2 can assume the role.
- The role can upload objects only to `s3://training-invoices/uploads/`.
- The role cannot delete objects.
- The application uses temporary credentials.
- You can inspect the role and verify its identity.

### Step 1: Prepare the trust policy

Create `ec2-trust-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TrustEC2",
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

### Step 2: Create the role

```bash
aws iam create-role \
  --role-name TrainingInvoiceRole \
  --assume-role-policy-document file://ec2-trust-policy.json
```

### Step 3: Create the permissions policy

Create `invoice-upload-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadOnlyToUploadsPrefix",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::training-invoices/uploads/*"
    }
  ]
}
```

### Step 4: Create a customer managed policy

```bash
aws iam create-policy \
  --policy-name TrainingInvoiceUploadPolicy \
  --policy-document file://invoice-upload-policy.json
```

### Step 5: Attach the policy

Replace the sample account ID:

```bash
aws iam attach-role-policy \
  --role-name TrainingInvoiceRole \
  --policy-arn arn:aws:iam::111122223333:policy/TrainingInvoiceUploadPolicy
```

### Step 6: Create an instance profile

```bash
aws iam create-instance-profile \
  --instance-profile-name TrainingInvoiceProfile
```

### Step 7: Add the role to the profile

```bash
aws iam add-role-to-instance-profile \
  --instance-profile-name TrainingInvoiceProfile \
  --role-name TrainingInvoiceRole
```

### Step 8: Associate the profile with an EC2 instance

```bash
aws ec2 associate-iam-instance-profile \
  --instance-id i-0123456789abcdef0 \
  --iam-instance-profile Name=TrainingInvoiceProfile
```

Replace the instance ID and profile name with actual values. If the instance already has an instance profile association, inspect it and use the appropriate replacement workflow.

### Step 9: Verify the identity from EC2

On the EC2 instance, run:

```bash
aws sts get-caller-identity
```

The returned ARN should indicate an assumed role session for `TrainingInvoiceRole`.

### Step 10: Test the allowed operation

```bash
echo "Training invoice" > invoice.txt

aws s3 cp invoice.txt \
  s3://training-invoices/uploads/invoice.txt
```

The bucket must exist, and the request must satisfy any bucket policy, encryption, endpoint, and organization controls.

### Step 11: Test an operation that should be denied

```bash
aws s3 rm \
  s3://training-invoices/uploads/invoice.txt
```

The role's identity policy does not grant `s3:DeleteObject`. If no other applicable policy grants it and no unusual resource-policy behavior changes the result, the request should be denied.

### Step 12: Clean up

Remove the test object using an authorized administrator identity, then remove the role association and IAM resources when they are no longer needed. Do not delete shared or production resources.

## 11. Troubleshooting AccessDenied

An `AccessDenied` error means the request was not authorized. Do not immediately attach `AdministratorAccess`.

Use this workflow.

### Step 1: Identify the caller

```bash
aws sts get-caller-identity
```

Confirm:
- Which account is being used?
- Is the caller an IAM user or assumed role?
- Is it the expected role session?

### Step 2: Identify the failed action and resource

Examples:
- `s3:GetObject`
- `s3:PutObject`
- `kms:Decrypt`
- `secretsmanager:GetSecretValue`

Record the exact bucket, object key, key ARN, or secret ARN involved.

### Step 3: Check the identity-based policy

```bash
aws iam list-attached-role-policies \
  --role-name TrainingInvoiceRole
```

Also inspect inline policies:

```bash
aws iam list-role-policies \
  --role-name TrainingInvoiceRole
```

### Step 4: Check the permissions boundary

```bash
aws iam get-role \
  --role-name TrainingInvoiceRole
```

Look for a permissions boundary in the role response.

### Step 5: Check the resource policy

For an S3 bucket:

```bash
aws s3api get-bucket-policy \
  --bucket training-invoices
```

A resource policy may grant or explicitly deny access.

### Step 6: Check organization controls

If the account belongs to AWS Organizations, ask the organization administrator to review applicable SCPs and inherited organizational restrictions.

### Step 7: Check the VPC endpoint policy

If the request uses a VPC endpoint, inspect that endpoint's policy. It may restrict the principal, action, or resource.

### Step 8: Check KMS permissions

For objects encrypted with SSE-KMS, the caller may need appropriate KMS permissions, and the key policy must permit the use. S3 permission alone may not be enough.

### Step 9: Check conditions

Look for conditions involving:
- Requested Region.
- Source IP.
- VPC endpoint.
- Principal tags.
- Secure transport.
- Encryption headers.
- Object prefixes.
- MFA context.

Condition-key support varies by service and action.

### Step 10: Use diagnostic tools

- IAM Policy Simulator.
- IAM Access Analyzer policy validation.
- CloudTrail event history.
- Relevant service logs and application error details.

### Troubleshooting table

| Symptom | Possible cause | What to inspect |
|---|---|---|
| Cannot assume role | Trust policy or source permission missing | Trust policy, `sts:AssumeRole` authorization |
| Cannot list bucket | Missing `s3:ListBucket` | Bucket ARN permission |
| Cannot download object | Missing `s3:GetObject` | Object ARN permission |
| Cannot upload object | Missing `s3:PutObject` or condition mismatch | Object ARN, bucket policy, encryption |
| Upload fails with KMS error | Missing KMS authorization | Key policy and KMS IAM permissions |
| Works outside VPC but not inside | Endpoint policy or network path | VPC endpoint configuration |
| Policy allows action but request is denied | Another control restricts access | Explicit Deny, boundary, SCP, session policy, resource policy |

## 12. Spring Boot: Design for Multiple Policy Layers

A production application may use:

- An EC2 instance role.
- A role identity policy.
- A permissions boundary.
- An organization SCP.
- An S3 bucket policy.
- A VPC endpoint policy.
- A KMS key policy if SSE-KMS is used.

Conceptual architecture:

```text
Spring Boot API
      |
      v
EC2 Instance
      |
      v
EC2 Instance Profile
      |
      v
IAM Role
      |
      +--> Identity Policy: PutObject on uploads/*
      |
      +--> Permissions Boundary: maximum allowed S3 actions
      |
      +--> SCP: organization guardrails
      |
      v
S3 Request
      |
      +--> Bucket Policy
      |
      +--> VPC Endpoint Policy (if used)
      |
      +--> KMS authorization (if SSE-KMS)
      |
      v
S3 Object
```

### Java client configuration

```java
@Configuration
public class AwsConfig {

    @Bean
    public S3Client s3Client() {
        return S3Client.builder()
                .region(Region.AP_SOUTHEAST_1)
                .build();
    }
}
```

Use the AWS SDK default credentials provider chain. On EC2, it can retrieve temporary credentials from the instance role. Do not hardcode keys or manually persist metadata credentials.

### Application authorization

IAM controls what the application workload can do in AWS. Spring Security and application business logic must separately determine whether an authenticated customer can access a particular invoice.

For example, a customer should not be able to download another customer's invoice merely by guessing an S3 object key.

## 13. Practical Exercises with Answers

### Exercise 1 — Permissions boundary

A role's identity policy allows `s3:DeleteObject`, but its permissions boundary does not include that action. Can the role use the identity-based permission?

**Answer:** No. The boundary limits the maximum permissions that identity-based policies can grant.

### Exercise 2 — SCP

An IAM role allows `ec2:RunInstances`, but an applicable SCP denies that action. Can the role launch an instance?

**Answer:** No. The SCP restricts the maximum available permissions for principals in the affected member account. It does not grant permissions.

### Exercise 3 — Session policy

Can a session policy give a role permission that the role itself does not have?

**Answer:** No. A session policy can further restrict the role session; it cannot grant permissions beyond the role's permissions.

### Exercise 4 — VPC endpoint policy

An IAM policy allows access to an S3 bucket, but the request goes through a VPC endpoint whose policy does not allow that bucket. What can happen?

**Answer:** The request can be denied by the endpoint policy even though the identity policy allows it.

### Exercise 5 — S3 listing

An application can download a known object but cannot list the bucket. Which action might be missing?

**Answer:** `s3:ListBucket` on the bucket ARN. The application may not need listing at all if it only reads known object keys.

### Exercise 6 — KMS encryption

An application has `s3:GetObject` but cannot download an SSE-KMS encrypted object. What else might be needed?

**Answer:** Appropriate KMS authorization, such as `kms:Decrypt`, and a key policy that permits the caller. The exact requirements depend on the encryption configuration and access path.

### Exercise 7 — Debugging

What should you check first when an AWS CLI command returns `AccessDenied`?

**Answer:** Run `aws sts get-caller-identity` to confirm which identity is making the request. Then identify the exact action and resource.

### Exercise 8 — SCP vs IAM policy

Which one grants permissions: an SCP or an IAM identity policy?

**Answer:** An SCP does not grant permissions. An IAM identity policy can grant permissions, subject to other applicable controls.

## 16. AWS Interview Questions and Answers

### Q1. What is a permissions boundary?

A permissions boundary is a managed policy that sets the maximum permissions an IAM user or role can receive through identity-based policies. It does not grant permissions by itself.

### Q2. What is an SCP?

A Service Control Policy is an AWS Organizations policy that sets the maximum permissions available to principals in affected member accounts. It does not grant permissions.

### Q3. What is the difference between an SCP and an IAM policy?

An IAM policy can grant permissions to an identity. An SCP restricts the maximum permissions available in affected organization accounts and does not grant access.

### Q4. What is a session policy?

A session policy is an optional policy passed during supported role assumption flows to further restrict the role session's permissions.

### Q5. What is a VPC endpoint policy?

It is a policy attached to a VPC endpoint that controls access through that endpoint. It does not replace IAM or resource-based policies.

### Q6. What is the difference between a resource policy and an identity policy?

An identity policy is attached to an IAM identity and defines its permissions. A resource policy is attached to a supported resource and identifies principals that can access it.

### Q7. Why might S3 access fail even when an IAM policy allows it?

Other controls may block the request, such as an explicit Deny, bucket policy, permissions boundary, SCP, session policy, VPC endpoint policy, or KMS key policy.

### Q8. What is the first step when troubleshooting AccessDenied?

Identify the caller with `aws sts get-caller-identity`, then determine the exact API action and resource.

### Q9. Does the IAM Policy Simulator guarantee that a live request will succeed?

No. It is a useful diagnostic tool, but it may not reproduce every live service behavior, resource policy, organization control, or condition.

### Q10. How should you fix an AccessDenied error?

Identify the exact missing permission or restrictive control, verify the application requirement, make the smallest safe policy change, and test it in a controlled environment.

## 17. Day 12 Summary

You learned:
- Multiple policy layers can affect one AWS authorization decision.
- Permissions boundaries set a ceiling for identity-based permissions.
- SCPs set maximum permissions for principals in affected organization accounts.
- Session policies can further restrict a role session.
- Resource-based policies are attached to supported resources.
- VPC endpoint policies control access through a specific endpoint.
- KMS key policies can affect access to encrypted objects.
- The IAM Policy Simulator and Access Analyzer help with policy review.
- `AccessDenied` should be diagnosed systematically rather than fixed with administrator access.
