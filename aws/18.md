## 2. What Is Amazon VPC?

**Amazon Virtual Private Cloud (Amazon VPC)** lets you define a logically isolated virtual network in AWS.

Within a VPC, you can control:

- IPv4 and IPv6 address ranges.
- Subnets.
- Route tables.
- Internet and private connectivity.
- Security groups.
- Network ACLs.
- DNS settings.
- Connections to other networks.

Think of a VPC as the network boundary for a group of AWS resources.

### Example

```text
                    AWS Region
                 ap-southeast-1
                         |
                         v
                  VPC: 10.0.0.0/16
                         |
          +--------------+--------------+
          |                             |
          v                             v
      Public Subnet                 Private Subnet
       10.0.1.0/24                   10.0.11.0/24
          |                             |
          v                             v
   Load Balancer                    EC2 App Server
                                        |
                                        v
                                    Amazon RDS
```

A VPC is regional. Subnets are created in individual Availability Zones within that Region.

### Why use a VPC?

- Isolate application networking.
- Separate public-facing and private resources.
- Control inbound and outbound routes.
- Restrict traffic between application tiers.
- Connect AWS workloads to on-premises networks.
- Build multi-AZ architectures.

## 3. VPC Components at a Glance

| Component | Purpose |
|---|---|
| VPC | Logically isolated virtual network |
| CIDR block | Defines the IP address range |
| Subnet | A range of IP addresses in one Availability Zone |
| Route table | Determines where network traffic is directed |
| Internet Gateway (IGW) | Provides a route between a VPC and the Internet |
| NAT Gateway | Allows private-subnet resources to initiate supported outbound Internet connections |
| Security Group | Stateful firewall for network interfaces |
| Network ACL | Stateless subnet-level traffic filter |
| VPC Endpoint | Private connectivity to supported AWS services |
| DHCP options | Network configuration such as domain-name settings |
| VPC Flow Logs | Records information about IP traffic to network interfaces or supported VPC resources |

These components work together. Creating a subnet or assigning a public IP alone does not make an application reachable from the Internet.

## 4. IPv4 Addressing Fundamentals

Before designing a VPC, understand IP addresses.

An IPv4 address contains 32 bits and is commonly written as four decimal numbers.

Example:

```text
10.0.1.25
```

Each section is between 0 and 255.

### Private IPv4 address ranges

The following ranges are reserved for private networks:

| Range | CIDR |
|---|---|
| 10.0.0.0 – 10.255.255.255 | `10.0.0.0/8` |
| 172.16.0.0 – 172.31.255.255 | `172.16.0.0/12` |
| 192.168.0.0 – 192.168.255.255 | `192.168.0.0/16` |

Private IPv4 addresses are not directly routable across the public Internet.

### What is CIDR?

**Classless Inter-Domain Routing (CIDR)** notation describes an IP address range.

Example:

```text
10.0.0.0/16
```

The `/16` means that the first 16 bits are the network portion. The remaining 16 bits are available for host addresses within the range.

### CIDR examples

| CIDR | Total IPv4 addresses | Typical interpretation |
|---|---:|---|
| `10.0.0.0/16` | 65,536 | Large VPC address range |
| `10.0.1.0/24` | 256 | Common subnet size |
| `10.0.1.0/25` | 128 | Smaller subnet |
| `10.0.1.0/26` | 64 | Smaller subnet |
| `10.0.1.0/28` | 16 | Small subnet; minimum IPv4 subnet size commonly supported by VPC |

For a normal IPv4 network, the number of addresses is \(2^{(32-prefix)}\).

### AWS-reserved IPv4 addresses in a subnet

For each IPv4 subnet, AWS reserves five addresses:

1. Network address.
2. VPC router address.
3. DNS address.
4. Reserved for future use.
5. Last address in the subnet range.

For example, a `/24` subnet contains 256 addresses, with 251 available for use by resources under this reservation rule.

Do not assume all addresses in the CIDR range can be assigned to instances.

### CIDR planning example

Suppose the VPC uses:

```text
VPC: 10.0.0.0/16
```

You can divide it into subnets such as:

```text
Public AZ-A:   10.0.1.0/24
Public AZ-B:   10.0.2.0/24

Private AZ-A:  10.0.11.0/24
Private AZ-B:  10.0.12.0/24

Database AZ-A: 10.0.21.0/24
Database AZ-B: 10.0.22.0/24
```

Avoid overlapping address ranges with other VPCs or on-premises networks that you may need to connect later.

## 5. What Is a Subnet?

A **subnet** is a range of IP addresses within a VPC.

Important facts:

- A subnet belongs to exactly one Availability Zone.
- A subnet's CIDR must be contained within the VPC CIDR.
- Subnets in the same VPC must not have overlapping IPv4 CIDR ranges.
- A subnet is associated with a route table.
- A subnet is not automatically public or private based only on its name.

### Public subnet

A subnet is commonly called public when its associated route table has a route to an Internet Gateway.

Example route:

```text
Destination: 0.0.0.0/0
Target:      igw-xxxxxxxx
```

For an EC2 instance to communicate directly with the public Internet, it also needs suitable public addressing and security rules.

### Private subnet

A private subnet does not have a direct route to an Internet Gateway for general Internet access.

It may have:

- A route to a NAT Gateway for outbound Internet access.
- VPC endpoint routes for private access to supported AWS services.
- Private routes to other VPCs or on-premises networks.

### Public vs private subnet

| Feature | Public subnet | Private subnet |
|---|---|---|
| Route to IGW | Commonly present | Not present for general Internet access |
| Public-facing ALB | Common placement | Usually not for an internet-facing ALB |
| Application EC2 | Possible, but often avoided in production | Common production placement |
| Database | Usually avoid | Common placement |
| Direct inbound Internet path | Possible with public addressing and allowed rules | Not directly through an IGW route |

**Important:** A public IP address alone does not make a subnet public. The route table must provide a suitable path to an Internet Gateway.

### Multi-AZ subnet design

```text
                       VPC
                   10.0.0.0/16
                         |
             +-----------+-----------+
             |                       |
             v                       v
       Availability Zone A     Availability Zone B
             |                       |
      +------+-------+        +------+-------+
      |              |        |              |
      v              v        v              v
   Public A       Private A Public B       Private B
   10.0.1/24     10.0.11/24 10.0.2/24     10.0.12/24
```

Using multiple Availability Zones helps support resilient application designs.

## 6. Route Tables

A **route table** contains rules that determine where network traffic is directed.

Each subnet is associated with one route table at a time. A route table can be associated with multiple subnets.

A route contains:

- Destination CIDR.
- Target, such as an Internet Gateway, NAT Gateway, or other supported target.

### Local route

When a VPC is created, its route table includes a local route for communication within the VPC CIDR.

Example:

| Destination | Target |
|---|---|
| `10.0.0.0/16` | `local` |
| `0.0.0.0/0` | `igw-xxxxxxxx` |

The local route lets resources communicate within the VPC, subject to security controls.

### Public route table

```text
Public Route Table
------------------
10.0.0.0/16  -> local
0.0.0.0/0    -> Internet Gateway
```

### Private route table with NAT

```text
Private Route Table
-------------------
10.0.0.0/16  -> local
0.0.0.0/0    -> NAT Gateway
```

### Route selection

When multiple routes match, routing uses the most specific matching route (longest prefix match), subject to AWS routing behavior and route-target availability.

Example:

| Destination | Target |
|---|---|
| `10.0.0.0/16` | local |
| `10.0.20.0/24` | VPC peering connection |
| `0.0.0.0/0` | NAT Gateway |

Traffic to `10.0.20.0/24` uses the more specific route rather than the default route.

### Main route table

Every VPC has a main route table. Subnets that are not explicitly associated with another route table use the main route table.

For production networks, explicitly associate subnets with purpose-specific route tables so the intended traffic path is clear.

## 7. Internet Gateway (IGW)

An **Internet Gateway** is a VPC component that enables communication between a VPC and the Internet when routes and addressing are configured appropriately.

### Requirements for an Internet-facing EC2 instance

Typically, the instance needs:

1. A subnet route to an Internet Gateway.
2. A public IPv4 address or another suitable public addressing arrangement.
3. A security group that permits the required inbound traffic.
4. Network ACL rules that permit the traffic and return traffic.
5. An operating-system firewall that permits the traffic.
6. An application listening on the expected interface and port.

### Architecture

```text
                  Internet
                      |
                      v
               Internet Gateway
                      |
                      v
                 Public Subnet
                      |
                      v
                 EC2 Instance
```

An Internet Gateway is horizontally scaled, redundant, and highly available within its VPC design. It does not require you to provision EC2 instances to operate it.

### Important distinction

An Internet Gateway does not automatically assign public IP addresses to instances. Public IPv4 assignment is a separate subnet or launch configuration setting.

## 8. NAT Gateway

A **NAT Gateway** allows resources in a private subnet to initiate supported connections to external networks, commonly the public Internet, without accepting unsolicited inbound Internet connections through that NAT path.

Typical use cases:

- Download operating-system updates.
- Access public package repositories.
- Call external APIs.
- Retrieve public dependencies during deployment.

### NAT architecture

```text
                 Internet
                    |
                    v
             Internet Gateway
                    |
                    v
              Public Subnet
                    |
                    v
                NAT Gateway
                    |
                    v
              Private Subnet
                    |
                    v
                EC2 Instance
```

The private subnet route table points its default route to the NAT Gateway.

### Important NAT Gateway facts

- A public NAT Gateway is created in a public subnet.
- It uses an Elastic IP address.
- The public subnet needs a route to an Internet Gateway.
- Private subnet route tables direct outbound Internet traffic to the NAT Gateway.
- A NAT Gateway does not allow unsolicited inbound Internet connections to private instances.
- NAT Gateway charges can include hourly usage and data processing; review current pricing.
- A NAT Gateway is zonal. For resilience, many architectures deploy one NAT Gateway per AZ and route each private subnet to a NAT Gateway in the same AZ.

### Multi-AZ NAT design

```text
                  Internet Gateway
                    /          \
                   /            \
                  v              v
             NAT Gateway A   NAT Gateway B
                  |              |
                  v              v
             Private AZ-A   Private AZ-B
                EC2             EC2
```

A single NAT Gateway may be simpler for a lab, but it can create a cross-AZ dependency and potential availability or data-transfer considerations. Production design should consider per-AZ NAT placement and cost.

### NAT Gateway vs Internet Gateway

| Feature | Internet Gateway | NAT Gateway |
|---|---|---|
| Main purpose | Internet connectivity for appropriately addressed resources | Outbound connectivity for private-subnet resources |
| Typical route | Public subnet default route | Private subnet default route |
| Public IP for EC2 required? | Typically yes for direct IPv4 Internet communication | Private instance can use NAT without its own public IPv4 |
| Accept unsolicited inbound to private instance | Not applicable as a NAT function | No |
| Managed service | Yes | Yes |

## 9. Security Groups

A **Security Group** is a stateful virtual firewall associated with network interfaces.

Security groups control inbound and outbound traffic.

### Key characteristics

- Stateful.
- Allow rules only; no explicit deny rules.
- Rules from all security groups attached to a network interface are aggregated.
- Return traffic for an allowed connection is automatically permitted.
- Rules can reference other security groups as sources or destinations in supported configurations.

### Example: ALB and application server

**ALB security group**

| Direction | Protocol | Port | Source / destination |
|---|---|---:|---|
| Inbound | TCP | 443 | Intended client networks |
| Outbound | TCP | 8080 | Application security group |

**Application security group**

| Direction | Protocol | Port | Source / destination |
|---|---|---:|---|
| Inbound | TCP | 8080 | ALB security group |
| Outbound | As required | As required | Required dependencies |

This design prevents clients from bypassing the load balancer to reach the application server directly.

### Security group best practices

- Allow only required ports.
- Restrict SSH (TCP 22) to trusted administrator networks or use Session Manager.
- Restrict RDP (TCP 3389) to approved networks.
- Use security group references for tier-to-tier access when practical.
- Avoid broad rules such as all traffic from `0.0.0.0/0`.
- Review both inbound and outbound rules.

## 10. Network ACLs (NACLs)

A **Network Access Control List (Network ACL)** is a stateless traffic filter associated with a subnet.

Unlike a security group, a NACL supports both allow and deny rules.

### Characteristics

- Stateless.
- Applies at subnet level.
- Has numbered rules.
- Rules are evaluated in ascending rule-number order.
- The first matching rule determines the result.
- Separate inbound and outbound rules are evaluated.
- Return traffic must be explicitly allowed.

### Security Group vs NACL

| Feature | Security Group | Network ACL |
|---|---|---|
| Scope | Network interface | Subnet |
| Stateful | Yes | No |
| Allow rules | Yes | Yes |
| Deny rules | No explicit deny rules | Yes |
| Rule evaluation | All applicable rules are considered | First matching numbered rule |
| Return traffic | Automatically allowed for tracked connections | Must be allowed separately |

### Example

Suppose a subnet NACL allows inbound HTTPS and the relevant ephemeral response ports for the expected traffic pattern. Because NACLs are stateless, you must consider both directions.

A correct NACL design depends on the client and server ports, connection direction, and required return traffic. Do not copy a generic rule set without understanding the flow.

### When to use each

- Security groups are usually the primary control for workload-level access.
- NACLs can provide an additional subnet-level boundary.
- Avoid making NACLs unnecessarily complex; a mistake can block return traffic and create confusing connectivity problems.

## 11. VPC DNS Settings

VPC DNS settings help instances resolve hostnames.

Two important VPC attributes are:

- `enableDnsSupport`: enables DNS resolution support in the VPC.
- `enableDnsHostnames`: enables DNS hostnames for instances that have public IP addresses, subject to AWS behavior and configuration.

For many common VPC workloads, both are enabled.

### Why DNS matters

Applications use DNS to resolve names such as:

- Public API hostnames.
- Database endpoints.
- Internal service names.
- AWS service endpoints.

A network connection can fail even when routing is correct if name resolution is not working.

### Inspect DNS attributes

```bash
aws ec2 describe-vpc-attribute \
  --vpc-id vpc-REPLACE_ME \
  --attribute enableDnsSupport

aws ec2 describe-vpc-attribute \
  --vpc-id vpc-REPLACE_ME \
  --attribute enableDnsHostnames
```

## 12. VPC Endpoints: Private Access to AWS Services

A **VPC Endpoint** provides private connectivity from a VPC to supported AWS services without requiring the traffic to traverse the public Internet.

Two common endpoint categories are:

### Gateway Endpoint

Gateway endpoints are available for supported services such as Amazon S3 and DynamoDB.

They add routes to selected route tables.

Example:

```text
Private EC2
    |
    v
Route Table
    |
    v
S3 Gateway Endpoint
    |
    v
Amazon S3
```

This can let private-subnet workloads access S3 without routing that S3 traffic through a NAT Gateway or Internet Gateway.

### Interface Endpoint

Interface endpoints use AWS PrivateLink and create endpoint network interfaces in selected subnets.

They are used for many AWS services and supported endpoint services.

### Endpoint comparison

| Feature | Gateway Endpoint | Interface Endpoint |
|---|---|---|
| Mechanism | Route-table target | Network interfaces using PrivateLink |
| Common services | S3, DynamoDB | Many AWS services |
| Security group | Not attached to gateway endpoint itself | Endpoint network interfaces use security groups |
| Cost model | No endpoint hourly charge for gateway endpoints; other data-related charges may apply | Hourly and data processing charges may apply |

Always check the service's current endpoint support and pricing.

## 13. VPC Flow Logs

**VPC Flow Logs** capture information about IP traffic to and from supported network interfaces or VPC resources.

They can help troubleshoot:

- Unexpected traffic.
- Security group or NACL rejection.
- Network connectivity.
- Traffic patterns.
- Security investigations.

Flow Logs can be published to supported destinations such as CloudWatch Logs or Amazon S3.

### Example use case

An EC2 instance cannot connect to a service. Flow Logs may help determine whether traffic was accepted or rejected at the network interface level.

Flow Logs do not capture every detail of every packet and are not a packet-capture replacement. Use them alongside application logs, route inspection, and other diagnostics.

## 14. AWS CLI: Inspect VPC Resources

The examples use the Singapore Region:

```bash
aws configure set region ap-southeast-1
aws sts get-caller-identity
```

### List VPCs

```bash
aws ec2 describe-vpcs \
  --query "Vpcs[].[VpcId,CidrBlock,IsDefault,State]" \
  --output table
```

### List subnets

```bash
aws ec2 describe-subnets \
  --query "Subnets[].[SubnetId,VpcId,CidrBlock,AvailabilityZone,MapPublicIpOnLaunch]" \
  --output table
```

### List route tables

```bash
aws ec2 describe-route-tables \
  --query "RouteTables[].[RouteTableId,VpcId,Routes]" \
  --output json
```

### List Internet Gateways

```bash
aws ec2 describe-internet-gateways \
  --query "InternetGateways[].[InternetGatewayId,Attachments]" \
  --output json
```

### List NAT Gateways

```bash
aws ec2 describe-nat-gateways \
  --filter "Name=state,Values=available,pending" \
  --query "NatGateways[].[NatGatewayId,VpcId,SubnetId,State]" \
  --output table
```

### List security groups

```bash
aws ec2 describe-security-groups \
  --query "SecurityGroups[].[GroupId,GroupName,VpcId,Description]" \
  --output table
```

### List network ACLs

```bash
aws ec2 describe-network-acls \
  --query "NetworkAcls[].[NetworkAclId,VpcId,IsDefault]" \
  --output table
```

### List VPC endpoints

```bash
aws ec2 describe-vpc-endpoints \
  --query "VpcEndpoints[].[VpcEndpointId,VpcId,ServiceName,VpcEndpointType,State]" \
  --output table
```

### Inspect VPC Flow Logs

```bash
aws ec2 describe-flow-logs \
  --query "FlowLogs[].[FlowLogId,ResourceId,ResourceType,TrafficType,LogDestinationType,FlowLogStatus]" \
  --output table
```

### Inspect route table associations

```bash
aws ec2 describe-route-tables \
  --route-table-ids rtb-REPLACE_ME
```

Review the actual routes and subnet associations before making network changes.

## 15. Hands-on Lab: Plan a Multi-AZ VPC

### Lab objective

Design a VPC for a Spring Boot application in Singapore.

The design includes:

- One VPC.
- Two public subnets.
- Two private application subnets.
- Two private database subnets.
- An Internet Gateway.
- Public and private route tables.
- NAT Gateway strategy.
- Security groups.

This section is a design lab. Creating NAT Gateways, load balancers, and other network resources in a live account can incur charges. Review current pricing and delete lab resources when finished.

### Step 1 — Choose a VPC CIDR

Use:

```text
VPC CIDR: 10.0.0.0/16
```

This is a private IPv4 range.

Check that it does not overlap with other VPCs or networks you need to connect.

### Step 2 — Plan subnets

| Subnet | Availability Zone | CIDR | Purpose |
|---|---|---|---|
| Public-A | AZ-A | `10.0.1.0/24` | Public ALB, NAT Gateway |
| Public-B | AZ-B | `10.0.2.0/24` | Public ALB, NAT Gateway |
| App-A | AZ-A | `10.0.11.0/24` | Spring Boot EC2 |
| App-B | AZ-B | `10.0.12.0/24` | Spring Boot EC2 |
| DB-A | AZ-A | `10.0.21.0/24` | Database subnet group |
| DB-B | AZ-B | `10.0.22.0/24` | Database subnet group |

Replace AZ-A and AZ-B with two actual Availability Zones returned by your account in `ap-southeast-1`.

### Step 3 — Create route-table design

**Public route table**

| Destination | Target |
|---|---|
| `10.0.0.0/16` | local |
| `0.0.0.0/0` | Internet Gateway |

Associate it with Public-A and Public-B.

**Private application route table**

For a per-AZ NAT design:

| Destination | Target |
|---|---|
| `10.0.0.0/16` | local |
| `0.0.0.0/0` | NAT Gateway in the same AZ |

Use separate route tables where needed so each private subnet routes through the intended NAT Gateway.

**Database route table**

A database subnet often does not need general Internet access. Its routes should allow only required internal connectivity and approved dependencies.

### Step 4 — Plan security groups

**ALB security group**

- Inbound TCP 443 from approved clients.
- Outbound application port to the application security group.

**Application security group**

- Inbound TCP 8080 from the ALB security group only.
- Outbound only to required dependencies, such as the database and approved AWS services.

**Database security group**

- Inbound database port only from the application security group.
- No public inbound database access.

### Step 5 — Draw the architecture

```text
                         Internet
                            |
                            v
                    Internet Gateway
                            |
               +------------+------------+
               |                         |
               v                         v
           Public AZ-A               Public AZ-B
               |                         |
          ALB subnet                ALB subnet
               |                         |
               +------------+------------+
                            |
                      Application ALB
                            |
               +------------+------------+
               |                         |
               v                         v
          Private App-A             Private App-B
             EC2 #1                    EC2 #2
               |                         |
               +------------+------------+
                            |
                    Database Security Group
                            |
               +------------+------------+
               |                         |
               v                         v
            DB subnet A               DB subnet B
                    Managed Database
```

This is a conceptual layout. A production design should also show NAT Gateways, route tables, endpoints, and the exact placement of database resources.

### Step 6 — Validate the design

Ask these questions:

1. Can public clients reach only the intended ALB listener?
2. Can the ALB reach the application instances?
3. Can the application instances reach the database on only the required port?
4. Can private instances reach required AWS services without unnecessary Internet paths?
5. Does each subnet use the intended route table?
6. Are private subnets distributed across multiple AZs?
7. Is there a clear plan for NAT Gateway availability and cost?
8. Are VPC CIDR ranges non-overlapping?

### Step 7 — Clean up

If you create resources in AWS, remove them in a safe dependency order after verifying that no workloads depend on them. NAT Gateways, Elastic IP addresses, and other network resources may continue to incur charges while allocated.

## 16. Common VPC Mistakes

1. Choosing a VPC CIDR that overlaps with an on-premises network.
2. Creating subnets with overlapping CIDR ranges.
3. Assuming a subnet is public because its name contains the word `public`.
4. Forgetting the route to an Internet Gateway.
5. Assuming a public IP alone makes an instance reachable.
6. Routing private application traffic through a NAT Gateway without considering cost and AZ resilience.
7. Exposing databases to the Internet.
8. Confusing Security Groups with Network ACLs.
9. Forgetting that NACLs are stateless and require return-traffic rules.
10. Allowing broad inbound rules such as all traffic from `0.0.0.0/0`.
11. Forgetting to associate the intended route table with each subnet.
12. Overlooking DNS settings and VPC endpoint options.
13. Making network changes without checking their impact on existing resources.

## 17. Practical Exercises

### Exercise 1 — VPC

**Question:** What is an Amazon VPC?

**Answer:** A VPC is a logically isolated virtual network in AWS where you control address ranges, subnets, routing, and network security.

### Exercise 2 — CIDR

**Question:** How many IPv4 addresses are in a `/24` CIDR block?

**Answer:** \(2^{32-24} = 256\) total addresses. AWS reserves five IPv4 addresses in each subnet.

### Exercise 3 — Subnets

**Question:** Can one subnet span two Availability Zones?

**Answer:** No. Each subnet belongs to one Availability Zone.

### Exercise 4 — Public subnet

**Question:** What makes a subnet public?

**Answer:** It has a route to an Internet Gateway. Resources also need appropriate addressing and security configuration for Internet communication.

### Exercise 5 — Route tables

**Question:** What is the local route in a VPC route table?

**Answer:** It allows routing within the VPC CIDR, subject to security controls.

### Exercise 6 — Internet Gateway

**Question:** Does an Internet Gateway automatically assign public IP addresses?

**Answer:** No. Public IP assignment is a separate configuration.

### Exercise 7 — NAT Gateway

**Question:** Why does a private EC2 instance use a NAT Gateway?

**Answer:** It can initiate supported outbound connections to the Internet without having its own public IPv4 address or accepting unsolicited inbound Internet connections through the NAT path.

### Exercise 8 — Security Groups

**Question:** Are Security Groups stateful or stateless?

**Answer:** Stateful.

### Exercise 9 — NACL

**Question:** Can a Network ACL deny traffic?

**Answer:** Yes. NACLs support numbered allow and deny rules and are stateless.

### Exercise 10 — VPC Endpoints

**Question:** What is the benefit of an S3 Gateway Endpoint?

**Answer:** It provides private routing from selected VPC route tables to S3 without requiring S3 traffic to traverse a NAT Gateway or Internet Gateway.

### Exercise 11 — DNS

**Question:** Name two VPC DNS attributes.

**Answer:** `enableDnsSupport` and `enableDnsHostnames`.

### Exercise 12 — Architecture

**Question:** Where should a production Spring Boot EC2 application commonly run when exposed through a public ALB?

**Answer:** In private subnets across multiple Availability Zones, with the ALB in public subnets and security groups restricting application traffic to the ALB.

## 20. AWS Interview Questions and Answers

### Q1. What is Amazon VPC?

Amazon VPC is a logically isolated virtual network in AWS. It allows you to define IP address ranges, subnets, routes, and network security.

### Q2. Is a VPC regional or global?

A VPC is regional. Its subnets are created in Availability Zones within that Region.

### Q3. Can a subnet span multiple Availability Zones?

No. A subnet belongs to one Availability Zone.

### Q4. What is CIDR notation?

CIDR notation describes an IP address range and its network prefix length. For example, `10.0.0.0/16` contains 65,536 IPv4 addresses before AWS subnet reservations.

### Q5. What makes a subnet public?

A public subnet has a route to an Internet Gateway. For an instance to communicate directly with the public Internet, it also needs suitable public addressing and network permissions.

### Q6. What is the purpose of a route table?

A route table determines where traffic from a subnet or network interface is directed based on destination addresses.

### Q7. What is an Internet Gateway?

An Internet Gateway is a VPC component that enables communication between the VPC and the Internet when routing, addressing, and security are configured correctly.

### Q8. What is a NAT Gateway?

A NAT Gateway enables resources in private subnets to initiate supported outbound connections, commonly to the Internet, without accepting unsolicited inbound Internet connections through that NAT path.

### Q9. What is the difference between a Security Group and a NACL?

A Security Group is stateful and applies to network interfaces. A NACL is stateless and applies at subnet level. Security Groups support allow rules, while NACLs support allow and deny rules.

### Q10. Why must NACL return traffic be configured?

NACLs are stateless. The inbound and outbound directions are evaluated separately, so return traffic must be explicitly allowed.

### Q11. What is a VPC Endpoint?

A VPC Endpoint provides private connectivity from a VPC to supported AWS services or endpoint services without requiring traffic to use the public Internet.

### Q12. What is the difference between Gateway and Interface Endpoints?

Gateway Endpoints add routes to route tables for supported services such as S3 and DynamoDB. Interface Endpoints use network interfaces and AWS PrivateLink for many supported services.

### Q13. What are VPC Flow Logs?

Flow Logs capture information about IP traffic to and from supported VPC resources or network interfaces. They help with monitoring and troubleshooting but are not a full packet capture.

### Q14. How would you design a VPC for a Spring Boot application?

I would create a VPC with public and private subnets across multiple Availability Zones. I would place an internet-facing ALB in public subnets, EC2 application instances in private subnets, and a database in private database subnets. Security Groups would restrict traffic between tiers.

### Q15. Why might a private EC2 instance fail to download software updates?

Possible causes include a missing NAT route, unavailable NAT Gateway, incorrect route table association, NACL or Security Group restrictions, DNS problems, or an operating-system firewall issue.

### Q16. Does assigning a public IP make an EC2 instance reachable?

No. The subnet needs a suitable route to an Internet Gateway, and Security Groups, NACLs, host firewall settings, and the application must allow the traffic.
