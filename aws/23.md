## 2. Review: ALB Request Flow

An Application Load Balancer operates at Layer 7 and supports HTTP/HTTPS-aware routing.

A typical request flow:

```text
                         Client
                           |
                           | HTTPS :443
                           v
                    ALB HTTPS Listener
                           |
                    Listener Rules
                           |
              +------------+------------+
              |                         |
              v                         v
       Orders Target Group       Products Target Group
              |                         |
          +---+---+                 +---+---+
          |       |                 |       |
          v       v                 v       v
        App A   App B             App C   App D
```

The listener receives the request, evaluates rules in priority order, and performs an action such as forwarding, redirecting, or returning a fixed response.

A target group defines the destinations that receive forwarded traffic and includes health-check configuration.

## 3. Host-Based Routing

Host-based routing sends requests to different target groups according to the hostname.

### Example

| Hostname | Target group |
|---|---|
| `api.example.com` | API target group |
| `admin.example.com` | Admin target group |
| `shop.example.com` | Storefront target group |

Architecture:

```text
                         ALB
                          |
                   HTTPS Listener
                          |
             +------------+------------+
             |            |            |
             v            v            v
       api.example.com admin.example.com shop.example.com
             |            |            |
             v            v            v
          API TG        Admin TG     Store TG
```

### Benefits

- Multiple services can share one ALB.
- Each hostname can route to a different application.
- Services can be deployed and scaled independently.
- Centralized TLS termination can simplify the entry architecture.

### Important considerations

- DNS records must resolve to the intended ALB.
- Listener rules must match the expected host header.
- Certificates must cover the hostnames used by clients.
- Security and authentication must still be enforced by the application and relevant AWS controls.

## 4. Path-Based Routing

Path-based routing sends requests to different target groups based on the URL path.

### Example

| Request path | Target group |
|---|---|
| `/api/orders/*` | Orders service |
| `/api/products/*` | Products service |
| `/api/users/*` | Users service |
| `/admin/*` | Admin service |

Architecture:

```text
                         ALB
                          |
                   HTTPS Listener
                          |
             +------------+------------+
             |            |            |
             v            v            v
       /api/orders/* /api/products/* /api/users/*
             |            |            |
             v            v            v
        Orders TG    Products TG     Users TG
```

### Example microservices

Suppose an e-commerce platform contains:

- Order Service.
- Product Service.
- User Service.

Each service can run in its own target group and scale independently.

### Rule priority

ALB listener rules have priorities. Rules are evaluated in priority order, and the default action is used if no rule matches.

Example:

| Priority | Condition | Action |
|---:|---|---|
| 10 | Path `/api/orders/*` | Forward to Orders TG |
| 20 | Path `/api/products/*` | Forward to Products TG |
| 30 | Path `/api/users/*` | Forward to Users TG |
| Default | No matching rule | Fixed response or default target |

Choose priorities carefully so that specific rules are not shadowed by broader rules.

## 5. Listener Actions

ALB listeners support different actions, depending on listener type and configuration.

Common action types include:

### Forward

Forward the request to one or more target groups.

### Redirect

Send the client to another URL.

Example: redirect HTTP to HTTPS.

```text
HTTP :80
   |
   v
Redirect to HTTPS :443
   |
   v
HTTPS Listener
   |
   v
Application Target Group
```

### Fixed response

Return a configured response directly from the load balancer.

Useful for:

- Maintenance responses.
- Simple default responses.
- Rejecting unmatched paths with an intentional status code.

### Authenticate

ALB supports authentication actions with supported identity providers and configurations. Review current service support and security requirements before using this for an application.

## 6. Weighted Forwarding

Weighted forwarding allows an ALB rule to distribute traffic across multiple target groups using configured weights.

This can be used for gradual traffic migration or testing a new application version.

### Example: Version migration

- Version 1 target group: weight 90.
- Version 2 target group: weight 10.

```text
                    ALB Listener
                          |
                  Weighted Forwarding
                          |
                +---------+---------+
                |                   |
                v                   v
          Version 1 TG         Version 2 TG
             Weight 90            Weight 10
                |                   |
                v                   v
          Stable Version       New Version
```

The weights influence the distribution of requests across target groups. They do not guarantee an exact percentage over a small number of requests.

### Gradual rollout example

| Stage | Version 1 | Version 2 |
|---|---:|---:|
| Initial | 100 | 0 |
| Test | 95 | 5 |
| Small rollout | 90 | 10 |
| Wider rollout | 50 | 50 |
| Complete | 0 | 100 |

### Important considerations

- Monitor error rates and latency for each version.
- Ensure both versions can safely use the same database schema during migration.
- Plan rollback before shifting traffic.
- Avoid incompatible database changes during a mixed-version deployment.
- A weighted rule alone is not a complete canary deployment system; monitoring and promotion decisions are also required.

## 7. Target Group Attributes

Target groups have attributes that affect how traffic is handled.

Examples include:

- Stickiness.
- Deregistration delay.
- Slow start, where supported.
- Load-balancing algorithm settings, where supported.
- Health-check behavior.

Available attributes depend on the load-balancer type and target-group configuration.

### Deregistration delay

Deregistration delay is commonly associated with connection draining.

When a target is deregistered, the load balancer can allow existing in-flight requests or connections time to complete before fully stopping traffic to the target, subject to protocol and configuration behavior.

Example:

```text
Target receives requests
          |
          v
Target begins deregistration
          |
          v
No new requests are sent to target
          |
          v
Existing work is allowed time to finish
          |
          v
Target removed from service
```

This helps reduce interrupted requests during deployments or scale-in events.

### Choosing a delay

The correct delay depends on:

- Typical request duration.
- Long-running requests.
- WebSocket or streaming behavior.
- Application shutdown behavior.
- Deployment timeout.
- Load-balancer and target configuration.

Do not choose a very long delay without considering deployment speed and operational impact.

## 8. Sticky Sessions

Sticky sessions, also called session affinity, can help route a user's requests to the same target for a configured period.

### Example

```text
User A ---> ALB ---> App Instance A
   |                   ^
   |                   |
   +---- next request -+
```

With stickiness enabled, the load balancer can use a cookie to maintain affinity to a target for the configured duration, subject to the target group and client behavior.

### When might stickiness help?

- Legacy applications keep session state locally.
- A workflow expects repeated requests to reach the same server.
- A temporary compatibility requirement exists.

### Trade-offs

- Traffic can become unevenly distributed.
- A target failure can still interrupt a user's session.
- It can hide poor session architecture.
- It does not replace shared session storage or stateless authentication.

### Better application design

Prefer:

- Stateless authentication where suitable.
- Shared session storage for applications that require server-side sessions.
- Externalized file storage such as S3.
- Avoiding local-instance state as a dependency.

## 9. ALB Integration with EC2 Auto Scaling

An EC2 Auto Scaling Group (ASG) maintains a desired number of EC2 instances within configured minimum and maximum limits.

When integrated with an ALB target group:

1. Auto Scaling launches an instance.
2. The instance is registered with the target group.
3. The target group performs health checks.
4. The ALB sends traffic to healthy targets.
5. During scale-in, the instance is deregistered.
6. Connection draining and lifecycle behavior help manage termination.

### Architecture

```text
                       Users
                         |
                         v
                        ALB
                         |
                         v
                   Target Group
                         |
              +----------+----------+
              |          |          |
              v          v          v
            EC2 A      EC2 B      EC2 C
              \          |          /
               \         |         /
                +--------+--------+
                         |
                         v
                 Auto Scaling Group
```

The ASG manages the instance fleet. The ALB distributes traffic to registered healthy targets.

### Capacity settings

| Setting | Meaning |
|---|---|
| Minimum capacity | Lowest number of instances the group should maintain |
| Desired capacity | Intended number of instances |
| Maximum capacity | Upper limit for scaling |

Example:

- Minimum: 2
- Desired: 2
- Maximum: 6

The ASG can scale between 2 and 6 instances according to its policies and conditions.

### Health check integration

An ASG can use EC2 health checks and, when configured, Elastic Load Balancing health checks.

If an instance is considered unhealthy by the configured health-check mechanism, Auto Scaling can replace it according to its settings.

Review grace periods and application startup time so that instances are not replaced prematurely.

## 10. Auto Scaling Policies

Auto Scaling policies adjust capacity based on metrics or schedules.

### Target tracking scaling

Target tracking attempts to maintain a selected metric near a target value.

Example:

- Maintain average CPU utilization around 50%.

### Step scaling

Step scaling adjusts capacity according to CloudWatch alarm thresholds and configured step adjustments.

### Scheduled scaling

Scheduled scaling changes desired capacity at known times.

Example:

- Increase capacity before a predictable daily traffic peak.
- Reduce capacity during a quiet period, while respecting minimum capacity.

### Predictive scaling

Predictive scaling uses historical patterns to forecast future demand and schedule capacity changes, subject to service support and configuration.

### Comparison

| Policy | Main idea | Example |
|---|---|---|
| Target tracking | Maintain a metric near a target | Average CPU around 50% |
| Step scaling | Apply adjustments based on alarm thresholds | Add 2 instances when CPU is high |
| Scheduled scaling | Scale at known times | Increase capacity before business hours |
| Predictive scaling | Forecast recurring demand | Prepare for recurring traffic patterns |

Choose metrics that represent application demand. CPU utilization alone may not accurately represent every workload.

## 11. Rolling, Blue/Green, and Canary Deployments

### Rolling deployment

Gradually replace old application instances with new ones.

```text
Start:       Old Old Old Old
Step 1:      New Old Old Old
Step 2:      New New Old Old
Step 3:      New New New Old
Complete:    New New New New
```

Advantages:
- Gradual replacement.
- Can use existing fleet infrastructure.

Considerations:
- Old and new versions may run simultaneously.
- Database changes must be backward-compatible during the rollout.
- Capacity must be sufficient while instances are replaced.

### Blue/green deployment

Run two separate environments:

- Blue: current production version.
- Green: new version.

```text
                  ALB
                   |
             Traffic Switch
               /       \
              v         v
          Blue Env   Green Env
          Current      New
```

After testing Green, shift traffic to it. Keep Blue available for rollback until the new environment is accepted and the rollback window ends.

Advantages:
- Clear separation between versions.
- Fast traffic switch.
- Rollback can be straightforward if dependencies remain compatible.

Considerations:
- Requires additional temporary capacity.
- Database changes need compatibility planning.
- Environment configuration must remain consistent.

### Canary deployment

Send a small portion of traffic to a new version, monitor it, and gradually increase traffic.

```text
                 ALB
                  |
          Weighted Forwarding
              /       \
             v         v
          Stable      Canary
           95%          5%
```

Advantages:
- Limits initial exposure.
- Supports real-traffic validation.

Considerations:
- Requires good observability.
- Small traffic samples may not reveal every problem.
- Rollback criteria must be defined.

### Comparison

| Strategy | Traffic / replacement approach | Main benefit | Main consideration |
|---|---|---|---|
| Rolling | Replace instances gradually | Uses existing fleet | Versions coexist temporarily |
| Blue/green | Switch between two environments | Clear rollback boundary | Extra environment capacity |
| Canary | Send a small share to new version | Limits initial exposure | Requires monitoring and controlled promotion |

## 12. Monitoring ALB and Auto Scaling

Use Amazon CloudWatch to monitor load balancers, target groups, and Auto Scaling.

### Useful ALB metrics

Examples include:

- Request count.
- Target response time.
- HTTP 4xx count.
- HTTP 5xx count.
- Healthy host count.
- Unhealthy host count.
- Rejected connection count, where applicable.

Metric names and dimensions vary by load-balancer type and service behavior.

### Useful Auto Scaling metrics

- Group desired capacity.
- Group in-service instances.
- Group pending instances.
- Group total instances.
- Scaling activity history.

### Logs

ALB access logs can help investigate:

- Client requests.
- Request paths.
- Target selection.
- Response status codes.
- Processing times.
- Client and target addresses.

Access logs are delivered to an S3 bucket when configured. Review permissions, retention, and data-protection requirements.

### Monitoring checklist

1. Alert on sustained 5xx increases.
2. Monitor target response time.
3. Monitor healthy and unhealthy target counts.
4. Monitor Auto Scaling activity.
5. Monitor application-specific metrics.
6. Correlate ALB access logs with application logs.
7. Review deployment events when errors increase.
8. Monitor capacity before predictable traffic peaks.

## 13. Spring Boot Architecture with ALB and Auto Scaling

### Scenario

Deploy an e-commerce API using:

- Application Load Balancer.
- EC2 Auto Scaling Group.
- Spring Boot application.
- Amazon RDS.
- S3 for product images.
- CloudWatch monitoring.

### Architecture

```text
                          Customers
                              |
                              v
                       Route 53 DNS
                              |
                              v
                            AWS WAF
                              |
                              v
                       Application ALB
                         HTTPS :443
                              |
                              v
                         Target Group
                              |
              +---------------+---------------+
              |               |               |
              v               v               v
            EC2 A           EC2 B           EC2 C
          Spring Boot     Spring Boot     Spring Boot
              \               |               /
               +--------------+--------------+
                              |
                     +--------+--------+
                     |                 |
                     v                 v
                 Amazon RDS       S3 Endpoint
                 Private DB       Product Images

                  Auto Scaling Group
                  manages EC2 capacity

                  CloudWatch monitors
                  ALB, targets, and ASG
```

### Application requirements

- Spring Boot listens on port 8080.
- ALB forwards traffic to target group port 8080.
- Target group health check uses a suitable endpoint.
- Application instances are in private subnets.
- ALB is deployed across appropriate public subnets.
- RDS accepts connections only from the application Security Group.
- Instances use IAM roles for AWS service access.
- Application logs are sent to a centralized logging destination.

### Session design

Avoid relying on local instance memory for user sessions when requests may reach different instances.

Options:

- Stateless token-based authentication.
- Shared session store.
- Externalized session management.

### File storage

Do not store user-uploaded files only on one EC2 instance's local disk.

Use shared object storage such as Amazon S3, with IAM permissions and suitable bucket policies.

### Database connection pool

When the ASG scales out, each instance may create its own database connection pool.

For example:

- 4 instances.
- Maximum pool size of 20 per instance.
- Potential maximum application connections: 80.

This is a simplified capacity calculation. Include background jobs, administrative connections, and other applications when planning database limits.

## 15. Hands-on Lab — ALB with Auto Scaling

### Lab objective

Design a Spring Boot application deployment that can scale between 2 and 6 EC2 instances.

### Requirements

- ALB in two public subnets.
- EC2 instances in two private application subnets.
- Target group listens on HTTP port 8080.
- Health check path is `/actuator/health`.
- Auto Scaling minimum: 2.
- Desired capacity: 2.
- Maximum capacity: 6.
- HTTPS listener on port 443.
- HTTP listener redirects to HTTPS.
- RDS is private.

### Step 1 — Create the application artifact

Build a Spring Boot JAR:

```bash
mvn clean package
```

The resulting artifact is commonly located under:

```text
target/
```

The exact filename depends on the Maven project configuration.

### Step 2 — Prepare the instance bootstrap process

A production-quality deployment should use a controlled image or deployment pipeline. A simplified user-data script might install Java and start an application artifact that is already available to the instance:

```bash
#!/bin/bash
set -e

dnf update -y
dnf install -y java-21-amazon-corretto-headless

mkdir -p /opt/spring-app

# Retrieve the application artifact using an approved
# private S3 path and the EC2 instance role.
aws s3 cp s3://YOUR_BUCKET/YOUR_PREFIX/app.jar /opt/spring-app/app.jar

cat > /etc/systemd/system/spring-app.service <<'EOF'
[Unit]
Description=Spring Boot Application
After=network.target

[Service]
User=root
WorkingDirectory=/opt/spring-app
ExecStart=/usr/bin/java -jar /opt/spring-app/app.jar
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable spring-app
systemctl start spring-app
```

This is a learning example, not a complete production bootstrap strategy. A production implementation should use a non-root service account, controlled artifact versions, secure configuration, robust logging, patch management, and an approved deployment mechanism. Confirm the operating system package manager and Java version for the selected AMI.

### Step 3 — Configure target group

Example design:

| Setting | Value |
|---|---|
| Target type | Instance |
| Protocol | HTTP |
| Port | 8080 |
| Health path | `/actuator/health` |
| Success code | 200 |

### Step 4 — Attach target group to ASG

Configure the Auto Scaling Group to register instances with the target group.

Ensure the ASG spans the intended private subnets across Availability Zones.

### Step 5 — Configure capacity

| Setting | Value |
|---|---:|
| Minimum | 2 |
| Desired | 2 |
| Maximum | 6 |

### Step 6 — Choose a scaling policy

For a learning exercise, evaluate target tracking using average CPU utilization.

A target such as 50% can be used as an illustrative starting point, but the correct metric and target must be determined through workload testing.

### Step 7 — Test health checks

- Confirm both targets register.
- Confirm the health endpoint returns the expected response.
- Check the target health reason if a target is unhealthy.
- Confirm ALB can reach port 8080.

### Step 8 — Test scaling

In a non-production environment:

1. Generate controlled test load.
2. Observe CloudWatch metrics.
3. Observe Auto Scaling activities.
4. Confirm new instances launch.
5. Confirm new targets register and become healthy.
6. Reduce test load.
7. Observe scale-in behavior.
8. Confirm connection draining and application shutdown behavior.

Do not run uncontrolled load tests against production.

### Step 9 — Test deployment behavior

Simulate a deployment using a test version:

- Register new targets or update the ASG through an approved deployment approach.
- Monitor health and 5xx metrics.
- Confirm requests continue to succeed.
- Roll back if error rates exceed the agreed threshold.

### Step 10 — Review cost and capacity

Consider:

- ALB hourly and capacity-related charges.
- EC2 instance costs.
- NAT Gateway costs if used.
- EBS storage.
- Data transfer.
- CloudWatch logs and metrics.
- RDS capacity and connection limits.

## 16. Troubleshooting Advanced ALB and Auto Scaling Problems

| Symptom | Possible cause | What to inspect |
|---|---|---|
| New EC2 instance never becomes healthy | App not ready, wrong port, SG issue | Instance logs, target health, SG |
| ASG launches too many instances | Scaling metric or thresholds unsuitable | Scaling policy, CloudWatch metric, cooldown behavior |
| ASG does not scale out | Alarm not triggered, policy missing, maximum reached | Alarm state, scaling activity, limits |
| Requests fail during deployment | Short drain period, abrupt shutdown, incompatible versions | Deregistration delay, lifecycle, app logs |
| Users lose sessions | Session state stored locally | Session architecture |
| New version causes 5xx | Application defect or incompatible dependency | Target-specific metrics, logs, rollback |
| ALB routes to wrong service | Listener condition or priority incorrect | Listener rules |
| Target group has no healthy targets | Targets not registered or health check failing | Target registration and health reason |
| Database fails after scale-out | Too many database connections | Pool sizing, RDS limits, application metrics |

### Useful troubleshooting sequence

1. Check ALB listener and rule configuration.
2. Check target-group registration.
3. Check target health and reason codes.
4. Check Security Groups and NACLs.
5. Check application process and listening port.
6. Check health endpoint response.
7. Review ALB access logs.
8. Review application logs.
9. Review CloudWatch metrics and alarms.
10. Review Auto Scaling activities and lifecycle events.

## 17. Practical Exercises

### Exercise 1 — Host-based routing

**Question:** How can an ALB route `api.example.com` and `admin.example.com` to different services?

**Answer:** Configure listener rules that match the Host header and forward each hostname to its corresponding target group.

### Exercise 2 — Path-based routing

**Question:** How can `/api/orders/*` and `/api/products/*` reach different microservices?

**Answer:** Create listener rules with path conditions and forward each rule to the appropriate target group.

### Exercise 3 — Weighted forwarding

**Question:** What is weighted forwarding useful for?

**Answer:** It can distribute traffic across multiple target groups, for example during a gradual migration or controlled rollout.

### Exercise 4 — Deregistration delay

**Question:** Why is deregistration delay useful?

**Answer:** It gives in-flight requests or connections time to complete when a target is being removed, subject to protocol and configuration behavior.

### Exercise 5 — Sticky sessions

**Question:** Why should an application avoid depending on sticky sessions for all session state?

**Answer:** Stickiness can cause uneven traffic and does not replace shared state. A target can fail, and local session data may be lost.

### Exercise 6 — Auto Scaling

**Question:** What are the minimum, desired, and maximum capacities?

**Answer:** Minimum is the lowest maintained capacity, desired is the intended current capacity, and maximum is the upper capacity limit.

### Exercise 7 — Target tracking

**Question:** What does target tracking scaling try to do?

**Answer:** It adjusts capacity to keep a selected metric near a configured target value.

### Exercise 8 — Blue/green

**Question:** What is a blue/green deployment?

**Answer:** It uses two environments, one running the current version and one running the new version, then shifts traffic after validation.

### Exercise 9 — Canary

**Question:** What is a canary deployment?

**Answer:** It sends a small portion of traffic to a new version, monitors behavior, and gradually increases traffic if the version is healthy.

### Exercise 10 — Health checks

**Question:** Why can a target fail a health check even when the EC2 instance is running?

**Answer:** The application may not be ready, the health path or port may be incorrect, the application may return an unexpected status, or network controls may block the health check.

### Exercise 11 — Sessions

**Question:** Why can local in-memory sessions fail behind an ALB?

**Answer:** Requests can reach different instances, and each instance has separate memory. Shared session storage or stateless authentication is usually more resilient.

### Exercise 12 — Database connections

**Question:** Why should database connection pools be considered when an ASG scales out?

**Answer:** Each application instance can create its own pool. Scaling the instance count can multiply the total database connections and exceed database capacity.

### Exercise 13 — Monitoring

**Question:** Which metrics help identify ALB problems?

**Answer:** Request count, target response time, HTTP 5xx count, healthy and unhealthy host counts, and relevant connection metrics.

### Exercise 14 — Architecture

**Question:** Describe a scalable Spring Boot architecture using ALB and Auto Scaling.

**Answer:** Deploy an ALB across public subnets, register private EC2 instances in a target group, attach the target group to an Auto Scaling Group, configure health checks, and monitor application and infrastructure metrics.

## 20. AWS Interview Questions and Answers

### Q1. What is host-based routing?

Host-based routing forwards requests to target groups based on the HTTP Host header.

### Q2. What is path-based routing?

Path-based routing forwards requests based on the URL path.

### Q3. What is weighted forwarding?

Weighted forwarding distributes requests across multiple target groups according to configured weights. It can support gradual traffic migration.

### Q4. Does a 90/10 weight guarantee exactly 90% and 10% for every small batch of requests?

No. Weights influence traffic distribution, but small samples can vary.

### Q5. What is deregistration delay?

It is the period associated with deregistering a target during which the load balancer can allow in-flight work to complete, according to supported behavior and configuration.

### Q6. What are sticky sessions?

Sticky sessions use session affinity so that a user's requests can be directed to the same target for a configured duration.

### Q7. What is an EC2 Auto Scaling Group?

An Auto Scaling Group manages a fleet of EC2 instances and maintains capacity within configured minimum and maximum limits.

### Q8. What is desired capacity?

Desired capacity is the intended number of instances the Auto Scaling Group should maintain.

### Q9. What is target tracking scaling?

It is a scaling policy that adjusts capacity to keep a selected metric near a target value.

### Q10. What is the difference between target tracking and step scaling?

Target tracking tries to maintain a metric near a target. Step scaling applies configured capacity changes based on alarm thresholds and step adjustments.

### Q11. What is a rolling deployment?

A rolling deployment gradually replaces old application instances with new ones.

### Q12. What is a blue/green deployment?

Blue/green deployment maintains separate old and new environments and shifts traffic to the new environment after validation.

### Q13. What is a canary deployment?

A canary deployment sends a small portion of traffic to a new version and gradually increases it after monitoring the results.

### Q14. Why is backward-compatible database migration important?

Old and new application versions may run simultaneously during a rollout. Both versions need to work with the database schema during that transition.

### Q15. Why is shared session storage useful?

Requests can reach different instances. Shared session storage avoids depending on one instance's local memory.

### Q16. What is connection draining?

It is the process of allowing existing requests or connections time to finish as a target is removed from service, according to the relevant configuration and protocol behavior.

### Q17. How does an ALB integrate with an Auto Scaling Group?

The target group is associated with the Auto Scaling Group. New instances can be registered and removed instances deregistered as the group scales.

### Q18. Why might an Auto Scaling Group replace a running instance?

It may be considered unhealthy by the configured health checks or replaced through scaling, maintenance, or deployment activities. Inspect the activity history and health-check configuration.

### Q19. Why can scaling out cause database problems?

Each application instance may create its own database connection pool. Increasing the instance count can increase total connections beyond database capacity.

### Q20. What should you monitor during a canary deployment?

Monitor error rates, latency, target health, application-specific metrics, logs, and downstream dependency health. Define rollback thresholds before increasing traffic.
