## 2. What Is Amazon SNS?

Amazon Simple Notification Service (Amazon SNS) is a fully managed pub/sub messaging service. A publisher sends a message to an SNS topic, and SNS delivers that message to subscribed endpoints.

The publisher does not need to know the details of every subscriber.

```text
                  Publisher
                Spring Boot API
                      |
                      v
                 SNS Topic
                /    |     \
               /     |      \
              v      v       v
           SQS A   Lambda   SQS B
              |      |       |
              v      v       v
          Billing  Email   Analytics
```

### Example

An e-commerce application creates an order. Several independent systems need to react:

- Billing service records the payment workflow.
- Notification service sends an order confirmation.
- Analytics service records an event.
- Fulfillment service starts shipment preparation.

Without pub/sub, the order API might need to call each service directly. With SNS, it publishes one event to a topic, and SNS routes copies to subscribed endpoints.

### Why use SNS?

- **Fanout:** one published message can reach many subscribers.
- **Decoupling:** publishers do not need to know subscribers.
- **Independent processing:** subscribers can use different services and technologies.
- **Filtering:** subscriptions can receive only messages matching defined attributes or body fields.
- **Managed delivery:** SNS handles delivery attempts to supported endpoints.

SNS is a messaging and notification service, not a general-purpose database or a replacement for durable application state.

## 3. Core SNS Concepts

| Term | Meaning |
|---|---|
| Topic | Logical communication channel to which publishers send messages |
| Publisher | Application or AWS service that publishes a message |
| Subscriber | Endpoint that receives messages |
| Subscription | Relationship between a topic and an endpoint |
| Protocol | Delivery mechanism, such as SQS, Lambda, email, or HTTPS |
| Message | Content published to the topic |
| Message attribute | Metadata used for filtering or endpoint-specific handling |
| Filter policy | Rules determining which messages a subscription receives |
| Delivery policy | Rules controlling retry behavior for supported endpoint types |

### Topic and subscription example

```text
Topic: OrderEvents

Subscriptions:
  - SQS: BillingQueue
  - SQS: FulfillmentQueue
  - Lambda: SendNotification
  - HTTPS: https://example.com/events
```

A message published to `OrderEvents` can be delivered to all four subscriptions, subject to their filter policies and endpoint configuration.

## 4. SNS Standard vs. FIFO Topics

SNS supports Standard and FIFO topic types.

| Feature | Standard topic | FIFO topic |
|---|---|---|
| Ordering | Best-effort | Preserved within message groups |
| Throughput | High, elastic | FIFO-specific throughput quotas and configuration |
| Deduplication | No FIFO deduplication feature | Supports deduplication |
| Delivery model | At-least-once for supported delivery paths; duplicates can occur | FIFO ordering/deduplication capabilities for supported integrations |
| Typical use | Notifications and independent event fanout | Ordered event processing where supported |

### Standard topics

Use Standard topics when:

- High-throughput event distribution is important.
- Subscribers can process messages independently.
- The application can handle occasional duplicate or out-of-order delivery.

### FIFO topics

Use FIFO topics when:

- Message order matters within a business entity.
- You can define a message group, such as `ORDER#O501`.
- The downstream subscription types and integration support the required FIFO behavior.

SNS FIFO topic support is more constrained than Standard topics. Verify the current supported subscriber types, throughput limits, and integration requirements before choosing FIFO. SNS FIFO topics are commonly used with SQS FIFO subscriptions for ordered fanout.

### Important: ordering is scoped

FIFO ordering is maintained within a message group, not as one global order across every message group. Different groups can be processed concurrently.

### Deduplication does not guarantee exactly-once side effects

Even when a FIFO topic deduplicates messages, a downstream consumer can fail after performing an external action but before acknowledging the message. Use application-level idempotency for payments, emails, and other business side effects.

## 5. SNS Fanout with SQS

One of the most useful SNS architectures is SNS-to-SQS fanout.

```text
                    Order API
                       |
                       v
                  SNS Topic
                 OrderEvents
                /     |      \
               v      v       v
          Billing   Shipping  Analytics
          SQS Queue SQS Queue SQS Queue
               |       |       |
               v       v       v
          Consumer  Consumer  Consumer
```

### Why combine SNS and SQS?

SNS provides message distribution. SQS provides a durable queue that allows each subscriber to process messages independently.

Benefits:

- Each consumer has its own queue and backlog.
- A slow billing consumer does not need to block analytics.
- Consumers can retry independently.
- Each queue can have its own visibility timeout and DLQ.
- Consumers can scale independently.

### SNS direct delivery vs. SNS-to-SQS

| Design | Behavior | Good fit |
|---|---|---|
| SNS to Lambda | SNS invokes Lambda | Short event-driven processing |
| SNS to SQS | SNS sends a message to a queue | Durable, independently scaled workers |
| SNS to HTTPS | SNS sends an HTTP notification | External webhooks |
| SNS to email/SMS | SNS sends notifications | Human-facing alerts |

For business-critical background work, SNS-to-SQS is often a strong pattern because the queue provides buffering and independent consumption.

## 6. Supported Subscription Protocols

Common SNS subscription protocols include:

| Protocol | Destination | Typical use |
|---|---|---|
| `sqs` | Amazon SQS queue | Durable background processing |
| `lambda` | AWS Lambda function | Event-driven function execution |
| `https` / `http` | Web endpoint | Webhooks and integrations |
| `email` | Email address | Human-readable notifications |
| `email-json` | Email address with JSON message format | Structured email notification |
| `sms` | Mobile phone number | Text notifications |

Endpoint support and configuration can vary by topic type and Region. For production integrations, check the current SNS documentation.

### Subscription confirmation

Some endpoint types, especially HTTP/S and email, require confirmation before SNS starts delivering messages.

Typical flow:

```text
Create subscription
       |
       v
SNS sends confirmation request
       |
       v
Endpoint owner confirms
       |
       v
Subscription becomes confirmed
       |
       v
SNS delivers notifications
```

For an HTTP/S endpoint, the application should validate that a confirmation request genuinely comes from SNS before following its confirmation URL. Do not blindly trust arbitrary incoming requests.

## 7. Message Attributes and Subscription Filtering

A topic can have many subscribers, but each subscriber may need only certain messages.

SNS subscription filter policies allow SNS to filter messages before delivery.

### 7.1 Message attributes

A publisher can attach metadata such as:

```text
eventType = ORDER_CREATED
region    = APAC
priority  = HIGH
```

A subscription can define a filter policy that matches selected attributes.

Example filter policy:

```json
{
  "eventType": ["ORDER_CREATED", "ORDER_PAID"],
  "priority": ["HIGH"]
}
```

A subscription with this policy receives messages whose attributes match the policy conditions.

### 7.2 Filter on message body

SNS can also filter on message body fields when the subscription is configured for body-based filtering.

Example body:

```json
{
  "eventType": "ORDER_CREATED",
  "order": {
    "orderId": "O501",
    "region": "APAC"
  }
}
```

Example body filter:

```json
{
  "eventType": ["ORDER_CREATED"],
  "order": {
    "region": ["APAC"]
  }
}
```

The subscription's filter policy scope must be configured appropriately. Message-attribute filtering and message-body filtering are different modes.

### 7.3 Why use filtering?

Without filtering, every subscriber may receive every event and must inspect it itself.

With filtering:

```text
                 SNS Topic
                    |
          +---------+---------+
          |                   |
          v                   v
     Billing Filter      Analytics Filter
     ORDER_PAID          All order events
          |                   |
          v                   v
     Billing Queue       Analytics Queue
```

Filtering reduces unnecessary deliveries and simplifies subscribers. It does not replace authorization or business validation inside the consumer.

## 8. Delivery Retries and Dead-Letter Queues

SNS delivery behavior depends on the endpoint protocol.

For supported managed endpoints, SNS retries delivery according to its delivery policy. Retry behavior for HTTP/S endpoints differs from delivery to AWS-managed endpoints such as SQS and Lambda.

### SNS delivery DLQ

A subscription can be configured with a dead-letter queue for messages that SNS cannot deliver successfully after its retry policy is exhausted, where supported.

```text
              SNS Topic
                  |
                  v
             Subscription
                  |
          +-------+-------+
          |               |
          v               v
      Delivery          Delivery
      succeeds          fails after retries
          |               |
          v               v
      Endpoint         Subscription DLQ
```

### Do not confuse two DLQs

| DLQ type | What it captures |
|---|---|
| SNS subscription DLQ | Messages SNS could not deliver to the subscribed endpoint |
| SQS consumer DLQ | Messages delivered to an SQS queue but repeatedly failed during consumer processing |

In an SNS-to-SQS design, you may need both:

```text
SNS Topic
   |
   v
SQS Main Queue
   |
   v
Application Consumer
   |
   +----> SQS Consumer DLQ

SNS delivery failure
   |
   +----> SNS Subscription DLQ (when configured and supported)
```

These DLQs protect different stages of the message flow.

### Operational practices

- Monitor each DLQ separately.
- Inspect failures and identify the failing stage.
- Fix the underlying problem before replaying messages.
- Use idempotency when replaying.
- Set retention and access controls deliberately.

## 9. AWS CLI: Create and Use SNS Topics

Examples use Region `ap-southeast-1`. Capture topic ARNs and subscription ARNs from command output.

### 9.1 Check identity

```bash
aws sts get-caller-identity
aws configure get region
```

### 9.2 Create a Standard topic

```bash
aws sns create-topic \
  --name OrderEvents \
  --region ap-southeast-1
```

Save the returned ARN:

```bash
TOPIC_ARN="PASTE_TOPIC_ARN_FROM_CREATE_TOPIC_OUTPUT"
```

### 9.3 List topics

```bash
aws sns list-topics \
  --region ap-southeast-1
```

### 9.4 Subscribe an email address

```bash
aws sns subscribe \
  --topic-arn "$TOPIC_ARN" \
  --protocol email \
  --notification-endpoint "your-test-email@example.com" \
  --region ap-southeast-1
```

The recipient must confirm the subscription using the confirmation email before notifications are delivered.

Use an address you control for a lab. Do not invent or use another person's address without permission.

### 9.5 Publish a message

```bash
aws sns publish \
  --topic-arn "$TOPIC_ARN" \
  --subject "Order created" \
  --message '{
    "eventId": "evt-10001",
    "eventType": "ORDER_CREATED",
    "orderId": "O501"
  }' \
  --region ap-southeast-1
```

### 9.6 Subscribe an SQS queue

First create an SQS queue and retrieve its ARN:

```bash
aws sqs create-queue \
  --queue-name BillingQueue \
  --region ap-southeast-1
```

```bash
aws sqs get-queue-attributes \
  --queue-url "$BILLING_QUEUE_URL" \
  --attribute-names QueueArn \
  --region ap-southeast-1
```

Save the returned ARN:

```bash
QUEUE_ARN="PASTE_QUEUE_ARN_FROM_OUTPUT"
```

Subscribe the queue:

```bash
aws sns subscribe \
  --topic-arn "$TOPIC_ARN" \
  --protocol sqs \
  --notification-endpoint "$QUEUE_ARN" \
  --region ap-southeast-1
```

### 9.7 Allow SNS to send to the SQS queue

The SQS queue needs a resource policy that allows the intended SNS topic to call `sqs:SendMessage`.

Example policy file `sqs-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOnlyThisSnsTopic",
      "Effect": "Allow",
      "Principal": {
        "Service": "sns.amazonaws.com"
      },
      "Action": "sqs:SendMessage",
      "Resource": "PASTE_QUEUE_ARN",
      "Condition": {
        "ArnEquals": {
          "aws:SourceArn": "PASTE_TOPIC_ARN"
        }
      }
    }
  ]
}
```

Apply the policy:

```bash
aws sqs set-queue-attributes \
  --queue-url "$BILLING_QUEUE_URL" \
  --attributes file://sqs-policy.json \
  --region ap-southeast-1
```

The policy restricts the SNS send permission to the specified topic. Use the actual queue ARN and topic ARN from your account.

### 9.8 List subscriptions

```bash
aws sns list-subscriptions-by-topic \
  --topic-arn "$TOPIC_ARN" \
  --region ap-southeast-1
```

### 9.9 Add a filter policy

Save this as `filter-policy.json`:

```json
{
  "eventType": ["ORDER_PAID"]
}
```

Find the subscription ARN from the list output, then apply the filter:

```bash
aws sns set-subscription-attributes \
  --subscription-arn "$SUBSCRIPTION_ARN" \
  --attribute-name FilterPolicy \
  --attribute-value file://filter-policy.json \
  --region ap-southeast-1
```

For body-based filtering, set the filter policy scope to `MessageBody` using the subscription attribute documented for the current SNS API.

### 9.10 Create a FIFO topic

FIFO topic names must end in `.fifo`.

```bash
aws sns create-topic \
  --name OrderEvents.fifo \
  --attributes '{
    "FifoTopic": "true",
    "ContentBasedDeduplication": "true"
  }' \
  --region ap-southeast-1
```

Publish to a FIFO topic with a message group ID:

```bash
aws sns publish \
  --topic-arn "$FIFO_TOPIC_ARN" \
  --message '{"orderId":"O501","status":"CREATED"}' \
  --message-group-id "ORDER#O501" \
  --region ap-southeast-1
```

If content-based deduplication is disabled, provide a message deduplication ID as required.

### 9.11 Delete a topic after the lab

```bash
aws sns delete-topic \
  --topic-arn "$TOPIC_ARN" \
  --region ap-southeast-1
```

Deleting a topic removes its subscriptions. Confirm that the topic is not shared or used by another application before deleting it.

## 10. Spring Boot Integration with AWS SDK for Java 2.x

This section demonstrates publishing an event to SNS from a Spring Boot application.

### 10.1 Maven dependencies

Use the AWS SDK for Java 2.x BOM and set `${aws.sdk.version}` to an approved current version.

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>software.amazon.awssdk</groupId>
            <artifactId>bom</artifactId>
            <version>${aws.sdk.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>sns</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
</dependencies>
```

### 10.2 Configuration

```yaml
app:
  aws:
    region: ap-southeast-1
  sns:
    order-topic-arn: ${ORDER_TOPIC_ARN}
```

```java
@Configuration
public class SnsConfiguration {

    @Bean
    SnsClient snsClient(
            @Value("${app.aws.region}") String region) {

        return SnsClient.builder()
                .region(Region.of(region))
                .credentialsProvider(
                    DefaultCredentialsProvider.create()
                )
                .build();
    }
}
```

Use IAM roles when the application runs on AWS. Avoid storing long-lived access keys in application configuration.

### 10.3 Event DTO

```java
public record OrderEvent(
        String eventId,
        String eventType,
        String orderId,
        String customerId,
        String status
) {}
```

### 10.4 SNS producer service

```java
@Service
public class OrderEventPublisher {

    private final SnsClient snsClient;
    private final ObjectMapper objectMapper;
    private final String topicArn;

    public OrderEventPublisher(
            SnsClient snsClient,
            ObjectMapper objectMapper,
            @Value("${app.sns.order-topic-arn}") String topicArn) {
        this.snsClient = snsClient;
        this.objectMapper = objectMapper;
        this.topicArn = topicArn;
    }

    public String publish(OrderEvent event) {
        try {
            String body = objectMapper.writeValueAsString(event);

            PublishResponse response = snsClient.publish(
                PublishRequest.builder()
                    .topicArn(topicArn)
                    .message(body)
                    .messageAttributes(Map.of(
                        "eventType",
                        MessageAttributeValue.builder()
                            .dataType("String")
                            .stringValue(event.eventType())
                            .build()
                    ))
                    .build()
            );

            return response.messageId();

        } catch (JsonProcessingException e) {
            throw new IllegalArgumentException(
                "Could not serialize order event", e
            );
        }
    }
}
```

The message attribute `eventType` can be used by subscriptions with an attribute-based filter policy.

### 10.5 Controller

```java
@RestController
@RequestMapping("/api/orders")
public class OrderEventController {

    private final OrderEventPublisher publisher;

    public OrderEventController(OrderEventPublisher publisher) {
        this.publisher = publisher;
    }

    @PostMapping("/{orderId}/publish-event")
    public ResponseEntity<Map<String, String>> publish(
            @PathVariable String orderId) {

        OrderEvent event = new OrderEvent(
            UUID.randomUUID().toString(),
            "ORDER_CREATED",
            orderId,
            "C1001",
            "CREATED"
        );

        String messageId = publisher.publish(event);

        return ResponseEntity.accepted().body(
            Map.of("messageId", messageId)
        );
    }
}
```

A successful publish response means SNS accepted the publish request. It does not prove that every subscriber has completed its business processing.

### 10.6 Suggested project structure

```text
src/main/java/com/example/orders/
|
+-- config/
|   +-- SnsConfiguration.java
|
+-- controller/
|   +-- OrderEventController.java
|
+-- dto/
|   +-- OrderEvent.java
|
+-- messaging/
    +-- OrderEventPublisher.java
```

## 11. SNS and SQS Together: Complete Event Architecture

A practical order event flow:

```text
                         Client
                           |
                           v
                    Spring Boot API
                           |
                           v
                    Save Order State
                           |
                           v
                      SNS Topic
                      OrderEvents
                    /      |       \
                   v       v        v
             Billing SQS  Shipping  Analytics
                 Queue     SQS       SQS
                   |       Queue      Queue
                   v         |         |
              Billing      Shipping  Analytics
              Worker       Worker    Worker
                   |         |         |
                   v         v         v
               Billing    Fulfillment Metrics

Each SQS queue can have its own consumer DLQ.
SNS subscriptions can have delivery DLQs where supported.
```

### Design responsibilities

| Component | Responsibility |
|---|---|
| Spring Boot API | Validate request and publish domain event |
| SNS topic | Fan out event to subscribers |
| Billing SQS | Buffer billing work |
| Shipping SQS | Buffer fulfillment work |
| Analytics SQS | Buffer analytics work |
| Consumers | Process each subscriber's business task |
| DLQs | Isolate messages that cannot be delivered or processed |
| CloudWatch | Monitor delivery and queue health |

### Important reliability consideration

If the API saves an order in a database and then publishes to SNS, the database save can succeed while the publish fails. For critical events, use a transactional outbox or another durable event-publication design. Make subscribers idempotent.

## 12. Security Best Practices

1. Use IAM roles for applications running on AWS.
2. Grant publishers only `sns:Publish` on the required topic.
3. Grant subscription-management permissions only to deployment or administrative roles.
4. Use topic policies to control cross-account publishing and subscription access.
5. Use encryption at rest when required by your security policy.
6. Use TLS for network communication.
7. Avoid placing secrets and unnecessary personal information in messages.
8. Restrict access to SQS queues and DLQs subscribed to SNS.
9. Validate SNS signatures for HTTP/S notification endpoints using the supported verification process.
10. Monitor changes to topic policies and subscriptions.

Example IAM policy for an application that only publishes to one topic:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "sns:Publish"
      ],
      "Resource": "arn:aws:sns:ap-southeast-1:123456789012:OrderEvents"
    }
  ]
}
```

Replace the example account ID and topic ARN. Do not grant broad `sns:*` permissions to a normal application role.

## 13. Monitoring and Operations

Useful SNS CloudWatch metrics include:

| Metric | Meaning |
|---|---|
| `NumberOfMessagesPublished` | Number of messages published |
| `NumberOfNotificationsDelivered` | Notifications successfully delivered |
| `NumberOfNotificationsFailed` | Notifications that failed delivery |
| `NumberOfNotificationsFilteredOut` | Notifications excluded by filter policies |
| `NumberOfNotificationsRedrivenToDlq` | Notifications moved to a subscription DLQ |
| `NumberOfNotificationsFailedToRedriveToDlq` | Failed attempts to move notifications to a DLQ |

Metric availability depends on endpoint type and configuration.

### Monitoring workflow

1. Check whether publishers are successfully publishing.
2. Compare published and delivered message counts.
3. Review failed notification metrics.
4. Check subscription confirmation and endpoint health.
5. Inspect filter policies if messages are not reaching a subscriber.
6. Check the SNS subscription DLQ.
7. For SNS-to-SQS, inspect each queue's visible-message count and oldest-message age.
8. Inspect consumer DLQs separately.

A message filtered out by a subscription policy is not the same as a delivery failure.

## 15. Troubleshooting

| Symptom or error | Possible cause | What to check |
|---|---|---|
| `AuthorizationError` | IAM role or topic policy denies publish | `sns:Publish`, topic ARN, policy conditions |
| SQS subscription receives nothing | Queue policy does not allow SNS | `sqs:SendMessage`, exact `aws:SourceArn` |
| Email subscription receives no messages | Subscription not confirmed | Confirmation email and subscription status |
| HTTP/S endpoint receives no notifications | Endpoint unavailable or subscription unconfirmed | Endpoint health, TLS, confirmation |
| Subscriber receives fewer messages than published | Filter policy excludes messages | Attribute names, data types, filter scope |
| FIFO publish fails | Missing group ID or deduplication ID | FIFO topic configuration and publish parameters |
| Duplicate notification is processed | Retry or duplicate delivery | Consumer idempotency |
| SNS delivery DLQ grows | Endpoint delivery failures | Endpoint health, permissions, retry policy |
| SQS consumer DLQ grows | Consumer processing failures | Application logs, visibility timeout, downstream dependencies |
| SNS message appears wrapped in JSON | Normal SNS-to-SQS notification envelope | Parse the `Message` field or configure raw delivery |

## 16. Practical Exercises with Answers

### Exercise 1 — What problem does SNS solve?

**Answer:** SNS provides pub/sub messaging so one publisher can distribute an event to multiple subscribers without tightly coupling the publisher to each consumer.

### Exercise 2 — What is fanout?

**Answer:** Fanout means distributing one published message to multiple subscribed endpoints, such as several SQS queues.

### Exercise 3 — Why combine SNS and SQS?

**Answer:** SNS distributes events, while each SQS queue buffers work for an independent consumer. This lets each service process and retry its own workload separately.

### Exercise 4 — What is a subscription filter policy?

**Answer:** It is a set of rules that determines which messages a particular subscription receives. It can filter by message attributes or, when configured, message body fields.

### Exercise 5 — What is the difference between an SNS subscription DLQ and an SQS consumer DLQ?

**Answer:** An SNS subscription DLQ stores notifications SNS could not deliver to the endpoint. An SQS consumer DLQ stores messages that reached the queue but repeatedly failed during consumer processing.

### Exercise 6 — Does publishing successfully mean all subscribers finished processing?

**Answer:** No. It means SNS accepted the publish request. Each subscriber processes the notification independently.

### Exercise 7 — Why validate an HTTP/S SNS notification?

**Answer:** Validation helps ensure that the request genuinely originated from SNS rather than an attacker sending a forged notification.

### Exercise 8 — What is the purpose of `MessageGroupId` on a FIFO topic?

**Answer:** It identifies the group whose messages must preserve order. Different groups can be processed independently.

### Exercise 9 — Why can a subscription filter reduce unnecessary work?

**Answer:** SNS can exclude messages that do not match the subscriber's interests before delivering them, so the consumer does not need to inspect every event.

### Exercise 10 — What reliability pattern helps avoid saving an order but losing its event?

**Answer:** The transactional outbox pattern stores the order and its event record in the same database transaction. A separate publisher sends the event to SNS.

## 18. English Speaking Practice

Read each question aloud and practice the model answer. Then try to explain the idea without reading.

### Question 1: What is Amazon SNS?

**Model answer:**

Amazon SNS is a managed publish/subscribe messaging service. A publisher sends a message to a topic, and SNS delivers it to subscribed endpoints. It is useful when one event needs to reach multiple services.

### Question 2: What is fanout?

**Model answer:**

Fanout means sending one message to multiple subscribers. For example, when an order is created, SNS can send the event to billing, shipping, and analytics queues.

### Question 3: Why do we combine SNS and SQS?

**Model answer:**

SNS distributes events to multiple subscribers. SQS gives each subscriber its own queue, so each service can process messages independently and handle temporary failures.

### Question 4: What is a filter policy?

**Model answer:**

A filter policy controls which messages a subscription receives. For example, the billing service can receive only order-paid events, while analytics can receive every order event.

### Question 5: What is the difference between two types of dead-letter queues?

**Model answer:**

An SNS subscription dead-letter queue stores notifications that SNS could not deliver. An SQS consumer dead-letter queue stores messages that a consumer repeatedly failed to process.

### Question 6: Does a successful SNS publish mean the business process is complete?

**Model answer:**

No. A successful publish means SNS accepted the message. Subscribers still need to receive and process it. I monitor each subscriber separately.

## 19. AWS Interview Questions and Answers

**Q1. What is Amazon SNS?**

Amazon SNS is a fully managed pub/sub messaging service that distributes messages from publishers to subscribers.

**Q2. What is an SNS topic?**

A topic is a logical channel to which publishers send messages and subscribers register to receive them.

**Q3. What is fanout architecture?**

It is an architecture in which one message is distributed to multiple subscribers, often using SNS with several SQS queues.

**Q4. What is the difference between SNS and SQS?**

SNS is primarily a pub/sub message distribution service. SQS is a message queue that stores messages until consumers retrieve and delete them. They are often used together.

**Q5. What is the difference between Standard and FIFO topics?**

Standard topics support high-throughput distribution with best-effort ordering. FIFO topics support ordered processing within message groups and deduplication features, subject to supported integrations and quotas.

**Q6. What is a subscription filter policy?**

It is a policy that filters messages for a subscription based on message attributes or configured message-body fields.

**Q7. Why does an email subscription need confirmation?**

The endpoint owner must confirm the subscription to prove control of the destination and authorize delivery.

**Q8. What is an SNS subscription DLQ?**

It is a queue that can capture notifications SNS could not deliver to a subscribed endpoint after delivery retries are exhausted, where supported.

**Q9. What is raw message delivery for an SNS-to-SQS subscription?**

It delivers the published message body directly to SQS instead of wrapping it in the standard SNS notification envelope.

**Q10. Does SNS guarantee that every subscriber completes processing before publish returns?**

No. Publish acceptance and subscriber business processing are separate stages.

**Q11. How do you secure SNS-to-SQS fanout?**

Use an SQS resource policy that permits `sns.amazonaws.com` to send messages only when the source ARN matches the intended SNS topic. Apply least-privilege IAM permissions.

**Q12. How do you avoid losing an event after a database write?**

Use a transactional outbox or another durable event-publication design, and make subscribers idempotent.
