## 2. What Is an IAM Policy?

An IAM policy is a JSON document that defines permissions. It describes what actions are allowed or denied, and under what conditions.

For example, a policy can allow an application to read objects from one specific S3 bucket without allowing it to delete objects or access other buckets.

A policy answers questions such as:

- Who or what is making the request?
- Which AWS action is requested?
- Which resource is being accessed?
- Does the request satisfy any required conditions?
- Is there an applicable explicit Deny?

A policy is not a password and does not authenticate a user. Authentication establishes an identity; authorization determines what that identity can do.

### Example: Allow reading objects from one bucket

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadObjectsFromReportsBucket",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::company-reports/*"
    }
  ]
}
```

This policy allows the principal to call `s3:GetObject` for objects inside `company-reports`. It does not automatically grant permission to list the bucket, upload objects, or delete objects.

## 3. Anatomy of a Policy

A policy commonly contains a top-level `Version` and one or more entries in `Statement`.

| Element | Purpose |
|---|---|
| `Version` | Identifies the policy language version |
| `Statement` | Contains one or more permission statements |
| `Sid` | Optional statement identifier |
| `Effect` | `Allow` or `Deny` |
| `Action` | AWS API actions covered by the statement |
| `NotAction` | Advanced alternative that matches actions other than those listed |
| `Resource` | Resources covered by the statement |
| `NotResource` | Advanced alternative that matches resources other than those listed |
| `Condition` | Optional conditions that must be satisfied |
| `Principal` | Identifies a principal in policies that support it, such as resource-based policies and role trust policies |

### 3.1 Version

```json
"Version": "2012-10-17"
```

This is the IAM policy language version. It is not the date the policy was created. Use `2012-10-17` for normal IAM policies.

### 3.2 Statement

A policy can contain multiple statements. Each statement is evaluated as part of the overall authorization decision.

```json
"Statement": [
  {
    "Sid": "AllowRead",
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::company-reports/*"
  },
  {
    "Sid": "DenyDelete",
    "Effect": "Deny",
    "Action": "s3:DeleteObject",
    "Resource": "arn:aws:s3:::company-reports/*"
  }
]
```

### 3.3 Effect

- `Allow`: grants the stated permission, subject to other applicable policy controls.
- `Deny`: explicitly denies the stated permission.

An explicit Deny takes precedence over an Allow in IAM policy evaluation.

### 3.4 Action

`Action` identifies the AWS API operations.

Examples:

- `s3:GetObject`
- `s3:PutObject`
- `s3:ListBucket`
- `ec2:DescribeInstances`
- `logs:CreateLogStream`

You can use wildcards, such as `s3:Get*`, but broad wildcards can grant more access than intended. Prefer listing the exact actions required.

### 3.5 Resource

`Resource` identifies the AWS resources to which the statement applies. Some actions support resource-level permissions; others require `"Resource": "*"`.

Always check the service authorization documentation for the action's supported resource types and condition keys.

## 4. Understanding Amazon Resource Names (ARNs)

An ARN uniquely identifies many AWS resources.

A common ARN pattern is:

```text
arn:partition:service:region:account-id:resource
```

The exact ARN format varies by service. Some fields can be empty.

| Part | Example | Meaning |
|---|---|---|
| `arn` | `arn` | Identifies the string as an ARN |
| Partition | `aws` | AWS partition |
| Service | `s3` | AWS service |
| Region | Empty for standard S3 bucket ARNs | Region field |
| Account ID | Empty for standard S3 bucket ARNs | Owning account |
| Resource | `company-reports/object.csv` | Resource identifier |

### 4.1 S3 bucket ARN vs object ARN

Bucket ARN:

```text
arn:aws:s3:::company-reports
```

All objects in the bucket:

```text
arn:aws:s3:::company-reports/*
```

Objects under a particular prefix:

```text
arn:aws:s3:::company-reports/finance/*
```

These are different resource types for authorization.

### 4.2 Important S3 permission distinction

| Action | Typical resource | What it allows |
|---|---|---|
| `s3:ListBucket` | Bucket ARN | List keys in a bucket |
| `s3:GetObject` | Object ARN | Read an object |
| `s3:PutObject` | Object ARN | Upload or replace an object |
| `s3:DeleteObject` | Object ARN | Delete an object |

A common mistake is to put the object ARN in a `s3:ListBucket` statement. `s3:ListBucket` is a bucket-level action and normally needs the bucket ARN.

### 4.3 Example: list one bucket and read its objects

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListReportsBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-reports"
    },
    {
      "Sid": "ReadReportsObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-reports/*"
    }
  ]
}
```

## 5. Wildcards: `*` and `?`

IAM policy elements such as `Action` and `Resource` support wildcard matching in applicable contexts.

- `*` matches zero or more characters.
- `?` matches a single character.

Examples:

```json
"Action": "s3:Get*"
```

This can match multiple S3 actions beginning with `Get`, not just `s3:GetObject`.

```json
"Resource": "arn:aws:s3:::company-reports/2026/*"
```

This covers objects under the `2026/` prefix.

### Security warning

Avoid using broad permissions such as:

```json
{
  "Effect": "Allow",
  "Action": "*",
  "Resource": "*"
}
```

This is effectively administrator-level access for many purposes. It is usually inappropriate for an application role.

Use exact actions and narrowly scoped resources whenever possible.

## 6. Identity-Based and Resource-Based Policies

### 6.1 Identity-based policy

An identity-based policy is attached to an IAM user, group, or role. It describes what that identity is allowed or denied to do.

Example: attach a policy to an EC2 application role so the application can read a specific S3 bucket.

### 6.2 Resource-based policy

A resource-based policy is attached to a resource that supports it, such as an S3 bucket policy. It identifies which principals can access that resource and what they can do.

Simplified S3 bucket policy example:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowApplicationRoleRead",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/ReportsApplicationRole"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-reports/*"
    }
  ]
}
```

Replace the example account ID and role name with real values in your environment.

### 6.3 Comparison

| Topic | Identity-based policy | Resource-based policy |
|---|---|---|
| Attached to | IAM user, group, or role | A supported AWS resource |
| Main question | What can this identity do? | Who can access this resource? |
| Principal field | Usually not included | Commonly included |
| Example | Role policy allowing S3 read | S3 bucket policy allowing a role |
| Common use | Give an application role permissions | Share access to a bucket or queue |

Both policy types may be relevant to one request. The final result depends on all applicable policy controls and the service's authorization rules.

## 7. Managed Policies and Inline Policies

### 7.1 AWS managed policies

Created and maintained by AWS. They are convenient, but you should still inspect their permissions before attaching them.

Example: `ReadOnlyAccess` is broad read-only access across many AWS services; it is not necessarily appropriate for every application.

### 7.2 Customer managed policies

Created and maintained in your AWS account. They can be reused across multiple IAM identities and centrally updated.

Use customer managed policies when you want reusable, controlled permission sets.

### 7.3 Inline policies

Embedded directly into one IAM user, group, or role. They have a one-to-one relationship with that identity.

Inline policies can be useful for a tightly coupled permission, but customer managed policies are often easier to reuse and audit.

| Type | Managed by | Reusable across identities? | Typical use |
|---|---|---:|---|
| AWS managed | AWS | Yes | Common predefined permissions |
| Customer managed | Your organization | Yes | Custom reusable permissions |
| Inline | Attached identity | No, not as a shared policy | Identity-specific permissions |

## 8. Conditions

A `Condition` adds requirements that must be met for a statement to match.

Condition support depends on the AWS service, action, and request context. Always verify the supported condition keys for the action you are controlling.

### 8.1 Restrict requests by AWS Region

Example pattern:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideApprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "route53:*",
        "cloudfront:*",
        "support:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": [
            "ap-southeast-1"
          ]
        }
      }
    }
  ]
}
```

This is an illustrative guardrail pattern, not a universal drop-in policy. Global services, service-linked operations, and services with special regional behavior may need carefully designed exceptions. Test it before applying it broadly.

### 8.2 Restrict S3 listing to a prefix

A bucket-level list permission can use the `s3:prefix` condition key:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOnlyFinancePrefix",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-reports",
      "Condition": {
        "StringLike": {
          "s3:prefix": [
            "finance",
            "finance/*"
          ]
        }
      }
    }
  ]
}
```

The application may also need a separate `s3:GetObject` permission on the corresponding object ARN prefix.

### 8.3 Restrict access by source IP

An illustrative condition:

```json
"Condition": {
  "IpAddress": {
    "aws:SourceIp": [
      "203.0.113.0/24"
    ]
  }
}
```

`203.0.113.0/24` is a documentation example range, not a real corporate network. The source IP seen by AWS can differ when requests pass through proxies, NAT gateways, or service-to-service paths.

### 8.4 MFA-related conditions

`aws:MultiFactorAuthPresent` can be useful in supported IAM request contexts, particularly for certain temporary credentials. It is not a universal MFA enforcement switch for every AWS service or authentication flow. Design MFA controls using current AWS guidance and test the actual sign-in and API paths.

### 8.5 Principal tags

Conditions can compare request context with principal tags, for example:

```json
"Condition": {
  "StringEquals": {
    "aws:PrincipalTag/Department": "Finance"
  }
}
```

This is useful for attribute-based access control (ABAC). The relevant tag must be present and supported in the request context.

## 9. Least Privilege

The principle of least privilege means granting only the permissions required to perform a specific task.

Imagine a Spring Boot application that uploads invoice PDFs to one S3 bucket.

It may need:

- `s3:PutObject` for the invoice object prefix.
- `s3:GetObject` only if the application later downloads invoices.
- `s3:ListBucket` only if the application actually lists objects.

It probably does not need:

- `s3:DeleteBucket`
- `s3:PutBucketPolicy`
- `iam:*`
- `ec2:*`
- `s3:*` on every bucket

### Practical process

1. Identify the application feature.
2. Identify the AWS API calls used by that feature.
3. Map each API call to the required IAM action.
4. Identify the narrowest supported resource ARN.
5. Add conditions only when they are understood and supported.
6. Test the policy in a controlled environment.
7. Review CloudTrail activity and application errors.
8. Remove permissions that are not needed.

Do not solve every `AccessDenied` error by attaching `AdministratorAccess`. Find the missing action and resource, then grant only what is necessary.

## 10. How AWS Evaluates Permissions

A simplified mental model:

1. Requests are made using an authenticated principal.
2. AWS gathers the policies and controls applicable to the request.
3. An applicable explicit Deny results in denial.
4. An Allow must exist where required.
5. Other policy controls may limit the effective permissions.

Important controls can include:

- Identity-based policies.
- Resource-based policies.
- Permissions boundaries.
- AWS Organizations service control policies (SCPs).
- STS session policies.
- VPC endpoint policies.
- Service-specific authorization rules.

The exact evaluation logic differs by policy type, principal, resource, and service. Do not assume that one Allow statement guarantees access.

### Key rules to remember

- By default, access is implicitly denied.
- An applicable explicit Deny overrides an Allow.
- A permissions boundary sets the maximum permissions an identity-based policy can grant.
- An SCP sets the maximum permissions available to principals in an affected organization account; it does not grant permissions by itself.
- A session policy can further restrict a role session.
- A VPC endpoint policy can restrict requests that pass through that endpoint.

## 11. Practical Policy Examples

### 11.1 Read-only access to one S3 bucket

This policy allows listing the bucket and reading its objects:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-reports"
    },
    {
      "Sid": "ReadObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-reports/*"
    }
  ]
}
```

### 11.2 Upload objects to one prefix

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadInvoices",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::company-reports/invoices/*"
    }
  ]
}
```

This does not grant bucket listing or object reading. Depending on the upload method and features used, additional permissions may be required—for example, multipart upload operations, encryption key permissions, or tagging permissions.

### 11.3 Describe EC2 instances

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DescribeInstances",
      "Effect": "Allow",
      "Action": [
        "ec2:DescribeInstances",
        "ec2:DescribeTags"
      ],
      "Resource": "*"
    }
  ]
}
```

Many EC2 `Describe` actions do not support resource-level permissions and therefore require `"Resource": "*"`. Check the service authorization reference for each action.

## 12. Inspect and Manage Policies with AWS CLI

The examples below assume that the AWS CLI is installed and configured with credentials that are allowed to inspect IAM.

### 12.1 Check the current identity

```bash
aws sts get-caller-identity
```

### 12.2 List customer managed policies in the account

```bash
aws iam list-policies --scope Local
```

### 12.3 List policies attached to a role

```bash
aws iam list-attached-role-policies \
  --role-name ReportsApplicationRole
```

### 12.4 List inline policies on a role

```bash
aws iam list-role-policies \
  --role-name ReportsApplicationRole
```

### 12.5 Get a managed policy

```bash
aws iam get-policy \
  --policy-arn arn:aws:iam::111122223333:policy/ReportsReadPolicy
```

### 12.6 Get the default policy version

First inspect the policy and note its `DefaultVersionId`, then retrieve that version:

```bash
aws iam get-policy-version \
  --policy-arn arn:aws:iam::111122223333:policy/ReportsReadPolicy \
  --version-id v1
```

Replace the sample ARN and version with the values from your account.

### 12.7 Read an inline role policy

```bash
aws iam get-role-policy \
  --role-name ReportsApplicationRole \
  --policy-name ReportsInlinePolicy
```

### 12.8 Validate and test

Useful tools include:

- IAM Policy Simulator: helps test how policies evaluate for selected actions and resources.
- IAM Access Analyzer policy validation: identifies policy grammar and security findings.
- CloudTrail: helps investigate recorded API activity and access-denied events.

These tools help with review, but they do not replace testing the application in a controlled environment.

## 13. Spring Boot Integration: Least-Privilege S3 Access

### Scenario

A Spring Boot application runs on an EC2 instance and stores invoice files in:

```text
s3://company-reports/invoices/
```

The application should upload files but should not delete them or administer the bucket.

### Architecture

```text
Customer
   |
   v
Spring Boot REST API
   |
   v
EC2 Instance
   |
   | Uses temporary credentials from an instance role
   v
IAM Role: ReportsApplicationRole
   |
   | Allows s3:PutObject on invoices/*
   v
Amazon S3: company-reports
```

### Step 1: Create a least-privilege policy

Save this as `reports-upload-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadInvoiceObjects",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::company-reports/invoices/*"
    }
  ]
}
```

Create a customer managed policy:

```bash
aws iam create-policy \
  --policy-name ReportsUploadPolicy \
  --policy-document file://reports-upload-policy.json
```

### Step 2: Attach the policy to the application role

After creating the role and its EC2 trust relationship, attach the policy:

```bash
aws iam attach-role-policy \
  --role-name ReportsApplicationRole \
  --policy-arn arn:aws:iam::111122223333:policy/ReportsUploadPolicy
```

Replace the example account ID with your AWS account ID.

### Step 3: Associate the role with EC2

Associate the role through an EC2 instance profile. The EC2 instance receives temporary credentials through the instance metadata service. Do not store long-lived access keys in application source code or configuration files.

### Step 4: Add AWS SDK for Java 2.x dependency

Maven example:

```xml
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>s3</artifactId>
</dependency>
```

Use the AWS SDK BOM in your project to manage compatible SDK module versions.

### Step 5: Configure an S3 client

```java
@Configuration
public class AwsS3Config {

    @Bean
    public S3Client s3Client() {
        return S3Client.builder()
                .region(Region.AP_SOUTHEAST_1)
                .build();
    }
}
```

The SDK's default credentials provider chain can obtain temporary credentials from the EC2 instance role when the application runs on EC2. The application should not hardcode access keys.

### Step 6: Upload an object

```java
@Service
public class InvoiceStorageService {

    private final S3Client s3Client;

    @Value("${app.aws.s3.bucket}")
    private String bucketName;

    public InvoiceStorageService(S3Client s3Client) {
        this.s3Client = s3Client;
    }

    public void uploadInvoice(String key, Path file) {
        PutObjectRequest request = PutObjectRequest.builder()
                .bucket(bucketName)
                .key("invoices/" + key)
                .contentType("application/pdf")
                .build();

        s3Client.putObject(request, RequestBody.fromFile(file));
    }
}
```

Configuration:

```yaml
app:
  aws:
    s3:
      bucket: company-reports
```

### Step 7: Verify the permission boundary of the design

The application role can upload objects to `invoices/*`, but it should not be able to:

- Delete invoice objects.
- Change the bucket policy.
- Create or delete buckets.
- Attach IAM policies.
- Access unrelated buckets.

Remember that bucket policies, encryption settings, organization controls, and other policies can also affect the final result.

## 14. Common Mistakes

| Mistake | Why it is a problem | Better approach |
|---|---|---|
| Using `Action: "*"` | Grants far more than most applications need | List exact actions |
| Using `Resource: "*"` everywhere | May expose unrelated resources | Scope resources where supported |
| Using object ARN for `s3:ListBucket` | Wrong resource type for that action | Use the bucket ARN |
| Assuming Allow always means access | Other policy controls can restrict access | Inspect all applicable policies |
| Adding a broad Deny without testing | Can block unrelated workloads | Test and scope Deny statements |
| Putting access keys in source code | Long-lived credentials can leak | Use IAM roles and temporary credentials |
| Treating `Version` as creation date | Misunderstands policy language version | Use `2012-10-17` |
| Assuming every condition key works everywhere | Support varies by service and action | Verify the authorization reference |

## 15. Practical Exercises with Answers

### Exercise 1 — Identify the policy elements

Given:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowRead",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::documents/*"
    }
  ]
}
```

Questions:

1. What is the policy language version?
2. What does `Effect` mean?
3. Which action is allowed?
4. Which resources are covered?

**Answers**

| Question | Answer |
|---|---|
| 1 | `2012-10-17` |
| 2 | The statement grants the specified permission |
| 3 | `s3:GetObject` |
| 4 | Objects inside the `documents` bucket |

### Exercise 2 — Choose the correct ARN

Which ARN should be used for `s3:ListBucket`?

A. `arn:aws:s3:::documents/*`

B. `arn:aws:s3:::documents`

**Answer:** B. `s3:ListBucket` is a bucket-level action.

### Exercise 3 — Write an upload policy

Requirement: allow uploading objects only to `company-data/uploads/`.

**Answer**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadOnlyToUploadsPrefix",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::company-data/uploads/*"
    }
  ]
}
```

### Exercise 4 — Understand explicit Deny

Policy A allows `s3:GetObject` on a bucket. Policy B explicitly denies `s3:GetObject` on one object.

Can the principal read that object?

**Answer:** No. An applicable explicit Deny takes precedence over an Allow.

### Exercise 5 — Choose the right policy type

A team wants to let a specific IAM role read objects from an S3 bucket. Which policy types might be involved?

**Answer:** An identity-based policy attached to the role can grant the read permission. An S3 bucket policy can also grant access to the role. The final result depends on all applicable policy controls.

### Exercise 6 — Diagnose an access error

An application can upload an object but cannot list the bucket. What might be missing?

**Answer:** It may need `s3:ListBucket` on the bucket ARN. Do not add it automatically; first confirm that listing is a required application feature.

## 17. English Speaking Practice

### Topic: Explaining IAM Policies

**Question 1: What is an IAM policy?**

Model answer:

An IAM policy is a JSON document that defines permissions in AWS. It specifies which actions are allowed or denied on which resources. We use IAM policies to control access to AWS services.

**Question 2: What is the difference between Allow and Deny?**

Model answer:

Allow grants a permission when the other authorization requirements are satisfied. Deny blocks a permission. An applicable explicit Deny takes precedence over an Allow.

**Question 3: What is the principle of least privilege?**

Model answer:

The principle of least privilege means giving a user or application only the permissions it needs. For example, an application that uploads files to S3 should not receive permission to delete every object in the account.

**Question 4: What is an ARN?**

Model answer:

An ARN is an Amazon Resource Name. It identifies an AWS resource. We use ARNs in IAM policies to specify which resources a permission applies to.

**Question 5: Why should we avoid wildcard permissions?**

Model answer:

Wildcard permissions can grant more access than an application needs. This increases security risk. We should use specific actions and resources whenever possible.

### Five-minute speaking script

Today, I learned about AWS IAM policies.

An IAM policy is a JSON document that defines permissions. It contains elements such as Effect, Action, Resource, and Condition.

The Effect can be Allow or Deny. An explicit Deny takes precedence over an Allow.

An ARN identifies an AWS resource. For example, an S3 bucket has a bucket ARN, while each object is covered by an object ARN.

There are identity-based policies and resource-based policies. We can also use managed policies and inline policies.

One important security principle is least privilege. We should give an application only the permissions it needs.

For example, a Spring Boot application may need permission to upload invoice files to one S3 prefix. It does not need administrator access.

IAM policies help us build secure applications on AWS.

## 18. AWS Interview Questions and Answers

### Q1. What is an IAM policy?

An IAM policy is a JSON document that defines permissions for AWS identities or resources. It specifies actions, resources, effects, and optional conditions.

### Q2. What are the main elements of an IAM policy?

Common elements include `Version`, `Statement`, `Effect`, `Action`, `Resource`, and `Condition`. `Sid` is an optional statement identifier. `Principal` is used in policy types that identify a principal, such as resource-based policies and trust policies.

### Q3. What is the difference between an identity-based policy and a resource-based policy?

An identity-based policy is attached to an IAM identity and defines what it can do. A resource-based policy is attached to a supported resource and defines which principals can access it.

### Q4. What is an ARN?

An ARN is an Amazon Resource Name used to identify an AWS resource. Its format varies by service.

### Q5. What is the difference between `s3:ListBucket` and `s3:GetObject`?

` s3:ListBucket` lists keys in a bucket and uses the bucket ARN. `s3:GetObject` reads an object and uses an object ARN.

### Q6. What is least privilege?

Least privilege means granting only the permissions required for a task, with no unnecessary access.

### Q7. What happens when an Allow and an explicit Deny both apply?

The explicit Deny takes precedence.

### Q8. What is the difference between AWS managed and customer managed policies?

AWS managed policies are created and maintained by AWS. Customer managed policies are created and maintained in your account and can be reused across identities.

### Q9. What is a policy Condition?

A Condition adds requirements that must be satisfied for a statement to apply. The available condition keys depend on the service and action.

### Q10. How should an EC2 application access S3 securely?

Attach an IAM role to the EC2 instance through an instance profile. Grant the role only the required S3 permissions. The application can use temporary credentials supplied through the AWS SDK default credentials provider chain.
