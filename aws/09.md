# PART 1 — IAM Policy fundamentals

## 2. What is an IAM Policy?

An IAM Policy is a JSON document that defines permissions for an AWS identity or resource.

It specifies:

- Which actions are allowed or denied.
- Which resources are affected.
- Under what conditions access is permitted.

For example, a developer needs to download files from an S3 bucket but should not upload or delete files.

You can create a policy that allows only `s3:GetObject`.

### Basic architecture

```
              AWS IAM
                 |
                 v
            IAM Policy
                 |
         +-------+-------+
         |               |
         v               v
       Action          Resource
         |               |
         v               v
    s3:GetObject    company-files/*
         |               |
         +-------+-------+
                 |
                 v
          Permission Check
                 |
                 v
           Access Decision
```

### Example policy

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-files/*"
    }
  ]
}
```

This policy grants permission to read objects in the `company-files` bucket.

It does not grant permission to upload or delete objects.

## 3. IAM Policy JSON structure

Let's examine the main fields.

```
{
  "Version": "2012-10-17",
  "Id": "ExamplePolicy",
  "Statement": [
    {
      "Sid": "AllowS3Read",
      "Effect": "Allow",
      "Principal": "*",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": [
        "arn:aws:s3:::company-files/*"
      ],
      "Condition": {
        "StringEquals": {
          "aws:RequestedRegion": "ap-southeast-1"
        }
      }
    }
  ]
}
```

This is an illustrative structure. `Principal` is used in resource-based policies and trust policies, not in ordinary identity-based permission statements.

### 3.1 Policy elements

| Element     | Description                                          | Required?         |
| ----------- | ---------------------------------------------------- | ----------------- |
| `Version`   | IAM policy language version                          | Recommended       |
| `Id`        | Optional policy identifier                           | No                |
| `Statement` | Permission statements                                | Yes               |
| `Sid`       | Optional statement identifier                        | No                |
| `Effect`    | Allow or Deny                                        | Yes               |
| `Action`    | AWS API actions                                      | Yes               |
| `Resource`  | Target AWS resources                                 | Usually           |
| `Principal` | Identity receiving access in resource-based policies | Context-dependent |
| `Condition` | Conditions for applying the statement                | No                |

### 3.2 Version

```
"Version": "2012-10-17"
```

This identifies the IAM policy language version.

It is not the date when you created the policy.

### 3.3 Statement

A policy can contain multiple statements.

Example:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowRead",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-files/*"
    },
    {
      "Sid": "AllowUpload",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::company-files/*"
    }
  ]
}
```

The first statement grants read access.

The second statement grants upload access.

You can place multiple permission statements in one policy.

# PART 2 — Understanding Effect, Action, and Resource

## 4. Effect

The `Effect` element specifies whether a permission statement allows or denies an action.

There are two possible values:

| Value   | Meaning                                    |
| ------- | ------------------------------------------ |
| `Allow` | Grant the specified permission             |
| `Deny`  | Explicitly reject the specified permission |

Example:

```
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::company-files/*"
}
```

This allows reading objects.

Example of Deny:

```
{
  "Effect": "Deny",
  "Action": "s3:DeleteObject",
  "Resource": "arn:aws:s3:::company-files/*"
}
```

This explicitly denies deleting objects.

Important: Explicit Deny overrides applicable Allow permissions.

## 5. Action

`Action` specifies which AWS API operations are affected.

Every AWS service defines its own actions.

### Common S3 actions

| Action                | Description              |
| --------------------- | ------------------------ |
| `s3:ListBucket`       | List objects in a bucket |
| `s3:GetObject`        | Download an object       |
| `s3:PutObject`        | Upload an object         |
| `s3:DeleteObject`     | Delete an object         |
| `s3:GetObjectTagging` | Read object tags         |
| `s3:PutObjectTagging` | Modify object tags       |

### Common EC2 actions

| Action                       | Description           |
| ---------------------------- | --------------------- |
| `ec2:DescribeInstances`      | View EC2 instances    |
| `ec2:StartInstances`         | Start instances       |
| `ec2:StopInstances`          | Stop instances        |
| `ec2:TerminateInstances`     | Terminate instances   |
| `ec2:CreateTags`             | Add tags to resources |
| `ec2:DescribeSecurityGroups` | View security groups  |

### Common Lambda actions

| Action                      | Description               |
| --------------------------- | ------------------------- |
| `lambda:InvokeFunction`     | Invoke a function         |
| `lambda:GetFunction`        | View function information |
| `lambda:UpdateFunctionCode` | Update function code      |
| `lambda:CreateFunction`     | Create a function         |
| `lambda:DeleteFunction`     | Delete a function         |

### Example: Allow read-only access to EC2

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ec2:DescribeInstances",
        "ec2:DescribeSecurityGroups"
      ],
      "Resource": "*"
    }
  ]
}
```

This grants the specified EC2 describe operations.

Some EC2 describe actions do not support resource-level permissions, so `Resource: "*"` is required for those actions.

## 6. Resource

`Resource` specifies which AWS resources a policy statement affects.

Resources are commonly identified using ARNs.

### Example: S3 bucket ARN

```
arn:aws:s3:::company-files
```

### Example: S3 object ARN

```
arn:aws:s3:::company-files/images/photo.jpg
```

### Example: All objects in a bucket

```
arn:aws:s3:::company-files/*
```

### Important difference

| ARN                                   | Meaning                         |
| ------------------------------------- | ------------------------------- |
| `arn:aws:s3:::company-files`          | The bucket itself               |
| `arn:aws:s3:::company-files/*`        | All objects inside the bucket   |
| `arn:aws:s3:::company-files/images/*` | Objects under the images prefix |

For example:

`s3:ListBucket` applies to the bucket ARN, while `s3:GetObject` applies to object ARNs.

A policy that needs both permissions should usually specify both resources.

Example:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-files"
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::company-files/*"
    }
  ]
}
```

# PART 3 — IAM Policy types

## 7. AWS Managed Policies

AWS Managed Policies are policies created and maintained by AWS.

You can attach them to IAM users, groups, and roles.

Examples:

| Policy                   | Purpose                             |
| ------------------------ | ----------------------------------- |
| `AdministratorAccess`    | Broad administrative access         |
| `ReadOnlyAccess`         | Broad read-only access              |
| `AmazonS3ReadOnlyAccess` | Read-only S3 permissions            |
| `AmazonEC2FullAccess`    | Broad EC2 management permissions    |
| `AWSLambda_FullAccess`   | Broad Lambda management permissions |

Example:

```
aws iam attach-user-policy \
  --user-name developer-a \
  --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
```

Advantages:

- Easy to use.
- Maintained by AWS.
- Useful for standard permissions.

Disadvantages:

- May grant more permissions than your application needs.
- Less specific than a carefully designed custom policy.

For production applications, review the policy permissions instead of attaching broad managed policies automatically.

## 8. Customer Managed Policies

Customer Managed Policies are policies created and maintained by your organization.

Example:

```
Policy: SpringBootS3UploadPolicy

Permissions:
- s3:PutObject
- s3:GetObject

Resource:
- company-images/*
```

You can attach the same managed policy to multiple users, groups, or roles.

### Advantages

- Reusable.
- Centrally managed.
- Supports policy versioning.
- Easier to maintain consistent permissions.

Example:

```
aws iam create-policy \
  --policy-name SpringBootS3Policy \
  --policy-document file://s3-policy.json
```

## 9. Inline Policies

An Inline Policy is embedded directly into one IAM identity.

For example, an inline policy can be attached directly to a role.

```
IAM Role: SpringBootRole
       |
       v
  Inline Policy
       |
       v
  S3 Permissions
```

Inline policies have a one-to-one relationship with the identity they belong to.

They are useful for permissions intended to be tightly associated with a particular identity, but customer managed policies are often easier to reuse and maintain.

### Policy comparison

| Feature                   | AWS Managed          | Customer Managed            | Inline                        |
| ------------------------- | -------------------- | --------------------------- | ----------------------------- |
| Created by                | AWS                  | Customer                    | Customer                      |
| Reusable                  | Yes                  | Yes                         | No                            |
| Independent policy object | Yes                  | Yes                         | No                            |
| Maintained by             | AWS                  | Customer                    | Customer                      |
| Versioning                | AWS-managed          | Yes                         | No managed-policy versioning  |
| Typical use               | Standard permissions | Custom reusable permissions | Identity-specific permissions |

### Which one should you use?

For a company with multiple Spring Boot services, I recommend customer managed policies for reusable application permissions.

For example:

```
                    AWS IAM
                       |
             +---------+---------+
             |                   |
             v                   v
       SpringBootRole       ImageProcessorRole
             |                   |
             v                   v
       S3UploadPolicy       S3ReadPolicy
```

Each role receives only the permissions it needs.

# PART 4 — Wildcards in IAM Policies

## 10. Understanding `*` and `?`

IAM policies support wildcard characters in action and resource patterns.

There are two commonly used wildcard characters:

| Wildcard | Meaning                         |
| -------- | ------------------------------- |
| `*`      | Matches zero or more characters |
| `?`      | Matches a single character      |

### 10.1 Wildcard in Action

Example:

```
{
  "Effect": "Allow",
  "Action": "s3:Get*",
  "Resource": "*"
}
```

This matches S3 actions beginning with `Get`, subject to the service's available actions and applicable permissions.

For example:

- `s3:GetObject`
- `s3:GetObjectTagging`
- `s3:GetBucketLocation`

Compare these policies:

| Action         | Meaning                         |
| -------------- | ------------------------------- |
| `s3:GetObject` | Read objects                    |
| `s3:Get*`      | Allow matching Get actions      |
| `s3:*`         | All S3 actions                  |
| `*`            | All actions across AWS services |

Security recommendation: Avoid `*` when a smaller permission set can accomplish the task.

### 10.2 Wildcard in Resource

Suppose you have this bucket:

```
company-files
```

You can restrict access to a particular folder prefix:

```
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::company-files/images/*"
}
```

This allows access to objects under the `images/` prefix.

Example objects:

```
company-files/
    |
    +-- images/
    |     |
    |     +-- product-1.jpg
    |     +-- product-2.jpg
    |
    +-- documents/
          |
          +-- invoice.pdf
```

| Object                  | Access                        |
| ----------------------- | ----------------------------- |
| `images/product-1.jpg`  | Allowed                       |
| `images/product-2.jpg`  | Allowed                       |
| `documents/invoice.pdf` | Not allowed by this statement |

### 10.3 Multiple resource patterns

```
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": [
    "arn:aws:s3:::company-files/images/*",
    "arn:aws:s3:::company-files/documents/public/*"
  ]
}
```

This permits reading objects from two specified prefixes.

# PART 5 — IAM Policy Conditions

## 11. What is a Condition?

A `Condition` adds additional requirements that must be satisfied for a policy statement to apply.

For example:

- Allow access only from a specific IP address.
- Allow access only through HTTPS.
- Allow access only when a specific tag exists.
- Restrict access based on the requested Region where the action supports that condition key.

Basic structure:

```
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::company-files/*",
  "Condition": {
    "StringEquals": {
      "aws:RequestedRegion": "ap-southeast-1"
    }
  }
}
```

This is an example of a Region condition. It is not a universal guarantee that every action or service is restricted by that key.

## 12. Important condition operators

| Operator          | Meaning                              |
| ----------------- | ------------------------------------ |
| `StringEquals`    | Exact string match                   |
| `StringNotEquals` | String does not match                |
| `StringLike`      | String pattern match                 |
| `StringNotLike`   | String pattern does not match        |
| `NumericEquals`   | Exact numeric match                  |
| `NumericLessThan` | Numeric value is lower               |
| `Bool`            | Boolean comparison                   |
| `IpAddress`       | IP address matches a specified range |
| `NotIpAddress`    | IP address does not match a range    |
| `DateGreaterThan` | Date is after a specified date       |
| `DateLessThan`    | Date is before a specified date      |
| `ArnEquals`       | ARN matches exactly                  |

## 13. Practical Condition examples

### Example 1 — Allow access only through HTTPS

Suppose you want to deny requests that do not use HTTPS.

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::company-files",
        "arn:aws:s3:::company-files/*"
      ],
      "Condition": {
        "Bool": {
          "aws:SecureTransport": "false"
        }
      }
    }
  ]
}
```

This is a resource-based S3 bucket policy.

Explanation:

- `Principal: "*"` means the statement applies to any principal.
- `s3:*` covers S3 actions.
- `aws:SecureTransport` checks whether the request uses secure transport.
- `false` means the request is not using HTTPS.
- `Deny` rejects those insecure requests.

### Example 2 — Restrict access by IP address

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-files/*",
      "Condition": {
        "IpAddress": {
          "aws:SourceIp": "203.0.113.10/32"
        }
      }
    }
  ]
}
```

This allows matching requests from the example IP address.

203.0.113.10 is a documentation-only example address. Replace it with an appropriate trusted public IP or CIDR range in a real deployment.

### Example 3 — Require a specific resource tag

Suppose your company wants an IAM user to stop EC2 instances only when they have a tag:

```
Environment = Development
```

Example policy:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ec2:StopInstances",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "ec2:ResourceTag/Environment": "Development"
        }
      }
    }
  ]
}
```

This condition restricts the allowed operation to matching tagged resources where the action supports resource-level authorization and the condition key.

### Example 4 — Restrict access using a time condition

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-files/*",
      "Condition": {
        "DateGreaterThan": {
          "aws:CurrentTime": "2026-11-04T08:00:00Z"
        },
        "DateLessThan": {
          "aws:CurrentTime": "2026-11-04T18:00:00Z"
        }
      }
    }
  ]
}
```

This example permits access during the specified UTC time window.

### Condition summary

| Business requirement   | Condition                          |
| ---------------------- | ---------------------------------- |
| Require HTTPS          | `Bool` + `aws:SecureTransport`     |
| Restrict source IP     | `IpAddress` + `aws:SourceIp`       |
| Require a resource tag | `StringEquals` + resource tag key  |
| Restrict time          | `DateGreaterThan` / `DateLessThan` |
| Match a string         | `StringEquals`                     |
| Match an ARN           | `ArnEquals`                        |

# PART 6 — IAM Policy Evaluation Logic

## 14. How does AWS decide whether a request is allowed?

When an application sends an AWS API request, AWS evaluates applicable policies and other authorization controls.

A simplified decision process:

```
            AWS API Request
                  |
                  v
         Identify Principal
                  |
                  v
        Evaluate Applicable Policies
                  |
                  v
         Is there an Explicit Deny?
             /          \
           Yes           No
            |             |
            v             v
          DENY       Is there an Allow?
                        /       \
                      Yes        No
                       |          |
                       v          v
               Check Other      DENY
               Restrictions
                       |
                       v
                Final Decision
```

This is a simplified model. Real AWS authorization can involve identity-based policies, resource-based policies, permissions boundaries, session policies, Service Control Policies (SCPs), resource control policies where applicable, and service-specific authorization rules.

## 15. Implicit Deny vs Explicit Deny

These concepts are extremely important.

### 15.1 Implicit Deny

An implicit Deny happens when there is no applicable Allow permission.

Example:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-files/*"
    }
  ]
}
```

The user can read objects but has no permission to upload them through this statement.

If the user attempts `s3:PutObject`, the request is implicitly denied unless another applicable authorization path permits it.

### 15.2 Explicit Deny

An explicit Deny is written directly in a policy.

Example:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::company-files/*"
    }
  ]
}
```

Even if another applicable policy allows `s3:DeleteObject`, this explicit Deny takes precedence.

### 15.3 Comparison

| Concept           | Implicit Deny                | Explicit Deny                     |
| ----------------- | ---------------------------- | --------------------------------- |
| How it happens    | No applicable Allow          | Policy explicitly says Deny       |
| Written in policy | Not necessarily              | Yes                               |
| Overrides Allow   | Not applicable               | Yes                               |
| Example           | No `s3:PutObject` permission | `Effect: Deny` for `s3:PutObject` |

## 16. Example — Multiple policies

Imagine a developer has three applicable permissions statements.

Policy A — Developer policy

```
{
  "Effect": "Allow",
  "Action": "s3:*",
  "Resource": "*"
}
```

Policy B — Security policy

```
{
  "Effect": "Deny",
  "Action": "s3:DeleteObject",
  "Resource": "*"
}
```

Policy C — Read policy

```
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "*"
}
```

Final result, considering these statements:

| Action            | Policy A | Policy B      | Policy C | Result |
| ----------------- | -------- | ------------- | -------- | ------ |
| `s3:GetObject`    | Allow    | No match      | Allow    | Allow  |
| `s3:PutObject`    | Allow    | No match      | No match | Allow  |
| `s3:DeleteObject` | Allow    | Explicit Deny | No match | Deny   |

The explicit Deny overrides the Allow.

## 17. Permissions boundaries and Service Control Policies

These are additional concepts worth understanding.

Permissions Boundary

A permissions boundary sets the maximum permissions an identity-based policy can grant to a user or role.

Service Control Policy (SCP)

An SCP defines maximum available permissions for accounts or organizational units within AWS Organizations.

Neither grants permissions by itself.

| Policy type           | Purpose                                                 |
| --------------------- | ------------------------------------------------------- |
| Identity-based policy | Grants permissions to an identity                       |
| Resource-based policy | Grants permissions through a resource                   |
| Permissions boundary  | Limits maximum identity permissions                     |
| SCP                   | Limits permissions available within an AWS Organization |
| Session policy        | Restricts permissions for a particular session          |

For example, a developer may have an identity policy allowing EC2 administration, but an organizational SCP can prevent that account from terminating certain resources.

Important: A permissions boundary or SCP does not independently grant an action. The request must also have the necessary applicable authorization.

# PART 7 — Practical AWS CLI: Create and manage IAM Policies

## 18. Prepare your AWS CLI environment

First, verify your AWS account.

```
aws sts get-caller-identity --profile development
```

Check your identity:

```
aws iam list-users --profile development
```

Check existing policies:

```
aws iam list-policies `
    --scope Local `
    --profile development
```

The `Local` scope shows customer-managed policies in your account.

## 19. Create an S3 policy

Create a JSON file named:

```
s3-upload-policy.json
```

Content:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowUpload",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::company-images/uploads/*"
    },
    {
      "Sid": "AllowDownload",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::company-images/*"
    }
  ]
}
```

This policy:

- Allows uploads to `uploads/`.
- Allows downloads from the bucket.
- Does not grant object deletion.

Create the policy:

```
aws iam create-policy `
    --policy-name S3UploadDownloadPolicy `
    --policy-document file://s3-upload-policy.json `
    --profile development
```

AWS returns a policy ARN.

Example:

```
arn:aws:iam::123456789012:policy/S3UploadDownloadPolicy
```

## 20. Attach a policy to an IAM role

Suppose you already have a role named `SpringBootEC2Role`.

```
aws iam attach-role-policy `
    --role-name SpringBootEC2Role `
    --policy-arn arn:aws:iam::123456789012:policy/S3UploadDownloadPolicy `
    --profile development
```

Check attached policies:

```
aws iam list-attached-role-policies `
    --role-name SpringBootEC2Role `
    --profile development
```

## 21. Inspect a managed policy

Get the policy information:

```
aws iam get-policy `
    --policy-arn arn:aws:iam::123456789012:policy/S3UploadDownloadPolicy `
    --profile development
```

Get its default version ID, then retrieve the JSON document:

```
aws iam get-policy-version `
    --policy-arn arn:aws:iam::123456789012:policy/S3UploadDownloadPolicy `
    --version-id v1 `
    --profile development
```

The default version may not always be `v1`. Use the `DefaultVersionId` returned by `get-policy`.

## 22. Simulate policy permissions

Before deploying your application, you can test whether a policy allows an action.

```
aws iam simulate-principal-policy `
    --policy-source-arn arn:aws:iam::123456789012:role/SpringBootEC2Role `
    --action-names s3:PutObject `
    --resource-arns arn:aws:s3:::company-images/uploads/test.jpg `
    --profile development
```

Test an action that should not be permitted:

```
aws iam simulate-principal-policy `
    --policy-source-arn arn:aws:iam::123456789012:role/SpringBootEC2Role `
    --action-names s3:DeleteObject `
    --resource-arns arn:aws:s3:::company-images/uploads/test.jpg `
    --profile development
```

Expected results for the example policy:

| Action                      | Expected evaluation |
| --------------------------- | ------------------- |
| `s3:PutObject` on uploads   | Allowed             |
| `s3:GetObject` on an object | Allowed             |
| `s3:DeleteObject`           | Implicitly denied   |

The simulator evaluates the supplied policy context; it does not reproduce every aspect of a real request, such as every resource policy, service-specific control, or live network condition.

# PART 8 — Java Spring Boot: IAM Policies in practice

## 23. Scenario: Different permissions for different services

Imagine an e-commerce application with three components:

1. Product API.
2. Image processing service.
3. Reporting service.

Each component has different S3 requirements.

| Application       | Required permission                        |
| ----------------- | ------------------------------------------ |
| Product API       | Read and upload product images             |
| Image processor   | Read original images and upload thumbnails |
| Reporting service | Read report files                          |

You should not give every service the same broad permissions.

### Recommended architecture

```
                   AWS Account
                        |
                        v
                       IAM
                        |
          +-------------+-------------+
          |             |             |
          v             v             v
      ProductRole   ImageRole    ReportingRole
          |             |             |
          v             v             v
       Product       Image          Report
       Policy        Policy         Policy
          |             |             |
          +-------------+-------------+
                        |
                        v
                    Amazon S3
```

## 24. Create three policies

### Policy A — Product API

```
{
  "Version": "2012-10-17",
```

## 25. Spring Boot configuration

The AWS SDK should use the default credentials provider chain.

Maven dependency:

```
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>s3</artifactId>
</dependency>
```

Create the configuration:

```
package com.example.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import software.amazon.awssdk.auth.credentials.DefaultCredentialsProvider;
import software.amazon.awssdk.regions.Region;
import software.amazon.awssdk.services.s3.S3Client;

@Configuration
public class AwsConfig {

    @Bean
    public S3Client s3Client() {
        return S3Client.builder()
                .region(Region.AP_SOUTHEAST_1)
                .credentialsProvider(
                    DefaultCredentialsProvider.create()
                )
                .build();
    }
}
```

## 26. Create a Spring Boot S3 service

```
package com.example.service;

import org.springframework.stereotype.Service;

import software.amazon.awssdk.core.sync.RequestBody;
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.services.s3.model.PutObjectRequest;
import software.amazon.awssdk.services.s3.model.GetObjectRequest;

import java.nio.file.Path;

@Service
public class ProductImageService {

    private final S3Client s3Client;

    private static final String BUCKET =
            "company-files";

    public ProductImageService(S3Client s3Client) {
        this.s3Client = s3Client;
    }

    public void uploadProductImage(
            String fileName,
            Path filePath
    ) {

        String key = "products/" + fileName;

        PutObjectRequest request =
                PutObjectRequest.builder()
                        .bucket(BUCKET)
                        .key(key)
                        .build();

        s3Client.putObject(
                request,
                RequestBody.fromFile(filePath)
        );
    }

    public void downloadProductImage(
            String fileName,
            Path destination
    ) {

        String key = "products/" + fileName;

        GetObjectRequest request =
                GetObjectRequest.builder()
                        .bucket(BUCKET)
                        .key(key)
                        .build();

        s3Client.getObject(
                request,
                destination
        );
    }
}
```

### What happens when the application uploads an image?

```
Spring Boot
    |
    v
ProductImageService
    |
    v
AWS SDK
    |
    v
Retrieve temporary credentials
    |
    v
Sign S3 API request
    |
    v
AWS IAM evaluates permissions
    |
    +------ Allow ------> S3 Upload
    |
    +------ Deny -------> AccessDenied
```

### Important security consideration

IAM permissions do not replace application-level security.

For example, even if your role allows uploading files, your Spring Boot API should still:

- Authenticate the user.
- Authorize the user to upload that particular product image.
- Validate file size and file type.
- Generate safe object keys.
- Avoid accepting arbitrary bucket names from clients.
- Avoid exposing sensitive AWS errors to end users.

Also, if your application uses SSE-KMS encryption with a customer-managed KMS key, additional KMS permissions and key policy authorization may be required.

# PART 9 — Troubleshooting IAM AccessDenied

## 27. Common IAM errors

| Error                   | Possible cause                      | What to check                       |
| ----------------------- | ----------------------------------- | ----------------------------------- |
| `AccessDenied`          | Missing permissions                 | IAM policy                          |
| `AccessDeniedException` | Service authorization failure       | Identity and resource policies      |
| `NoSuchBucket`          | Bucket does not exist or wrong name | Bucket name and Region              |
| `InvalidAccessKeyId`    | Invalid or unavailable credentials  | Credential source                   |
| `ExpiredToken`          | Temporary credentials expired       | Refresh SSO/session                 |
| `SignatureDoesNotMatch` | Request signing or credential issue | Credentials, Region, clock, request |

### Troubleshooting checklist

When your Spring Boot application cannot upload to S3:

1. Verify the AWS identity being used.
2. Check the EC2 instance profile or local SSO profile.
3. Confirm the role has `s3:PutObject`.
4. Check the object ARN and bucket name.
5. Check bucket policies for explicit Deny.
6. Check permissions boundaries and organizational SCPs.
7. Check whether the bucket uses KMS encryption.
8. Check CloudTrail events where available.

Useful command:

```
aws sts get-caller-identity
```

This is often the first command I would run when investigating an AWS SDK permission problem.

## 33. Exercise 5: Write your own IAM Policy

Scenario:

A Spring Boot application needs to:

- Read objects from `company-documents`.
- Upload objects to `company-documents/uploads/`.
- Never delete objects.

Write the policy.

Suggested answer

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowReadDocuments",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-documents/*"
    },
    {
      "Sid": "AllowUploadDocuments",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::company-documents/uploads/*"
    },
    {
      "Sid": "DenyDeleteDocuments",
      "Effect": "Deny",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::company-documents/*"
    }
  ]
}
```

Explanation:

- First statement: Read objects.
- Second statement: Upload only to the uploads prefix.
- Third statement: Explicitly deny deleting objects.

This is an example of combining least privilege with an explicit security restriction.

# PART 12 — Interview questions and answers

## 34. Beginner questions

Q1. What is an IAM Policy?

Answer:

An IAM Policy is a JSON document that defines permissions for AWS identities or resources. It specifies which actions are allowed or denied and which resources are affected.

Q2. What are the main elements of an IAM Policy?

Answer:

The main elements are Version, Statement, Effect, Action, Resource, and optionally Condition, Sid, and Principal where applicable.

Q3. What is the difference between Allow and Deny?

Answer:

Allow grants permission to perform an action, while Deny explicitly rejects permission. An explicit Deny takes precedence over an applicable Allow.

Q4. What is the difference between AWS Managed and Customer Managed Policies?

Answer:

AWS Managed Policies are created and maintained by AWS. Customer Managed Policies are created and maintained by customers and can be reused across multiple identities.

Q5. What is an Inline Policy?

Answer:

An Inline Policy is embedded directly into an IAM identity, such as a user, group, or role.

## 35. Intermediate questions

Q6. What is the difference between `s3:ListBucket` and `s3:GetObject`?

Answer:

`s3:ListBucket` allows listing objects in a bucket. `s3:GetObject` allows retrieving a specific object. They generally require different resource ARNs.

Q7. What is a wildcard in IAM Policies?

Answer:

A wildcard is a special character used to match multiple action names or resource patterns. The asterisk `*` matches zero or more characters, while `?` matches one character.

Q8. What is an IAM Condition?

Answer:

A Condition adds requirements to a policy statement, such as restricting access based on source IP, transport security, resource tags, or time.

Q9. What is Explicit Deny?

Answer:

Explicit Deny is a policy statement that directly denies an action. It overrides an applicable Allow permission.

Q10. What is Implicit Deny?

Answer:

Implicit Deny happens when there is no applicable Allow permission for the requested action.

## 36. Advanced questions

Q11. What is the difference between a permissions boundary and an IAM policy?

Answer:

An identity-based policy can grant permissions. A permissions boundary defines the maximum permissions that an identity-based policy can grant to an IAM user or role. The boundary does not independently grant access.

Q12. What is a Service Control Policy?

Answer:

An SCP is an AWS Organizations policy that defines the maximum permissions available to accounts or organizational units. It does not independently grant permissions.

Q13. How do you troubleshoot an AccessDenied error?

Answer:

I check the caller identity, attached IAM policies, resource ARN, resource-based policies, explicit Deny statements, permissions boundaries, session policies, and organizational policies.

Q14. Why should we avoid `Action: "*"` and `Resource: "*"`?

Answer:

They can grant excessively broad permissions. Following the Principle of Least Privilege reduces the risk of unauthorized actions and accidental resource modification.

Q15. How do you implement least privilege for multiple Spring Boot microservices?

Answer:

I create separate IAM roles for each workload, attach customer-managed policies with only the required actions and resource ARNs, and avoid sharing broad permissions across services.

## 38. Speaking challenge — Explain policy evaluation

Question: How does AWS IAM evaluate a permission request?

Suggested answer:

> When an application sends a request to AWS, AWS identifies the calling identity and evaluates the applicable authorization policies.
>
> AWS checks whether an applicable policy allows or denies the requested action.
>
> If there is an explicit Deny, the request is rejected.
>
> If there is no applicable Allow, the request is also denied.
>
> If there is an Allow, AWS checks other applicable restrictions, such as permissions boundaries and Service Control Policies.
>
> Finally, AWS decides whether the request is authorized.
