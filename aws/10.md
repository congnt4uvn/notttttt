## 2. What Is an IAM Role?

An IAM role is an identity in AWS that has a set of permissions. A trusted identity—such as an AWS service, an IAM user, or another role—can assume the role and receive temporary security credentials.

A role is not normally associated with one person's permanent password or long-term access keys. Instead, it is assumed when needed.

### Example

A Spring Boot application runs on an EC2 instance and needs to upload files to Amazon S3.

A secure design is:

1. Create an IAM role named `InvoiceApplicationRole`.
2. Configure its trust policy to allow the EC2 service to assume it.
3. Attach a permissions policy that allows uploads to one S3 prefix.
4. Associate the role with the EC2 instance through an instance profile.
5. The AWS SDK obtains temporary credentials automatically.
6. The application uses those credentials to call S3.

```text
Spring Boot Application
        |
        | AWS SDK request
        v
EC2 Instance
        |
        | Instance profile provides role credentials
        v
IAM Role: InvoiceApplicationRole
        |
        | Allows s3:PutObject on a specific prefix
        v
Amazon S3
```

The application does not need a permanent AWS access key in `application.yml`.

## 3. IAM User vs IAM Role

| Feature | IAM User | IAM Role |
|---|---|---|
| Main purpose | Represents an IAM identity, often for a person or workload needing IAM user credentials | Provides permissions to a trusted principal that assumes it |
| Long-term credentials | Can have a console password and/or access keys | Does not have its own long-term password or access keys |
| Temporary credentials | Can obtain them through supported federation or STS flows | Assumption normally provides temporary credentials |
| Typical use | Legacy workloads or specific IAM-user scenarios; workforce access is generally better handled through federation | AWS services, applications, federated users, and cross-account access |
| Can be assumed? | An IAM user can call STS to assume a role if authorized and trusted | A trusted principal assumes the role |

For new workloads running on AWS compute services, prefer IAM roles or the relevant workload identity mechanism over storing long-term IAM user access keys.

### IAM Group

An IAM group is a way to organize IAM users and attach common identity-based policies. A group is not a principal that can sign in or assume a role.

## 4. The Two Main Policies of an IAM Role

A role commonly has two different policy types.

### 4.1 Trust policy

The trust policy is also called the role's assume-role policy. It defines **who can assume the role** and under which conditions.

Example: allow the EC2 service to assume a role.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowEC2ToAssumeRole",
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

Important fields:

- `Principal`: identifies the trusted entity.
- `Action`: usually `sts:AssumeRole` for this role-assumption pattern.
- `Effect`: allows or denies the assumption.
- `Condition`: can restrict when assumption is permitted.

This policy does not grant S3 access. It only controls who can assume the role.

### 4.2 Permissions policy

The permissions policy defines **what the role can do after it is assumed**.

Example: allow uploads to an invoice prefix.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadInvoiceFiles",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::company-invoices/invoices/*"
    }
  ]
}
```

### 4.3 Trust policy vs permissions policy

| Question | Trust policy | Permissions policy |
|---|---|---|
| Main question | Who can assume this role? | What can the role do? |
| Common field | `Principal` | `Action`, `Resource` |
| Common action | `sts:AssumeRole` | `s3:GetObject`, `s3:PutObject`, etc. |
| Attached to | Role as its assume-role policy | Role as an attached or inline policy |
| Example | EC2 service can assume the role | Role can upload to one S3 prefix |

**Remember:** Trust controls entry into the role. Permissions control what the role session can access.

## 5. AWS Security Token Service (STS)

AWS Security Token Service (STS) provides temporary security credentials for supported AWS access patterns.

A typical set of temporary credentials contains:

1. Access key ID.
2. Secret access key.
3. Session token.
4. An expiration time.

Unlike long-term IAM user access keys, temporary credentials expire.

### 5.1 AssumeRole flow

```text
Trusted Principal
      |
      | 1. Requests role assumption
      v
AWS Security Token Service (STS)
      |
      | 2. Evaluates trust and applicable authorization
      v
IAM Role
      |
      | 3. STS returns temporary credentials
      v
Trusted Principal
      |
      | 4. Uses temporary credentials
      v
AWS Service (for example, S3)
```

The exact authorization checks depend on the principal type and the role-assumption scenario.

### 5.2 Common STS operation

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::111122223333:role/ReportsReadRole \
  --role-session-name ReportsReadSession
```

The response includes temporary credentials. Treat them as secrets. Do not paste them into source control, logs, or chat messages.

### 5.3 Role session duration

Role sessions are temporary. The maximum and permitted session duration depend on the role configuration and the assumption method. Some AWS service role sessions have service-specific behavior.

Use the shortest practical duration for human or automation sessions, and follow the service's supported limits.

## 6. EC2 Instance Roles and Instance Profiles

An EC2 instance often needs permission to access other AWS services.

For example:

- Read configuration from S3.
- Send logs or metrics.
- Retrieve a secret from Secrets Manager.
- Upload generated files to S3.

Do not store permanent access keys on the EC2 instance.

### 6.1 What is an instance profile?

An instance profile is a container for an IAM role that can be associated with an EC2 instance. EC2 uses the instance profile to make the role's temporary credentials available to applications on the instance through the Instance Metadata Service (IMDS).

In the EC2 console, you commonly select an IAM role when configuring the instance. AWS handles the instance profile association.

### 6.2 Architecture

```text
                    AWS Account
--------------------------------------------------
EC2 Instance
  |
  +-- Spring Boot Application
  |       |
  |       +-- AWS SDK default credentials provider
  |                    |
  |                    v
  |              EC2 Instance Metadata
  |                    |
  |                    v
  |             Temporary Role Credentials
  |
  +-- Instance Profile
          |
          v
    IAM Role: InvoiceApplicationRole
          |
          v
    Permissions Policy
          |
          v
    Amazon S3
--------------------------------------------------
```

### 6.3 Why use an instance role?

- No permanent access keys need to be embedded in the application.
- AWS rotates the temporary credentials as part of the role credential lifecycle.
- Permissions can be centrally managed in IAM.
- Different EC2 workloads can use different roles.

### 6.4 IMDS security

Use Instance Metadata Service Version 2 (IMDSv2) where possible. IMDSv2 uses a session-oriented token flow that helps protect metadata access.

For production systems:

- Require IMDSv2 on EC2 instances where compatible.
- Limit unnecessary access to the metadata endpoint.
- Do not expose metadata responses through application endpoints.
- Keep application dependencies and host software updated.
- Do not assume IMDSv2 replaces application security or network controls.

## 7. Create an EC2 Role: Conceptual Steps

This section shows the main steps. Use a test account and verify the role and policy before attaching them to production instances.

### Step 1: Create the trust policy

Save as `ec2-trust-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EC2Trust",
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

### Step 2: Create the role

```bash
aws iam create-role \
  --role-name InvoiceApplicationRole \
  --assume-role-policy-document file://ec2-trust-policy.json
```

### Step 3: Create a permissions policy

Save as `invoice-s3-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadInvoiceFiles",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::company-invoices/invoices/*"
    }
  ]
}
```

### Step 4: Create the customer managed policy

```bash
aws iam create-policy \
  --policy-name InvoiceS3UploadPolicy \
  --policy-document file://invoice-s3-policy.json
```

### Step 5: Attach the policy to the role

Replace the sample account ID:

```bash
aws iam attach-role-policy \
  --role-name InvoiceApplicationRole \
  --policy-arn arn:aws:iam::111122223333:policy/InvoiceS3UploadPolicy
```

### Step 6: Create an instance profile

```bash
aws iam create-instance-profile \
  --instance-profile-name InvoiceApplicationProfile
```

### Step 7: Add the role to the instance profile

```bash
aws iam add-role-to-instance-profile \
  --instance-profile-name InvoiceApplicationProfile \
  --role-name InvoiceApplicationRole
```

### Step 8: Associate the instance profile with an EC2 instance

For an existing instance:

```bash
aws ec2 associate-iam-instance-profile \
  --instance-id i-0123456789abcdef0 \
  --iam-instance-profile Name=InvoiceApplicationProfile
```

Replace the example instance ID and profile name with your actual values. If the instance already has a profile association, inspect it and use the appropriate replacement operation rather than attempting a second association.

## 8. Spring Boot: Access S3 Through an EC2 Role

### Scenario

A Spring Boot service runs on EC2. It needs to upload PDF invoices to:

```text
s3://company-invoices/invoices/
```

The application uses AWS SDK for Java 2.x.

### 8.1 Maven dependency

```xml
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>s3</artifactId>
</dependency>
```

Use the AWS SDK BOM in your Maven dependency management to keep module versions aligned.

### 8.2 S3 client configuration

```java
@Configuration
public class AwsConfig {

    @Bean
    public S3Client s3Client() {
        return S3Client.builder()
                .region(Region.AP_SOUTHEAST_1)
                .build();
    }
}
```

The SDK uses its default credentials provider chain. When deployed on EC2 with an attached role, the chain can retrieve temporary credentials from the instance metadata service.

### 8.3 Service class

```java
@Service
public class InvoiceStorageService {

    private final S3Client s3Client;

    @Value("${app.aws.s3.bucket}")
    private String bucketName;

    public InvoiceStorageService(S3Client s3Client) {
        this.s3Client = s3Client;
    }

    public void uploadInvoice(String fileName, Path filePath) {
        String key = "invoices/" + fileName;

        PutObjectRequest request = PutObjectRequest.builder()
                .bucket(bucketName)
                .key(key)
                .contentType("application/pdf")
                .build();

        s3Client.putObject(
                request,
                RequestBody.fromFile(filePath)
        );
    }
}
```

### 8.4 Configuration

```yaml
app:
  aws:
    s3:
      bucket: company-invoices
```

Do not put AWS access keys in this YAML file.

### 8.5 Local development

When running locally, use a developer profile or another approved credential provider rather than copying production instance credentials.

Example:

```bash
aws configure --profile dev
```

Run the application with the profile selected:

```bash
export AWS_PROFILE=dev
```

On Windows PowerShell:

```powershell
$env:AWS_PROFILE = "dev"
```

Ensure the local identity has only the development permissions it needs.

## 9. Cross-Account Role Assumption

A cross-account role allows a principal in one AWS account to access resources in another account by assuming a role there.

### Example

- Account A: `111122223333` — application account.
- Account B: `444455556666` — data account.
- Account B contains an S3 bucket.
- Account A has an application role that needs read access to that bucket.

### Architecture

```text
Account A: Application
------------------------------
Spring Boot / EC2
      |
      | sts:AssumeRole
      v
AWS STS
      |
      v
Role in Account B
------------------------------
Trust policy trusts Account A role
      |
      v
Permissions policy allows S3 read
      |
      v
S3 bucket in Account B
```

### 9.1 Trust policy in Account B

The role in Account B can trust a specific role from Account A:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TrustApplicationRole",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/ApplicationRole"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

Trusting a specific role is generally preferable to trusting an entire account when only one role needs access.

### 9.2 Permissions policy in Account A

The source role also needs permission to call `sts:AssumeRole` on the target role:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AssumeDataReadRole",
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::444455556666:role/DataReadRole"
    }
  ]
}
```

### 9.3 Permissions policy on the target role in Account B

The target role needs the actual S3 permissions:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadDataBucket",
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::shared-company-data"
    },
    {
      "Sid": "ReadDataObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::shared-company-data/*"
    }
  ]
}
```

For a successful cross-account role assumption, the source principal must be authorized to call `sts:AssumeRole`, and the target role's trust policy must trust it. Organization controls and other applicable policies can still block the request.

### 9.4 Test the assumption

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::444455556666:role/DataReadRole \
  --role-session-name ApplicationDataRead
```

The returned credentials represent the assumed role session. Protect them and do not log them.

## 10. IAM Roles for Other AWS Services

Roles are used by many AWS services, but the trust principal and setup differ by service.

| Service or workload | Role purpose | Example |
|---|---|---|
| EC2 | Permissions for software on an instance | Read S3 configuration |
| Lambda | Permissions for function execution | Write logs and read a secret |
| ECS tasks | Permissions for containers | Access S3 from a task |
| CodeBuild | Permissions for build jobs | Read source and publish artifacts |
| EC2 Auto Scaling | Service-linked role for service operations | Manage instances in a group |
| Cross-account access | Permissions in another account | Read a shared data bucket |

Do not assume every service uses the same trust policy. For example, EC2 commonly uses `ec2.amazonaws.com`, while Lambda uses `lambda.amazonaws.com`. ECS distinguishes task roles from task execution roles.

### ECS task role vs task execution role

| Role | Used by | Example permissions |
|---|---|---|
| Task role | Application code inside the container | Read S3 objects |
| Task execution role | ECS agent/platform operations | Pull images from ECR, publish logs |

This distinction prevents application permissions from being mixed with infrastructure startup permissions.


```bash

  --role-name InvoiceApplicationRole
```

### 11.5 Get an inline policy

```bash
aws iam get-role-policy \
  --role-name InvoiceApplicationRole \
  --policy-name InlineInvoicePolicy
```

### 11.6 Inspect the current caller

```bash
aws sts get-caller-identity
```

When running on EC2 with an instance role, this should identify an assumed-role session rather than a long-term IAM user.

### 11.7 Inspect EC2 instance profile association

```bash
aws ec2 describe-iam-instance-profile-associations \
  --filters Name=instance-id,Values=i-0123456789abcdef0
```

```bash
aws iam get-instance-profile \
  --instance-profile-name InvoiceApplicationProfile
```

Use the correct Region for regional EC2 commands. IAM is a global service, while EC2 resources are regional.

## 12. Security Best Practices

1. Prefer IAM roles and temporary credentials for workloads running on AWS.
2. Do not embed access keys in source code, Docker images, or application configuration.
3. Keep trust policies narrow: trust only the principals that need to assume the role.
4. Apply least privilege to the role's permissions policy.
5. Use separate roles for separate workloads and environments when practical.
6. Require IMDSv2 for EC2 workloads where supported.
7. Protect temporary credentials and never log them.
8. Review role trust relationships regularly.
9. Use CloudTrail to investigate role assumptions and API activity.
10. Consider external IDs for appropriate third-party cross-account access scenarios.
11. Use conditions such as source identity, tags, or organization identifiers when suitable and supported.
12. Avoid wildcard principals in trust policies unless there is a carefully designed reason and compensating conditions.

### Common mistakes

| Mistake | Risk | Better approach |
|---|---|---|
| Putting access keys in source code | Credential leakage | Use workload roles |
| Confusing trust and permission policies | Role cannot be assumed or lacks access | Check both policies |
| Trusting every principal | Unintended role assumption | Trust specific principals |
| Giving `s3:*` on `*` | Excessive permissions | Restrict actions and resources |
| Confusing ECS task and execution roles | Application or platform gets wrong permissions | Assign each role its intended purpose |
| Ignoring IMDS protections | Metadata credential exposure risk | Require IMDSv2 and review network access |
| Assuming role trust alone grants S3 access | Role session lacks S3 permission | Attach a permissions policy too |

## 13. Practical Exercises with Answers

### Exercise 1 — Trust policy or permissions policy?

A policy allows `ec2.amazonaws.com` to call `sts:AssumeRole`.

Which policy is it?

**Answer:** A trust policy. It identifies EC2 as a trusted service principal.

### Exercise 2 — What does the permissions policy do?

A role has this statement:

```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::company-documents/*"
}
```

**Answer:** The role can read objects in the `company-documents` bucket, subject to other applicable authorization controls. This statement does not grant bucket listing.

### Exercise 3 — Why use an EC2 instance role?

**Answer:** It gives applications on the EC2 instance temporary credentials and centrally managed permissions without requiring hardcoded long-term access keys.

### Exercise 4 — What is STS?

**Answer:** AWS Security Token Service provides temporary security credentials and supports operations such as assuming IAM roles.

### Exercise 5 — Cross-account access

Account A wants to assume a role in Account B. What two main configurations are needed?

**Answer:**
1. The target role in Account B must trust the source principal from Account A.
2. The source principal in Account A must be allowed to call `sts:AssumeRole` on the target role.

Other applicable controls can still restrict the request.

### Exercise 6 — Diagnose an EC2 application error

A Spring Boot application on EC2 reports that no AWS credentials are available. What should you check?

**Answer:**
- Is an IAM role associated with the EC2 instance?
- Does the instance profile contain the expected role?
- Is the application using a supported AWS SDK credentials provider?
- Can the instance reach the metadata service?
- Is IMDS configured correctly?
- Are there local environment variables or profiles overriding the expected credential source?

### Exercise 7 — Role access design

An application only uploads PDF files to `s3://company-invoices/invoices/`. Should the role have `s3:*` on `*`?

**Answer:** No. Grant `s3:PutObject` on `arn:aws:s3:::company-invoices/invoices/*`, plus only any additional permissions genuinely required by the upload implementation.

A trust policy defines who can assume a role. A permissions policy defines what the role can do after it is assumed. Both are important for secure access.

**Model answer:**

AWS STS stands for Security Token Service. It provides temporary security credentials. One common operation is AssumeRole, which allows a trusted principal to use another role's permissions.

**Model answer:**

Cross-account role assumption allows a principal in one AWS account to access resources in another account by assuming a role. The target role must trust the source principal, and the source principal must be allowed to assume the role.

## 16. AWS Interview Questions and Answers

### Q1. What is an IAM role?

An IAM role is an AWS identity with permissions that a trusted principal can assume. The principal receives temporary credentials for the role session.

### Q2. What is the difference between an IAM user and an IAM role?

An IAM user is an identity that can have long-term credentials. An IAM role is assumed by a trusted principal and normally provides temporary credentials.

### Q3. What is a trust policy?

A trust policy is the role's assume-role policy. It identifies which principals can assume the role and can include conditions.

### Q4. What is a permissions policy?

A permissions policy defines which actions and resources the role session can access, subject to other applicable controls.

### Q5. What is AWS STS?

AWS Security Token Service provides temporary security credentials and supports role assumption.

### Q6. What is an EC2 instance profile?

An instance profile is a container for an IAM role that can be associated with an EC2 instance. It makes the role available to applications running on that instance through the EC2 metadata service.

### Q7. Does an EC2 application need access keys in its configuration?

No. With an appropriately configured instance role, an AWS SDK can obtain temporary credentials through its default credentials provider chain.

### Q8. What is cross-account role assumption?

It is a way for a principal in one AWS account to assume a role in another account. The target role trust policy and source principal permissions must both allow the operation.

### Q9. What is the difference between an ECS task role and an execution role?

The task role is used by application code inside the container. The execution role is used by the ECS agent or platform for operations such as pulling images and publishing logs.

### Q10. How can you identify which role your AWS CLI session is using?

Run:

```bash
aws sts get-caller-identity
```

The ARN in the response identifies the caller. An assumed-role session ARN indicates role-based credentials.
