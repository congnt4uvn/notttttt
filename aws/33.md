## 2. What Is Event-Driven Architecture?

Event-driven architecture (EDA) is a design style in which components communicate by producing and reacting to events.

An event describes something that has happened.

Examples:

- `ORDER_CREATED`
- `PAYMENT_COMPLETED`
- `CUSTOMER_REGISTERED`
- `INVENTORY_LOW`
- `FILE_UPLOADED`

Instead of one service directly calling every other service, it publishes an event. Other services subscribe or configure rules to react to it.

```text
                  Order Service
                       |
                       | publishes event
                       v
                EventBridge Bus
                 /      |      \
                /       |       \
               v        v        v
           Billing   Shipping  Analytics
           Service   Service   Service
```

### Why use event-driven architecture?

- Loose coupling between services.
- Independent deployment and scaling.
- Easier integration across AWS services.
- Content-based routing.
- Better support for asynchronous workflows.

However, EDA introduces distributed-systems concerns: duplicate delivery, retries, event ordering, eventual consistency, observability, and schema evolution.

## 3. What Is Amazon EventBridge?

Amazon EventBridge is a serverless event bus service that receives events from AWS services, custom applications, and supported SaaS partners, then routes them to targets based on rules.

A simplified flow:

```text
Event Source
     |
     v
EventBridge Event Bus
     |
     v
Rule + Event Pattern
     |
     v
Target
```

### Core components

| Component | Meaning |
|---|---|
| Event | A record describing something that happened |
| Event bus | Receives and routes events |
| Rule | Defines which events match and where they should go |
| Event pattern | JSON matching criteria for incoming events |
| Target | Destination that receives a matched event |
| Archive | Stores events for later replay when configured |
| Replay | Re-sends archived events to the event bus |
| Schema registry | Stores and helps discover event structure |

EventBridge is not a general-purpose queue. It routes events to targets. Use SQS when you need a durable work queue where consumers explicitly receive and delete messages.

## 4. Event Structure

EventBridge events use a standard JSON envelope.

Example:

```json
{
  "version": "0",
  "id": "12345678-1234-1234-1234-123456789012",
  "detail-type": "Order Created",
  "source": "com.example.orders",
  "account": "123456789012",
  "time": "2026-11-04T02:30:00Z",
  "region": "ap-southeast-1",
  "resources": [],
  "detail": {
    "orderId": "O501",
    "customerId": "C1001",
    "total": 125.50,
    "status": "CREATED"
  }
}
```

Important fields:

| Field | Purpose |
|---|---|
| `source` | Identifies the application or service that emitted the event |
| `detail-type` | Describes the event category |
| `detail` | Contains application-specific event data |
| `id` | Unique event identifier |
| `time` | Event timestamp |
| `region` | AWS Region associated with the event |

Use stable event names and version your event contracts deliberately.

## 5. Event Buses: Default, Custom, and Partner

EventBridge supports different event bus types.

### 5.1 Default event bus

The default event bus receives events from AWS services in the account.

Examples include events from services such as EC2, S3, and other AWS services that integrate with EventBridge.

### 5.2 Custom event bus

A custom event bus is created for application events.

Example:

```text
Event bus: ApplicationBus

Sources:
  com.example.orders
  com.example.payments
  com.example.inventory
```

Custom buses help separate application domains and control access to event publishing and consumption.

### 5.3 Partner event bus

A partner event bus is associated with supported SaaS partner integrations. It allows events from external services to enter EventBridge through an integration.

### Comparison

| Event bus | Typical source | Example |
|---|---|---|
| Default | AWS services | EC2 state change |
| Custom | Your applications | Order created |
| Partner | Supported SaaS partners | External CRM event |

Choose a bus design based on ownership, security boundaries, and integration needs. Avoid creating many buses without a clear operational reason.

## 6. Rules and Event Patterns

An EventBridge rule decides which incoming events should be routed to one or more targets.

### 6.1 Example event pattern

Suppose the application publishes:

```json
{
  "source": "com.example.orders",
  "detail-type": "Order Created",
  "detail": {
    "status": "CREATED",
    "region": "APAC"
  }
}
```

A matching event pattern:

```json
{
  "source": ["com.example.orders"],
  "detail-type": ["Order Created"],
  "detail": {
    "status": ["CREATED"],
    "region": ["APAC"]
  }
}
```

This rule matches events from the specified source and detail type whose nested detail fields match the listed values.

### 6.2 Match a numeric range

Example:

```json
{
  "source": ["com.example.orders"],
  "detail-type": ["Order Created"],
  "detail": {
    "total": [
      {
        "numeric": [">=", 100]
      }
    ]
  }
}
```

This matches order events where `detail.total` is at least 100.

### 6.3 Match multiple values

```json
{
  "source": ["com.example.orders"],
  "detail": {
    "status": ["CREATED", "PAID", "SHIPPED"]
  }
}
```

### 6.4 Negation and existence

Event patterns support operators such as `anything-but` and `exists`.

Example:

```json
{
  "detail": {
    "status": [
      {
        "anything-but": ["CANCELLED"]
      }
    ]
  }
}
```

Pattern syntax has specific rules. Validate patterns with the AWS console or `test-event-pattern` CLI command before deploying them.

### 6.5 Test an event pattern

Save the pattern to `pattern.json` and an example event to `event.json`.

```bash
aws events test-event-pattern \
  --event-pattern file://pattern.json \
  --event file://event.json \
  --region ap-southeast-1
```

The event passed to this API must use the expected EventBridge event structure.

## 7. Targets and Routing

A rule can route matched events to supported targets, such as:

- AWS Lambda.
- Amazon SQS.
- Amazon SNS.
- AWS Step Functions.
- Kinesis streams.
- Event buses.
- API destinations.
- Other supported AWS service targets.

Example:

```text
                 ApplicationBus
                       |
              +--------+--------+
              |        |        |
              v        v        v
          Rule A    Rule B    Rule C
          ORDER     PAYMENT   HIGH VALUE
          CREATED   COMPLETED ORDER
              |        |        |
              v        v        v
           Lambda    SQS      Step Functions
```

A rule can have multiple targets. A target can receive an input transformation or input path where supported, allowing the event payload to be shaped for the destination.

### Target permissions

EventBridge needs permission to invoke or send to many target types. Depending on the target, configure a resource-based policy or an IAM role for EventBridge.

For example:

- Lambda resource policy allows EventBridge to invoke the function.
- SQS queue policy allows EventBridge to send messages.
- SNS topic policy allows EventBridge to publish.
- Step Functions target role grants the required start-execution permission.

Use least privilege and scope permissions to the specific rule or event bus where possible.

## 8. EventBridge vs. SNS vs. SQS

These services can work together, but they solve different problems.

| Feature | EventBridge | SNS | SQS |
|---|---|---|---|
| Main purpose | Event routing and integration | Pub/sub fanout | Message queue |
| Routing | Rich event patterns | Topic subscriptions and filters | Consumers pull from queue |
| Message storage | Not a work queue; archives are optional | Delivery to subscribers | Stores messages until deleted/expired |
| Consumer model | Pushes to targets | Pushes to subscribers | Consumers poll or use event source integrations |
| Best fit | Event routing across services | Broadcast notifications | Durable asynchronous work |

### Example combined architecture

```text
Order Service
     |
     v
EventBridge
     |
     +------> Lambda: fraud check
     |
     +------> SQS: billing worker
     |
     +------> SNS: customer notifications
```

Choose the service based on the behavior required. A common pattern is EventBridge for routing and SQS for buffering work for a consumer.

## 9. Scheduled Rules and EventBridge Scheduler

EventBridge supports time-based triggering.

There are two concepts to know:

### Scheduled rules

Legacy scheduled rules on an event bus use rate or cron expressions to trigger targets. They remain useful in existing systems, but AWS recommends EventBridge Scheduler for many new scheduling use cases.

### EventBridge Scheduler

EventBridge Scheduler is a serverless scheduling service that supports one-time and recurring schedules and can invoke supported AWS API targets.

Examples:

- Run a cleanup task every night.
- Trigger a report at a specific time.
- Start a workflow once at a future time.
- Schedule a retry or follow-up task.

Example schedule expressions:

```text
rate(5 minutes)
rate(1 day)
cron(0 9 ? * MON-FRI *)
```

Cron expressions are interpreted in UTC unless a time zone is specified through the Scheduler configuration. Scheduler supports time-zone-aware schedules.

For new scheduling workflows, evaluate Scheduler rather than automatically creating a legacy scheduled rule.

## 10. Retry Policies and Dead-Letter Queues

When EventBridge cannot deliver an event to a target, it retries according to the configured retry policy.

A rule target can have:

- Maximum event age.
- Maximum retry attempts.
- A dead-letter queue for events that cannot be delivered.

Conceptual flow:

```text
EventBridge Rule
       |
       v
     Target
       |
   +---+---+
   |       |
Success  Delivery fails
   |       |
   v       v
Done    Retry
           |
       Retry exhausted
           |
           v
          DLQ
```

### Important distinction

An EventBridge target DLQ captures delivery failures from EventBridge to the target. It does not automatically capture failures that happen later inside a Lambda function or an SQS consumer.

For example:

```text
EventBridge --> Lambda --> downstream API
     |             |
     |             +--> Lambda async failure handling / destination
     |
     +--> EventBridge target DLQ for invoke-delivery failures
```

Configure error handling at each stage of the architecture.

### Reliability practices

- Make targets idempotent.
- Configure retries based on the business requirement.
- Use a DLQ for target delivery failures.
- Alarm on DLQ depth.
- Inspect and replay events only after correcting the failure.
- Monitor target invocation failures and latency.

## 11. Event Archives and Replay

EventBridge archives can retain selected events from an event bus. Replay can send archived events back to an event bus for reprocessing.

Use cases:

- Recover from a downstream processing bug after it has been fixed.
- Rebuild derived data.
- Reprocess events after a deployment.
- Support controlled recovery workflows.

Considerations:

- Define which events should be archived.
- Choose retention based on business and compliance needs.
- Replayed events can trigger rules and targets again.
- Consumers must be idempotent.
- Replay can create a large workload; monitor downstream capacity.

An archive is not a substitute for a business database or a complete backup strategy.

## 12. Event Schemas and Schema Registry

An event schema defines the structure and data types of an event.

Example:

```json
{
  "type": "object",
  "properties": {
    "orderId": {"type": "string"},
    "customerId": {"type": "string"},
    "status": {"type": "string"},
    "total": {"type": "number"}
  },
  "required": ["orderId", "status"]
}
```

EventBridge Schema Registry can help discover and manage schemas for supported event sources and can generate code bindings for supported languages.

### Schema design best practices

- Use stable field names.
- Include event identity and event type.
- Include a schema version when evolution requires it.
- Prefer additive changes where possible.
- Avoid changing the meaning or type of an existing field without a migration plan.
- Make consumers tolerant of unknown optional fields.
- Do not put secrets or unnecessary personal information in event payloads.

### Example versioned event

```json
{
  "source": "com.example.orders",
  "detail-type": "Order Created",
  "detail": {
    "schemaVersion": "1",
    "eventId": "evt-10001",
    "orderId": "O501",
    "status": "CREATED"
  }
}
```

## 13. AWS CLI: Create a Custom Event Bus and Rule

Examples use Region `ap-southeast-1`.

### 13.1 Check identity

```bash
aws sts get-caller-identity
aws configure get region
```

### 13.2 Create a custom event bus

```bash
aws events create-event-bus \
  --name ApplicationBus \
  --region ap-southeast-1
```

### 13.3 List event buses

```bash
aws events list-event-buses \
  --region ap-southeast-1
```

### 13.4 Publish a custom event

```bash
aws events put-events \
  --entries '[
    {
      "Source": "com.example.orders",
      "DetailType": "Order Created",
      "EventBusName": "ApplicationBus",
      "Detail": "{\"orderId\":\"O501\",\"customerId\":\"C1001\",\"status\":\"CREATED\",\"total\":125.50}"
    }
  ]' \
  --region ap-southeast-1
```

Check the response for failed entries. A successful API call does not guarantee every target has completed processing.

### 13.5 Create an event pattern

Save as `order-pattern.json`:

```json
{
  "source": ["com.example.orders"],
  "detail-type": ["Order Created"],
  "detail": {
    "status": ["CREATED"]
  }
}
```

### 13.6 Create a rule

```bash
aws events put-rule \
  --name OrderCreatedRule \
  --event-bus-name ApplicationBus \
  --event-pattern file://order-pattern.json \
  --state ENABLED \
  --description "Route newly created order events" \
  --region ap-southeast-1
```

### 13.7 Add an SQS target

First create an SQS queue and retrieve its ARN. Then add it as a target:

```bash
aws events put-targets \
  --rule OrderCreatedRule \
  --event-bus-name ApplicationBus \
  --targets '[{
    "Id": "BillingQueueTarget",
    "Arn": "PASTE_SQS_QUEUE_ARN",
    "RoleArn": "PASTE_EVENTBRIDGE_TARGET_ROLE_ARN"
  }]' \
  --region ap-southeast-1
```

The role must allow EventBridge to send messages to the queue. The queue policy and role configuration must follow the target type's permission model.

### 13.8 Inspect the rule

```bash
aws events describe-rule \
  --name OrderCreatedRule \
  --event-bus-name ApplicationBus \
  --region ap-southeast-1
```

### 13.9 Inspect targets

```bash
aws events list-targets-by-rule \
  --rule OrderCreatedRule \
  --event-bus-name ApplicationBus \
  --region ap-southeast-1
```

### 13.10 Remove resources after the lab

Remove targets first:

```bash
aws events remove-targets \
  --rule OrderCreatedRule \
  --event-bus-name ApplicationBus \
  --ids BillingQueueTarget \
  --region ap-southeast-1
```

Delete the rule:

```bash
aws events delete-rule \
  --name OrderCreatedRule \
  --event-bus-name ApplicationBus \
  --region ap-southeast-1
```

Delete the custom bus after its rules and other dependencies are removed:

```bash
aws events delete-event-bus \
  --name ApplicationBus \
  --region ap-southeast-1
```

**Cost note:** EventBridge pricing depends on event ingestion, delivery, archive/replay, Scheduler invocations, and other features. Review current regional pricing and clean up lab resources.

## 14. Spring Boot Integration with AWS SDK for Java 2.x

This example publishes a custom event to EventBridge.

### 14.1 Maven dependencies

Use the AWS SDK for Java 2.x BOM and set `${aws.sdk.version}` to an approved current version.

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>software.amazon.awssdk</groupId>
            <artifactId>bom</artifactId>
            <version>${aws.sdk.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>eventbridge</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
</dependencies>
```

### 14.2 Configuration

```yaml
app:
  aws:
    region: ap-southeast-1
  eventbridge:
    event-bus-name: ApplicationBus
```

```java
@Configuration
public class EventBridgeConfiguration {

    @Bean
    EventBridgeClient eventBridgeClient(
            @Value("${app.aws.region}") String region) {

        return EventBridgeClient.builder()
                .region(Region.of(region))
                .credentialsProvider(
                    DefaultCredentialsProvider.create()
                )
                .build();
    }
}
```

Use an IAM role when the application runs on AWS. Do not hardcode access keys.

### 14.3 Event DTO

```java
public record OrderCreatedDetail(
        String eventId,
        String orderId,
        String customerId,
        String status,
        BigDecimal total
) {}
```

### 14.4 Publisher service

```java
@Service
public class OrderEventPublisher {

    private final EventBridgeClient eventBridgeClient;
    private final ObjectMapper objectMapper;
    private final String eventBusName;

    public OrderEventPublisher(
            EventBridgeClient eventBridgeClient,
            ObjectMapper objectMapper,
            @Value("${app.eventbridge.event-bus-name}")
            String eventBusName) {
        this.eventBridgeClient = eventBridgeClient;
        this.objectMapper = objectMapper;
        this.eventBusName = eventBusName;
    }

    public String publish(OrderCreatedDetail detail) {
        try {
            String json = objectMapper.writeValueAsString(detail);

            PutEventsResponse response =
                eventBridgeClient.putEvents(
                    PutEventsRequest.builder()
                        .entries(PutEventsRequestEntry.builder()
                            .eventBusName(eventBusName)
                            .source("com.example.orders")
                            .detailType("Order Created")
                            .detail(json)
                            .build())
                        .build()
                );

            if (response.failedEntryCount() != null
                    && response.failedEntryCount() > 0) {
                throw new IllegalStateException(
                    "EventBridge rejected one or more entries"
                );
            }

            return response.entries().get(0).eventId();

        } catch (JsonProcessingException e) {
            throw new IllegalArgumentException(
                "Could not serialize order event", e
            );
        }
    }
}
```

The EventBridge API can return failed entries within a successful HTTP response. Check the failed-entry count and inspect per-entry errors. Production code should implement appropriate retry and logging behavior for retryable failures.

### 14.5 Controller

```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderEventPublisher publisher;

    public OrderController(OrderEventPublisher publisher) {
        this.publisher = publisher;
    }

    @PostMapping("/{orderId}/events")
    public ResponseEntity<Map<String, String>> publish(
            @PathVariable String orderId) {

        OrderCreatedDetail event = new OrderCreatedDetail(
            UUID.randomUUID().toString(),
            orderId,
            "C1001",
            "CREATED",
            new BigDecimal("125.50")
        );

        String eventId = publisher.publish(event);

        return ResponseEntity.accepted().body(
            Map.of("eventId", eventId)
        );
    }
}
```

A successful response indicates that EventBridge accepted the event entry. It does not prove that all downstream targets completed their work.

### 14.6 Suggested project structure

```text
src/main/java/com/example/orders/
|
+-- config/
|   +-- EventBridgeConfiguration.java
|
+-- controller/
|   +-- OrderController.java
|
+-- dto/
|   +-- OrderCreatedDetail.java
|
+-- messaging/
    +-- OrderEventPublisher.java
```

## 16. Troubleshooting

| Symptom or error | Possible cause | What to check |
|---|---|---|
| Event is accepted but target receives nothing | Rule pattern does not match | Source, detail type, field paths, value types |
| `PutEvents` has failed entries | Invalid event bus or entry fields, permissions, or size issue | Per-entry error code and message |
| SQS target receives no event | Target role or queue policy is incorrect | `sqs:SendMessage`, queue ARN, role trust |
| Lambda target is not invoked | Lambda resource policy or target configuration is missing | `lambda:InvokeFunction` permission |
| EventBridge DLQ grows | Target delivery keeps failing | Target health, role, resource policy, retry settings |
| Rule matches too many events | Event pattern is too broad | Add source, detail-type, and detail constraints |
| Rule matches no events | Incorrect case, JSON path, or data type | Compare actual event with pattern |
| Replayed events duplicate business actions | Consumer is not idempotent | Event ID, idempotency store, side effects |
| Scheduled task runs at unexpected time | UTC/time-zone assumption or cron expression | Scheduler time zone and schedule expression |
| Event is filtered out | Pattern conditions do not match | Test pattern against an actual event |

## 17. Practical Exercises with Answers

### Exercise 1 — What is an event?

**Answer:** An event is a record describing something that has happened, such as an order being created or a payment being completed.

### Exercise 2 — What does EventBridge do?

**Answer:** EventBridge receives events and routes them to targets based on rules and event patterns.

### Exercise 3 — What is the difference between a default and custom event bus?

**Answer:** The default bus receives events from AWS services. A custom bus is created for application or domain events.

### Exercise 4 — What is an event pattern?

**Answer:** It is a JSON structure that defines which incoming events match a rule.

### Exercise 5 — How is EventBridge different from SQS?

**Answer:** EventBridge routes events to targets. SQS stores messages in a queue until consumers receive and delete them.

### Exercise 6 — Why use EventBridge with SQS?

**Answer:** EventBridge provides flexible event routing, while SQS provides a durable buffer for independent consumer processing.

### Exercise 7 — What does a target DLQ capture?

**Answer:** It captures events EventBridge could not successfully deliver to a target after the configured retry policy is exhausted.

### Exercise 8 — What is EventBridge archive and replay?

**Answer:** An archive stores selected events, and replay sends archived events back to an event bus for reprocessing.

### Exercise 9 — Why should consumers be idempotent?

**Answer:** Events can be retried or replayed. Idempotency prevents repeated delivery from causing duplicate business actions.

### Exercise 10 — What is the difference between a scheduled rule and EventBridge Scheduler?

**Answer:** Scheduled rules are a legacy event-bus scheduling capability. EventBridge Scheduler is a dedicated scheduling service designed for one-time and recurring schedules and is recommended for many new scheduling use cases.

## 19. English Speaking Practice

Read each question aloud and practice the model answer. Then explain the same idea without reading.

### Question 1: What is Amazon EventBridge?

**Model answer:**

Amazon EventBridge is a serverless event bus service. It receives events from AWS services and applications, then routes them to targets based on rules. It helps build loosely coupled event-driven applications.

### Question 2: What is an event bus?

**Model answer:**

An event bus receives events from different sources. Rules inspect those events and route matching events to targets such as Lambda, SQS, or SNS.

### Question 3: What is an event pattern?

**Model answer:**

An event pattern is a JSON structure that describes which events should match a rule. For example, I can match events from my order service where the event type is Order Created.

### Question 4: What is the difference between EventBridge and SQS?

**Model answer:**

EventBridge is mainly used for event routing. SQS is a queue that stores messages until consumers process and delete them. I can use both services together.

### Question 5: What is an EventBridge dead-letter queue?

**Model answer:**

A target dead-letter queue stores events that EventBridge could not deliver to a target after retrying. It helps me investigate delivery failures.

### Question 6: Why do we need event schemas?

**Model answer:**

Event schemas define the structure of event data. They help producers and consumers agree on field names and data types. Versioning helps applications evolve without breaking other services.

## 20. AWS Interview Questions and Answers

**Q1. What is Amazon EventBridge?**

It is a serverless event bus service that routes events from AWS services, custom applications, and supported partners to targets based on rules.

**Q2. What is an event bus?**

An event bus is the logical destination that receives events and evaluates rules for routing.

**Q3. What is the difference between default, custom, and partner event buses?**

The default bus receives AWS service events, custom buses receive application events, and partner buses integrate with supported SaaS partners.

**Q4. What is an EventBridge rule?**

A rule contains an event pattern or schedule and defines which targets should receive matching events.

**Q5. What is an event pattern?**

It is a JSON matching structure that filters incoming events by fields such as source, detail type, and detail values.

**Q6. Can one rule have multiple targets?**

Yes. A rule can route matching events to multiple configured targets, subject to target and permission limits.

**Q7. What is the difference between EventBridge and SNS?**

EventBridge provides event routing with rich event patterns and integrations. SNS provides pub/sub topic fanout and notification delivery. Both can distribute events to multiple destinations.

**Q8. What is the difference between EventBridge and SQS?**

EventBridge routes events. SQS stores messages in a queue for consumers to retrieve and delete.

**Q9. What is an EventBridge target DLQ?**

It is a queue that receives events EventBridge could not deliver to a target after retry attempts are exhausted, when configured and supported.

**Q10. What are archive and replay?**

Archive stores selected events, and replay sends those events back to an event bus for reprocessing.

**Q11. Why should event consumers be idempotent?**

Because retries and replays can cause an event to be delivered more than once. Idempotency prevents duplicate business effects.

**Q12. When should you use EventBridge Scheduler?**

Use it for one-time or recurring time-based invocations of supported targets, especially for new scheduling workflows.
