## 2. What Is AWS IAM?

**AWS Identity and Access Management (IAM)** is a service that helps you control access to AWS resources.

IAM answers two important questions:

1. **Who is making the request?** — Authentication.
2. **What is that identity allowed to do?** — Authorization.

For example, an employee may be allowed to view an S3 bucket but not delete objects from it.

IAM helps you manage:

- Users and identities.
- Groups.
- Roles.
- Permissions and policies.
- Trust relationships.
- Authentication options.

IAM is a foundational AWS security service. You should understand it before deploying production workloads.

### 2.1 Simple IAM architecture

```text
                  AWS Account
                       |
                       v
                      IAM
                       |
          +------------+------------+
          |            |            |
          v            v            v
        Users        Groups        Roles
          |            |            |
          +------------+------------+
                       |
                       v
                    Policies
                       |
                       v
                Allowed AWS actions
                       |
                       v
              AWS resources and APIs
```

This is a conceptual diagram. Policies can be attached to users, groups, or roles, and resource-based policies can also grant access to supported resources.

## 3. Authentication vs Authorization

These two concepts are related but different.

### 3.1 Authentication

Authentication verifies the identity making a request.

Examples:

- Signing in with a username and password.
- Using MFA to provide an additional verification factor.
- Using temporary credentials obtained by assuming an IAM role.
- Using a federated identity from an external identity provider.

Question answered:

> Who are you?

### 3.2 Authorization

Authorization determines what an authenticated identity is allowed to do.

Examples:

- List objects in an S3 bucket.
- Read an object from S3.
- Start an EC2 instance.
- View an RDS database configuration.
- Delete a resource, if explicitly permitted.

Question answered:

> What are you allowed to do?

### 3.3 Comparison

| Topic | Authentication | Authorization |
|---|---|---|
| Purpose | Verify identity | Evaluate permissions |
| Main question | Who are you? | What can you do? |
| Example | Sign in with MFA | Permission to read an S3 object |
| Related IAM features | Credentials, MFA, federation, role assumption | IAM policies, resource policies, permission boundaries |

### 3.4 Example

A developer successfully signs in to AWS.

The developer then runs:

```bash
aws s3 ls
```

If the identity does not have permission to list the relevant buckets, AWS may return `AccessDenied`.

The sign-in can succeed while the requested action is denied.

**Remember:** Authentication does not automatically grant permission to every AWS resource.

## 4. The Four Main IAM Concepts

The foundational IAM concepts are:

1. IAM users
2. IAM groups
3. IAM roles
4. IAM policies

### 4.1 IAM user

An IAM user is an identity in an AWS account.

An IAM user can be configured with credentials such as:

- A console password.
- Programmatic access keys.

IAM users can receive permissions through policies attached directly to the user or through groups.

For human access, AWS commonly recommends federation and IAM Identity Center where appropriate rather than creating long-lived IAM users for every employee.

Example:

```text
IAM User: developer-alex
       |
       v
IAM Policy: ReadOnlyAccess (example)
       |
       v
Can perform permitted read operations
```

### 4.2 IAM group

An IAM group is a collection of IAM users.

You can attach permissions to a group so that users in the group receive those permissions.

Example:

```text
                 IAM Group
              Developers
                    |
          +---------+---------+
          |         |         |
          v         v         v
       User A    User B    User C
          |
          v
   Group permissions
```

Example groups:

- `Developers`
- `ReadOnlyUsers`
- `Operations`
- `DatabaseAdmins`

Groups simplify permission management for IAM users. IAM roles are generally preferred for workloads and federated access.

### 4.3 IAM role

An IAM role is an identity with permissions that a trusted principal can assume.

A role does not rely on a permanent password or long-lived access key belonging to the role itself. When a principal assumes the role, AWS provides temporary security credentials.

Common use cases:

- An EC2 instance accessing S3.
- A Lambda function writing to DynamoDB.
- A developer assuming an elevated role for a limited task.
- A user signing in through an external identity provider.
- One AWS account accessing resources in another account.

Example:

```text
EC2 instance
     |
     v
Assumes / receives credentials for IAM role
     |
     v
IAM role policy
     |
     v
Read objects from approved S3 bucket
```

### 4.4 IAM policy

An IAM policy is a document that defines permissions.

A policy can specify:

- Which actions are allowed or denied.
- Which resources the actions apply to.
- Optional conditions that must be satisfied.

Example: Allow an application role to list one S3 bucket.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::example-app-bucket"
    }
  ]
}
```

This policy allows the `s3:ListBucket` action on the specified bucket. It does not grant permission to download objects.

## 5. IAM Users vs Groups vs Roles vs Policies

| IAM concept | What it represents | Main purpose |
|---|---|---|
| User | An identity in an AWS account | Represent a user or specific identity |
| Group | A collection of IAM users | Manage common user permissions |
| Role | An assumable identity | Provide temporary access to trusted principals |
| Policy | A permissions document | Define allowed or denied actions |

### Easy way to remember

- **User:** Who is the identity?
- **Group:** Which users share permissions?
- **Role:** Which identity can be assumed?
- **Policy:** What actions are allowed or denied?

A policy is not an identity. It is a document that describes permissions.

## 6. Types of IAM Policies

AWS supports several policy categories. This lesson introduces the most important ones.

### 6.1 Identity-based policies

Identity-based policies are attached to IAM users, groups, or roles.

They define what the identity can do.

Example:

```text
IAM Role: AppS3Reader
       |
       v
Identity-based policy
       |
       v
Allow s3:GetObject on a specific bucket path
```

### 6.2 Resource-based policies

Resource-based policies are attached to supported resources.

They define which principals can access the resource and what actions they can perform.

Examples include:

- S3 bucket policies.
- SQS queue policies.
- SNS topic policies.
- Lambda resource-based policies.

Example concept:

```text
IAM Role / AWS Account
          |
          v
   S3 bucket policy
          |
          v
   Access to bucket resource
```

A resource policy can grant access to a principal, subject to the full AWS policy evaluation process and applicable controls.

### 6.3 Managed policies

Managed policies are standalone IAM policies that can be attached to multiple identities.

Two common types:

- **AWS managed policies:** Created and maintained by AWS.
- **Customer managed policies:** Created and maintained by your organization.

Customer managed policies are useful when you need to reuse and maintain a permission set across multiple identities.

### 6.4 Inline policies

An inline policy is embedded directly in one IAM user, group, or role.

Inline policies have a one-to-one relationship with the identity they are embedded in. For reusable permissions, customer managed policies are often easier to maintain.

### 6.5 Policy comparison

| Policy type | Attached to | Main purpose |
|---|---|---|
| Identity-based | User, group, or role | Define what the identity can do |
| Resource-based | Supported AWS resource | Define who can access the resource |
| AWS managed | IAM identities | Reusable policy maintained by AWS |
| Customer managed | IAM identities | Reusable policy maintained by your organization |
| Inline | One identity | Policy embedded directly in that identity |

## 7. Anatomy of an IAM Policy

Let's examine a simple policy.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOneBucket",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": [
        "arn:aws:s3:::example-app-bucket/*"
      ]
    }
  ]
}
```

### 7.1 Policy elements

| Element | Meaning |
|---|---|
| `Version` | Policy language version |
| `Statement` | One or more permission statements |
| `Sid` | Optional statement identifier |
| `Effect` | `Allow` or `Deny` |
| `Action` | AWS API actions affected by the statement |
| `Resource` | Resources to which the statement applies |
| `Condition` | Optional conditions that affect when the statement applies |

### 7.2 Effect

Two common values:

- `Allow` — permits the specified action if no applicable control prevents it.
- `Deny` — explicitly denies the specified action.

### 7.3 Action

The `Action` element specifies API actions.

Examples:

| Action | Meaning |
|---|---|
| `s3:ListBucket` | List objects in a bucket |
| `s3:GetObject` | Read an object |
| `s3:PutObject` | Upload an object |
| `ec2:DescribeInstances` | View EC2 instance information |
| `ec2:StartInstances` | Start an EC2 instance |
| `rds:DescribeDBInstances` | View RDS instance information |

The exact permission required depends on the API operation and service behavior.

### 7.4 Resource

The `Resource` element identifies the resources to which the statement applies.

Example S3 bucket ARN:

```text
arn:aws:s3:::example-app-bucket
```

Example S3 object ARN pattern:

```text
arn:aws:s3:::example-app-bucket/*
```

The bucket ARN and object ARN are different. For example, `s3:ListBucket` normally applies to the bucket ARN, while `s3:GetObject` applies to object ARNs.

### 7.5 Condition

A `Condition` can limit when a permission applies.

For example, a policy may use conditions involving:

- Requested Region.
- Source IP address.
- Resource tags.
- Requested encryption settings.
- Principal attributes.

Conditions should be designed carefully. An incorrect condition can unintentionally block legitimate access or permit access more broadly than intended.

## 8. How AWS Evaluates Permissions — Basic Model

AWS policy evaluation can involve multiple policy types and controls. For this introductory lesson, remember these core principles:

1. By default, access is denied.
2. An applicable explicit `Deny` overrides an `Allow`.
3. An applicable `Allow` is required for the request to succeed.
4. Other controls, such as service control policies and permissions boundaries, can limit permissions.
5. Resource-based policies and cross-account access add additional evaluation details.

### 8.1 Simple examples

| Situation | Result |
|---|---|
| No applicable Allow | Denied by default |
| Applicable Allow and no applicable Deny or limiting control | Allowed |
| Applicable explicit Deny | Denied |
| Identity policy allows, but a relevant permissions boundary limits the action | Denied |
| An organization policy prevents the action | Denied |

### 8.2 Explicit Deny example

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::example-app-bucket/*"
    }
  ]
}
```

This statement explicitly denies deleting objects in the specified bucket.

An Allow statement elsewhere does not override an applicable explicit Deny.

### 8.3 Important distinction

A policy that contains an Allow statement does not guarantee that every request will succeed. Other policies, resource policies, permissions boundaries, organization controls, session policies, and service-specific rules may also affect the final decision.

## 9. Practical IAM Design for a Development Team

Imagine a team with three types of access needs:

- Developers need to inspect application resources.
- Operations engineers need to manage selected infrastructure.
- A Spring Boot application needs to read product images from S3.

A simple conceptual design:

```text
Human users
    |
    v
Federated access / IAM Identity Center
    |
    +--------------------------+
    |                          |
    v                          v
Developer permission set   Operations permission set
    |                          |
    v                          v
Read / limited access       Approved operations access


Spring Boot EC2 application
    |
    v
EC2 instance profile
    |
    v
IAM role: ProductImageReader
    |
    v
Allow s3:GetObject on approved S3 object path
```

### 9.1 Design principles

- Prefer federated access for human users where appropriate.
- Use roles for AWS workloads.
- Separate development and production access.
- Avoid sharing credentials between team members.
- Use managed policies or reusable permission sets where suitable.
- Keep permissions narrowly scoped.
- Review and remove unused permissions.

### 9.2 Example: Application role policy

A Spring Boot application needs to download product images from one bucket.

Example identity-based policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadProductImages",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": [
        "arn:aws:s3:::example-product-images/products/*"
      ]
    }
  ]
}
```

This grants object-read permission only for objects under the `products/` prefix in the named bucket.

If the application also needs to list the bucket, it may require a separate `s3:ListBucket` permission on the bucket ARN, possibly restricted with a prefix condition.

## 10. AWS CLI — Inspect IAM

The following commands are read-only inspection examples. They require appropriate IAM permissions.

### 10.1 Get the current identity

```bash
aws sts get-caller-identity
```

### 10.2 List IAM users

```bash
aws iam list-users
```

### 10.3 List IAM groups

```bash
aws iam list-groups
```

### 10.4 List IAM roles

```bash
aws iam list-roles
```

### 10.5 List managed policies

```bash
aws iam list-policies --scope Local
```

### 10.6 Get a specific role

```bash
aws iam get-role --role-name ProductImageReader
```

### 10.7 List policies attached to a role

```bash
aws iam list-attached-role-policies \
  --role-name ProductImageReader
```

### 10.8 Inspect a named profile

```bash
aws sts get-caller-identity --profile dev
```

**Important:** IAM is a global service for most identity resources. The CLI commands above do not require a Region parameter in the same way that regional services such as EC2 do.

## 11. Security Best Practices

### 11.1 Use least privilege

Grant only the permissions required for the task.

Avoid granting broad permissions such as `Action: "*"` and `Resource: "*"` unless there is a justified administrative use case with suitable controls.

### 11.2 Prefer temporary credentials

Use IAM roles and federation where possible.

Temporary credentials reduce reliance on long-lived access keys.

### 11.3 Enable MFA

Enable MFA for privileged identities and follow your organization's authentication policy.

### 11.4 Protect credentials

- Never commit access keys to Git repositories.
- Do not put credentials in Docker images.
- Avoid printing secrets in logs.
- Use a suitable secrets-management service for application secrets.
- Remove credentials that are no longer needed.

### 11.5 Review permissions

Periodically review:

- Users and groups.
- Roles and trust policies.
- Attached policies.
- Unused credentials.
- Access key age and use.
- Permissions that are broader than necessary.

### 11.6 Use separate environments

Use separate accounts or carefully isolated environments for development, testing, and production when appropriate.

### 11.7 Monitor activity

Use CloudTrail and other suitable monitoring tools to help identify unexpected API activity and investigate security events.

| A request is denied because the identity lacks permission | Authorization decision |

### Exercise 3 — Read the policy

Given:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-files/reports/*"
    }
  ]
}
```

**Question:** What can the identity do?

**Answer:** It can read objects under the `reports/` prefix in the `company-files` bucket, subject to other applicable policies and controls.

**Question:** Can it list every bucket in the account?

**Answer:** No. This policy does not grant `s3:ListAllMyBuckets` or `s3:ListBucket`.

### Exercise 4 — Choose the right identity

**Scenario:** An EC2-hosted Spring Boot application needs to read images from S3.

**Answer:** Use an IAM role attached to the EC2 instance through an instance profile. Give it only the required S3 permissions.

### Exercise 5 — Explicit Deny

**Question:** An identity has an Allow policy for `s3:DeleteObject`, but another applicable policy explicitly denies the same action. What happens?

**Answer:** The explicit Deny takes precedence, so the request is denied.

### Exercise 6 — Diagnose AccessDenied

**Question:** A developer can sign in but cannot read an S3 object. List three things to check.

**Answer:**

1. Confirm the active identity with `aws sts get-caller-identity`.
2. Check whether the identity has `s3:GetObject` permission for the correct object ARN.
3. Check the bucket policy and other applicable controls, including explicit Deny statements.

| Task | Main responsible party |
|---|---|
| Physical AWS data-centre security | AWS |
| EC2 guest OS patching | Customer |
| S3 bucket access policy | Customer |
| Physical server maintenance | AWS |

## 15. AWS Interview Questions and Answers

### Q1. What is AWS IAM?

**Answer:** IAM is an AWS service that controls access to AWS resources by managing identities, authentication, and permissions.

### Q2. What are the main IAM components?

**Answer:** The foundational components include users, groups, roles, and policies.

### Q3. What is an IAM policy?

**Answer:** It is a permissions document that defines allowed or denied actions on specified resources, optionally under specified conditions.

### Q4. What is the difference between identity-based and resource-based policies?

**Answer:** Identity-based policies are attached to identities such as users, groups, or roles. Resource-based policies are attached to supported resources and specify which principals can access them.

### Q5. What is the difference between an IAM role and an IAM user?

**Answer:** An IAM user is an account identity that may have associated credentials. An IAM role is an assumable identity that provides temporary credentials to a trusted principal.

### Q6. What is an explicit Deny?

**Answer:** An explicit Deny is a policy statement that denies a specified action. An applicable explicit Deny takes precedence over an Allow.

### Q7. What does least privilege mean?

**Answer:** It means granting only the permissions required for an identity to perform its intended tasks.

### Q8. Why should EC2 use an IAM role to access S3?

**Answer:** An IAM role provides temporary credentials and avoids storing long-lived access keys in the application or instance configuration.

### Q9. What is the difference between `s3:ListBucket` and `s3:GetObject`?

**Answer:** `s3:ListBucket` allows listing objects in a bucket and applies to the bucket ARN. `s3:GetObject` allows reading an object and applies to object ARNs.

### Q10. Does an Allow policy guarantee that an action succeeds?

**Answer:** No. An applicable explicit Deny, permissions boundary, service control policy, session policy, resource policy, or other applicable control can affect the final decision.

### Q11. What is a trust policy?

**Answer:** A role's trust policy defines which principals are allowed to assume the role.

### Q12. What is the difference between authentication and authorization?

**Answer:** Authentication verifies identity. Authorization evaluates what the identity is permitted to do.
