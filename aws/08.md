## 2. What is AWS IAM?

AWS Identity and Access Management (IAM) is an AWS service that helps you control who can access your AWS account and what they can do.

IAM stands for:

- Identity: Who is accessing AWS?
- Access: Which resources can they access?
- Management: How are permissions controlled?

For example, imagine a company has three developers:

| Employee    | Responsibility          | Required AWS access                      |
| ----------- | ----------------------- | ---------------------------------------- |
| Developer A | Backend development     | Read and upload files to S3              |
| Developer B | Database administration | Manage specific RDS resources            |
| Developer C | DevOps                  | Manage EC2 and deployment infrastructure |

You should not give all three developers full administrator access.

Instead, IAM allows you to assign different permissions according to each person's responsibilities.

### 2.1 Basic IAM architecture

```
                    AWS Account
                         |
                         v
                        IAM
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
       Users           Groups          Roles
          |              |              |
          +--------------+--------------+
                         |
                         v
                    IAM Policies
                         |
                         v
                 Permissions Evaluation
                         |
             +-----------+-----------+
             |                       |
             v                       v
           Allow                    Deny
             |                       |
             v                       v
       Access Granted           Access Rejected
```

IAM controls access to AWS resources such as:

- EC2 instances.
- S3 buckets.
- RDS databases.
- Lambda functions.
- SQS queues.
- SNS topics.
- Secrets Manager secrets.

Important: IAM is a global AWS service. IAM identities are not created separately in each Region.

# 3. The four fundamental IAM components

There are four concepts you must understand:

1. IAM User.
2. IAM Group.
3. IAM Role.
4. IAM Policy.

Let's examine each one.

## 3.1 IAM User

An IAM User is an identity within an AWS account.

It can represent a person or, in some legacy designs, an application.

An IAM user can have:

- A username.
- A password for AWS Console access.
- Access keys for programmatic access, if configured.
- Permissions through attached policies or group membership.

Example:

A company has three developers.

```
AWS Account
    |
    v
   IAM
    |
    +-- User: developer-a
    |
    +-- User: developer-b
    |
    +-- User: developer-c
```

Each developer can have different permissions.

### IAM User authentication

There are two common authentication mechanisms:

| Authentication                    | Purpose                                 |
| --------------------------------- | --------------------------------------- |
| Console password                  | Sign in to the AWS Management Console   |
| Access key ID + Secret Access Key | Programmatic access, such as CLI or SDK |

An access key consists of:

- Access Key ID.
- Secret Access Key.

Example format (illustrative only):

```
Access Key ID:     AKIAEXAMPLE123456
Secret Access Key: example-secret-value-not-real
```

Security warning

Do not put IAM access keys in:

- Java source code.
- `application.properties`.
- GitHub repositories.
- Docker images.
- Public environment files.

For human users, prefer IAM Identity Center and temporary credentials. For applications running on AWS, prefer IAM roles.

## 3.2 IAM Group

An IAM Group is a collection of IAM users.

Instead of assigning the same policy to every user individually, you can attach a policy to a group.

Example:

```
                     AWS IAM
                        |
             +----------+----------+
             |                     |
             v                     v
       Developer Group       Administrator Group
             |                     |
       +-----+-----+               |
       |     |     |               |
       v     v     v               v
      A      B     C          Admin User
```

Suppose all developers need read access to certain S3 buckets.

You can create a group called `Developers` and attach an appropriate S3 policy.

All users in the group receive permissions granted through that group policy.

### IAM Group advantages

- Easier permission management.
- Less duplicated configuration.
- Consistent access for employees with similar responsibilities.
- Easier onboarding and offboarding.

### Example

| IAM Group      | Members                 | Permissions                               |
| -------------- | ----------------------- | ----------------------------------------- |
| Developers     | Developer A, B, C       | Access to development resources           |
| DatabaseAdmins | Database administrators | Database administration                   |
| ReadOnlyUsers  | Auditors                | Read-only access                          |
| DevOps         | DevOps engineers        | Deployment and infrastructure permissions |

Important: IAM Groups contain IAM users, not other groups or IAM roles.

## 3.3 IAM Role

An IAM Role is an identity with a set of permissions that can be assumed by an authorized principal.

Unlike a typical IAM user, a role does not have permanent long-term credentials.

When someone or something assumes a role, AWS STS can provide temporary security credentials.

Roles are especially important for AWS workloads.

### Example 1: EC2 accessing S3

Imagine your Spring Boot application runs on EC2 and needs to upload images to S3.

A secure design is:

```
       Spring Boot Application
                 |
                 v
             EC2 Instance
                 |
                 v
              IAM Role
                 |
                 v
          Temporary Credentials
                 |
                 v
              Amazon S3
```

The EC2 instance receives temporary credentials through its attached IAM role.

Your Java application can use the AWS SDK's default credential provider chain to retrieve them.

You do not need to hardcode access keys.

### Example 2: Lambda accessing DynamoDB

```
          Lambda Function
                 |
                 v
            IAM Role
                 |
                 v
          Temporary Credentials
                 |
                 v
             DynamoDB
```

The Lambda execution role determines which AWS resources the function can access.

### Common IAM Role use cases

| Role                  | Purpose                                                                |
| --------------------- | ---------------------------------------------------------------------- |
| EC2 Instance Role     | Allow EC2 applications to access AWS services                          |
| Lambda Execution Role | Allow Lambda functions to access AWS services                          |
| Cross-Account Role    | Allow an authorized principal from another account to access resources |
| Service Role          | Allow an AWS service to perform authorized actions                     |

### IAM User vs IAM Role

| Feature               | IAM User                               | IAM Role                       |
| --------------------- | -------------------------------------- | ------------------------------ |
| Identity              | Persistent IAM identity                | Assumable identity             |
| Long-term credentials | Can have them                          | Does not have them             |
| Temporary credentials | Can use federation or other mechanisms | Commonly provided when assumed |
| Typical use           | Legacy or specific IAM identities      | Workloads and delegated access |
| EC2 access            | Not recommended                        | Recommended                    |
| Application access    | Avoid long-term user keys              | Recommended                    |

Remember: IAM Roles are one of the most important concepts for AWS developers.

## 3.4 IAM Policy

An IAM Policy is a JSON document that defines permissions.

A policy tells AWS:

- Which actions are allowed or denied?
- Which AWS resources are affected?
- Under what conditions does the policy apply?

Example:

Suppose a developer needs to read files from an S3 bucket.

You can create a policy allowing `s3:GetObject` on objects in a specific bucket.

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::my-company-bucket/*"
    }
  ]
}
```

Let's understand each field.

| Field       | Meaning                                      |
| ----------- | -------------------------------------------- |
| `Version`   | IAM policy language version                  |
| `Statement` | One or more permission statements            |
| `Effect`    | `Allow` or `Deny`                            |
| `Action`    | AWS API actions                              |
| `Resource`  | Resources affected by the statement          |
| `Condition` | Optional conditions for applying permissions |

### Understanding the policy

```
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-company-bucket/*"
}
```

This means:

- `Effect: Allow` — Allow the action.
- `Action: s3:GetObject` — Read an S3 object.
- `Resource` — Objects inside `my-company-bucket`.

It does not grant permission to delete objects or upload new objects.

### Common IAM actions

| AWS action              | Meaning                       |
| ----------------------- | ----------------------------- |
| `s3:GetObject`          | Download/read an object       |
| `s3:PutObject`          | Upload/write an object        |
| `s3:DeleteObject`       | Delete an object              |
| `s3:ListBucket`         | List bucket contents          |
| `ec2:DescribeInstances` | View EC2 instance information |
| `ec2:StartInstances`    | Start EC2 instances           |
| `ec2:StopInstances`     | Stop EC2 instances            |
| `lambda:InvokeFunction` | Invoke a Lambda function      |
| `dynamodb:GetItem`      | Read a DynamoDB item          |
| `dynamodb:PutItem`      | Write a DynamoDB item         |

# 4. How IAM policies work

Now let's understand how AWS evaluates permissions.

## 4.1 Identity-based policies

An identity-based policy is attached to an IAM identity:

- IAM User.
- IAM Group.
- IAM Role.

Example:

```
IAM User: developer-a
       |
       v
IAM Policy: S3ReadOnly
       |
       v
Allow s3:GetObject
       |
       v
Amazon S3
```

The policy grants the user permission to read objects from the specified S3 bucket.

## 4.2 Resource-based policies

A resource-based policy is attached directly to an AWS resource.

For example, an S3 bucket policy defines which principals can access that bucket.

Example:

```
IAM Role
    |
    v
Amazon S3 Bucket
    |
    v
Bucket Policy
    |
    v
Allow or Deny access
```

### Identity-based vs Resource-based policies

| Feature     | Identity-based policy         | Resource-based policy       |
| ----------- | ----------------------------- | --------------------------- |
| Attached to | User, group, or role          | AWS resource                |
| Controls    | What the identity can do      | Who can access the resource |
| Example     | IAM policy                    | S3 bucket policy            |
| Common use  | Grant application permissions | Control bucket access       |

## 4.3 Allow and Deny

IAM policies use two important effects:

- `Allow`
- `Deny`

Example:

```
{
  "Effect": "Deny",
  "Action": "s3:DeleteObject",
  "Resource": "arn:aws:s3:::my-company-bucket/*"
}
```

This explicitly denies deleting objects in the specified bucket.

Important IAM rule: An explicit Deny overrides an Allow.

For ordinary identity-based access evaluation, access is denied by default unless an applicable policy allows it. Other policy types, such as Service Control Policies and permissions boundaries, can further restrict access.

### Example

Imagine a user has two policies:

Policy A:

```
{
  "Effect": "Allow",
  "Action": "s3:*",
  "Resource": "*"
}
```

Policy B:

```
{
  "Effect": "Deny",
  "Action": "s3:DeleteObject",
  "Resource": "*"
}
```

Result:

| Action            | Result                                     |
| ----------------- | ------------------------------------------ |
| Read S3 objects   | Allowed                                    |
| Upload S3 objects | Allowed                                    |
| List S3 buckets   | Allowed, subject to applicable permissions |
| Delete S3 objects | Denied                                     |

Even though Policy A allows all S3 actions, Policy B explicitly denies deleting objects.

## 4.4 AWS ARN — Amazon Resource Name

An ARN uniquely identifies an AWS resource.

General format:

```
arn:partition:service:region:account-id:resource
```

Example:

```
arn:aws:s3:::my-company-bucket
```

Example for an EC2 instance:

```
arn:aws:ec2:ap-southeast-1:123456789012:instance/i-0123456789abcdef0
```

Example for an IAM role:

```
arn:aws:iam::123456789012:role/EC2S3AccessRole
```

### ARN components

| Component  | Example          | Meaning             |
| ---------- | ---------------- | ------------------- |
| Partition  | `aws`            | AWS partition       |
| Service    | `ec2`            | AWS service         |
| Region     | `ap-southeast-1` | AWS Region          |
| Account ID | `123456789012`   | AWS account         |
| Resource   | `instance/i-...` | Resource identifier |

Some services, including IAM and S3 bucket ARNs, have resource formats without a Region component.

# 5. Trust Policy vs Permissions Policy

This is an important IAM Role concept.

An IAM Role commonly has two different types of policy:

1. Trust Policy.
2. Permissions Policy.

They solve different problems.

## 5.1 Trust Policy

A trust policy determines who or what is allowed to assume a role.

Example: Allow EC2 to assume an IAM role.

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

Explanation:

| Field            | Meaning                           |
| ---------------- | --------------------------------- |
| `Principal`      | Who can assume the role           |
| `Service`        | AWS service principal             |
| `Action`         | Permission to assume the role     |
| `sts:AssumeRole` | AWS Security Token Service action |

## 5.2 Permissions Policy

A permissions policy determines what the assumed role can do.

Example:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::my-company-bucket/*"
    }
  ]
}
```

This role can upload and read objects in the specified bucket.

## 5.3 Trust Policy vs Permissions Policy

| Question              | Trust Policy          | Permissions Policy       |
| --------------------- | --------------------- | ------------------------ |
| What does it control? | Who can assume a role | What the role can do     |
| Main purpose          | Establish trust       | Grant permissions        |
| Example principal     | `ec2.amazonaws.com`   | Not usually required     |
| Example action        | `sts:AssumeRole`      | `s3:GetObject`           |
| Attached to           | IAM Role              | IAM identity or resource |

### Complete role architecture

```
              EC2 Instance
                   |
                   | 1. Requests role credentials
                   v
              IAM Role
                   |
          +--------+--------+
          |                 |
          v                 v
     Trust Policy     Permissions Policy
          |                 |
          v                 v
    EC2 can assume     S3 GetObject
       this role       S3 PutObject
          |                 |
          +--------+--------+
                   |
                   v
             Amazon S3
```

Remember:

- Trust Policy: Who can use the role?
- Permissions Policy: What can the role do?

# 6. AWS CLI practical examples

Let's use AWS CLI to explore IAM.

For these examples, assume you have an authorized development account and an AWS CLI profile named `development`.

## 6.1 Verify your AWS identity

```
aws sts get-caller-identity --profile development
```

This shows which account and identity your CLI session is using.

## 6.2 List IAM users

```
aws iam list-users --profile development
```

Example output:

```
{
  "Users": [
    {
      "UserName": "developer-a",
      "Arn": "arn:aws:iam::123456789012:user/developer-a"
    },
    {
      "UserName": "developer-b",
      "Arn": "arn:aws:iam::123456789012:user/developer-b"
    }
  ]
}
```

## 6.3 List IAM groups

```
aws iam list-groups --profile development
```

## 6.4 List IAM roles

```
aws iam list-roles --profile development
```

## 6.5 List policies attached to a user

```
aws iam list-attached-user-policies \
  --user-name developer-a \
  --profile development
```

## 6.6 List policies attached to a role

```
aws iam list-attached-role-policies \
  --role-name EC2S3AccessRole \
  --profile development
```

## 6.7 Create an IAM policy file

Create a file called `s3-read-policy.json`:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-company-bucket",
        "arn:aws:s3:::my-company-bucket/*"
      ]
    }
  ]
}
```

Create the policy:

```
aws iam create-policy \
  --policy-name S3ReadPolicy \
  --policy-document file://s3-read-policy.json \
  --profile development
```

The account will create a managed IAM policy.

## 6.8 Create a group and attach the policy

Create the group:

```
aws iam create-group \
  --group-name Developers \
  --profile development
```

Attach the policy:

```
aws iam attach-group-policy \
  --group-name Developers \
  --policy-arn arn:aws:iam::123456789012:policy/S3ReadPolicy \
  --profile development
```

Replace the example account ID with your actual AWS account ID and use the policy ARN returned when you created the policy.

Add an existing IAM user to the group:

```
aws iam add-user-to-group \
  --user-name developer-a \
  --group-name Developers \
  --profile development
```

The user now receives permissions through group membership.

These commands create persistent IAM resources and require appropriate administrative permissions. Use a dedicated training account, not a production account.

## 6.9 Test a policy with IAM Policy Simulator

You can simulate whether a policy allows a particular action.

```
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::123456789012:user/developer-a \
  --action-names s3:GetObject \
  --resource-arns arn:aws:s3:::my-company-bucket/example.jpg \
  --profile development
```

This helps troubleshoot permission problems before making real requests.

# 7. Java Spring Boot integration with AWS IAM

Now let's connect IAM with your Java development experience.

## 7.1 Scenario: Spring Boot uploads files to S3

Business requirement:

You are developing an e-commerce backend.

Your application needs to:

- Upload product images to S3.
- Download product images.
- Avoid hardcoded AWS credentials.
- Use IAM permissions to control access.

### Recommended architecture

```
              Client
                 |
                 v
          Spring Boot API
                 |
                 v
             EC2 Instance
                 |
                 v
          EC2 Instance Profile
                 |
                 v
              IAM Role
                 |
                 v
        Temporary AWS Credentials
                 |
                 v
          AWS SDK for Java v2
                 |
                 v
              Amazon S3
```

The important point is that your Spring Boot application does not need to know the permanent AWS secret access key.

## 7.2 Step 1 — Create an IAM permissions policy

Create a policy named `SpringBootS3Policy`.

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::my-company-bucket/*"
    }
  ]
}
```

This allows the application to upload and download objects.

If your application needs to list objects, add `s3:ListBucket` on the bucket ARN separately.

## 7.3 Step 2 — Attach the policy to an EC2 role

Create an IAM role named:

```
SpringBootEC2Role
```

Its trust policy allows EC2 to assume it:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

Attach `SpringBootS3Policy` to the role.

Then attach the role to your EC2 instance through an instance profile.

## 7.4 Step 3 — Add AWS SDK dependency

For Maven, add the AWS SDK v2 BOM and S3 dependency.

```
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>software.amazon.awssdk</groupId>
            <artifactId>bom</artifactId>
            <version>${aws.sdk.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>s3</artifactId>
    </dependency>
</dependencies>
```

Define `aws.sdk.version` using a current AWS SDK for Java v2 release in your Maven properties.

## 7.5 Step 4 — Configure S3Client

```
package com.example.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import software.amazon.awssdk.auth.credentials.DefaultCredentialsProvider;
import software.amazon.awssdk.regions.Region;
import software.amazon.awssdk.services.s3.S3Client;

@Configuration
public class AwsConfig {

    @Bean
    public S3Client s3Client() {
        return S3Client.builder()
                .region(Region.AP_SOUTHEAST_1)
                .credentialsProvider(
                    DefaultCredentialsProvider.create()
                )
                .build();
    }
}
```

The `DefaultCredentialsProvider` checks supported credential sources.

Depending on the environment, these can include:

- Environment credentials.
- Shared AWS configuration and credential profiles.
- IAM Identity Center credentials.
- Web identity credentials.
- Container credentials.
- EC2 instance profile credentials.

For production EC2 workloads, the instance profile is the recommended approach.

## 7.6 Step 5 — Create an S3 service

```
package com.example.service;

import org.springframework.stereotype.Service;

import software.amazon.awssdk.core.sync.RequestBody;
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.services.s3.model.PutObjectRequest;
import software.amazon.awssdk.services.s3.model.GetObjectRequest;

import java.nio.file.Path;

@Service
public class S3Service {

    private final S3Client s3Client;

    private final String bucketName = "my-company-bucket";

    public S3Service(S3Client s3Client) {
        this.s3Client = s3Client;
    }

    public void uploadFile(
            String key,
            Path filePath
    ) {
        PutObjectRequest request =
                PutObjectRequest.builder()
                        .bucket(bucketName)
                        .key(key)
                        .build();

        s3Client.putObject(
                request,
                RequestBody.fromFile(filePath)
        );
    }

    public void downloadFile(
            String key,
            Path destination
    ) {
        GetObjectRequest request =
                GetObjectRequest.builder()
                        .bucket(bucketName)
                        .key(key)
                        .build();

        s3Client.getObject(
                request,
                destination
        );
    }
}
```

## 7.7 Step 6 — Understand what happens at runtime

When your Spring Boot application calls:

```
s3Client.putObject(request, RequestBody.fromFile(filePath));
```

The flow is:

```
1. Spring Boot calls S3Client
          |
          v
2. AWS SDK requests credentials
          |
          v
3. EC2 instance profile provides
   temporary role credentials
          |
          v
4. SDK signs the AWS request
          |
          v
5. AWS evaluates IAM permissions
          |
          v
6. S3 accepts or rejects request
          |
          v
7. Result returned to Spring Boot
```

If the role has `s3:PutObject` permission on the target object, and no other applicable control blocks the request, S3 can accept the upload.

If the permission is missing, AWS may return an `AccessDenied` error.

### Important development note

When running locally, you can authenticate using an IAM Identity Center profile:

```
aws sso login --profile development
```

Then run your Spring Boot application with the profile selected:

```
$env:AWS_PROFILE="development"
$env:AWS_REGION="ap-southeast-1"
```

Your AWS SDK can use the cached SSO credentials.

Do not create permanent access keys just to make local development easier.

# 8. IAM security best practices

Before moving to exercises, let's review some important security principles.

## 8.1 Principle of Least Privilege

The Principle of Least Privilege means giving an identity only the permissions it needs to perform its tasks.

Example:

A Spring Boot application only needs to upload files to S3.

Bad policy:

```
{
  "Effect": "Allow",
  "Action": "s3:*",
  "Resource": "*"
}
```

Better policy:

```
{
  "Effect": "Allow",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::my-company-bucket/uploads/*"
}
```

The second policy restricts access to uploading objects in a specific folder.

## 8.2 Recommended IAM practices

| Best practice              | Explanation                                |
| -------------------------- | ------------------------------------------ |
| Least privilege            | Grant only necessary permissions           |
| Enable MFA                 | Add another authentication factor          |
| Use IAM roles              | Prefer temporary credentials for workloads |
| Avoid root user            | Do not use root for daily operations       |
| Rotate credentials         | Replace credentials when necessary         |
| Audit permissions          | Regularly review IAM policies              |
| Use groups                 | Manage human users by job function         |
| Avoid wildcard permissions | Restrict actions and resources             |
| Monitor activity           | Use CloudTrail to audit API activity       |

Remember: An IAM policy containing `"Action": "*"` and `"Resource": "*"` can grant extremely broad access. Avoid this unless there is a specific, justified administrative requirement.

## Exercise 5 — Real-world scenario

Scenario:

You have a Spring Boot application running on an EC2 instance.

It needs to:

- Upload images to S3.
- Download images from S3.
- Never delete images.

Which IAM permissions should you assign?

Answer

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::company-images/*"
    }
  ]
}
```

Explanation:

- `s3:PutObject`: Upload images.
- `s3:GetObject`: Download images.
- No `s3:DeleteObject`: The application is not granted permission to delete objects through this policy.

Attach this permissions policy to an IAM role trusted by EC2, then attach the role to the instance.

# 11. Interview questions and answers

## Beginner to intermediate

Q1. What is AWS IAM?

Answer:

AWS IAM is a service that allows administrators to manage identities, authentication, authorization, and permissions for accessing AWS resources.

Q2. What is the difference between an IAM User and an IAM Role?

Answer:

An IAM User is a persistent identity in an AWS account. An IAM Role is an identity that can be assumed by an authorized principal and commonly provides temporary security credentials.

Q3. What is an IAM Group?

Answer:

An IAM Group is a collection of IAM users. Administrators can attach policies to groups to manage permissions for multiple users.

Q4. What is an IAM Policy?

Answer:

An IAM Policy is a JSON document that defines permissions, including allowed or denied actions, resources, and optional conditions.

Q5. What is the Principle of Least Privilege?

Answer:

It is a security principle that grants users and applications only the permissions required to perform their tasks.

Q6. What is the difference between a Trust Policy and a Permissions Policy?

Answer:

A Trust Policy defines which principals can assume an IAM role. A Permissions Policy defines what actions the role can perform after it is assumed.

Q7. What is an IAM ARN?

Answer:

An Amazon Resource Name is a unique identifier used to identify AWS resources.

## Intermediate and advanced

Q8. Why should an EC2 application use an IAM Role instead of access keys?

Answer:

An IAM role provides temporary credentials through an EC2 instance profile. This avoids storing long-lived access keys in application code or configuration files.

Q9. What happens if one IAM policy allows an action and another explicitly denies it?

Answer:

The explicit Deny takes precedence over the Allow.

Q10. What is AWS STS?

Answer:

AWS Security Token Service provides temporary security credentials for authorized users and applications.

Q11. Can an IAM User belong to multiple groups?

Answer:

Yes. An IAM user can belong to multiple IAM groups and receive permissions from those groups.

Q12. What happens when an application tries to access S3 without the required IAM permissions?

Answer:

AWS rejects the request, typically returning an AccessDenied error.

Q13. What is the difference between identity-based and resource-based policies?

Answer:

Identity-based policies are attached to identities such as users, groups, or roles. Resource-based policies are attached to resources and define which principals can access those resources.

Q14. How would you troubleshoot an AccessDenied error in Spring Boot?

Answer:

I would check the AWS identity used by the SDK, the attached IAM role, the IAM permissions policy, the resource ARN, any explicit Deny, and applicable bucket policies or other access controls.
