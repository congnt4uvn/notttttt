## 2. Network Security in AWS

A secure network uses multiple layers of protection. No single control should be expected to solve every security problem.

A typical web application architecture:

```text
                    Internet
                       |
                       v
                Route 53 / DNS
                       |
                       v
                 CloudFront
                       |
                       v
                  AWS WAF
                       |
                       v
              Application Load Balancer
                 Public Subnets
                       |
                       v
              Spring Boot Application
                 Private Subnets
                       |
                       v
                  RDS Database
                 Private Subnets
```

The architecture can use several security controls:

- Security Groups control traffic to network interfaces and resources.
- Network ACLs control traffic entering and leaving subnets.
- AWS WAF filters HTTP and HTTPS requests.
- AWS Shield helps protect applications against DDoS events.
- AWS Network Firewall provides managed network firewall capabilities.
- VPC Flow Logs record metadata about IP traffic.
- IAM controls who can change network resources.

### Defense in depth

Defense in depth means applying multiple complementary security controls.

For example:

1. AWS WAF filters unwanted web requests.
2. The ALB Security Group allows HTTPS only from intended sources.
3. The application Security Group accepts traffic only from the ALB Security Group.
4. The database Security Group accepts traffic only from the application Security Group.
5. Private subnets reduce direct exposure.
6. IAM restricts who can modify these resources.
7. Monitoring helps detect unexpected traffic.

## 3. Security Groups

A **Security Group (SG)** is a virtual firewall associated with supported resources, such as EC2 network interfaces, load balancers, and RDS instances.

Security Groups control inbound and outbound traffic.

### Key characteristics

- Security Groups are stateful.
- They contain allow rules; there are no explicit deny rules in a Security Group.
- Return traffic for an allowed connection is automatically permitted.
- Rules can reference other Security Groups where supported.
- Multiple Security Groups can be associated with a network interface.
- All applicable rules are evaluated together.

### Example: Web application

Suppose you have:

- ALB Security Group: `sg-alb`
- Application Security Group: `sg-app`
- Database Security Group: `sg-db`

Recommended logical rules:

| Security Group | Direction | Protocol / Port | Source or destination |
|---|---|---|---|
| `sg-alb` | Inbound | TCP 443 | Approved client CIDRs or intended upstream |
| `sg-alb` | Outbound | TCP 8080 | `sg-app` |
| `sg-app` | Inbound | TCP 8080 | `sg-alb` |
| `sg-app` | Outbound | TCP 5432 | `sg-db` |
| `sg-db` | Inbound | TCP 5432 | `sg-app` |

This creates a controlled application path:

```text
Client
  |
  | HTTPS :443
  v
ALB (sg-alb)
  |
  | TCP :8080
  v
Spring Boot (sg-app)
  |
  | TCP :5432
  v
Database (sg-db)
```

The application does not need to accept inbound traffic from every IP address. It only needs to accept the intended traffic from the ALB.

### Why reference a Security Group?

Instead of allowing all addresses in a subnet, you can use a Security Group as the source of an inbound rule.

For example:

- Database inbound TCP 5432.
- Source: application Security Group.

This means the database allows connections from network interfaces associated with that Security Group, subject to the supported rule and network design.

### Stateful behavior

If an EC2 instance receives an allowed inbound TCP connection, response traffic for that connection is automatically allowed by the Security Group state tracking.

You do not need to create a separate inbound rule for the response packet.

### Common Security Group mistakes

- Allowing SSH (`22`) from `0.0.0.0/0`.
- Allowing database ports from the entire Internet.
- Allowing application ports from every VPC CIDR without a reason.
- Forgetting outbound rules when they have been restricted.
- Assuming a Security Group can deny a connection explicitly.
- Assuming a Security Group alone replaces subnet-level network controls.

## 4. Network Access Control Lists (NACLs)

A **Network ACL** is a subnet-level network filter.

NACLs evaluate inbound and outbound traffic for the subnet.

### Key characteristics

- NACLs are stateless.
- They support allow and deny rules.
- Rules are evaluated in ascending rule-number order.
- The first matching rule is applied.
- Inbound and outbound rules are evaluated separately.
- Return traffic must be allowed explicitly.
- A subnet is associated with one NACL at a time; a NACL can be associated with multiple subnets.

### Example

A public subnet NACL might include:

| Rule number | Direction | Protocol | Port range | Source / destination | Action |
|---:|---|---|---|---|---|
| 100 | Inbound | TCP | 443 | Approved client CIDRs | Allow |
| 110 | Inbound | TCP | 1024–65535 | Required client CIDRs for return traffic, if applicable | Allow |
| 120 | Inbound | All | All | `0.0.0.0/0` | Deny |
| 100 | Outbound | TCP | 443 | Approved destinations | Allow |
| 110 | Outbound | TCP | 1024–65535 | Required client CIDRs for return traffic, if applicable | Allow |
| 120 | Outbound | All | All | `0.0.0.0/0` | Deny |

This is an illustrative rule set, not a universal production template. Actual rules depend on traffic direction, subnet role, client behavior, and the ports used by the application.

### Why ephemeral ports matter

Clients and servers use temporary source ports for TCP connections. With a stateless NACL, you must allow the relevant return traffic explicitly.

A common TCP flow:

```text
Client: 198.51.100.20:53000
             |
             | Request to server TCP 443
             v
Server: 10.0.1.10:443
             |
             | Response to client port 53000
             v
Client: 198.51.100.20:53000
```

The server response is destined for the client's temporary port. If the NACL blocks that return traffic, the connection can fail even when the inbound request was allowed.

### Security Group vs NACL

| Feature | Security Group | Network ACL |
|---|---|---|
| Scope | Resource / network interface | Subnet |
| Stateful | Yes | No |
| Rules | Allow rules | Allow and deny rules |
| Rule evaluation | All applicable rules | Lowest numbered matching rule |
| Return traffic | Automatically allowed for tracked connections | Must be explicitly allowed |
| Common use | Workload-level access control | Additional subnet-level filtering |

### Practical recommendation

Use Security Groups as the primary workload-level control. Use NACLs when subnet-level filtering or explicit deny rules are needed and the operational complexity is understood.

## 5. Stateful vs Stateless

This distinction is essential when troubleshooting network traffic.

### Stateful firewall

A stateful firewall tracks connections.

Example: Security Group.

If inbound traffic is allowed and a connection is established, the response traffic is automatically allowed by the stateful control.

### Stateless firewall

A stateless firewall evaluates each packet independently.

Example: Network ACL.

You must define rules for both directions of the traffic flow.

| Concept | Stateful | Stateless |
|---|---|---|
| Tracks connections | Yes | No |
| Return traffic | Automatically permitted for tracked connections | Requires explicit rules |
| AWS example | Security Group | Network ACL |
| Rule management | Usually simpler for application flows | Requires careful bidirectional rules |

## 6. VPC Flow Logs

**VPC Flow Logs** capture metadata about IP traffic to and from supported network interfaces, subnets, or VPCs.

They help investigate network behavior and security issues.

### What information can Flow Logs contain?

Depending on the selected format, records can include:

- Source IP address.
- Destination IP address.
- Source port.
- Destination port.
- Protocol.
- Packet and byte counts.
- Start and end times.
- Action such as `ACCEPT` or `REJECT`.
- Interface identifier.
- Flow direction.
- Log status.

### Example record

The following is a simplified illustrative record:

```text
2  eni-0123456789abcdef0
198.51.100.20 10.0.2.15
53000 8080 6 12 840
1700000000 1700000060 ACCEPT OK
```

Interpretation:

- Source IP: `198.51.100.20`
- Destination IP: `10.0.2.15`
- Source port: `53000`
- Destination port: `8080`
- Protocol: `6` (TCP)
- Action: `ACCEPT`

Actual record structure depends on the Flow Logs format configured.

### ACCEPT vs REJECT

- `ACCEPT`: Traffic was accepted by the relevant network controls represented in the flow record.
- `REJECT`: Traffic was rejected by a network control.

Flow Logs do not explain every application-level failure. An `ACCEPT` record does not prove that the application successfully processed the request.

### Flow Logs destinations

Flow Logs can publish to supported destinations such as:

- Amazon CloudWatch Logs.
- Amazon S3.
- Amazon Data Firehose.

The destination affects how you query, retain, and analyze the data.

### Important limitations

VPC Flow Logs are metadata records, not packet captures.

They do not provide the full packet payload. They are not a replacement for application logs, packet analysis tools, or service-specific monitoring.

### Example use cases

1. Find rejected traffic to an application port.
2. Identify unexpected connections to a database.
3. Investigate communication between two private subnets.
4. Analyze traffic patterns during an incident.
5. Support network troubleshooting and security reviews.

## 7. Reachability Analyzer

**VPC Reachability Analyzer** analyzes whether a network path is possible between supported source and destination resources based on configuration.

It can help identify blockers such as:

- Missing routes.
- Security Group rules.
- Network ACL rules.
- Unsupported or incorrectly configured network paths.

### Example

```text
EC2 Instance
     |
     v
Route Table
     |
     v
Network Controls
     |
     v
Application Load Balancer
```

You can define a source and destination and ask the analyzer to evaluate the supported path.

### Important distinction

Reachability Analyzer is a configuration analysis tool. It is not a live packet capture and does not prove that an application is healthy.

For example, it cannot replace checking:

- Whether the application process is running.
- Whether the application listens on the expected port.
- Whether TLS certificates are valid.
- Whether the database accepts the credentials.
- Whether the application returns a successful HTTP response.

### Reachability Analyzer vs Flow Logs

| Feature | Reachability Analyzer | VPC Flow Logs |
|---|---|---|
| Main purpose | Analyze configured network reachability | Record observed IP traffic metadata |
| Method | Configuration analysis | Traffic metadata logging |
| Shows packet payload | No | No |
| Helps find missing routes | Yes, for supported paths | Can provide clues, but not configuration analysis |
| Shows accepted/rejected flow records | No | Yes, when available |
| Proves application health | No | No |

Use both tools as part of a troubleshooting process.

## 8. AWS Network Firewall

**AWS Network Firewall** is a managed network firewall service for protecting VPC traffic.

It can help inspect and control traffic using firewall policies and rule groups.

### Typical architecture

```text
                 Internet Gateway
                       |
                       v
                Inspection Subnet
                       |
                AWS Network Firewall
                       |
                       v
                 Application VPC
```

A production design needs careful route-table configuration so that the intended traffic actually passes through the firewall.

### Common capabilities

Depending on configuration and supported rule types, Network Firewall can provide:

- Stateful network traffic inspection.
- Stateless packet filtering.
- Domain-related filtering capabilities.
- Centralized firewall policies.
- Logging for monitoring and investigation.

### When might you use it?

- Centralized inspection of traffic.
- Filtering traffic between network zones.
- Inspecting egress traffic.
- Implementing network-level security policies.
- Supporting security requirements across multiple VPCs.

### Network Firewall vs Security Groups

| Feature | AWS Network Firewall | Security Group |
|---|---|---|
| Scope | Network traffic inspection and filtering architecture | Resource / network interface |
| Stateful capabilities | Yes, with supported stateful rules | Yes |
| Stateless capabilities | Yes | No |
| Typical use | Centralized network inspection | Workload-level access control |
| Management | Firewall policies and rule groups | Inbound/outbound allow rules |

Network Firewall is not a substitute for carefully designed Security Groups.

## 9. AWS WAF

**AWS WAF** is a web application firewall.

It helps protect web applications and APIs by inspecting HTTP and HTTPS requests.

### Common use cases

- Filter requests based on IP addresses.
- Apply managed rule groups.
- Detect and block common web exploits.
- Rate-limit requests.
- Filter requests using headers, URI paths, query strings, and other supported request components.

### Example

```text
Internet
   |
   v
CloudFront / Application Load Balancer / Supported Resource
   |
   v
AWS WAF
   |
   v
Spring Boot API
```

### Example policy ideas

- Allow expected API paths.
- Block requests matching known malicious patterns.
- Apply rate limits to authentication endpoints.
- Restrict administrative paths to approved sources.
- Use managed rule groups as one layer of protection.

WAF rules must be tested carefully. Overly broad rules can block legitimate users.

## 10. AWS Shield

**AWS Shield** helps protect applications against Distributed Denial of Service (DDoS) attacks.

### Shield tiers

| Service | Overview |
|---|---|
| AWS Shield Standard | Provides baseline DDoS protection for supported AWS services |
| AWS Shield Advanced | Provides enhanced DDoS protection and additional response and visibility capabilities, subject to its service terms |

### WAF vs Shield vs Network Firewall

| Service | Primary purpose |
|---|---|
| AWS WAF | Filter HTTP and HTTPS web requests |
| AWS Shield | DDoS protection |
| AWS Network Firewall | Network traffic inspection and filtering |
| Security Group | Resource-level network access control |
| Network ACL | Subnet-level stateless traffic filtering |

These services solve different problems and can be used together.

## 11. Private Subnet Access Patterns

A private subnet does not have a direct route to an Internet Gateway for direct Internet access from its resources.

However, private resources may need to access external services or AWS APIs.

### Common patterns

**NAT Gateway**

Allows resources in a private subnet to initiate supported outbound IPv4 connections to external destinations. It does not permit unsolicited inbound Internet connections to those private resources.

**VPC Gateway Endpoint**

Provides private connectivity to supported services such as Amazon S3 and DynamoDB through route-table integration.

**VPC Interface Endpoint**

Creates endpoint network interfaces in selected subnets for supported services. It uses AWS PrivateLink.

### Comparison

| Requirement | Common solution |
|---|---|
| Private instance needs outbound Internet access | NAT Gateway |
| Private instance needs S3 access | S3 Gateway Endpoint |
| Private instance needs supported AWS API access | Interface Endpoint |
| Private application needs inbound access from users | Load balancer or another approved ingress architecture |
| Private application needs access from on-premises | VPN or Direct Connect with appropriate routing |

### Security reminder

Do not use a NAT Gateway as a replacement for inbound access control. Keep application resources private and expose only the intended entry point.

## 12. Secure Spring Boot Architecture

Consider an e-commerce application with:

- Spring Boot REST API.
- Application Load Balancer.
- RDS database.
- S3 for product images.
- CloudWatch for logs and metrics.

### Architecture

```text
                        Internet
                           |
                           v
                       CloudFront
                           |
                           v
                         AWS WAF
                           |
                           v
                  Application Load Balancer
                       Public Subnets
                           |
                     HTTPS / HTTP
                           |
                           v
                   Spring Boot EC2 / ECS
                      Private Subnets
                           |
                 +---------+----------+
                 |                    |
                 v                    v
             Amazon RDS          Amazon S3
             Private DB          Gateway Endpoint
                 |
                 v
            Database Storage

       CloudWatch receives application and
       infrastructure logs and metrics.
```

### Recommended Security Group design

| Resource | Inbound | Source |
|---|---|---|
| ALB | TCP 443 | Intended client sources |
| Spring Boot | TCP 8080 | ALB Security Group |
| RDS | TCP 5432 | Application Security Group |

The database port shown is an example for PostgreSQL. Use the actual database engine and configured port.

### Spring Boot configuration

Keep secrets out of source code and version control.

Example environment-based configuration:

```yaml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
```

Use a suitable secrets-management approach, such as AWS Secrets Manager or Systems Manager Parameter Store, and grant the workload only the permissions it needs.

### Application security recommendations

1. Use HTTPS at the intended public entry point.
2. Keep application instances in private subnets where practical.
3. Allow application traffic only from the ALB Security Group.
4. Allow database traffic only from the application Security Group.
5. Use IAM roles for AWS service access instead of long-lived access keys.
6. Store secrets securely.
7. Enable appropriate logs and metrics.
8. Patch operating systems, runtimes, and dependencies.
9. Restrict administrative access.
10. Test security changes before production rollout.

### CLI safety notes

## 14. Practical Lab: Secure a Three-Tier Application

### Objective

Design a secure network for a Spring Boot application with a database.

### Requirements

- Users access the application over HTTPS.
- The ALB is in public subnets.
- Spring Boot runs in private subnets.
- RDS runs in private database subnets.
- Only the application can access the database.
- Application workloads can access S3 privately.
- Network traffic should be observable.

### Step 1 — Define the network

Example:

| Component | Example CIDR |
|---|---|
| VPC | `10.50.0.0/16` |
| Public subnet AZ A | `10.50.1.0/24` |
| Public subnet AZ B | `10.50.2.0/24` |
| Application subnet AZ A | `10.50.11.0/24` |
| Application subnet AZ B | `10.50.12.0/24` |
| Database subnet AZ A | `10.50.21.0/24` |
| Database subnet AZ B | `10.50.22.0/24` |

These are example ranges. Check for overlap with existing networks before use.

### Step 2 — Define Security Groups

**ALB Security Group**

- Inbound TCP 443 from intended clients.
- Outbound application port to the application Security Group.

**Application Security Group**

- Inbound application port only from the ALB Security Group.
- Outbound database port to the database Security Group.
- Outbound access to required AWS services through approved endpoints or egress paths.

**Database Security Group**

- Inbound database port only from the application Security Group.
- No public inbound access.

### Step 3 — Define subnet routing

- Public subnet route tables use an Internet Gateway for intended public ingress/egress.
- Private application subnet route tables use approved endpoints and, if needed, a NAT Gateway for outbound IPv4 access.
- Database subnet route tables do not provide direct Internet ingress.

### Step 4 — Add private S3 access

Create an S3 Gateway VPC Endpoint and associate it with the relevant private subnet route tables.

Review the endpoint policy and bucket policy so that access is limited to the required buckets and actions.

### Step 5 — Enable Flow Logs

Choose an appropriate scope and destination.

Decide:

- Which VPC, subnet, or network interfaces to monitor.
- Whether to capture accepted, rejected, or all traffic.
- The destination.
- Retention and access controls.
- Cost and data-volume expectations.

### Step 6 — Add web protection

Evaluate AWS WAF for the public application entry point.

Start with an appropriate rule strategy, test in a safe mode where available, review false positives, and only then enforce blocking rules.

### Step 7 — Test expected and prohibited flows

| Test | Expected result |
|---|---|
| User to ALB over HTTPS | Allowed |
| Internet directly to private application instance | Not allowed |
| ALB to Spring Boot application port | Allowed |
| Unapproved source to Spring Boot application port | Not allowed |
| Spring Boot to database port | Allowed |
| Internet directly to database | Not allowed |
| Spring Boot to S3 through endpoint | Allowed if policies permit |
| Unauthorized workload to database | Not allowed |

### Step 8 — Troubleshoot

If a test fails:

1. Confirm DNS resolution.
2. Confirm the destination IP and port.
3. Inspect subnet route tables.
4. Inspect Security Group rules.
5. Inspect NACL rules.
6. Review Flow Logs.
7. Use Reachability Analyzer for supported paths.
8. Check operating-system firewalls.
9. Check that the application listens on the expected interface and port.
10. Review application and load-balancer health logs.

### Step 9 — Document the design

Record:

- Network diagram.
- CIDR allocation.
- Security Group rules.
- NACL rules.
- Route tables.
- Endpoint policies.
- Logging destinations.
- Approved traffic flows.
- Owners and review dates.

## 15. Troubleshooting Common Network Problems

### Problem 1: Connection timed out

Possible causes:

- Missing route.
- Security Group does not allow the traffic.
- NACL blocks the request or response.
- Firewall blocks the connection.
- Destination is unavailable.
- Return path is missing.

### Problem 2: Connection refused

Possible causes:

- The destination is reachable, but no process is listening on the port.
- The application is bound to the wrong network interface.
- The service is stopped.
- A host firewall actively rejects the connection.

### Problem 3: DNS name does not resolve

Check:

- VPC DNS support and DNS hostnames settings.
- Route 53 hosted-zone records.
- Private hosted-zone VPC associations.
- Resolver rules and forwarding configuration.
- Client-side DNS configuration and cache.

### Problem 4: ALB reports unhealthy targets

Check:

- Target application is running.
- Health-check path is correct.
- Target port is correct.
- Application Security Group allows traffic from the ALB Security Group.
- Application returns the expected health-check response.
- Network ACLs permit the flow and return traffic.

### Problem 5: Database connection fails

Check:

- Database endpoint hostname.
- Database port.
- Application-to-database route.
- Database Security Group inbound rule.
- NACL rules in both directions.
- Database status.
- Credentials and TLS requirements.
- Connection pool configuration.

### Useful Linux commands

Check listening ports:

```bash
sudo ss -lntp
```

Test TCP connectivity:

```bash
nc -vz DB_HOSTNAME 5432
```

Test DNS resolution:

```bash
nslookup DB_HOSTNAME
```

Test HTTPS:

```bash
curl -Iv https://example.com
```

Check the local route table:

```bash
ip route
```

These commands should be run from an authorized host. Replace example hostnames and ports with your actual configuration.

## 16. Practical Exercises

### Exercise 1 — Security Groups

**Question:** Are Security Groups stateful or stateless?

**Answer:** Stateful. Return traffic for an allowed connection is automatically permitted by connection tracking.

### Exercise 2 — Network ACLs

**Question:** Can a Network ACL explicitly deny traffic?

**Answer:** Yes. NACLs support allow and deny rules.

### Exercise 3 — Rule order

**Question:** How are NACL rules evaluated?

**Answer:** In ascending rule-number order. The first matching rule is applied.

### Exercise 4 — Stateful vs stateless

**Question:** Why must NACL rules account for return traffic?

**Answer:** Because NACLs are stateless and evaluate inbound and outbound packets independently.

### Exercise 5 — Security Group source

**Question:** Why might you use the ALB Security Group as the source of an application Security Group rule?

**Answer:** It restricts application access to traffic originating from network interfaces associated with the ALB Security Group, rather than allowing a broad CIDR range.

### Exercise 6 — Flow Logs

**Question:** Do VPC Flow Logs capture full packet contents?

**Answer:** No. They record metadata about IP traffic, not packet payloads.

### Exercise 7 — Reachability Analyzer

**Question:** Does Reachability Analyzer prove that a Spring Boot application is healthy?

**Answer:** No. It analyzes supported network paths based on configuration. Application health must be checked separately.

### Exercise 8 — AWS WAF

**Question:** What kind of traffic does AWS WAF primarily inspect?

**Answer:** HTTP and HTTPS web requests.

### Exercise 9 — AWS Shield

**Question:** What is the main purpose of AWS Shield?

**Answer:** DDoS protection for supported AWS resources and applications.

### Exercise 10 — Network Firewall

**Question:** What is AWS Network Firewall used for?

**Answer:** Managed network traffic inspection and filtering within supported VPC architectures.

### Exercise 11 — Private S3 access

**Question:** Which VPC endpoint type is commonly used for private S3 access?

**Answer:** An S3 Gateway VPC Endpoint.

### Exercise 12 — Connection timeout

**Question:** Name four areas to inspect when a connection times out.

**Answer:** Route tables, Security Groups, NACLs, and firewall or return-path configuration. Also check DNS and destination health.

### Exercise 13 — Database security

**Question:** Should an RDS database accept inbound connections from `0.0.0.0/0`?

**Answer:** No. Restrict database access to the application or other explicitly approved sources.

### Exercise 14 — Architecture

**Question:** How would you secure a public Spring Boot application hosted on AWS?

**Answer:** Use an approved public entry point such as an ALB, apply HTTPS and WAF where appropriate, keep application instances in private subnets, restrict application access to the ALB Security Group, restrict database access to the application Security Group, and enable monitoring.

## 19. AWS Interview Questions and Answers

### Q1. What is a Security Group?

A Security Group is a stateful virtual firewall associated with supported resources or network interfaces. It controls inbound and outbound traffic using allow rules.

### Q2. Are Security Groups stateful?

Yes. Return traffic for an allowed connection is automatically permitted by the Security Group's state tracking.

### Q3. Can a Security Group have explicit deny rules?

No. Security Groups use allow rules. Traffic that is not allowed by the applicable rules is not permitted.

### Q4. What is a Network ACL?

A Network ACL is a subnet-level stateless traffic filter that supports allow and deny rules.

### Q5. How are NACL rules evaluated?

Rules are evaluated in ascending rule-number order. The first matching rule determines the action.

### Q6. What is the main difference between a Security Group and a NACL?

A Security Group is stateful and applies to supported resources or network interfaces. A NACL is stateless and applies at the subnet boundary.

### Q7. Why are ephemeral ports important for NACLs?

Because NACLs are stateless. The rules must allow the relevant return traffic, which may use temporary client-side ports.

### Q8. What are VPC Flow Logs?

Flow Logs capture metadata about IP traffic to and from supported VPC resources. They help with monitoring and troubleshooting.

### Q9. Do Flow Logs capture packet payloads?

No. They record traffic metadata rather than full packet contents.

### Q10. What does `REJECT` mean in a Flow Log record?

It indicates that the traffic was rejected by a relevant network control represented in the flow record. Further investigation is needed to identify the exact cause.

### Q11. What is Reachability Analyzer?

It analyzes supported network paths based on resource configuration and helps identify potential connectivity blockers.

### Q12. Does Reachability Analyzer test application health?

No. It does not replace application-level health checks or connectivity tests.

### Q13. What is AWS Network Firewall?

It is a managed network firewall service that supports network traffic inspection and filtering through firewall policies and rule groups.

### Q14. What is AWS WAF?

AWS WAF is a web application firewall that inspects HTTP and HTTPS requests and applies rules to help protect web applications and APIs.

### Q15. What is AWS Shield?

AWS Shield provides DDoS protection for supported AWS services. Shield Advanced offers enhanced protection and additional capabilities.

### Q16. What is the difference between WAF and Network Firewall?

WAF focuses on web requests such as HTTP and HTTPS. Network Firewall provides network-level traffic inspection and filtering.

### Q17. How do you secure an RDS database?

Place it in private subnets, avoid public accessibility unless explicitly required, restrict its Security Group to approved application sources, protect credentials, use encryption, and enable appropriate monitoring and backups.

### Q18. How would you troubleshoot an ALB target health-check failure?

Check target health details, application status, health-check path and port, application Security Group rules, NACL rules, route tables, host firewall, and application logs.

### Q19. How would you investigate rejected network traffic?

Use VPC Flow Logs to identify source, destination, ports, protocol, and action. Then inspect Security Groups, NACLs, route tables, and other relevant network controls.

### Q20. How would you secure a three-tier application?

Use a public entry layer such as an ALB, private application subnets, private database subnets, restrictive Security Groups, carefully designed NACLs, secure secrets, IAM roles, logging, and appropriate WAF or DDoS protections.
