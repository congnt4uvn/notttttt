## 2. Why Do We Need Advanced EC2 Features?

Imagine that your Spring Boot application normally receives 500 requests per minute. During a promotion, traffic increases to 10,000 requests per minute.

With one EC2 instance:

- CPU and memory may become overloaded.
- Response times may increase.
- The instance may become a single point of failure.
- You may need to manually launch more servers.

Advanced EC2 features help solve these problems.

| Problem | AWS feature |
|---|---|
| Need consistent instance configuration | Launch Template |
| Need more instances during high demand | Auto Scaling Group |
| Need to distribute traffic | Load Balancer |
| Need to replace unhealthy instances | Auto Scaling health checks |
| Need to monitor CPU and other metrics | CloudWatch |
| Need lower compute cost | Appropriate purchasing option |
| Need instances placed for a specific network/performance goal | Placement Group |

### High-level architecture

```text
                    Internet
                       |
                       v
              Application Load Balancer
                       |
              +--------+--------+
              |                 |
              v                 v
          EC2 Instance      EC2 Instance
          Spring Boot       Spring Boot
              |                 |
              +--------+--------+
                       |
                 Auto Scaling
                 Group manages
                 instance count
                       |
                       v
                 Amazon RDS
```

The load balancer distributes incoming requests. The Auto Scaling Group maintains the required number of EC2 instances and can add or remove capacity according to configured policies.

## 3. EC2 Purchasing Options

AWS offers different ways to pay for EC2 compute capacity. The best option depends on workload predictability, flexibility, and interruption tolerance.

### 3.1 On-Demand Instances

You pay for compute capacity according to the applicable usage-based pricing.

Use On-Demand when:

- You are learning AWS.
- You are developing or testing.
- Workload demand is unpredictable.
- You do not want a long-term commitment.
- You need flexibility while evaluating instance sizes.

Advantages:

- No long-term compute commitment.
- Flexible capacity selection.
- Useful for short-term and variable workloads.

Disadvantages:

- Can cost more than commitment-based options for steady usage.
- You must monitor usage and resource waste.

### 3.2 Reserved Instances

Reserved Instances provide a billing discount in exchange for a commitment with specified attributes and a term. They are not physical servers reserved exclusively for you in the ordinary meaning of the word.

They are useful when you have predictable, steady-state EC2 usage and the reservation attributes fit your workload.

Important considerations include:

- Term length.
- Payment option.
- Region or Availability Zone scope, depending on offering.
- Instance family and other matching attributes.
- Whether the reservation is Standard or Convertible.

Always compare the current offering and flexibility before committing.

### 3.3 Savings Plans

Savings Plans are a flexible pricing model based on a commitment to a consistent amount of eligible compute usage measured in dollars per hour over a term.

Common categories include:

- **Compute Savings Plans:** broader flexibility across eligible compute usage.
- **EC2 Instance Savings Plans:** narrower scope, generally tied to an instance family in a Region, with more limited flexibility.

Savings Plans are billing commitments. They do not automatically create, launch, or reserve EC2 instances.

### 3.4 Spot Instances

Spot Instances use spare AWS compute capacity and can offer substantial discounts, but AWS can interrupt them when capacity is needed or other interruption conditions apply.

Use Spot for interruption-tolerant workloads such as:

- Batch processing.
- Data analysis jobs that can checkpoint progress.
- CI/CD workers.
- Stateless, distributed compute.
- Flexible workloads that can retry.

Avoid relying only on Spot for a critical workload that cannot tolerate interruption.

### 3.5 Dedicated Hosts and Dedicated Instances

| Option | Meaning | Common reason to use |
|---|---|---|
| Dedicated Host | A physical server dedicated to your use, with visibility into host-level placement and sockets/cores | Certain licensing, compliance, or host-placement requirements |
| Dedicated Instance | EC2 instances running on hardware dedicated to a single customer | Dedicated hardware tenancy requirements |

These options are not interchangeable. Review licensing, tenancy, and compliance requirements carefully.

### Purchasing option comparison

| Option | Commitment | Interruption risk | Typical use |
|---|---|---|---|
| On-Demand | No long-term commitment | Normal EC2 operational risks | Flexible workloads |
| Reserved Instance | Term commitment | Not a Spot interruption model | Predictable usage and billing discount |
| Savings Plans | Term spend commitment | Not a Spot interruption model | Consistent compute spend |
| Spot | No long-term commitment | Can be interrupted | Fault-tolerant batch or distributed work |
| Dedicated Host | Host allocation and pricing model | Depends on configuration | Host-level licensing or compliance needs |
| Dedicated Instance | Dedicated tenancy | Depends on configuration | Dedicated hardware tenancy |

**Practical strategy:** A production system may use On-Demand or commitment-covered baseline capacity, with Spot capacity for suitable fault-tolerant workers. Do not choose solely by discount percentage; consider availability and operational design.

## 4. EC2 Placement Groups

A placement group influences how EC2 instances are placed on underlying hardware.

AWS provides three main placement group strategies.

### 4.1 Cluster placement group

Places instances close together in a single Availability Zone to support low-latency, high-throughput communication.

Useful for:

- High-performance computing.
- Tightly coupled distributed applications.
- Workloads that communicate heavily between instances.

Trade-off: concentrating instances can increase correlated failure or capacity considerations. Design for the failure characteristics of the selected Availability Zone.

### 4.2 Spread placement group

Places a small number of instances on distinct underlying hardware to reduce the chance that a hardware failure affects multiple instances.

Useful for:

- Critical individual instances.
- Small groups of important servers.
- Workloads that need separation.

### 4.3 Partition placement group

Spreads groups of instances across logical partitions. Each partition uses separate sets of racks, reducing the impact of certain correlated hardware failures.

Useful for:

- Large distributed systems.
- Hadoop, Kafka, and Cassandra-style workloads.

### Comparison

| Strategy | Main goal | Typical workload |
|---|---|---|
| Cluster | Low latency and high throughput | HPC |
| Spread | Separate instances across hardware | Critical small instance groups |
| Partition | Separate groups of instances | Large distributed systems |

Placement groups do not replace multi-AZ architecture. A cluster placement group is scoped to one Availability Zone, while resilience across AZs requires an architecture that uses multiple AZs.

## 5. Launch Templates

A **Launch Template** stores the configuration AWS should use when launching EC2 instances.

It can include:

- AMI ID.
- Instance type.
- Key pair.
- Security groups.
- Network interface settings.
- IAM instance profile.
- EBS volume mappings.
- User data.
- Tags.
- Purchasing and placement options, where supported.

### Why use a Launch Template?

Without a template, administrators may manually launch instances and accidentally configure them differently.

A Launch Template helps standardize instance creation.

```text
              Launch Template
                    |
          +---------+---------+
          |         |         |
          v         v         v
        EC2 #1    EC2 #2    EC2 #3
       Same base configuration
```

### Launch Template versions

Launch Templates support versions:

- A default version can be selected.
- A new version can introduce updated configuration.
- An Auto Scaling Group can reference a specific version or a version selection strategy.

A safe deployment process is:

1. Create a new Launch Template version.
2. Review the AMI, instance type, security groups, and user data.
3. Update the Auto Scaling Group to use the intended version.
4. Use an Instance Refresh or another controlled replacement strategy when you need existing instances to adopt the new configuration.
5. Monitor health and application metrics during rollout.

Updating a Launch Template does not automatically reconfigure every already-running EC2 instance.

## 6. Auto Scaling Groups (ASG)

An **Auto Scaling Group** manages a collection of EC2 instances.

It can:

- Maintain a target number of instances.
- Launch instances when capacity is below the desired level.
- Remove instances when capacity should decrease.
- Replace instances that fail configured health checks.
- Work with load balancers to register and deregister instances.

### Three important capacity values

| Setting | Meaning |
|---|---|
| Minimum capacity | Lowest number of instances the group should maintain |
| Desired capacity | Target number of instances |
| Maximum capacity | Highest number of instances the group may scale to |

Example:

```text
Minimum capacity: 2
Desired capacity: 2
Maximum capacity: 6
```

The group attempts to maintain two instances initially. Scaling policies can increase the desired capacity up to six or reduce it no lower than two.

### ASG architecture

```text
                 Auto Scaling Group
                 Min: 2
                 Desired: 2
                 Max: 6
                       |
          +------------+------------+
          |            |            |
          v            v            v
        EC2 #1       EC2 #2       EC2 #3
        Running      Running      Added
```

The diagram illustrates an example after scaling. The actual number depends on the current desired capacity and group state.

### Multi-AZ configuration

A production Auto Scaling Group commonly uses subnets in at least two Availability Zones.

```text
                    VPC
                     |
          +----------+----------+
          |                     |
          v                     v
      AZ: ap-southeast-1a   AZ: ap-southeast-1b
          |                     |
      Private Subnet         Private Subnet
          |                     |
        EC2 #1                EC2 #2
          |                     |
          +----------+----------+
                     |
              Auto Scaling Group
```

The group can distribute instances across the selected Availability Zones. It does not guarantee that every AZ always has identical capacity, but it can help maintain service when an instance or AZ has a problem.

### Important ASG settings

- Minimum, desired, and maximum capacity.
- VPC subnets.
- Launch Template and version.
- Health check type and grace period.
- Load balancer target group integration.
- Scaling policies.
- Instance maintenance and replacement behavior.

## 7. Auto Scaling Health Checks

Auto Scaling can use EC2 health checks and, when integrated with a load balancer, Elastic Load Balancing health checks.

### EC2 health checks

EC2 status checks help detect certain system and instance-level problems.

### Load balancer health checks

A load balancer can periodically send requests to a configured target health-check path and port.

Example:

```text
Health check path: /actuator/health
Protocol: HTTP
Port: traffic port
Expected response: successful HTTP response
```

This example assumes the Spring Boot application exposes a suitable health endpoint and that access is configured securely.

### Health check grace period

When an instance first launches, an application may need time to start. A health check grace period gives the instance time to initialize before the Auto Scaling Group treats certain health-check failures as grounds for replacement.

Set this value based on measured startup and readiness times. Do not make it unnecessarily long because that can delay detection of a genuinely unhealthy instance.

### What happens when an instance is unhealthy?

A typical sequence:

1. A health check reports the instance as unhealthy.
2. The Auto Scaling Group determines that the instance should be replaced.
3. The group terminates or replaces the unhealthy instance according to its configuration.
4. A new instance launches from the configured Launch Template.
5. The load balancer registers the new instance after it becomes eligible and healthy.

Applications should be designed so that replacing an instance does not lose important user data. Keep durable state in appropriate managed storage, not only on an individual EC2 server.

## 8. Scaling Policies

An Auto Scaling Group can change desired capacity based on policies.

### 8.1 Target tracking scaling

Target tracking tries to maintain a metric near a target value.

Example:

```text
Metric: Average CPU utilization
Target: 50%
```

If average CPU remains above the target, the group can add capacity. If it stays below the target, the group can reduce capacity, subject to its minimum and maximum settings and policy behavior.

Other supported metrics and predefined metrics can be used depending on the configuration.

Target tracking is often a good starting point for common workloads.

### 8.2 Step scaling

Step scaling responds to CloudWatch alarms and applies different capacity adjustments depending on how far a metric crosses a threshold.

Illustrative example:

| Average CPU alarm | Scaling adjustment |
|---|---|
| 60% to below 75% | Add 1 instance |
| 75% to below 90% | Add 2 instances |
| 90% or higher | Add 3 instances |

These values are examples only. Real thresholds should be based on load testing and service behavior.

### 8.3 Scheduled scaling

Scheduled scaling changes capacity at known times.

Example:

- Increase desired capacity before a daily traffic peak.
- Reduce capacity overnight.
- Increase capacity before a planned event.

Scheduled scaling is useful when demand patterns are predictable.

### Policy comparison

| Policy | Trigger | Best suited for |
|---|---|---|
| Target tracking | Metric target | Common dynamic workloads |
| Step scaling | CloudWatch alarm thresholds | Workloads needing tiered responses |
| Scheduled scaling | Time schedule | Predictable traffic patterns |

### Scaling considerations

- Scaling takes time; instances need to launch and applications need to become ready.
- CPU may not be the best metric for every application.
- Queue depth, request count, latency, or custom application metrics may be more useful.
- Scale-in can disrupt sessions or in-progress jobs if the application is not designed for graceful shutdown.
- Configure cooldown or instance warmup behavior appropriately for the selected policy.

## 9. Elastic Load Balancing (ELB)

Elastic Load Balancing distributes incoming traffic across registered targets such as EC2 instances.

It helps improve availability and scalability by directing requests to healthy targets.

### Main load balancer types

| Type | Layer / protocol focus | Common use |
|---|---|---|
| Application Load Balancer (ALB) | Layer 7, HTTP/HTTPS | Web applications, REST APIs, path/host routing |
| Network Load Balancer (NLB) | Layer 4, TCP/UDP/TLS | Very high performance, low-latency network traffic, static IP needs |
| Gateway Load Balancer (GWLB) | Network traffic inspection and appliance integration | Security appliances and traffic inspection |
| Classic Load Balancer (CLB) | Older generation | Legacy architectures; generally consider newer types for new designs |

### Application Load Balancer

ALB is commonly used for Spring Boot web applications.

It supports routing based on information such as:

- Host name.
- URL path.
- HTTP headers and other supported conditions.

Example:

```text
api.example.com/users  ---> Target Group: User Service
api.example.com/orders ---> Target Group: Order Service
```

### ALB architecture

```text
                         Internet
                            |
                            v
                 Application Load Balancer
                            |
                       Target Group
                            |
                +-----------+-----------+
                |                       |
                v                       v
             EC2 #1                  EC2 #2
          Spring Boot             Spring Boot
                |                       |
                +-----------+-----------+
                            |
                         Amazon RDS
```

The ALB is placed in suitable subnets, commonly public subnets for a public application. EC2 application instances can remain in private subnets.

### Target groups

A target group defines the destinations to which a load balancer forwards requests.

For an EC2-based application, targets are commonly registered by instance ID and port.

The target group health check determines whether a target is healthy enough to receive traffic.

### Security group design

A common secure pattern:

- ALB security group: allow inbound HTTPS from intended clients.
- EC2 application security group: allow application traffic only from the ALB security group.
- Do not allow the entire Internet to access the Spring Boot application port directly.

## 10. Amazon CloudWatch Monitoring

Amazon CloudWatch collects and monitors metrics, logs, and events from AWS resources and applications.

### EC2 metrics

Common EC2 metrics include:

- CPU utilization.
- Network in/out.
- Disk read/write activity for supported metrics.
- Status check failures.

Memory utilization is not automatically available as a standard EC2 hypervisor metric in the same way as CPU. To collect operating-system memory and other detailed metrics, install and configure the CloudWatch Agent.

### CloudWatch Alarms

An alarm watches a metric or expression and changes state when its configured condition is met.

Example:

```text
Metric: CPUUtilization
Statistic: Average
Period: 5 minutes
Threshold: Greater than 70%
Evaluation periods: 3
Action: Notify or trigger an integrated scaling workflow
```

This is an illustrative configuration, not a universal production recommendation.

### CloudWatch Logs

A Spring Boot application can send logs to CloudWatch Logs using the CloudWatch Agent, a supported logging integration, or a container/platform logging configuration.

Centralized logs help with:

- Debugging.
- Security investigations.
- Operational monitoring.
- Tracking application errors across multiple instances.

### Monitoring architecture

```text
EC2 Instances
     |
     +---- Metrics --------+
     |                     |
     +---- Logs            v
                       CloudWatch
                           |
                    +------+------+
                    |             |
                    v             v
                 Alarm        Dashboard
                    |
                    v
             Notification /
             Scaling action
```

## 11. AWS CLI: Inspect Advanced EC2 Resources

The examples use the Singapore Region, `ap-southeast-1`.

Set the Region:

```bash
aws configure set region ap-southeast-1
```

Check the current identity:

```bash
aws sts get-caller-identity
```

### List launch templates

```bash
aws ec2 describe-launch-templates \
  --query "LaunchTemplates[].[LaunchTemplateId,LaunchTemplateName,DefaultVersionNumber,LatestVersionNumber]" \
  --output table
```

### Inspect launch template versions

```bash
aws ec2 describe-launch-template-versions \
  --launch-template-id lt-REPLACE_ME
```

### List Auto Scaling Groups

```bash
aws autoscaling describe-auto-scaling-groups \
  --query "AutoScalingGroups[].[AutoScalingGroupName,MinSize,DesiredCapacity,MaxSize]" \
  --output table
```

### Inspect an Auto Scaling Group

```bash
aws autoscaling describe-auto-scaling-groups \
  --auto-scaling-group-names REPLACE_WITH_ASG_NAME
```

### List scaling policies

```bash
aws autoscaling describe-policies \
  --auto-scaling-group-name REPLACE_WITH_ASG_NAME
```

### List load balancers

```bash
aws elbv2 describe-load-balancers \
  --query "LoadBalancers[].[LoadBalancerName,Type,State.Code,DNSName]" \
  --output table
```

### List target groups

```bash
aws elbv2 describe-target-groups \
  --query "TargetGroups[].[TargetGroupName,Protocol,Port,TargetType]" \
  --output table
```

### Inspect target health

```bash
aws elbv2 describe-target-health \
  --target-group-arn REPLACE_WITH_TARGET_GROUP_ARN
```

### List CloudWatch alarms

```bash
aws cloudwatch describe-alarms \
  --query "MetricAlarms[].[AlarmName,StateValue,MetricName,Namespace]" \
  --output table
```

### Change ASG desired capacity

**Caution:** This changes the number of instances the group tries to maintain and can affect cost and availability.

```bash
aws autoscaling set-desired-capacity \
  --auto-scaling-group-name REPLACE_WITH_ASG_NAME \
  --desired-capacity 3
```

### Suspend and resume processes

Auto Scaling supports process suspension for maintenance scenarios. Use this carefully; suspending health checks or replacement processes can reduce resilience.

Do not suspend processes in production without understanding the operational impact and a clear recovery plan.

## 12. Hands-on Design Lab: Spring Boot with ALB and Auto Scaling

### Lab objective

Design a highly available architecture for a Spring Boot API using:

- A Launch Template.
- An Auto Scaling Group.
- Subnets in at least two Availability Zones.
- An Application Load Balancer.
- A Target Group.
- CloudWatch monitoring.

This lesson focuses on architecture and resource relationships. Creating all components in a live account can incur charges. Review current pricing and clean up resources after any practical deployment.

### Step 1 — Plan the network

You need:

- A VPC.
- At least two public subnets for an internet-facing ALB, in different AZs.
- At least two private subnets for EC2 application instances, in different AZs.
- Suitable route tables and network connectivity.
- Security groups for the ALB and EC2 instances.

Do not assume these resources already exist.

### Step 2 — Design security groups

**ALB security group**

| Direction | Port | Source / destination |
|---|---:|---|
| Inbound | 443 | Intended client networks; public Internet if the API is public |
| Outbound | Application port, e.g. 8080 | EC2 application security group |

**EC2 application security group**

| Direction | Port | Source / destination |
|---|---:|---|
| Inbound | 8080 | ALB security group only |
| Outbound | Required application dependencies | Restrict where practical |

Do not expose SSH to the Internet for routine administration. Consider Session Manager.

### Step 3 — Prepare the application

The Spring Boot service should:

- Listen on the intended application port.
- Expose an appropriate readiness or health endpoint.
- Handle graceful shutdown.
- Avoid storing durable user data only on the local instance.
- Send logs to a centralized destination.
- Obtain AWS credentials through an IAM role when it needs AWS services.

For example, if using Spring Boot Actuator, configure and secure a health endpoint such as `/actuator/health`. Ensure the ALB health check can reach the required endpoint.

### Step 4 — Create a Launch Template

Configure:

- A current, supported AMI.
- An appropriate instance type.
- The EC2 application security group.
- An IAM instance profile with least-privilege permissions.
- Encrypted EBS volumes.
- User data or an immutable application image.
- Tags for ownership and cost allocation.

Prefer a repeatable deployment method. For production, consider building a versioned AMI or using a container-based deployment rather than downloading an unverified artifact during every instance launch.

### Step 5 — Create a Target Group

Configure:

- Target type: Instances.
- Protocol: HTTP or HTTPS as appropriate for the target connection.
- Port: the application port.
- Health check path: a configured readiness endpoint.
- VPC: the application VPC.

Verify the target group's health-check success criteria match the application response.

### Step 6 — Create an Application Load Balancer

Configure:

- Internet-facing or internal scheme based on application requirements.
- Subnets in at least two AZs.
- ALB security group.
- HTTPS listener with a suitable TLS certificate for public production traffic.
- Listener rule forwarding to the target group.

### Step 7 — Create the Auto Scaling Group

Configure:

- The Launch Template and intended version.
- Private subnets in at least two AZs.
- Minimum capacity: 2.
- Desired capacity: 2.
- Maximum capacity: 6.
- Target group integration.
- Health check type and grace period.

The numbers are example lab settings. Adjust them to the workload and budget.

### Step 8 — Add a scaling policy

Start with a target tracking policy based on a suitable metric. Average CPU utilization can be a simple starting point, but it may not reflect application demand accurately.

For a request-driven API, consider whether request count per target, latency, queue depth, or a custom metric better represents load.

### Step 9 — Monitor the system

Create or inspect:

- EC2 CPU and network metrics.
- Auto Scaling Group activity history.
- ALB request count and target response metrics.
- Target group health.
- Application logs in CloudWatch Logs.
- CloudWatch alarms for meaningful failure or saturation conditions.

### Step 10 — Test and clean up

Test carefully in a non-production environment:

1. Confirm both instances become healthy.
2. Send requests through the ALB DNS name.
3. Stop or make one test instance unhealthy and observe replacement behavior.
4. Generate controlled test traffic and observe scaling.
5. Confirm the application remains available during replacement.
6. Delete the lab resources in dependency order when finished.

Avoid aggressive load testing against public services or systems you do not own.

## 13. Common Auto Scaling and Load Balancing Mistakes

1. Setting minimum, desired, and maximum capacity without considering cost.
2. Putting every application instance in only one Availability Zone.
3. Updating a Launch Template but assuming existing instances change automatically.
4. Using an incorrect health-check path.
5. Making the health-check grace period too short for application startup.
6. Allowing direct Internet access to application instances when only the ALB should reach them.
7. Using CPU utilization as the only scaling metric even when it does not represent user demand.
8. Scaling in while applications still have active work.
9. Forgetting that instance launch and application readiness take time.
10. Using Spot capacity for workloads that cannot tolerate interruption.
11. Ignoring Auto Scaling activity history and target health when troubleshooting.
12. Forgetting to delete test load balancers, NAT resources, EBS volumes, and other billable resources.

## 14. Practical Exercises

### Exercise 1 — On-Demand

**Question:** When is On-Demand a suitable purchasing option?

**Answer:** When you need flexibility, have unpredictable demand, or are developing and testing without a long-term commitment.

### Exercise 2 — Spot

**Question:** Why is Spot useful for batch processing?

**Answer:** It can reduce compute cost, and batch jobs can often be designed to checkpoint, retry, and tolerate interruption.

### Exercise 3 — Savings Plans

**Question:** Does purchasing a Savings Plan automatically launch EC2 instances?

**Answer:** No. A Savings Plan is a billing commitment for eligible compute usage. It does not create instances.

### Exercise 4 — Placement groups

**Question:** Which placement group strategy is designed for low-latency communication between instances?

**Answer:** Cluster placement group.

### Exercise 5 — Launch Templates

**Question:** What is the purpose of a Launch Template?

**Answer:** It stores reusable instance launch configuration so instances can be launched consistently.

### Exercise 6 — Auto Scaling

**Question:** An ASG has minimum 2, desired 3, and maximum 8. What is its target number of instances initially?

**Answer:** Three instances. The group can scale down no lower than two and up no higher than eight, subject to its configuration and capacity availability.

### Exercise 7 — Health checks

**Question:** What can happen when an instance is marked unhealthy by an integrated Auto Scaling health-check process?

**Answer:** The Auto Scaling Group can replace the unhealthy instance to help maintain the desired capacity.

### Exercise 8 — Scaling policies

**Question:** Which scaling policy attempts to maintain a metric near a configured target?

**Answer:** Target tracking scaling.

### Exercise 9 — Load balancing

**Question:** Which load balancer is commonly used for HTTP path-based routing?

**Answer:** Application Load Balancer.

### Exercise 10 — Security

**Question:** Should EC2 application instances accept port 8080 directly from the entire Internet when they are behind an ALB?

**Answer:** Usually no. The application security group should normally allow the application port only from the ALB security group.

### Exercise 11 — Monitoring

**Question:** Is EC2 memory utilization automatically available as a standard EC2 metric?

**Answer:** Not in the same way as CPU utilization. Configure the CloudWatch Agent or another supported collection method to publish operating-system memory metrics.

### Exercise 12 — Deployment

**Question:** Why should a Spring Boot application avoid storing important user data only on its EC2 local disk?

**Answer:** Auto Scaling can replace or terminate instances. Durable data should be stored in appropriate persistent or managed services.

## 17. AWS Interview Questions and Answers

### Q1. What is an Auto Scaling Group?

An Auto Scaling Group manages a collection of EC2 instances. It maintains desired capacity, can scale in or out, and can replace unhealthy instances.

### Q2. What is the difference between minimum, desired, and maximum capacity?

- Minimum: the lowest capacity the group should maintain.
- Desired: the target capacity.
- Maximum: the highest capacity the group may reach.

### Q3. What is a Launch Template?

A Launch Template stores reusable EC2 launch configuration, including the AMI, instance type, security groups, storage mappings, IAM instance profile, and user data.

### Q4. Does updating a Launch Template automatically update existing instances?

No. Existing instances do not automatically change their configuration. Use a controlled replacement process, such as an Auto Scaling Instance Refresh, when appropriate.

### Q5. What is target tracking scaling?

It is a scaling policy that adjusts capacity to keep a selected metric near a configured target.

### Q6. What is the difference between scale out and scale up?

- Scale out adds more instances.
- Scale up increases the resources of an individual instance, usually by changing to a larger instance type.

### Q7. What is an Application Load Balancer?

An ALB is a Layer 7 load balancer designed for HTTP and HTTPS traffic. It supports host-based and path-based routing.

### Q8. What is a target group?

A target group defines the targets that receive traffic from a load balancer listener rule. It also defines health-check configuration.

### Q9. How does an Auto Scaling Group replace an unhealthy instance?

When the configured health-check process identifies an instance as unhealthy, the group can replace it to maintain the desired capacity.

### Q10. What is the difference between Spot Instances and On-Demand Instances?

On-Demand provides flexible capacity without a long-term commitment. Spot uses spare capacity at a lower price but can be interrupted.

### Q11. What is a cluster placement group?

It places instances close together in one Availability Zone to support low-latency, high-throughput communication.

### Q12. Why use CloudWatch with Auto Scaling?

CloudWatch provides metrics and alarms that can help monitor system behavior and trigger scaling policies or operational notifications.

### Q13. How would you deploy a Spring Boot application with high availability?

A common design uses an ALB across multiple public subnets, an Auto Scaling Group with EC2 instances in private subnets across multiple AZs, a suitable database such as RDS, centralized logging, and health checks.

### Q14. What should you consider before using Spot Instances in production?

The application must tolerate interruption. Use checkpointing, retries, graceful shutdown, diversified capacity options, and an appropriate baseline of more reliable capacity where needed.
