## 2. What Is Workflow Orchestration?

A workflow is a sequence of steps that work together to complete a business process.

Example: an e-commerce order may require:

1. Validate the order.
2. Check inventory.
3. Process payment.
4. Reserve stock.
5. Arrange shipping.
6. Notify the customer.

If each step is implemented as unrelated service calls, it can become difficult to understand the overall process, retry failures, and track execution state.

**Workflow orchestration** coordinates the steps, their order, branching, parallel execution, and error handling.

```text
                 Order API
                     |
                     v
              Step Functions
                     |
                     v
              Validate Order
                     |
                     v
              Check Inventory
                     |
                     v
              Process Payment
                     |
                     v
              Arrange Shipping
                     |
                     v
              Send Notification
```

### Orchestration vs. choreography

| Orchestration | Choreography |
|---|---|
| A central workflow coordinates steps | Services react to events independently |
| Workflow is visible in one state machine | Process is distributed across services |
| Easier to inspect step-by-step execution | Services are more independently coordinated |
| Central workflow can become a dependency | End-to-end flow can be harder to trace |

Step Functions is an orchestration service. EventBridge, SNS, and SQS are commonly used in event-driven choreography patterns. Many real systems combine both approaches.

## 3. What Is AWS Step Functions?

AWS Step Functions is a managed workflow service that coordinates tasks across AWS services and application components.

A Step Functions workflow is called a **state machine**. It is defined using Amazon States Language (ASL), a JSON-based language.

### Core concepts

| Term | Meaning |
|---|---|
| State machine | Definition of the workflow |
| State | One step or decision in the workflow |
| Execution | One running instance of a state machine |
| Task state | Performs work, often by invoking a service or activity |
| Transition | Movement from one state to another |
| Input | Data passed into a state or execution |
| Output | Data produced by a state or execution |
| ASL | Amazon States Language, the JSON-based workflow definition |

### Example state machine

```text
Start
  |
  v
Validate Order
  |
  v
Check Inventory
  |
  +---- unavailable ----> Reject Order ----> End
  |
  v available
  |
  v
Process Payment
  |
  v
Create Shipment
  |
  v
Send Confirmation
  |
  v
Success
```

Step Functions provides execution history and visual workflow inspection in the AWS Console.

## 4. Standard vs. Express Workflows

Step Functions provides two workflow types.

| Feature | Standard | Express |
|---|---|---|
| Typical duration | Long-running workflows, up to one year | Short-running workflows, up to five minutes |
| Execution model | Exactly-once workflow execution model, with service-specific integration behavior | At-least-once or asynchronous execution options depending on invocation mode |
| Execution history | Detailed execution history in Step Functions | CloudWatch Logs are commonly used for execution diagnostics |
| Throughput | Designed for durable workflows | Designed for high-volume event processing |
| Typical use | Order processing, approvals, business workflows | High-volume event ingestion and short workflows |

### Important distinction

The Standard workflow execution model does not make every external side effect exactly once. A task may be retried, a service integration may have its own semantics, and an external API may not support idempotency.

Design tasks to be safe under retries.

### Choosing a workflow type

Choose Standard when:

- The process may run for minutes, hours, or days.
- You need detailed execution history.
- The workflow coordinates important business steps.
- You need human approval or long waits.

Choose Express when:

- The workflow is short-lived.
- The application processes a high volume of events.
- The workflow fits Express duration and execution semantics.
- CloudWatch Logs and the selected invocation mode meet your observability requirements.

## 5. Amazon States Language (ASL)

ASL defines a state machine using JSON.

A simple workflow:

```json
{
  "Comment": "Simple order workflow",
  "StartAt": "ValidateOrder",
  "States": {
    "ValidateOrder": {
      "Type": "Pass",
      "Result": {
        "valid": true
      },
      "ResultPath": "$.validation",
      "Next": "OrderAccepted"
    },
    "OrderAccepted": {
      "Type": "Succeed"
    }
  }
}
```

### Important top-level fields

| Field | Purpose |
|---|---|
| `Comment` | Optional description |
| `StartAt` | Name of the first state |
| `States` | Map of state names to state definitions |
| `TimeoutSeconds` | Optional state machine timeout |
| `Version` | ASL language version when specified |

Each state has a `Type`, such as `Task`, `Choice`, `Wait`, or `Pass`.

## 6. Important State Types

### 6.1 Pass state

A Pass state passes input through or adds a fixed result. It is useful for simple data transformations and testing.

```json
{
  "PrepareOrder": {
    "Type": "Pass",
    "Result": {
      "status": "VALIDATED"
    },
    "ResultPath": "$.validation",
    "Next": "NextStep"
  }
}
```

### 6.2 Task state

A Task state performs work, such as invoking Lambda or calling an AWS service integration.

Example using the optimized Lambda integration:

```json
{
  "ValidateOrder": {
    "Type": "Task",
    "Resource": "arn:aws:states:::lambda:invoke",
    "Parameters": {
      "FunctionName": "arn:aws:lambda:ap-southeast-1:123456789012:function:ValidateOrder",
      "Payload.$": "$"
    },
    "OutputPath": "$.Payload",
    "Next": "CheckResult"
  }
}
```

Replace the account ID and function name with real values. The Step Functions execution role needs permission to invoke the function.

### 6.3 Choice state

A Choice state branches based on input values.

```json
{
  "CheckInventory": {
    "Type": "Choice",
    "Choices": [
      {
        "Variable": "$.inventory.available",
        "BooleanEquals": true,
        "Next": "ProcessPayment"
      }
    ],
    "Default": "RejectOrder"
  }
}
```

### 6.4 Wait state

A Wait state pauses for a duration or until a specified timestamp.

```json
{
  "WaitForFiveSeconds": {
    "Type": "Wait",
    "Seconds": 5,
    "Next": "Continue"
  }
}
```

For longer business scheduling, consider whether EventBridge Scheduler or a callback pattern is more suitable.

### 6.5 Parallel state

A Parallel state runs branches concurrently and returns their results as an array.

```json
{
  "RunParallelChecks": {
    "Type": "Parallel",
    "Branches": [
      {
        "StartAt": "CheckFraud",
        "States": {
          "CheckFraud": {
            "Type": "Pass",
            "Result": {"fraudCheck": "PASSED"},
            "End": true
          }
        }
      },
      {
        "StartAt": "CheckCustomer",
        "States": {
          "CheckCustomer": {
            "Type": "Pass",
            "Result": {"customerCheck": "PASSED"},
            "End": true
          }
        }
      }
    ],
    "Next": "ContinueOrder"
  }
}
```

### 6.6 Map state

A Map state processes a collection of items. It can be useful for processing order line items, files, or records.

Conceptual example:

```json
{
  "ProcessOrderItems": {
    "Type": "Map",
    "ItemsPath": "$.items",
    "ItemProcessor": {
      "ProcessorConfig": {
        "Mode": "INLINE"
      },
      "StartAt": "ValidateItem",
      "States": {
        "ValidateItem": {
          "Type": "Pass",
          "End": true
        }
      }
    },
    "End": true
  }
}
```

Map supports different processing modes and configuration options. Distributed Map is designed for large-scale parallel processing and has additional requirements and limits.

### 6.7 Succeed and Fail states

- `Succeed` ends an execution successfully.
- `Fail` ends an execution as failed and can include an error name and cause.

## 7. Workflow Data: Input and Output

Step Functions passes JSON data between states. Understanding data flow is essential.

Important fields include:

- `InputPath`
- `Parameters`
- `ResultSelector`
- `ResultPath`
- `OutputPath`

These fields control what a state receives, how request parameters are built, and what data continues to the next state.

### Example

Input:

```json
{
  "orderId": "O501",
  "customerId": "C1001",
  "total": 125.50,
  "debug": true
}
```

A state might select only the order identifier:

```json
{
  "InputPath": "$.orderId"
}
```

A Task state can build request parameters from input:

```json
{
  "Parameters": {
    "orderId.$": "$.orderId"
  }
}
```

### Data flow summary

| Field | Purpose |
|---|---|
| `InputPath` | Selects part of the incoming state input |
| `Parameters` | Builds the request sent to a task |
| `ResultSelector` | Shapes the raw task result |
| `ResultPath` | Places the task result into the state's input |
| `OutputPath` | Selects what is passed to the next state |

Modern ASL also supports JSONata in supported state machine definitions. JSONPath examples are used throughout this lesson because they are widely recognizable. Do not mix JSONPath and JSONata syntax without configuring the state appropriately.

## 8. Error Handling: Retry and Catch

Distributed systems fail for many reasons:

- Network timeouts.
- Temporary service unavailability.
- Throttling.
- Invalid business data.
- Permission errors.

Step Functions supports `Retry` and `Catch` in states that support error handling.

### 8.1 Retry

Example:

```json
{
  "ProcessPayment": {
    "Type": "Task",
    "Resource": "arn:aws:states:::lambda:invoke",
    "Parameters": {
      "FunctionName": "arn:aws:lambda:ap-southeast-1:123456789012:function:ProcessPayment",
      "Payload.$": "$"
    },
    "Retry": [
      {
        "ErrorEquals": [
          "Lambda.ServiceException",
          "Lambda.TooManyRequestsException"
        ],
        "IntervalSeconds": 2,
        "BackoffRate": 2,
        "MaxAttempts": 3
      }
    ],
    "Next": "PaymentCompleted"
  }
}
```

This retries selected errors with exponential backoff.

### 8.2 Catch

Example:

```json
{
  "ProcessPayment": {
    "Type": "Task",
    "Resource": "arn:aws:states:::lambda:invoke",
    "Parameters": {
      "FunctionName": "arn:aws:lambda:ap-southeast-1:123456789012:function:ProcessPayment",
      "Payload.$": "$"
    },
    "Catch": [
      {
        "ErrorEquals": ["States.ALL"],
        "ResultPath": "$.error",
        "Next": "PaymentFailed"
      }
    ],
    "Next": "PaymentCompleted"
  }
}
```

A Catch handler can route execution to compensation or failure-handling logic.

### Retry vs. Catch

| Retry | Catch |
|---|---|
| Tries the failed operation again | Handles the error after it is caught |
| Useful for transient errors | Useful for fallback or compensation |
| Can use backoff and maximum attempts | Can store error information and transition |

Do not retry every error. A validation error will usually not become successful just because it is retried.

## 9. Integrating Step Functions with AWS Services

Step Functions can coordinate many AWS services using service integrations.

Common integrations:

- AWS Lambda.
- Amazon SQS.
- Amazon SNS.
- Amazon DynamoDB.
- AWS Glue.
- Amazon ECS.
- AWS Batch.
- Amazon EventBridge.
- AWS Step Functions callback patterns with supported integrations.

### Example architecture

```text
                 Spring Boot API
                       |
                       v
               Start State Machine
                       |
                       v
                Step Functions
                       |
          +------------+------------+
          |            |            |
          v            v            v
       Lambda       DynamoDB       SQS
     Validation    Save Status   Fulfillment
          |
          v
       Choice
          |
     +----+----+
     |         |
     v         v
   Success   Failure
```

### Direct service integration vs. Lambda

Use direct service integration when Step Functions can call the AWS service operation you need. This can reduce the amount of custom Lambda code.

Use Lambda when you need custom application logic, validation, or an integration that is not directly supported in the required way.

## 10. AWS CLI: Create and Run a State Machine

### 10.1 Check identity

```bash
aws sts get-caller-identity
aws configure get region
```

### 10.2 Create a state machine definition

Save this as `order-workflow.json`:

```json
{
  "Comment": "Basic order workflow",
  "StartAt": "ValidateOrder",
  "States": {
    "ValidateOrder": {
      "Type": "Pass",
      "Parameters": {
        "orderId.$": "$.orderId",
        "customerId.$": "$.customerId",
        "validated": true
      },
      "Next": "CheckOrder"
    },
    "CheckOrder": {
      "Type": "Choice",
      "Choices": [
        {
          "Variable": "$.validated",
          "BooleanEquals": true,
          "Next": "OrderAccepted"
        }
      ],
      "Default": "OrderRejected"
    },
    "OrderAccepted": {
      "Type": "Succeed"
    },
    "OrderRejected": {
      "Type": "Fail",
      "Error": "OrderValidationFailed",
      "Cause": "The order did not pass validation"
    }
  }
}
```

### 10.3 Create an execution role

The state machine needs an IAM role that Step Functions can assume. The role's trust policy must allow `states.amazonaws.com` to assume it.

A basic trust policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "states.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

Create the role and attach only the permissions required by the workflow. A Pass/Choice-only state machine needs no Lambda invocation permission, but a Task that invokes Lambda needs permission to invoke that function.

### 10.4 Create the state machine

```bash
aws stepfunctions create-state-machine \
  --name OrderWorkflow \
  --definition file://order-workflow.json \
  --role-arn "PASTE_EXECUTION_ROLE_ARN" \
  --type STANDARD \
  --region ap-southeast-1
```

Save the returned state machine ARN.

### 10.5 Start an execution

```bash
aws stepfunctions start-execution \
  --state-machine-arn "PASTE_STATE_MACHINE_ARN" \
  --name "order-O501-test-001" \
  --input '{
    "orderId": "O501",
    "customerId": "C1001"
  }' \
  --region ap-southeast-1
```

### 10.6 Describe an execution

Use the execution ARN returned by `start-execution`:

```bash
aws stepfunctions describe-execution \
  --execution-arn "PASTE_EXECUTION_ARN" \
  --region ap-southeast-1
```

### 10.7 View execution history

```bash
aws stepfunctions get-execution-history \
  --execution-arn "PASTE_EXECUTION_ARN" \
  --region ap-southeast-1
```

### 10.8 List state machines

```bash
aws stepfunctions list-state-machines \
  --region ap-southeast-1
```

**Cost note:** Step Functions pricing depends on workflow type and state transitions or duration, depending on the workflow model. Other invoked services can incur separate charges. Review current regional pricing before running production workloads.

## 11. Spring Boot Integration with AWS SDK for Java 2.x

Spring Boot can start a Step Functions execution through the AWS SDK.

### 11.1 Maven dependency

Use the AWS SDK for Java 2.x BOM and set `${aws.sdk.version}` to an approved current version.

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>software.amazon.awssdk</groupId>
            <artifactId>bom</artifactId>
            <version>${aws.sdk.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>sfn</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
</dependencies>
```

### 11.2 Configuration

```yaml
app:
  aws:
    region: ap-southeast-1
  step-functions:
    state-machine-arn: ${ORDER_STATE_MACHINE_ARN}
```

```java
@Configuration
public class StepFunctionsConfiguration {

    @Bean
    SfnClient sfnClient(
            @Value("${app.aws.region}") String region) {

        return SfnClient.builder()
                .region(Region.of(region))
                .credentialsProvider(
                    DefaultCredentialsProvider.create()
                )
                .build();
    }
}
```

Use an IAM role when the application runs on AWS. Do not hardcode access keys.

### 11.3 Request DTO

```java
public record StartOrderWorkflowRequest(
        String orderId,
        String customerId
) {}
```

### 11.4 Workflow service

```java
@Service
public class OrderWorkflowService {

    private final SfnClient sfnClient;
    private final ObjectMapper objectMapper;
    private final String stateMachineArn;

    public OrderWorkflowService(
            SfnClient sfnClient,
            ObjectMapper objectMapper,
            @Value("${app.step-functions.state-machine-arn}")
            String stateMachineArn) {
        this.sfnClient = sfnClient;
        this.objectMapper = objectMapper;
        this.stateMachineArn = stateMachineArn;
    }

    public String start(StartOrderWorkflowRequest request) {
        try {
            String input = objectMapper.writeValueAsString(request);

            StartExecutionResponse response =
                sfnClient.startExecution(
                    StartExecutionRequest.builder()
                        .stateMachineArn(stateMachineArn)
                        .input(input)
                        .build()
                );

            return response.executionArn();

        } catch (JsonProcessingException e) {
            throw new IllegalArgumentException(
                "Could not serialize workflow input", e
            );
        }
    }
}
```

For Standard workflows, execution names must be unique among running executions of the same state machine. Design naming and idempotency carefully. Express workflows use different start APIs and execution semantics.

### 11.5 Controller

```java
@RestController
@RequestMapping("/api/order-workflows")
public class OrderWorkflowController {

    private final OrderWorkflowService workflowService;

    public OrderWorkflowController(
            OrderWorkflowService workflowService) {
        this.workflowService = workflowService;
    }

    @PostMapping
    public ResponseEntity<Map<String, String>> start(
            @RequestBody StartOrderWorkflowRequest request) {

        String executionArn = workflowService.start(request);

        return ResponseEntity.accepted().body(
            Map.of("executionArn", executionArn)
        );
    }
}
```

HTTP `202 Accepted` means the workflow execution was started. It does not mean the order has completed every workflow step.

### 11.6 Suggested project structure

```text
src/main/java/com/example/orders/
|
+-- config/
|   +-- StepFunctionsConfiguration.java
|
+-- controller/
|   +-- OrderWorkflowController.java
|
+-- dto/
|   +-- StartOrderWorkflowRequest.java
|
+-- service/
    +-- OrderWorkflowService.java
```

## 12. Production Workflow Design

A practical order workflow can use the following structure:

```text
Start
  |
  v
Validate Request
  |
  v
Check Inventory
  |
  +---- Out of stock ----> Reject Order ----> End
  |
  v
Reserve Inventory
  |
  v
Process Payment
  |
  +---- Payment failed --> Release Inventory --> Notify Failure --> End
  |
  v
Create Shipment
  |
  v
Update Order Status
  |
  v
Notify Customer
  |
  v
Success
```

### Compensation and Saga pattern

A distributed workflow may complete some steps before a later step fails.

Example:

1. Inventory is reserved.
2. Payment fails.
3. Inventory reservation must be released.

The release operation is a **compensating action**. It does not roll back a distributed transaction automatically; it performs a new business operation that counteracts an earlier step.

This is related to the Saga pattern.

### Production design checklist

- Give every order a stable business identifier.
- Make tasks idempotent.
- Set state machine and task timeouts.
- Retry only transient errors.
- Use Catch for business failure and compensation.
- Store workflow status where the application needs to query it.
- Restrict the state machine execution role to required resources.
- Monitor failed and timed-out executions.
- Define how operators investigate and redrive failed workflows.
- Avoid placing sensitive data in execution input or logs unless required and protected.

## 13. Monitoring and Operations

Useful monitoring signals include:

- Executions started.
- Executions succeeded.
- Executions failed.
- Executions timed out.
- Execution throttling.
- Execution duration.
- Lambda errors and throttles for invoked functions.
- SQS queue depth and age for queue-based tasks.

Metric names and dimensions differ by workflow type and integration. Use the Step Functions console, CloudWatch metrics, and execution history together.

### Operational workflow

1. Identify the failed execution ARN.
2. Inspect execution history to locate the failed state.
3. Read the error name and cause.
4. Check the downstream service logs and metrics.
5. Determine whether the failure is transient or permanent.
6. Correct the underlying issue.
7. Retry or redrive using a controlled process.
8. Confirm that duplicate side effects cannot occur.

### Goal

### Step 1 — Create the ASL definition

Save the JSON in Section 10.2 as `order-workflow.json`.

## 15. Troubleshooting

| Symptom or error | Possible cause | What to check |
|---|---|---|
| `AccessDenied` | Execution role lacks permission | Trust policy and service action permissions |
| State machine cannot invoke Lambda | Missing Lambda invoke permission | Execution role policy and function resource policy |
| Invalid state machine definition | ASL syntax or transition error | JSON validity, state names, `Next`, `End` |
| Choice goes to default unexpectedly | Input path or type does not match | Actual execution input and Choice condition |
| Task times out | Downstream operation exceeds timeout | Task timeout, Lambda timeout, service latency |
| Retry repeats a payment | Task is not idempotent | Payment idempotency key and retry configuration |
| Execution fails after a service call | Service integration error or malformed response | Execution history and downstream logs |
| Execution name conflict | Name already used for a running Standard execution | Unique execution naming strategy |
| Workflow input is unexpectedly missing | InputPath, Parameters, ResultPath, or OutputPath issue | Inspect each state's input and output |
| Express execution history is incomplete in console | Express observability differs from Standard | CloudWatch Logs configuration and retention |

## 16. Practical Exercises with Answers

### Exercise 1 — What is workflow orchestration?

**Answer:** It is the coordination of multiple steps, decisions, and services to complete a business process.

### Exercise 2 — What is a state machine?

**Answer:** A state machine is the workflow definition that describes the states, transitions, and behavior of an execution.

### Exercise 3 — What is the difference between Standard and Express workflows?

**Answer:** Standard workflows are designed for durable, long-running workflows with detailed execution history. Express workflows are designed for high-volume, short-duration workflows with different execution and observability characteristics.

### Exercise 4 — What does a Choice state do?

**Answer:** It evaluates input conditions and chooses the next state based on the matching rule.

### Exercise 5 — What is a Parallel state?

**Answer:** It executes multiple branches concurrently and combines their results.

### Exercise 6 — What is a Map state?

**Answer:** It processes a collection of items by running a defined set of steps for each item, with supported concurrency modes.

### Exercise 7 — What is the difference between Retry and Catch?

**Answer:** Retry attempts the failed operation again. Catch routes the execution to a handler after an error is caught.

### Exercise 8 — Why should payment tasks be idempotent?

**Answer:** A task may be retried after a timeout or uncertain response. Idempotency prevents the same logical payment from being charged more than once.

### Exercise 9 — What is a compensating action?

**Answer:** It is a business operation that counteracts an earlier completed step, such as releasing reserved inventory after a payment failure.

### Exercise 10 — Does starting an execution mean the business process is complete?

**Answer:** No. It means the state machine execution has started. The workflow may still be running or may later fail.

### Question 1: What is AWS Step Functions?

**Model answer:**

AWS Step Functions is a managed workflow service. It coordinates different tasks and AWS services using a state machine. It helps me build workflows with branching, parallel execution, retries, and error handling.

### Question 2: What is a state machine?

**Model answer:**

A state machine is a definition of a workflow. It contains states and transitions. Each execution is one running instance of that workflow.

### Question 3: What is the difference between Standard and Express workflows?

**Model answer:**

Standard workflows are suitable for long-running business processes and provide detailed execution history. Express workflows are suitable for high-volume, short-running processes.

### Question 4: What is a Choice state?

**Model answer:**

A Choice state checks conditions in the input and selects the next state. For example, it can send an order to the payment step when inventory is available.

### Question 5: What is the difference between Retry and Catch?

**Model answer:**

Retry tries an operation again when an error occurs. Catch handles an error and moves the workflow to another state, such as a failure or compensation step.

### Question 6: What is a compensating action?

**Model answer:**

A compensating action reverses the business effect of an earlier step. For example, if payment fails after inventory is reserved, the workflow can release the reserved inventory.

## 19. AWS Interview Questions and Answers

**Q1. What is AWS Step Functions?**

It is a managed workflow orchestration service that coordinates tasks and AWS services using state machines.

**Q2. What is Amazon States Language?**

ASL is the JSON-based language used to define Step Functions state machines.

**Q3. What is the difference between a state machine and an execution?**

A state machine is the workflow definition. An execution is one running instance of that definition.

**Q4. What is a Task state?**

A Task state performs work, such as invoking Lambda or calling a supported AWS service integration.

**Q5. What is a Choice state?**

It evaluates conditions and routes execution to a matching next state.

**Q6. What is a Parallel state?**

It runs multiple branches concurrently and returns their results.

**Q7. What is a Map state?**

It applies a set of workflow steps to a collection of items, with supported processing modes.

**Q8. What is the difference between Retry and Catch?**

Retry repeats an operation after selected errors. Catch handles an error and transitions to a specified state.

**Q9. What is the Saga pattern?**

It is a distributed transaction pattern in which a sequence of local transactions is coordinated with compensating actions for failures.

**Q10. Why is idempotency important in workflows?**

Retries and uncertain outcomes can cause the same task to run more than once. Idempotency prevents duplicate business effects.

**Q11. When should you use Standard instead of Express?**

Use Standard for long-running, durable workflows that benefit from detailed execution history. Use Express for short-duration, high-volume workflows that fit its execution semantics.

**Q12. How can Spring Boot start a workflow?**

Use AWS SDK for Java 2.x `SfnClient` and call `startExecution` with the state machine ARN and JSON input.
