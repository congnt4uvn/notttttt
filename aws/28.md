## 2. RDS High Availability: Deployment Options

High availability means designing the database service to continue operating when certain infrastructure or database failures occur.

RDS provides several deployment options. Their architecture and capabilities depend on the database engine and deployment type.

### 2.1 Single-AZ DB instance

A Single-AZ DB instance runs in one Availability Zone.

```text
                 Application
                      |
                      v
                 RDS endpoint
                      |
                      v
                    AZ-a
                 Primary DB
```

**Advantages**
- Lower cost than many high-availability configurations.
- Simple architecture.
- Suitable for development, test, and some workloads with acceptable downtime.

**Disadvantages**
- No standby instance ready for managed Multi-AZ failover.
- An AZ or instance failure can cause longer recovery time.
- Maintenance and infrastructure events may interrupt availability.

### 2.2 Multi-AZ DB instance deployment

A traditional Multi-AZ DB instance deployment maintains a standby DB instance in another Availability Zone.

```text
                 Application
                      |
                      v
                 RDS endpoint
                      |
                +-----+-----+
                |           |
              AZ-a        AZ-b
                |           |
             Primary      Standby
                |           |
                +-- sync ---+
                 replication
```

The standby is maintained for failover and is not normally used to serve read traffic.

**Benefits**
- Managed failover for supported failure events.
- Synchronous replication in the traditional Multi-AZ DB instance architecture.
- A single database endpoint can redirect to the new primary after failover.

**Important:** Failover causes a connection interruption. Applications must reconnect and handle transient errors safely.

### 2.3 Multi-AZ DB cluster deployment

Some RDS engines support Multi-AZ DB cluster deployments with a different architecture, commonly involving a writer and readable instances across multiple Availability Zones.

```text
                 Application
                      |
                Cluster endpoint
                      |
          +-----------+-----------+
          |           |           |
        AZ-a        AZ-b        AZ-c
          |           |           |
        Writer      Reader      Reader
          \           |           /
           \---- cluster storage /
```

The exact number of instances, endpoints, read capabilities, and replication design depend on the engine and deployment type. Do not assume every RDS engine supports the same cluster model.

### 2.4 Compare deployment types

| Deployment | Main purpose | Read scaling | Availability |
|---|---|---|---|
| Single-AZ DB instance | Basic database hosting | No built-in replica | Lower |
| Traditional Multi-AZ DB instance | High availability and failover | Standby not normally readable | Higher |
| Multi-AZ DB cluster | High availability with cluster architecture | Readable instances may be available | Higher |
| Read replica | Scale read workloads | Yes | Can be promoted, but not equivalent to automatic Multi-AZ standby behavior |

Choose based on workload, recovery objectives, supported engine features, and cost.

## 3. Read Replicas: Creation, Use, and Promotion

A read replica receives changes from a source DB instance and can serve read-only queries.

### 3.1 Architecture

```text
                   Application
                        |
             +----------+----------+
             |                     |
          Write path             Read path
             |                     |
             v                     v
         Primary DB          Read Replica
             |                     ^
             +--- replication -----+
```

### 3.2 Common use cases

- Reporting dashboards.
- Search and browse workloads.
- Read-heavy APIs.
- Separating analytical queries from transactional queries.
- Some cross-Region data access patterns.

### 3.3 Replication lag

Many RDS read replica configurations use asynchronous replication. The replica may temporarily lag behind the primary.

Example:

```text
10:00:00 — Write order 500 to primary
10:00:01 — Application reads from replica
10:00:03 — Replica receives the change
```

If the application reads from the replica before replication catches up, it may see stale data.

Use the primary for consistency-sensitive reads, such as immediately reading a record after creating it, unless your application explicitly handles replica lag.

### 3.4 Create a read replica

Illustrative AWS CLI command:

```bash
aws rds create-db-instance-read-replica \
  --region ap-southeast-1 \
  --db-instance-identifier app-mysql-read-1 \
  --source-db-instance-identifier app-mysql-db \
  --db-instance-class db.t3.micro
```

The source and replica must meet engine, Region, encryption, and other service requirements. Confirm current limitations before creating a production replica.

Inspect instances:

```bash
aws rds describe-db-instances \
  --region ap-southeast-1 \
  --query "DBInstances[*].[DBInstanceIdentifier,ReadReplicaSourceDBInstanceIdentifier,DBInstanceStatus]"
```

### 3.5 Promote a read replica

Promotion turns a read replica into an independent writable DB instance.

```bash
aws rds promote-read-replica \
  --region ap-southeast-1 \
  --db-instance-identifier app-mysql-read-1
```

Promotion is an operational recovery or migration action, not a transparent substitute for a normal read endpoint. Plan application endpoint changes, data consistency, DNS behavior, and the fate of the former source.

### 3.6 Read routing in Spring Boot

A simple architecture can route:
- Writes to the primary endpoint.
- Read-only reporting queries to a replica endpoint.

Be careful with transactions. A transaction that writes to the primary and then reads from a replica may not see the new data immediately.

## 4. RDS Proxy

**Amazon RDS Proxy** is a managed database proxy that sits between applications and supported RDS or Aurora databases.

It helps manage database connections, especially when applications create many short-lived connections or scale rapidly.

### 4.1 Architecture

```text
        Spring Boot instances
          /      |      \
         /       |       \
        v        v        v
             RDS Proxy
                 |
                 v
             Amazon RDS
```

### 4.2 Why use RDS Proxy?

Applications running on EC2, ECS, EKS, or Lambda may create many database connections.

Without connection management:

```text
App instance 1 ----\
App instance 2 -----+---- Many connections ----> RDS
App instance 3 ----/
```

With a proxy:

```text
App instances
      |
      v
   RDS Proxy
      |
      v
  Managed backend
  connection pool
      |
      v
     RDS
```

Potential benefits:
- Connection pooling and reuse.
- Reduced connection-management overhead.
- Improved application resilience during certain database failover scenarios.
- Better handling of bursty connection demand.

RDS Proxy does not make an overloaded database infinitely scalable. Query workload, database capacity, transaction behavior, and connection limits still matter.

### 4.3 Connection pooling vs. RDS Proxy

| Feature | HikariCP in Spring Boot | RDS Proxy |
|---|---|---|
| Location | Inside application process | Managed AWS service |
| Pools connections | Yes | Yes, across clients |
| Controls app-to-proxy connections | Yes | Not applicable |
| Manages backend DB connections | No, directly connects to DB | Yes |
| Useful across many app instances | Each instance has its own pool | Shared proxy layer |

They can be used together. Tune both layers to avoid excessive connections and unexpected queueing.

### 4.4 RDS Proxy considerations

- Supported engines and authentication methods vary.
- Configure an appropriate Secrets Manager secret or supported IAM authentication flow.
- Set the proxy's VPC subnets and security groups correctly.
- Allow application traffic to the proxy and proxy traffic to the database.
- Monitor connection borrow latency, client connections, and database connections.
- Some session behavior or SQL features can reduce connection multiplexing.

## 5. AWS Secrets Manager for Database Credentials

Do not store database passwords in source code or commit them to Git.

AWS Secrets Manager can store and manage secrets such as database credentials.

### 5.1 Architecture

```text
Spring Boot application
          |
          | IAM role
          v
   Secrets Manager
          |
          | Retrieve secret
          v
   Database username/password
          |
          v
       Amazon RDS
```

### 5.2 Benefits

- Centralized secret storage.
- IAM-controlled access.
- Secret rotation capabilities for supported configurations.
- Auditability through AWS logging services.
- Reduced risk of credentials being embedded in application artifacts.

### 5.3 Create a secret

For a learning environment, the console is a practical way to create a secret. RDS can also manage the master user password in Secrets Manager for supported configurations.

Do not place real passwords directly into shell commands that may be recorded in terminal history or logs.

Inspect secret metadata:

```bash
aws secretsmanager describe-secret \
  --region ap-southeast-1 \
  --secret-id app/database/credentials
```

Retrieve a secret value only from an authorized environment:

```bash
aws secretsmanager get-secret-value \
  --region ap-southeast-1 \
  --secret-id app/database/credentials
```

Be careful: command output can expose credentials in terminal history, logs, or screenshots. Avoid printing secrets in production troubleshooting.

### 5.4 IAM permissions

An application role should receive only the required permission to retrieve the specific secret, for example `secretsmanager:GetSecretValue` on one secret ARN. If the secret uses a customer-managed KMS key, the role may also need appropriate `kms:Decrypt` permission.

### 5.5 Rotation

Rotation changes credentials according to a configured workflow.

Plan for:
- Application refresh of credentials.
- Connection pool behavior.
- Database user permissions.
- Rotation failure monitoring.
- Avoiding downtime during credential changes.

Do not assume an application automatically reloads a changed secret. Implement a supported refresh strategy or restart/redeploy workflow.

## 6. IAM Database Authentication

Some RDS engines support IAM database authentication.

Instead of relying only on a long-lived database password, an authorized application can generate a short-lived authentication token and use it when opening a database connection.

### 6.1 Concept

```text
Spring Boot application
          |
          | IAM role credentials
          v
      AWS IAM
          |
          | Generate DB auth token
          v
      RDS endpoint
          |
          v
     Database user
```

### 6.2 Important points

- Support varies by database engine and version.
- The database user must be configured for IAM authentication.
- The application role needs the required `rds-db:connect` permission for the DB resource and user.
- Tokens are short-lived and used during connection establishment.
- TLS configuration is important.
- Connection pools must handle token refresh for new connections.

IAM database authentication is not the same as using IAM permissions for every SQL query. Once connected, database-level privileges still control SQL operations.

## 7. Parameter Groups and Database Tuning

A DB parameter group defines supported engine settings.

Examples of areas that may be configurable:
- Connection limits.
- Logging.
- Query behavior.
- Time zone.
- Memory-related settings.
- Engine-specific features.

### 7.1 Parameter group workflow

```text
Create parameter group
         |
         v
Change selected parameters
         |
         v
Associate with DB instance
         |
         v
Apply immediately or during maintenance
         |
         v
Reboot if required
```

### 7.2 Dynamic vs. static parameters

- **Dynamic parameters:** Can often be applied without a reboot.
- **Static parameters:** Usually require a DB instance reboot.

Check the parameter's apply type and allowed values before changing it.

### 7.3 Inspect parameter groups

```bash
aws rds describe-db-parameter-groups \
  --region ap-southeast-1
```

Inspect parameters in a group:

```bash
aws rds describe-db-parameters \
  --region ap-southeast-1 \
  --db-parameter-group-name app-mysql-params
```

### 7.4 Safe tuning process

1. Measure the current behavior.
2. Identify a specific bottleneck.
3. Review the engine documentation.
4. Change one or a small number of parameters.
5. Apply in a test environment.
6. Observe metrics and query behavior.
7. Roll back if results are worse.
8. Document the change.

Do not increase connection limits or memory-related parameters without understanding the DB instance's capacity.

## 8. Monitoring: CloudWatch and Database Performance Tools

Monitoring helps identify whether a database is limited by CPU, memory, storage, connections, locks, or query design.

### 8.1 CloudWatch metrics

Useful RDS metrics include:

| Metric | What it helps identify |
|---|---|
| CPUUtilization | CPU pressure |
| FreeableMemory | Memory availability |
| FreeStorageSpace | Remaining allocated storage |
| DatabaseConnections | Connection count |
| ReadIOPS / WriteIOPS | Storage operation rate |
| ReadLatency / WriteLatency | Storage latency |
| ReadThroughput / WriteThroughput | Storage throughput |
| ReplicaLag | Read replica delay, where applicable |

Metric availability and names can vary by engine and deployment type.

### 8.2 Enhanced Monitoring

Enhanced Monitoring provides operating-system-level metrics for the DB instance, such as CPU, memory, and process information, at a configurable granularity.

It complements CloudWatch database metrics rather than replacing them.

### 8.3 Performance Insights and current database insights capabilities

AWS has evolved its database performance analysis capabilities over time. Depending on engine, Region, and current service configuration, you may encounter Performance Insights or newer CloudWatch Database Insights experiences.

These tools help analyze:
- Database load.
- SQL statements contributing to load.
- Wait events.
- Top users or hosts.
- Performance trends.

Check current AWS service documentation and console labels for the selected engine and Region.

### 8.4 Query plan

Use the database engine's query-plan tools to understand query execution.

For MySQL:

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 1001;
```

For PostgreSQL:

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 1001;
```

Use `EXPLAIN ANALYZE` only when appropriate because it executes the query in PostgreSQL. Be careful with expensive or modifying statements.

## 9. Maintenance, Upgrades, and Failover Testing

RDS maintenance can include:
- Database engine minor version updates.
- Operating system maintenance.
- Hardware or infrastructure maintenance.
- Applying pending modifications.
- Certificate updates.

### 9.1 Maintenance window

Choose a maintenance window that minimizes business impact. Maintenance behavior depends on the type of change and deployment configuration.

### 9.2 Engine upgrades

Before an engine upgrade:

1. Read the engine upgrade notes.
2. Confirm supported upgrade paths.
3. Test application compatibility.
4. Review deprecated features and parameter changes.
5. Create a snapshot or verify backup availability.
6. Test restore and rollback procedures.
7. Schedule a controlled maintenance window.
8. Monitor after the upgrade.

### 9.3 Failover testing

A failover test validates that:
- The application detects lost connections.
- The connection pool discards stale connections.
- The application reconnects.
- Retry logic does not duplicate transactions.
- Monitoring and alerts work.
- Recovery time meets the target.

Perform tests in a non-production environment first. In production, use a formally approved change plan and communicate expected impact.

### 9.4 Failover behavior

During failover:
- Existing connections can break.
- DNS resolution and client caches can affect reconnection time.
- Connection pools may temporarily contain stale connections.
- In-flight transactions can fail and need application-level handling.

Do not assume a failover is completely invisible to the application.

## 10. Spring Boot Production Database Patterns

### 10.1 Use a stable endpoint

Use the RDS endpoint or RDS Proxy endpoint in configuration. Do not hard-code an IP address.

```yaml
spring:
  datasource:
    url: jdbc:mysql://${DB_ENDPOINT}:3306/appdb
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
```

### 10.2 Connection pool sizing

Assume:
- Maximum EC2 application instances: 6.
- Hikari maximum pool size: 8 per instance.

The theoretical maximum is:

```text
6 × 8 = 48 application connections
```

Also account for:
- RDS Proxy backend connections if used.
- Administrative connections.
- Migration jobs.
- Monitoring.
- Other applications.

Set limits based on database capacity and actual workload.

### 10.3 Timeouts and retries

Configure:
- Connection timeout.
- Query timeout where appropriate.
- Transaction timeout.
- Retry with exponential backoff for suitable transient failures.

Do not retry every SQL exception. A constraint violation or invalid query is not a transient network problem.

### 10.4 Transaction boundaries

Use Spring's `@Transactional` for clear business operations.

Example:

```java
@Service
public class TransferService {

    private final AccountRepository accountRepository;

    public TransferService(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    @Transactional
    public void transfer(
            Long fromId,
            Long toId,
            BigDecimal amount) {

        Account from = accountRepository.findById(fromId)
                .orElseThrow();

        Account to = accountRepository.findById(toId)
                .orElseThrow();

        from.debit(amount);
        to.credit(amount);

        accountRepository.save(from);
        accountRepository.save(to);
    }
}
```

This is a simplified example. A production transfer must validate positive amounts, concurrency, account state, currency, authorization, and sufficient balance. Use appropriate locking or atomic database updates to prevent race conditions.

### 10.5 Schema migration strategy

For rolling deployments, use an expand-and-contract approach:

1. Add a backward-compatible column or table.
2. Deploy code that can work with old and new schema.
3. Backfill data if needed.
4. Switch application behavior.
5. Remove old schema only after all old application versions are gone.

This reduces the risk of one application version failing while another is still running.

## 12. Hands-on Lab — Improve a Spring Boot RDS Architecture

### Goal

Extend the private RDS design from Day 27 with better connection management, secret handling, monitoring, and recovery planning.

### Step 1 — Review the existing database

Record:
- Engine and version.
- Instance class.
- Storage type and size.
- VPC and subnet group.
- Security groups.
- Backup retention.
- Encryption configuration.
- Current endpoint.

### Step 2 — Create a least-privilege application user

Do not use the master database account for normal application traffic.

Create a dedicated database user and grant only the permissions required by the application schema.

### Step 3 — Store credentials securely

1. Create a Secrets Manager secret.
2. Store the application database username and password.
3. Attach an IAM role to the application.
4. Allow retrieval of only the required secret.
5. Confirm the application does not log the secret.

### Step 4 — Review connection pooling

Set a reasonable HikariCP pool size. Calculate the maximum total connections across all possible application instances.

### Step 5 — Evaluate RDS Proxy

If the workload has many short-lived or bursty connections, evaluate whether RDS Proxy is appropriate for the engine and application.

Do not add a proxy without a measured reason. It adds cost and another component to monitor.

### Step 6 — Configure monitoring

Review CloudWatch metrics for:
- CPU utilization.
- Freeable memory.
- Free storage.
- Database connections.
- Read/write latency.
- Replica lag if using a replica.

Create alarms based on workload-specific thresholds.

### Step 7 — Test backup recovery

In a disposable environment:
1. Create a manual snapshot.
2. Restore it to a new DB instance.
3. Verify database contents.
4. Measure the time needed.
5. Document the recovery process.

### Step 8 — Plan failover

If the selected deployment supports a controlled failover test, perform it in a non-production environment. Observe application connection errors and recovery.

### Step 9 — Document RPO and RTO

Define:
- Maximum acceptable data loss.
- Maximum acceptable recovery time.
- Backup retention.
- Escalation owner.
- Recovery verification steps.

### Step 10 — Cleanup

Remove test proxies, replicas, restored DB instances, snapshots, secrets, and monitoring resources only after confirming they are not needed. Review all related charges.

## 13. Troubleshooting

| Symptom | Possible cause | What to inspect |
|---|---|---|
| Replica data is stale | Replication lag | Replica lag and query routing |
| Replica cannot be created | Unsupported configuration or permissions | Engine, source state, encryption, quotas |
| Promotion causes application outage | Endpoint and connection handling not updated | DNS, application configuration, transactions |
| RDS Proxy connection failure | Security group, subnet, authentication, or secret issue | Proxy status, target health, IAM and secret |
| Too many database connections | Pool sizes too large or clients not closing connections | Hikari metrics, RDS connections, proxy metrics |
| Secret retrieval denied | Missing IAM or KMS permission | Role policy and secret encryption key |
| IAM DB authentication fails | Missing `rds-db:connect` or DB user setup | IAM resource ARN, DB user, token, TLS |
| Parameter change not applied | Static parameter requires reboot | Parameter apply type and pending changes |
| High CPU | Expensive queries or insufficient capacity | Query insights, execution plans, CPU metrics |
| Failover causes long recovery | Stale pool connections or retry design | DNS caching, pool validation, retry behavior |
| Upgrade fails | Unsupported path or incompatible parameter | Upgrade notes, engine version, parameter group |

### Debugging checklist

1. Confirm DB instance or cluster status.
2. Check RDS events and pending modifications.
3. Confirm endpoint, port, and DNS resolution.
4. Check security groups and network routes.
5. Verify IAM and Secrets Manager permissions.
6. Check database user privileges.
7. Inspect HikariCP active, idle, and pending connections.
8. Review CloudWatch and database performance metrics.
9. Check query plans and lock waits.
10. Verify backup and failover behavior in a controlled environment.

## 14. Exercises with Answers

### Exercise 1 — Multi-AZ

What is the primary purpose of a traditional Multi-AZ DB instance deployment?

**Answer:** High availability and managed failover. The standby is not normally used for read traffic.

### Exercise 2 — Read replica

Why might a read replica return stale data?

**Answer:** Replication is often asynchronous, so changes made on the primary may take time to reach the replica.

### Exercise 3 — Promotion

What happens when a read replica is promoted?

**Answer:** It becomes an independent writable DB instance. Applications and operational procedures may need to be updated to use its endpoint.

### Exercise 4 — RDS Proxy

What problem does RDS Proxy help solve?

**Answer:** It manages and reuses database connections across application clients, which can help workloads with frequent connection creation or bursty scaling.

### Exercise 5 — Secrets Manager

Why should a Spring Boot application retrieve credentials from a secret store instead of a Git repository?

**Answer:** It reduces the risk of long-lived credentials being exposed in source code and allows access to be controlled and audited.

### Exercise 6 — IAM database authentication

Does IAM database authentication replace SQL database permissions?

**Answer:** No. IAM controls the ability to authenticate to the database. Database grants still control which SQL operations the connected user can perform.

### Exercise 7 — Parameter groups

Why might a parameter change require a reboot?

**Answer:** Some engine parameters are static and can only be applied when the database process restarts.

### Exercise 8 — Monitoring

Which metric can help identify whether the database is running out of storage?

**Answer:** `FreeStorageSpace`.

### Exercise 9 — Connection pool

Six application instances each have a maximum Hikari pool size of 12. What is the theoretical maximum application connection count?

**Answer:** 6 × 12 = 72 connections, excluding other database clients.

### Exercise 10 — Failover

Why should the application not blindly retry every failed transaction?

**Answer:** Some operations may already have committed even if the client did not receive the response. Blind retries can duplicate business actions. Use idempotency keys or transaction-aware recovery where appropriate.

## 16. English Speaking Practice

Read each question aloud, then practice the model answer.

### Q1. What is the difference between Multi-AZ and a read replica?

**Model answer:**

Multi-AZ is mainly used for high availability and failover. A read replica is mainly used to scale read workloads. A read replica may have replication lag.

### Q2. What is RDS Proxy?

**Model answer:**

RDS Proxy is a managed database proxy. It helps manage and reuse database connections between applications and supported RDS databases.

### Q3. Why should we use Secrets Manager?

**Model answer:**

Secrets Manager stores sensitive information such as database credentials. It allows us to control access and manage credential rotation.

### Q4. What is IAM database authentication?

**Model answer:**

IAM database authentication allows supported database users to authenticate using short-lived tokens generated with AWS IAM credentials.

### Q5. What is a DB parameter group?

**Model answer:**

A DB parameter group contains database engine configuration settings. Some changes apply immediately, while others require a database reboot.

### Q6. How do you monitor RDS performance?

**Model answer:**

I monitor CPU, memory, storage, connections, IOPS, and latency using CloudWatch and database performance tools. I also inspect slow queries and execution plans.

### Q7. What happens during an RDS failover?

**Model answer:**

RDS switches database operation to the supported standby or cluster member. Existing connections may be interrupted, so the application must reconnect safely.

### Q8. How do you prepare a database for a major upgrade?

**Model answer:**

I review the supported upgrade path, test application compatibility, create or verify backups, test restoration, and schedule the upgrade during an approved maintenance window.

## 17. AWS Interview Questions and Answers

### 1. What is the difference between Single-AZ and Multi-AZ?

**Answer:** Single-AZ uses one Availability Zone for the DB instance. Multi-AZ provides a higher-availability architecture with standby or cluster resources across multiple AZs, depending on deployment type.

### 2. Does a traditional Multi-AZ standby serve read traffic?

**Answer:** No. The standby in a traditional Multi-AZ DB instance deployment is for failover, not normal read scaling.

### 3. What is the difference between a read replica and a standby?

**Answer:** A read replica is designed to serve read queries and may be promoted. A traditional Multi-AZ standby is maintained for high availability and is not normally readable by the application.

### 4. What is replication lag?

**Answer:** It is the delay between a change being committed on the source database and becoming visible on the replica.

### 5. What is RDS Proxy?

**Answer:** RDS Proxy is a managed proxy that pools and manages database connections between applications and supported database engines.

### 6. Does RDS Proxy replace HikariCP?

**Answer:** Not necessarily. HikariCP manages connections inside each application process, while RDS Proxy manages connections at the AWS service layer. They can be used together with careful tuning.

### 7. How does Secrets Manager help secure database credentials?

**Answer:** It stores credentials securely and allows access through IAM policies. It can also support rotation workflows for compatible database configurations.

### 8. What is IAM database authentication?

**Answer:** It is an authentication method for supported RDS engines that uses short-lived IAM-generated tokens rather than relying solely on a long-lived database password.

### 9. Does IAM database authentication grant SQL privileges?

**Answer:** No. The database user still needs appropriate database-level grants.

### 10. What is a parameter group?

**Answer:** It is a collection of database engine parameters applied to an RDS DB instance or cluster, depending on the parameter group type.

### 11. What is Enhanced Monitoring?

**Answer:** It provides more detailed operating-system-level metrics for an RDS DB instance, complementing CloudWatch database metrics.

### 12. What is the purpose of a maintenance window?

**Answer:** It defines a preferred time for eligible maintenance activities, helping teams plan around potential service impact.

### 13. Why can failover interrupt application traffic?

**Answer:** Existing database connections can be closed, and applications need time to resolve the endpoint, establish new connections, and retry safe operations.

### 14. How would you prevent duplicate transactions after a connection failure?

**Answer:** I would design idempotent operations, use unique request or transaction identifiers, and determine whether the original transaction committed before retrying.
