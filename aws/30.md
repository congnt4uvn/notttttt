## 2. Review: DynamoDB Data Modeling

DynamoDB performance depends heavily on designing tables around access patterns.

Example application requirements:

1. Get an order by customer and order ID.
2. List a customer's orders in date order.
3. Find an order by its order ID.
4. Retrieve all items belonging to an order.
5. React when an order changes.

A possible table design:

```text
Table: ApplicationData

PK                  SK                         Entity
----------------------------------------------------------------
CUSTOMER#C1001      PROFILE                    Customer
CUSTOMER#C1001      ORDER#2026-11-01#O501      Order
CUSTOMER#C1001      ORDER#2026-11-03#O503      Order
ORDER#O501          ITEM#P100                  OrderItem
ORDER#O501          ITEM#P101                  OrderItem
```

A possible GSI for looking up orders by order ID:

```text
GSI1PK = ORDER#O501
GSI1SK = CUSTOMER#C1001
```

This is an illustrative single-table pattern. Multiple tables can be a better choice when they simplify ownership, access control, or operations.

### Access-pattern design checklist

- List every important read and write operation.
- Identify the exact key values available to each operation.
- Decide whether Query can serve the operation.
- Add an index only when a real access pattern requires it.
- Consider item size, write rate, key distribution, and consistency requirements.
- Avoid frequent Scan operations for user-facing requests.

## 3. DynamoDB Enhanced Client with Java

The low-level `DynamoDbClient` uses `AttributeValue` maps. The DynamoDB Enhanced Client provides a higher-level object-mapping API.

### 3.1 Maven dependencies

Use the AWS SDK for Java 2.x BOM so SDK modules use aligned versions. Set `${aws.sdk.version}` to an approved current version in your build.

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>software.amazon.awssdk</groupId>
            <artifactId>bom</artifactId>
            <version>${aws.sdk.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>dynamodb-enhanced</artifactId>
    </dependency>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>dynamodb</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
</dependencies>
```

### 3.2 Configure the enhanced client

```java
@Configuration
public class DynamoDbConfiguration {

    @Bean
    DynamoDbEnhancedClient dynamoDbEnhancedClient(
            @Value("${app.aws.region}") String region) {

        DynamoDbClient client = DynamoDbClient.builder()
                .region(Region.of(region))
                .credentialsProvider(
                    DefaultCredentialsProvider.create()
                )
                .build();

        return DynamoDbEnhancedClient.builder()
                .dynamoDbClient(client)
                .build();
    }
}
```

In a larger application, define the low-level client as its own Spring bean and inject it into the enhanced-client configuration. This makes lifecycle and testing easier.

### 3.3 Map a Java class to a DynamoDB item

This example uses a composite key.

```java
@DynamoDbBean
public class OrderRecord {

    private String customerId;
    private String orderKey;
    private String status;
    private BigDecimal total;

    @DynamoDbPartitionKey
    public String getCustomerId() {
        return customerId;
    }

    public void setCustomerId(String customerId) {
        this.customerId = customerId;
    }

    @DynamoDbSortKey
    public String getOrderKey() {
        return orderKey;
    }

    public void setOrderKey(String orderKey) {
        this.orderKey = orderKey;
    }

    public String getStatus() {
        return status;
    }

    public void setStatus(String status) {
        this.status = status;
    }

    public BigDecimal getTotal() {
        return total;
    }

    public void setTotal(BigDecimal total) {
        this.total = total;
    }
}
```

The Java property names and types must match the intended DynamoDB attribute mapping. For production money values, use a deliberate numeric representation and validation strategy.

### 3.4 Repository-style service

```java
@Service
public class OrderRepository {

    private final DynamoDbTable<OrderRecord> table;

    public OrderRepository(
            DynamoDbEnhancedClient enhancedClient,
            @Value("${app.dynamodb.table-name}") String tableName) {

        this.table = enhancedClient.table(
            tableName,
            TableSchema.fromBean(OrderRecord.class)
        );
    }

    public void save(OrderRecord order) {
        table.putItem(order);
    }

    public OrderRecord find(
            String customerId,
            String orderKey) {

        Key key = Key.builder()
                .partitionValue(customerId)
                .sortValue(orderKey)
                .build();

        return table.getItem(
            GetItemEnhancedRequest.builder()
                .key(key)
                .consistentRead(true)
                .build()
        );
    }

    public void delete(
            String customerId,
            String orderKey) {

        Key key = Key.builder()
                .partitionValue(customerId)
                .sortValue(orderKey)
                .build();

        table.deleteItem(key);
    }
}
```

### 3.5 Query with a sort-key prefix

```java
public List<OrderRecord> findCustomerOrders(
        String customerId) {

    QueryConditional condition =
        QueryConditional.keyEqualTo(
            Key.builder()
                .partitionValue(customerId)
                .build()
        );

    return table.query(condition)
            .items()
            .stream()
            .toList();
}
```

The query returns matching items for the partition key. For a production application, use a sort-key condition or a dedicated entity prefix when the partition contains multiple entity types.

## 4. Pagination and Batch Operations

### 4.1 Pagination

DynamoDB Query and Scan responses can be paginated. The service returns a `LastEvaluatedKey` when more results may be available.

The Enhanced Client exposes pages:

```java
PageIterable<OrderRecord> pages = table.query(
    QueryConditional.keyEqualTo(
        Key.builder()
            .partitionValue("CUSTOMER#C1001")
            .build()
    )
);

for (Page<OrderRecord> page : pages) {
    System.out.println("Items in page: " + page.items().size());
}
```

For an API, avoid loading an unbounded result set into memory. Return a limited page and preserve a continuation token safely for the next request.

### 4.2 Batch reads and writes

Batch operations reduce application round trips when working with multiple items. They are not a substitute for transactions:

- Batch operations do not provide all-or-nothing atomicity across all items.
- Some items may be unprocessed and need retrying.
- Use exponential backoff with jitter for unprocessed items.
- Use transactions when atomic business consistency is required.

Conceptual example using the Enhanced Client:

```java
ReadBatch readBatch = ReadBatch.builder(OrderRecord.class)
    .mappedTableResource(table)
    .addGetItem(Key.builder()
        .partitionValue("CUSTOMER#C1001")
        .sortValue("ORDER#2026-11-01#O501")
        .build())
    .addGetItem(Key.builder()
        .partitionValue("CUSTOMER#C1001")
        .sortValue("ORDER#2026-11-03#O503")
        .build())
    .build();

BatchGetResultPageIterable result =
    enhancedClient.batchGetItem(
        BatchGetItemEnhancedRequest.builder()
            .readBatches(readBatch)
            .build()
    );
```

Check the exact Enhanced Client API for the SDK version used by your project, and handle unprocessed keys in production.

## 5. DynamoDB Streams

DynamoDB Streams capture a time-ordered sequence of item-level changes in a table.

A stream record can describe:

- A new item (`INSERT`).
- An updated item (`MODIFY`).
- A removed item (`REMOVE`).

The stream view type controls which item images are included:

| Stream view type | Data returned |
|---|---|
| `KEYS_ONLY` | Key attributes only |
| `NEW_IMAGE` | Item after the change |
| `OLD_IMAGE` | Item before the change |
| `NEW_AND_OLD_IMAGES` | Both before and after images |

### 5.1 Event-driven architecture

```text
Spring Boot Order API
        |
        v
DynamoDB Orders Table
        |
        v
DynamoDB Stream
        |
        v
AWS Lambda Consumer
        |
        +------> Send order confirmation
        |
        +------> Update analytics
        |
        +------> Publish event to another service
```

### 5.2 Enable a stream with AWS CLI

```bash
aws dynamodb update-table \
  --table-name Orders \
  --stream-specification \
    StreamEnabled=true,StreamViewType=NEW_AND_OLD_IMAGES \
  --region ap-southeast-1
```

Inspect stream details:

```bash
aws dynamodb describe-table \
  --table-name Orders \
  --region ap-southeast-1
```

The table description includes stream information when a stream is enabled.

### 5.3 Connect Lambda to the stream

In the AWS Console:

1. Open the Lambda function.
2. Add a trigger.
3. Select DynamoDB.
4. Select the Orders table stream.
5. Configure batch size and starting position.
6. Configure failure handling and monitoring.
7. Verify the Lambda execution role has permission to read the stream and write to any downstream service.

A Lambda event source mapping polls the stream and invokes the function with batches of records.

### 5.4 Lambda handler example (Python)

```python
def lambda_handler(event, context):
    for record in event.get("Records", []):
        event_name = record.get("eventName")

        if event_name == "INSERT":
            print("A new item was inserted")

        elif event_name == "MODIFY":
            print("An item was updated")

        elif event_name == "REMOVE":
            print("An item was removed")

    return {"statusCode": 200}
```

This is a teaching example. A production consumer should parse the item image, validate required fields, handle failures, and emit structured logs.

### 5.5 Reliability and duplicate processing

Design stream consumers to be idempotent. A record may be retried, so processing the same logical event more than once must not create duplicate side effects.

Useful techniques:

- Store a processed-event identifier.
- Use conditional writes.
- Pass an idempotency key to downstream APIs.
- Configure retry and failure destinations appropriately.
- Keep Lambda work bounded and avoid long-running synchronous operations.

## 6. Global Tables and Multi-Region Replication

DynamoDB Global Tables replicate table data across selected AWS Regions.

Example:

```text
              Global Table
             /             \
            v               v
     ap-southeast-1      ap-northeast-2
       (Singapore)          (Seoul)
            |                 |
            v                 v
       App Region A       App Region B
```

### Benefits

- Applications in multiple Regions can access local replicas.
- Supports multi-Region resilience and disaster recovery designs.
- Helps reduce cross-Region data-access latency for suitable workloads.

### Important design considerations

- Global Tables use multi-Region replication; replication is not instantaneous.
- Applications must account for replication delay.
- Concurrent writes to the same item in different Regions require conflict-aware application design.
- Review the consistency mode and feature constraints for the Global Tables version and configuration you choose.
- Replicated writes and storage in multiple Regions affect cost.
- Test failover and recovery procedures instead of assuming replication alone is a complete disaster recovery plan.

### When should you use Global Tables?

Use them when the application genuinely needs multi-Region data access or resilience. A single-Region application does not automatically benefit from the added complexity and cost.

## 7. Backup, Restore, and Point-in-Time Recovery

DynamoDB provides backup capabilities for data protection.

### 7.1 On-demand backups

On-demand backups create a backup at a chosen time. They are useful before risky changes or for retention requirements.

Create a backup:

```bash
aws dynamodb create-backup \
  --table-name Orders \
  --backup-name Orders-before-change \
  --region ap-southeast-1
```

List backups:

```bash
aws dynamodb list-backups \
  --table-name Orders \
  --region ap-southeast-1
```

### 7.2 Point-in-time recovery (PITR)

PITR provides continuous backups that allow restoration to a selected point within the supported recovery window.

Enable PITR:

```bash
aws dynamodb update-continuous-backups \
  --table-name Orders \
  --point-in-time-recovery-specification \
    PointInTimeRecoveryEnabled=true \
  --region ap-southeast-1
```

Check status:

```bash
aws dynamodb describe-continuous-backups \
  --table-name Orders \
  --region ap-southeast-1
```

### 7.3 Restore to a new table

```bash
aws dynamodb restore-table-to-point-in-time \
  --source-table-name Orders \
  --target-table-name Orders-Restored \
  --use-latest-restorable-time \
  --region ap-southeast-1
```

A restore creates a new table; it does not overwrite the source table. Validate the restored table and application configuration before switching traffic.

### 7.4 Recovery planning

Define:

- **RPO (Recovery Point Objective):** How much data loss is acceptable?
- **RTO (Recovery Time Objective):** How long can recovery take?

Test restoration regularly. A backup that has never been restored in a test is an unverified recovery plan.

## 8. TTL and Data Lifecycle

TTL removes expired items asynchronously based on a numeric Unix epoch timestamp stored in the configured attribute.

Example item:

```json
{
  "sessionId": {"S": "SESSION#ABC123"},
  "expiresAt": {"N": "1794000000"}
}
```

Enable TTL:

```bash
aws dynamodb update-time-to-live \
  --table-name Sessions \
  --time-to-live-specification \
    Enabled=true,AttributeName=expiresAt \
  --region ap-southeast-1
```

Describe TTL:

```bash
aws dynamodb describe-time-to-live \
  --table-name Sessions \
  --region ap-southeast-1
```

### TTL best practices

- Use a numeric Unix epoch timestamp in seconds.
- Ensure the attribute name is consistent.
- Do not depend on deletion at an exact second.
- Application authorization must reject expired sessions even if the item has not yet been physically deleted.
- TTL is useful for lifecycle cleanup, not for precise scheduled workflows.

## 9. DAX and Caching

DynamoDB Accelerator (DAX) is an in-memory cache designed for DynamoDB workloads. It can reduce read latency for workloads with repeated reads and suitable cache behavior.

```text
Application
    |
    v
DAX Cluster
    |
    v
DynamoDB Table
```

### DAX considerations

- DAX is useful when the workload benefits from caching and very low read latency.
- Cache behavior and consistency requirements must be understood.
- It introduces another component to deploy, secure, monitor, and pay for.
- It is not a universal performance fix.
- For many workloads, direct DynamoDB access is sufficient.

### DAX vs. application cache

| Topic | DAX | Application cache |
|---|---|---|
| Integration | DynamoDB-compatible client path | Application-defined |
| Cache behavior | Managed for DynamoDB access patterns | Designed by developers |
| Operational responsibility | Managed service, but cluster still needs planning | Application and cache service management |
| Best fit | Repeated DynamoDB reads | General application caching and custom logic |

Before adding a cache, measure latency and read patterns. A poorly invalidated cache can return stale business data.

## 10. Monitoring with CloudWatch and Contributor Insights

Monitor DynamoDB to identify throttling, capacity pressure, latency, and uneven key usage.

### Important CloudWatch metrics

| Metric | What it helps you understand |
|---|---|
| `ConsumedReadCapacityUnits` | Read capacity consumed |
| `ConsumedWriteCapacityUnits` | Write capacity consumed |
| `ThrottledRequests` | Requests throttled |
| `ReadThrottleEvents` | Read throttling events |
| `WriteThrottleEvents` | Write throttling events |
| `SuccessfulRequestLatency` | Service-side request latency |
| `SystemErrors` | Service errors |

Metric availability and dimensions depend on the table, index, and capacity configuration.

### Contributor Insights

DynamoDB Contributor Insights can help identify frequently accessed and throttled partition keys. This is useful when investigating hot keys.

### Monitoring workflow

1. Identify the time window when errors occurred.
2. Check throttling and consumed-capacity metrics.
3. Compare table-level and index-level metrics.
4. Look for concentrated partition-key traffic.
5. Review application retry behavior.
6. Fix key design or capacity settings.
7. Load-test the change and confirm the metrics improve.

Do not respond to every throttling event by simply increasing capacity. First determine whether the workload is concentrated on a small number of keys.

## 11. Production Design for Spring Boot

A practical production architecture:

```text
                 Users / Clients
                       |
                       v
                 Application LB
                       |
                       v
                 Spring Boot API
                       |
              IAM Role / SDK v2
                       |
                       v
                DynamoDB Table
                       |
             +---------+---------+
             |                   |
             v                   v
       DynamoDB Stream       PITR / Backup
             |
             v
          Lambda
             |
      +------+------+
      |             |
      v             v
 Notifications   Event processing

CloudWatch monitors application and database metrics.
```

### Production checklist

**Data modeling**
- Design keys around documented access patterns.
- Avoid hot partition keys.
- Add indexes only for justified queries.
- Keep items appropriately sized.
- Use conditional writes for concurrency-sensitive changes.

**Application**
- Use the AWS SDK for Java 2.x.
- Use IAM roles instead of static credentials.
- Reuse SDK clients rather than creating a client per request.
- Configure timeouts and retry behavior deliberately.
- Handle conditional failures and throttling distinctly.
- Use pagination for large result sets.
- Validate request data and avoid logging sensitive attributes.

**Security**
- Apply least-privilege IAM permissions.
- Use encryption at rest and TLS in transit.
- Use a VPC endpoint where private connectivity is required.
- Protect secrets and avoid embedding credentials.
- Audit access and operational changes.

**Reliability**
- Enable PITR when required by the recovery plan.
- Test restore procedures.
- Make stream consumers idempotent.
- Define retry and failure handling.
- Document RPO and RTO.

**Cost**
- Choose on-demand or provisioned mode based on workload.
- Review storage and index overhead.
- Avoid unnecessary scans.
- Review backups, streams, Global Tables, and DAX costs.
- Set budgets and alarms appropriate to the environment.

## 14. Troubleshooting

| Problem | Possible cause | Recommended action |
|---|---|---|
| Lambda does not receive stream events | Stream disabled, mapping disabled, or role lacks permissions | Check stream status, event source mapping, and Lambda role |
| Lambda processes an event more than once | Retry or at-least-once processing behavior | Make handler idempotent |
| Stream consumer falls behind | Slow processing or insufficient concurrency | Check iterator age, errors, batch size, and downstream latency |
| Restore operation takes time | Table and data restoration are in progress | Monitor restore status and validate the new table |
| PITR is not enabled | Continuous backups not configured | Enable PITR and verify status |
| Global Table data is briefly different between Regions | Replication delay or concurrent writes | Design for replication and conflict behavior |
| DAX returns stale data | Cache behavior or invalidation expectations | Review consistency requirements and cache strategy |
| High DynamoDB cost | Unneeded indexes, scans, backups, or cross-Region replication | Review access patterns, capacity, storage, and enabled features |
| Enhanced Client mapping error | Bean schema or key annotations do not match the table | Verify getter annotations, property types, and key schema |

## 15. Practical Exercises with Answers

### Exercise 1 — What is DynamoDB Streams?

**Answer:** DynamoDB Streams capture item-level changes such as inserts, updates, and deletes. They can trigger event-driven processing through services such as AWS Lambda.

### Exercise 2 — Why should a stream consumer be idempotent?

**Answer:** A record can be retried or processed more than once. Idempotent processing prevents duplicate side effects when the same logical event is received again.

### Exercise 3 — What is the purpose of Global Tables?

**Answer:** Global Tables replicate DynamoDB data across selected AWS Regions, supporting multi-Region applications and resilience designs.

### Exercise 4 — Does Global Tables replication mean every Region is instantly identical?

**Answer:** No. Replication is not instantaneous. Applications must account for replication delay and concurrent-write behavior.

### Exercise 5 — What is PITR?

**Answer:** Point-in-time recovery provides continuous backups that allow a table to be restored to a selected point within the supported recovery window.

### Exercise 6 — Does restoring a DynamoDB table overwrite the source?

**Answer:** No. A restore creates a new table. Validate it before switching application traffic.

### Exercise 7 — Is TTL an exact scheduler?

**Answer:** No. TTL deletion is asynchronous. Applications must enforce expiration rules themselves when exact authorization behavior matters.

### Exercise 8 — When should you use DAX?

**Answer:** Consider DAX when repeated read patterns benefit from caching and low-latency access. Measure first because DAX adds cost and operational complexity.

### Exercise 9 — What can Contributor Insights help identify?

**Answer:** It can help identify frequently accessed or throttled partition keys, which is useful for diagnosing hot-key patterns.

### Exercise 10 — Why is a backup restore test important?

**Answer:** It verifies that the backup can be restored and that the team understands the steps and timing needed to recover the application.

## 17. English Speaking Practice

Read the questions aloud. Answer in your own words, then compare with the model answers.

### Question 1: What are DynamoDB Streams?

**Model answer:**

### Question 2: Why should a Lambda stream consumer be idempotent?

### Question 3: What are DynamoDB Global Tables?

**Model answer:**

Global Tables replicate data across multiple AWS Regions. They are useful for applications that need multi-Region access and improved resilience. However, I must consider replication delay and conflict handling.

### Question 4: What is point-in-time recovery?

**Model answer:**

Point-in-time recovery is a backup feature that allows me to restore a DynamoDB table to a selected time within the supported recovery period. It helps protect data from accidental changes or deletion.

### Question 5: What is the difference between DAX and DynamoDB?

**Model answer:**

DynamoDB is the database that stores the data. DAX is an in-memory cache designed to accelerate suitable DynamoDB read workloads. DAX does not replace the database.

### Question 6: How do you monitor DynamoDB in production?

**Model answer:**

I use Amazon CloudWatch to monitor consumed capacity, throttling, request latency, and errors. I can also use Contributor Insights to investigate hot partition keys.

## 18. AWS Interview Questions and Answers

**Q1. What is the DynamoDB Enhanced Client?**

It is a higher-level Java SDK interface that maps Java objects to DynamoDB items and simplifies common database operations.

**Q2. What does DynamoDB Streams capture?**

It captures item-level changes, including inserts, modifications, and removals.

**Q3. Does a DynamoDB Stream guarantee that a consumer's business action happens exactly once?**

No. Consumers should be designed to handle retries and duplicate processing safely. Use idempotency controls for side effects.

**Q4. What is a DynamoDB Global Table?**

It is a multi-Region DynamoDB table configuration that replicates data among selected Regions.

**Q5. What is PITR?**

Point-in-time recovery is a continuous backup capability that supports restoring a table to a selected point within its supported recovery window.

**Q6. Does a restore replace the original DynamoDB table?**

No. It creates a new table that must be validated before use.

**Q7. What is TTL used for?**

TTL asynchronously removes items after their configured expiration timestamp. It is commonly used for temporary records and session data.

**Q8. What is DAX?**

DynamoDB Accelerator is an in-memory cache designed to reduce read latency for suitable DynamoDB workloads.

**Q9. What is the purpose of Contributor Insights?**

It helps identify frequently accessed or throttled keys and can assist with hot-key diagnosis.

**Q10. What do RPO and RTO mean?**

RPO describes the acceptable amount of data loss measured in time. RTO describes the target time to restore service.

**Q11. Why are backups not enough by themselves?**

A team must also test restore procedures, validate the restored data, and understand how to reconnect the application.

**Q12. What are important production practices for DynamoDB?**

Design keys around access patterns, avoid hot keys, use least-privilege IAM roles, monitor throttling, handle retries safely, enable appropriate backups, and test recovery procedures.
