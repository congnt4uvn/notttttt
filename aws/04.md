# 1. What is AWS Global Infrastructure?

## 1.1 Definition

AWS Global Infrastructure is the worldwide network of AWS data centers, Regions, Availability Zones, and Edge Locations that provides cloud computing services to customers around the world.

AWS operates infrastructure in different geographical locations to help customers:

- Deploy applications closer to users.
- Reduce network latency.
- Improve application availability.
- Protect data.
- Support disaster recovery.
- Meet data residency requirements.

### Simple example

Imagine you are developing an e-commerce application in Vietnam.

Your customers are located in:

- Vietnam.
- Singapore.
- Japan.
- United States.
- Germany.

You want your application to be available to all these customers.

You can deploy your application using AWS infrastructure in suitable geographical locations.

For example:

| Customer location | Possible AWS Region      |
| ----------------- | ------------------------ |
| Vietnam           | Asia Pacific (Singapore) |
| Singapore         | Asia Pacific (Singapore) |
| Japan             | Asia Pacific (Tokyo)     |
| United States     | US East (N. Virginia)    |
| Germany           | Europe (Frankfurt)       |

These are examples of possible choices, not automatic mappings. The best Region depends on latency, service availability, compliance, cost and architecture.

## 1.2 Main components of AWS Global Infrastructure

There are three important concepts:

| Component         | Meaning                                                                         |
| ----------------- | ------------------------------------------------------------------------------- |
| Region            | Geographical area containing AWS infrastructure                                 |
| Availability Zone | Isolated infrastructure location within a Region                                |
| Edge Location     | Location used by services such as CloudFront to deliver content closer to users |

Architecture overview:

```
                  AWS GLOBAL INFRASTRUCTURE
                              |
             +----------------+----------------+
             |                |                |
             v                v                v
          REGION 1         REGION 2         REGION 3
             |                |                |
         +---+---+        +---+---+        +---+---+
         |   |   |        |   |   |        |   |   |
         v   v   v        v   v   v        v   v   v
        AZ  AZ  AZ       AZ  AZ  AZ       AZ  AZ  AZ

                  AWS EDGE LOCATIONS
                           |
                           v
                  Content Delivery
                     CloudFront
```

Important: Edge Locations are part of AWS's broader global network and are not simply another type of Availability Zone.

# 2. What is an AWS Region?

## 2.1 Definition

An AWS Region is a separate geographical area where AWS operates infrastructure.

Each Region is designed to be isolated from other AWS Regions.

A Region contains multiple Availability Zones.

For example:

| Region name              | Region code      |
| ------------------------ | ---------------- |
| US East (N. Virginia)    | `us-east-1`      |
| US West (Oregon)         | `us-west-2`      |
| Asia Pacific (Singapore) | `ap-southeast-1` |
| Asia Pacific (Tokyo)     | `ap-northeast-1` |
| Asia Pacific (Seoul)     | `ap-northeast-2` |
| Europe (Frankfurt)       | `eu-central-1`   |
| Europe (Ireland)         | `eu-west-1`      |

AWS Region codes are important because you will frequently use them in:

- AWS CLI.
- AWS SDK.
- Terraform.
- CloudFormation.
- AWS Console.
- Application configurations.

## 2.2 How does an AWS Region work?

Imagine you create an AWS account and select Singapore:

`ap-southeast-1`

You create:

- EC2 instances.
- RDS databases.
- S3 buckets.
- VPC networks.

Many of these resources are associated with a particular Region.

Example:

```
              AWS ACCOUNT
                   |
                   v
        Asia Pacific (Singapore)
             ap-southeast-1
                   |
          +--------+--------+
          |        |        |
          v        v        v
         EC2      RDS      VPC
          |        |        |
          +--------+--------+
                   |
                   v
             Application
```

If you switch to Tokyo:

`ap-northeast-1`

You may see different regional resources because the resources are associated with their respective Regions.

## 2.3 AWS Regions are independent

Consider two Regions:

```
       AWS REGION: SINGAPORE
          ap-southeast-1
                 |
         +-------+-------+
         |       |       |
         v       v       v
        EC2     RDS     S3


       AWS REGION: TOKYO
         ap-northeast-1
                 |
         +-------+-------+
         |       |       |
         v       v       v
        EC2     RDS     S3
```

These Regions operate independently.

For example:

- An EC2 instance created in Singapore does not automatically appear in Tokyo.
- An RDS database created in Singapore does not automatically replicate to Tokyo.
- You need to configure cross-Region replication or another disaster recovery mechanism when required.

## 2.4 Why do companies use multiple Regions?

There are several reasons.

A. Low latency

Deploying applications closer to customers can reduce network latency.

Example:

A company has customers in Japan.

Deploying its application in Tokyo may provide lower latency for Japanese users than hosting everything in the United States.

B. Disaster Recovery

If an entire Region becomes unavailable, a company may use another Region to recover its applications.

C. Data residency

Some organizations have legal, regulatory or contractual requirements concerning where data is stored and processed.

D. Global business

Companies operating internationally may deploy infrastructure in multiple geographical locations.

## 2.5 How to choose an AWS Region

Consider these five factors:

| Factor               | Explanation                                            |
| -------------------- | ------------------------------------------------------ |
| Latency              | Choose a Region close to users when appropriate        |
| Service availability | Not every AWS service is available in every Region     |
| Cost                 | Pricing can vary between Regions                       |
| Compliance           | Consider data residency and regulatory requirements    |
| Resilience           | Consider geographical separation for disaster recovery |

### Practical example — Choosing a Region for Vietnam

Suppose you are building an application for Vietnamese customers.

You may initially consider:

`ap-southeast-1` — Singapore.

Why?

- It is geographically close to Vietnam.
- It offers a broad range of AWS services.
- It can be a practical deployment location for Southeast Asian customers.

However, you should benchmark actual network latency and check the application's data residency requirements before choosing.

# 3. What is an Availability Zone (AZ)?

## 3.1 Definition

An Availability Zone (AZ) is one or more discrete data centers with independent infrastructure within an AWS Region.

Availability Zones are designed to be isolated from failures in other Availability Zones.

They are connected through low-latency, high-bandwidth networking.

### Simple definition

A Region is a geographical area.

An Availability Zone is an isolated infrastructure location inside that Region.

## 3.2 Availability Zone architecture

Imagine Singapore has three Availability Zones available in a particular AWS Region.

```
          AWS REGION
       ap-southeast-1
                |
       +--------+--------+
       |        |        |
       v        v        v
      AZ-a     AZ-b     AZ-c
       |        |        |
       v        v        v
      EC2      EC2      EC2
       |        |        |
       v        v        v
   Database  Database  Database
```

The three Availability Zones are designed to operate independently.

They are connected through AWS networking.

## 3.3 Why do we need Availability Zones?

The main reason is High Availability.

Imagine your application runs in only one Availability Zone.

```
             AWS REGION
                  |
                  v
                 AZ-a
                  |
                  v
                EC2
                  |
                  v
             Application
```

What happens if AZ-a experiences an outage?

Your application may become unavailable.

Now imagine your application runs across two Availability Zones.

```
             AWS REGION
                  |
          +-------+-------+
          |               |
          v               v
         AZ-a            AZ-b
          |               |
          v               v
         EC2             EC2
          |               |
          +-------+-------+
                  |
                  v
             Application
```

If AZ-a experiences an outage, traffic can be directed to the application running in AZ-b, provided the load balancer, application and dependencies are configured for failover.

This improves availability.

## 3.4 Important characteristics of Availability Zones

| Characteristic  | Explanation                                             |
| --------------- | ------------------------------------------------------- |
| Isolation       | AZs are designed to isolate infrastructure failures     |
| Redundancy      | Applications can run across multiple AZs                |
| Connectivity    | AZs are connected through high-speed networking         |
| Fault isolation | Failures in one AZ are designed not to affect other AZs |
| Regional scope  | Each AZ belongs to a specific Region                    |

## 3.5 Availability Zone naming

AWS Availability Zones have identifiers.

For example:

```
ap-southeast-1a
ap-southeast-1b
ap-southeast-1c
```

These are AZ names within Singapore.

An important technical detail:

AWS maps AZ names to physical Availability Zones on a per-account basis. The name `ap-southeast-1a` may not represent the same physical AZ for two different AWS accounts.

For consistent cross-account identification, AWS provides AZ IDs, such as `apse1-az1`.

## 3.6 Practical example — Spring Boot in Multi-AZ

Suppose you deploy your application on EC2.

You want to avoid relying on only one Availability Zone.

Architecture:

```
                  USERS
                    |
                    v
            Application Load Balancer
                    |
             +------+------+
             |             |
             v             v
           AZ-a           AZ-b
             |             |
             v             v
          EC2 #1         EC2 #2
             |             |
             +------+------+
                    |
                    v
               RDS Multi-AZ
                    |
             +------+------+
             |             |
             v             v
          Primary       Standby
          Database      Database
```

The application is deployed across two AZs.

RDS Multi-AZ can maintain a standby database in another AZ for supported configurations and automatically perform failover.

Important:

- A standby database is not necessarily available for normal read traffic.
- Multi-AZ database deployment is primarily for availability and failover.
- Read scaling may require read replicas or other database configurations.

# 4. What is an Edge Location?

## 4.1 Definition

An Edge Location is an AWS infrastructure location used by services such as Amazon CloudFront to deliver content closer to end users.

The main purpose is to reduce latency and improve content delivery performance.

### Simple example

Imagine your website is hosted in Singapore.

A customer in the United States requests an image from your website.

Without a content delivery network:

```
       US CUSTOMER
            |
            v
         Internet
            |
            v
      AWS Singapore
            |
            v
        S3 Bucket
            |
            v
       Return Image
```

The request must travel to the origin location to retrieve the content.

With Amazon CloudFront:

```
           US CUSTOMER
                |
                v
          CLOUDFRONT
                |
                v
          US EDGE LOCATION
                |
         +------+------+
         |             |
         v             v
      Cached       Cache Miss
      Content          |
         |             v
         |        AWS Singapore
         |             |
         |             v
         |          S3 Bucket
         |             |
         +------+------+
                |
                v
          Return Content
```

If the requested content is already cached at the Edge Location, CloudFront can deliver it without retrieving it from the origin again.

If the content is not cached, CloudFront retrieves it from the origin and may cache it according to the configured caching behavior.

## 4.2 How does an Edge Location work?

Let's understand the process.

Step 1 — User requests content

A customer opens your website.

For example:

```
https://example.com/images/product.jpg
```

Step 2 — DNS routing

The request is routed to an appropriate CloudFront edge location.

Step 3 — Check cache

CloudFront checks whether the requested content is available in its cache.

Step 4 — Cache hit or cache miss

- Cache Hit: Content is already cached and can be delivered.
- Cache Miss: CloudFront retrieves the content from the origin.

Step 5 — Deliver content

CloudFront returns the requested content to the user.

## 4.3 What is caching?

Caching means temporarily storing frequently accessed data so that future requests can be served faster.

Example:

Your e-commerce website has:

- Product images.
- CSS files.
- JavaScript files.
- Videos.
- Static documents.

Instead of retrieving these files from the origin every time, CloudFront can cache them at edge locations.

## 4.4 AWS services related to Edge Locations

| AWS Service            | Purpose                                    |
| ---------------------- | ------------------------------------------ |
| Amazon CloudFront      | Content Delivery Network (CDN)             |
| AWS Global Accelerator | Improve global application traffic routing |
| Amazon Route 53        | DNS and traffic routing                    |

Important distinction:

- CloudFront uses a global network of edge locations and caches content.
- Global Accelerator routes application traffic through the AWS global network toward endpoints in supported AWS Regions.
- Route 53 provides DNS services and routing policies.

These services solve related but different networking problems.

## 4.5 Advantages of Edge Locations

| Advantage              | Explanation                             |
| ---------------------- | --------------------------------------- |
| Lower latency          | Deliver content closer to users         |
| Faster websites        | Improve static content delivery         |
| Reduced origin traffic | Cache frequently accessed content       |
| Global reach           | Serve customers around the world        |
| Security integration   | Integrate with services such as AWS WAF |
| Better user experience | Improve content loading performance     |

## 4.6 Real-world example — E-commerce Website

Imagine your Spring Boot e-commerce application runs in Singapore.

Your product images are stored in S3.

Customers are located in Vietnam, Japan, Germany and the United States.

Architecture:

```
                  CUSTOMERS
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
        Vietnam      Japan      Germany
          |           |           |
          +-----------+-----------+
                      |
                      v
                 CLOUDFRONT
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       Edge A      Edge B      Edge C
          |           |           |
          +-----------+-----------+
                      |
                      v
                AWS SINGAPORE
                      |
               +------+------+
               |             |
               v             v
              S3          Spring Boot
          Product Images   Application
```

CloudFront delivers static content from its edge network, while your application can continue running in Singapore.

# 5. Region vs Availability Zone vs Edge Location

This is one of the most important topics in AWS Fundamentals.

## 5.1 Main comparison

| Criteria     | Region                  | Availability Zone                        | Edge Location                   |
| ------------ | ----------------------- | ---------------------------------------- | ------------------------------- |
| Meaning      | Geographical AWS area   | Isolated infrastructure location         | Content delivery location       |
| Purpose      | Host AWS resources      | Improve availability and fault isolation | Deliver content closer to users |
| Location     | Large geographical area | Inside a Region                          | Distributed globally            |
| Main usage   | Deploy applications     | Multi-AZ architecture                    | CDN and edge delivery           |
| Example      | Singapore               | ap-southeast-1a                          | CloudFront edge location        |
| AWS services | EC2, RDS, VPC           | EC2, RDS Multi-AZ                        | CloudFront                      |

## 5.2 Remember using this analogy

Imagine an international company.

- Region = A country where the company operates.
- Availability Zone = Separate office buildings in that country.
- Edge Location = A local distribution center closer to customers.

Each component has a different purpose.

## 5.3 Important architecture example

```
                 AWS GLOBAL NETWORK
                         |
             +-----------+-----------+
             |                       |
             v                       v
       REGION: SINGAPORE        REGION: TOKYO
             |                       |
       +-----+-----+           +-----+-----+
       |     |     |           |     |     |
       v     v     v           v     v     v
      AZ-a  AZ-b  AZ-c        AZ-a  AZ-b  AZ-c


               EDGE LOCATIONS
                      |
           +----------+----------+
           |          |          |
           v          v          v
         Vietnam    Japan     Germany
```

Remember:

- Region = Where your AWS infrastructure is deployed.
- AZ = Where your resources can be distributed for availability.
- Edge Location = Where content can be cached and delivered closer to users.

# 6. Regional Services vs Global Services

AWS services can operate at different scopes.

Some services are Regional, while others are Global.

Understanding this distinction is important when designing AWS architectures.

## 6.1 What are Regional Services?

A Regional Service operates within a specific AWS Region.

When you create a Regional resource, you generally select the Region where it will operate.

Examples:

- Amazon EC2.
- Amazon RDS.
- Amazon VPC.
- Amazon ECS.
- Amazon EKS.

### Architecture

```
               AWS ACCOUNT
                    |
          +---------+---------+
          |                   |
          v                   v
      SINGAPORE             TOKYO
          |                   |
          v                   v
         EC2                 EC2
          |                   |
          v                   v
         RDS                 RDS
          |                   |
          v                   v
         VPC                 VPC
```

The resources in Singapore and Tokyo are separate regional resources.

They do not automatically replicate or synchronize with one another.

## 6.2 What are Global Services?

A Global Service is designed to operate across multiple AWS Regions or at a global scope.

Examples include:

| AWS Service       | Scope                    | Purpose                        |
| ----------------- | ------------------------ | ------------------------------ |
| AWS IAM           | Global                   | Identity and access management |
| Amazon CloudFront | Global                   | Content delivery               |
| Amazon Route 53   | Global                   | DNS services                   |
| AWS Organizations | Global                   | Manage multiple AWS accounts   |
| AWS WAF           | Depends on resource type | Protect supported resources    |

Important: Some services have global and Regional resource configurations. For example, AWS WAF can protect CloudFront distributions using a global configuration, while Regional resources use Regional configurations.

## 6.3 Regional vs Global Comparison

| Criteria              | Regional Service                 | Global Service                   |
| --------------------- | -------------------------------- | -------------------------------- |
| Scope                 | Specific Region                  | Multiple Regions or global       |
| Deployment            | Usually select Region            | Depends on service               |
| Example               | EC2                              | IAM                              |
| Example               | RDS                              | CloudFront                       |
| Example               | VPC                              | Route 53                         |
| Regional independence | Resources are generally separate | Service operates at global scope |

## 6.4 Practical example — IAM and EC2

Suppose you create an IAM user and an EC2 instance.

```
                  AWS ACCOUNT
                       |
              +--------+--------+
              |                 |
              v                 v
          GLOBAL IAM        SINGAPORE
              |                 |
              v                 v
          IAM User            EC2
              |                 |
              +-----------------+
                       |
                       v
                Access Control
```

IAM is global in its scope.

EC2 instances are Regional resources.

You can use IAM permissions to control access to EC2 instances across multiple Regions.

## 6.5 Practical AWS CLI examples

Check your AWS CLI configuration:

```
aws configure list
```

Show your current Region:

```
aws configure get region
```

List EC2 instances in Singapore:

```
aws ec2 describe-instances \
    --region ap-southeast-1
```

List EC2 instances in Tokyo:

```
aws ec2 describe-instances \
    --region ap-northeast-1
```

Notice that the same command can query different Regions by changing the `--region` parameter.

# 7. How to Choose an AWS Region

When deploying applications, selecting a Region is an important architectural decision.

## 7.1 Five important factors

1\. Latency

Choose infrastructure close to your customers when lower network latency is important.

Example:

A company primarily serves Vietnamese customers and considers Singapore as its initial hosting location.

2\. Service Availability

Not every AWS service or feature is available in every Region.

Before choosing a Region, verify that your required services are available there.

3\. Cost

AWS service prices can vary by Region.

You should compare:

- EC2 pricing.
- RDS pricing.
- S3 storage pricing.
- Data transfer pricing.
- Networking costs.

4\. Compliance and Data Residency

Some organizations have requirements regarding where their data must be stored or processed.

Check applicable laws, contracts and industry requirements.

5\. Disaster Recovery

For critical systems, you may need a second Region to recover from a Regional outage.

## 7.2 Example — Choosing a Region for a Vietnamese company

Suppose your company has:

- 50,000 customers in Vietnam.
- A Spring Boot backend.
- PostgreSQL database.
- Product images.
- A mobile application.

Possible initial architecture:

```
               VIETNAM USERS
                     |
                     v
                  INTERNET
                     |
                     v
              CLOUDFRONT
                     |
                     v
              AWS SINGAPORE
               ap-southeast-1
                     |
            +--------+--------+
            |        |        |
            v        v        v
           ALB      ECS       S3
                     |
                     v
                    RDS
```

Why Singapore?

- It is a nearby AWS Region.
- It provides many commonly used AWS services.
- It may offer suitable latency for Southeast Asian customers.

However, the final decision should be based on actual latency tests, pricing, compliance requirements and service availability.

# 8. High Availability (HA)

## 8.1 What is High Availability?

High Availability (HA) is the ability of a system to remain accessible and operational with minimal downtime.

In AWS, High Availability is commonly achieved through:

- Multiple Availability Zones.
- Load Balancers.
- Auto Scaling.
- Database redundancy.
- Health Checks.
- Monitoring and automated recovery.

### Simple example

Imagine your application runs on one EC2 instance.

If the instance fails, the application becomes unavailable.

This is a single point of failure.

```
              USERS
                 |
                 v
                EC2
                 |
                 v
            Application
                 |
                 v
              DATABASE
```

Now let's improve the architecture.

```
                 USERS
                   |
                   v
            LOAD BALANCER
                   |
           +-------+-------+
           |               |
           v               v
          AZ-a            AZ-b
           |               |
           v               v
         EC2 #1          EC2 #2
           |               |
           +-------+-------+
                   |
                   v
               RDS Multi-AZ
```

If one application instance or Availability Zone fails, the other can continue serving requests, provided the application and its dependencies are healthy.

## 8.2 AWS services used for High Availability

| Service                | Purpose                                  |
| ---------------------- | ---------------------------------------- |
| Elastic Load Balancing | Distribute traffic                       |
| EC2 Auto Scaling       | Replace or add instances                 |
| Amazon RDS Multi-AZ    | Database availability and failover       |
| Amazon Route 53        | DNS routing and health checks            |
| Amazon CloudWatch      | Monitoring and alarms                    |
| Amazon ECS             | Run multiple application tasks           |
| Amazon EKS             | Run containerized workloads across nodes |

## 8.3 High Availability vs Scalability

These concepts are related but different.

High Availability:

The system remains operational despite failures.

Scalability:

The system can handle increasing workloads by adding or increasing resources.

Example:

| Scenario                                      | Concept                   |
| --------------------------------------------- | ------------------------- |
| Run EC2 in two AZs                            | High Availability         |
| Add more EC2 instances during traffic spikes  | Scalability               |
| Automatically replace unhealthy EC2 instances | Resilience / availability |
| Increase EC2 instance size                    | Vertical scalability      |
| Add more EC2 instances                        | Horizontal scalability    |

# 9. Fault Tolerance

## 9.1 What is Fault Tolerance?

Fault Tolerance is the ability of a system to continue operating when one or more components fail.

A fault-tolerant system is designed to minimize or eliminate service interruption during certain failures.

### Example

Imagine an application has:

- Two application servers.
- Redundant network paths.
- Replicated storage.
- Database redundancy.

If one component fails, the system can continue operating through other components.

## 9.2 Fault Tolerance Architecture

```
                 USERS
                   |
                   v
              LOAD BALANCER
                   |
           +-------+-------+
           |               |
           v               v
         EC2 #1           EC2 #2
           |               |
           +-------+-------+
                   |
              DATABASE
                   |
           +-------+-------+
           |               |
           v               v
        Primary          Standby
        Database         Database
```

This is an illustrative redundant architecture.

Actual fault tolerance depends on the failure modes, replication design, application state, networking and recovery mechanisms.

## 9.3 High Availability vs Fault Tolerance

| Criteria   | High Availability                  | Fault Tolerance                     |
| ---------- | ---------------------------------- | ----------------------------------- |
| Main goal  | Minimize downtime                  | Continue operation despite failures |
| Recovery   | May involve failover               | Designed to avoid interruption      |
| Complexity | Varies                             | Often higher                        |
| Cost       | Varies                             | Often higher due to redundancy      |
| Example    | Multi-AZ application with failover | Continuously redundant components   |

Important: Neither Multi-AZ nor redundancy automatically guarantees zero downtime.

# 10. Multi-AZ Architecture

## 10.1 What is Multi-AZ?

Multi-AZ means deploying resources across multiple Availability Zones within the same AWS Region.

The goal is to improve availability and resilience.

### Single-AZ architecture

```
             AWS REGION
                  |
                  v
                 AZ-a
                  |
                  v
                 EC2
                  |
                  v
              Application
```

Problem:

If AZ-a becomes unavailable, your application may become unavailable.

### Multi-AZ architecture

```
                AWS REGION
                     |
             +-------+-------+
             |               |
             v               v
            AZ-a            AZ-b
             |               |
             v               v
            EC2             EC2
             |               |
             +-------+-------+
                     |
                     v
                LOAD BALANCER
```

In practice, the load balancer is deployed across multiple Availability Zones and routes traffic to healthy targets.

## 10.2 Multi-AZ with RDS

Amazon RDS supports Multi-AZ deployments.

For a typical Multi-AZ DB instance deployment:

```
                AWS REGION
                     |
             +-------+-------+
             |               |
             v               v
            AZ-a            AZ-b
             |               |
             v               v
        Primary DB       Standby DB
             |               |
             +-------+-------+
                     |
                Replication
```

The standby is maintained for failover.

If the primary database becomes unavailable, RDS can automatically fail over to the standby.

Important: Multi-AZ DB instance standby replicas are generally not used for normal read traffic. If you need read scaling, consider RDS Read Replicas or suitable Multi-AZ DB cluster configurations.

## 10.3 Multi-AZ vs Multi-Region

| Criteria     | Multi-AZ                | Multi-Region                                         |
| ------------ | ----------------------- | ---------------------------------------------------- |
| Deployment   | Multiple AZs            | Multiple Regions                                     |
| Geography    | Same Region             | Different Regions                                    |
| Main purpose | High Availability       | Regional resilience and geographic reach             |
| Latency      | Usually low between AZs | Depends on geographical distance                     |
| Complexity   | Moderate                | Usually higher                                       |
| Cost         | Additional resources    | Additional regional infrastructure and data transfer |

### Multi-AZ example

```
          AWS SINGAPORE
                 |
         +-------+-------+
         |               |
         v               v
        AZ-a            AZ-b
         |               |
         v               v
        EC2             EC2
```

### Multi-Region example

```
       AWS SINGAPORE          AWS TOKYO
             |                   |
             v                   v
          EC2 + RDS           EC2 + RDS
             |                   |
             +--------+----------+
                      |
                Data Replication
```

Multi-Region replication must be explicitly configured. AWS does not automatically replicate all resources between Regions.

# 11. Disaster Recovery (DR)

## 11.1 What is Disaster Recovery?

Disaster Recovery (DR) is the process of restoring applications, infrastructure and data after a major failure or disaster.

Examples of disasters:

- AWS Region outage.
- Data center failure.
- Database corruption.
- Accidental deletion.
- Cyberattack.
- Application failure.
- Network outage.

Companies need a Disaster Recovery strategy to minimize business disruption.

## 11.2 Important DR terminology

RTO — Recovery Time Objective

RTO is the maximum acceptable time required to restore a system after a disruption.

Example:

Your application becomes unavailable at 10:00 AM.

Your RTO is 2 hours.

The application should be restored by 12:00 PM.

RPO — Recovery Point Objective

RPO is the maximum acceptable amount of data loss measured in time.

Example:

Your RPO is 15 minutes.

This means the company aims to recover data with no more than 15 minutes of data loss.

### RTO vs RPO

| Concept | Meaning                              | Example    |
| ------- | ------------------------------------ | ---------- |
| RTO     | How quickly must the system recover? | 2 hours    |
| RPO     | How much data loss is acceptable?    | 15 minutes |

Remember:

- RTO = Recovery time.
- RPO = Recovery data point.

## 11.3 Four AWS Disaster Recovery Strategies

### Strategy 1 — Backup and Restore

The company backs up its data and restores infrastructure when a disaster occurs.

```
       PRIMARY REGION
             |
             v
         Application
             |
             v
          Database
             |
             v
          Backups
             |
             v
       S3 / Backup Storage
             |
             v
       Restore After Disaster
             |
             v
       Recovery Environment
```

Advantages:

- Lower cost.
- Simple to understand.
- Suitable for workloads with longer recovery times.

Disadvantages:

- Recovery may take significant time.
- Infrastructure must be restored after failure.

### Strategy 2 — Pilot Light

A minimal version of the infrastructure is maintained in the recovery Region.

```
       PRIMARY REGION
             |
             v
       Full Application
             |
             v
          Database
             |
             | Replication
             v
       RECOVERY REGION
             |
             v
       Minimal Resources
```

During a disaster, additional resources are provisioned.

Advantages:

- Faster recovery than backup and restore.
- Lower cost than maintaining a complete duplicate environment.

Disadvantages:

- Additional infrastructure must be provisioned.
- Recovery requires operational procedures.

### Strategy 3 — Warm Standby

A smaller but functional version of the production environment runs in the recovery Region.

```
       PRIMARY REGION
             |
             v
       Full Application
             |
             v
          Database
             |
             | Replication
             v
       RECOVERY REGION
             |
             v
       Smaller Application
             |
             v
          Database
```

During a disaster, the recovery environment can be scaled up.

Advantages:

- Faster recovery.
- The recovery environment is already operational.

Disadvantages:

- Higher ongoing costs.
- Requires synchronization and monitoring.

### Strategy 4 — Multi-Site / Active-Active

Applications run simultaneously in multiple Regions.

```
                  USERS
                    |
                    v
             GLOBAL ROUTING
                    |
             +------+------+
             |             |
             v             v
       REGION A        REGION B
             |             |
             v             v
        Application    Application
             |             |
             v             v
          Database      Database
             |             |
             +------+------+
                    |
             Data Synchronization
```

Advantages:

- Very fast failover when properly designed.
- Both environments can serve traffic.
- Supports geographic distribution.

Disadvantages:

- High cost.
- Complex data synchronization.
- Conflict resolution may be necessary.
- More complicated operational management.

## 11.4 Compare DR strategies

| Strategy                 | Recovery speed      | Cost        | Complexity |
| ------------------------ | ------------------- | ----------- | ---------- |
| Backup and Restore       | Slowest             | Low         | Low–Medium |
| Pilot Light              | Moderate            | Low–Medium  | Medium     |
| Warm Standby             | Faster              | Medium–High | High       |
| Multi-Site Active-Active | Potentially fastest | Highest     | Very High  |

These are relative comparisons. Actual recovery time depends on architecture, automation, testing and workload requirements.

## 16.2 Technical conversation — B1

Question 1: What is an AWS Region?

Answer:

An AWS Region is a geographical area where AWS operates its infrastructure. Companies can deploy applications and services in different Regions depending on their requirements.

Question 2: What is an Availability Zone?

Answer:

An Availability Zone is an isolated infrastructure location within an AWS Region. Companies can deploy applications across multiple Availability Zones to improve availability.

Question 3: What is an Edge Location?

Answer:

An Edge Location is used by services such as Amazon CloudFront to deliver content closer to users. It helps reduce latency and improve content delivery performance.

Question 4: What is the difference between Multi-AZ and Multi-Region?

Answer:

Multi-AZ deploys resources across multiple Availability Zones within the same Region. Multi-Region deploys resources across different geographical Regions. Multi-AZ improves availability, while Multi-Region can support geographic resilience and disaster recovery.
