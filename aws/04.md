## 2. What Is AWS Global Infrastructure?

AWS operates cloud infrastructure in many geographic locations around the world. This infrastructure allows customers to deploy applications closer to users, improve availability, and meet geographic or regulatory requirements.

The main concepts in this lesson are:

1. **Region** — a separate geographic area where AWS has infrastructure.
2. **Availability Zone (AZ)** — an isolated location within a Region, made up of one or more data centres.
3. **Edge Location** — a site used by services such as Amazon CloudFront to deliver content closer to end users.

A simplified hierarchy:

```text
AWS Global Infrastructure
|
+-- Region A
|   |
|   +-- Availability Zone A
|   |   +-- Data centre(s)
|   |
|   +-- Availability Zone B
|   |   +-- Data centre(s)
|   |
|   +-- Availability Zone C
|       +-- Data centre(s)
|
+-- Region B
|   |
|   +-- Availability Zone A
|   +-- Availability Zone B
|   +-- Availability Zone C
|
+-- Edge Locations
    +-- Distributed locations for content delivery
```

This diagram is conceptual. The number of Regions, Availability Zones, and Edge Locations changes over time.

## 3. AWS Regions

### 3.1 Definition

An AWS Region is a separate geographic area where AWS operates infrastructure.

Examples of Region names include:

- `us-east-1` — US East (N. Virginia)
- `us-west-2` — US West (Oregon)
- `ap-southeast-1` — Asia Pacific (Singapore)
- `ap-southeast-2` — Asia Pacific (Sydney)
- `ap-northeast-1` — Asia Pacific (Tokyo)

For example, an application serving users in Southeast Asia might evaluate a Region such as Singapore. The final choice should be based on latency testing, service availability, cost, data-residency requirements, and resilience needs—not geographic distance alone.

### 3.2 Why does AWS use Regions?

Regions help customers:

- Deploy applications in a geographic area suitable for their users.
- Separate workloads for operational or regulatory reasons.
- Build disaster recovery strategies across geographic locations.
- Choose where certain data and workloads are stored, subject to service design and configuration.
- Avoid depending on a single geographic area for every workload.

### 3.3 Choosing a Region

Consider these factors before selecting a Region:

| Factor | Questions to ask |
|---|---|
| Latency | Is the Region close enough to the users who need fast responses? |
| Service availability | Are all required AWS services and features available there? |
| Cost | How do compute, storage, data transfer, and managed-service prices compare? |
| Compliance | Are there data residency or regulatory requirements? |
| Resilience | Does the architecture need backup or disaster recovery in another Region? |
| Connectivity | Are there suitable network connections to users, offices, and other systems? |

**Practical example**

A company in Vietnam is building an online shopping application for customers mainly in Vietnam and nearby countries.

The team might evaluate Singapore and other suitable Regions. It should test application latency from real user locations, verify that required services are available, compare costs, and review any applicable data requirements before deciding.

### 3.4 Important point

A Region is not the same as an Availability Zone. A Region contains multiple Availability Zones. A multi-Region architecture uses resources in more than one Region.

## 4. Availability Zones (AZs)

### 4.1 Definition

An Availability Zone is an isolated location within an AWS Region. An AZ consists of one or more discrete data centres with redundant power, networking, and connectivity.

Availability Zones are designed to be isolated from failures in other AZs while remaining connected within the Region through high-bandwidth, low-latency networking.

A Region commonly has multiple Availability Zones. The exact number varies by Region.

### 4.2 Why are Availability Zones important?

If an application runs in only one AZ, a problem affecting that AZ may interrupt the application.

If an application is designed to run across multiple AZs, it can continue serving users when one AZ experiences a failure, provided the application and its dependencies are configured for that resilience.

### 4.3 Single-AZ vs Multi-AZ

**Single-AZ architecture**

```text
Users
  |
  v
Application
  |
  v
AZ-A
  |
  +-- EC2 instance
  +-- Database
```

Potential issue: the application depends on one Availability Zone. An AZ-level disruption may make the workload unavailable.

**Multi-AZ architecture**

```text
                         Users
                           |
                           v
                    Load Balancer
                           |
             +-------------+-------------+
             |                           |
             v                           v
           AZ-A                         AZ-B
             |                           |
        EC2 instance                EC2 instance
             |                           |
             +-------------+-------------+
                           |
                           v
                    Multi-AZ database
```

This is a simplified conceptual design. A real implementation must configure load balancing, health checks, scaling, database failover, networking, and application behavior correctly.

### 4.4 Benefits of Multi-AZ

- Higher availability for workloads designed to use multiple AZs.
- Better resilience to certain data-centre or AZ-level failures.
- Ability to distribute application instances across failure boundaries.
- Reduced dependence on one physical location.

### 4.5 Multi-AZ does not mean zero downtime

Failover may take time. Some requests may fail during a disruption. Applications should use retries carefully, handle temporary errors, and avoid assuming every operation completes exactly once.

## 5. Edge Locations

### 5.1 Definition

An Edge Location is a site in AWS's global network used by services such as Amazon CloudFront to deliver content closer to end users.

Edge locations are not the same as Regions or Availability Zones.

### 5.2 What is Amazon CloudFront?

Amazon CloudFront is a content delivery network (CDN). It caches and delivers content from locations closer to users when possible.

Common content includes:

- Images
- CSS and JavaScript files
- Videos
- Downloadable files
- Cacheable API responses, when configured appropriately

### 5.3 Example: Delivering product images

Imagine an e-commerce application hosted in one AWS Region. Customers in different countries need to load product images.

Without a CDN, image requests may travel to the origin server for every request.

With CloudFront:

```text
Customer in Vietnam
        |
        v
CloudFront edge location
        |
        | Cache hit: return cached content
        |
        +------------------------------+
                                       |
                         Cache miss / origin request
                                       |
                                       v
                                Origin in AWS
                                       |
                                       v
                                  Amazon S3
```

The diagram is simplified. CloudFront uses its global edge network and may use regional edge caches as part of its delivery architecture.

### 5.4 Benefits of CloudFront

- Reduces latency for cacheable content.
- Reduces repeated requests to the origin.
- Can improve delivery performance for users in different geographic areas.
- Integrates with AWS security and access-control capabilities.

**Important:** CloudFront does not automatically make every dynamic API request faster. Caching behavior depends on cache policies, headers, query strings, cookies, and application design.

## 6. Region vs Availability Zone vs Edge Location

| Feature | Region | Availability Zone | Edge Location |
|---|---|---|---|
| Meaning | Geographic AWS area | Isolated location inside a Region | Site in AWS's edge network |
| Main purpose | Geographic deployment and regional isolation | Workload availability and fault isolation | Low-latency content delivery |
| Contains | Multiple AZs | One or more data centres | Edge infrastructure |
| Common use | Deploy an application in Singapore | Run application instances across AZs | Deliver cached images and files |
| Example | `ap-southeast-1` | An AZ within `ap-southeast-1` | CloudFront edge site |

### Easy way to remember

- **Region:** Which geographic AWS area?
- **Availability Zone:** Which isolated location inside that Region?
- **Edge Location:** Where can content be delivered closer to the user?

## 7. Regional Services vs Global Services

AWS services can be regional, global, or have components that operate across multiple locations. Always check the service documentation for its exact scope.

### 7.1 Regional services

A regional service is generally managed within a selected AWS Region.

Examples include:

- Amazon EC2 instances
- Amazon RDS databases
- Amazon VPC
- Amazon EBS volumes
- Many Amazon S3 bucket configurations and resources (S3 is a regional service, although its console and namespace behavior have global aspects)

For example, an EC2 instance launched in Singapore belongs to that Region. To run another instance in another Region, you must create or deploy a separate resource there.

### 7.2 Global services

Some AWS services have global control planes or global resource scopes.

Examples commonly treated as global include:

- AWS Identity and Access Management (IAM)
- Amazon Route 53
- Amazon CloudFront

Service behavior can be nuanced. For example, CloudFront is a global content delivery service, while its origins may be regional. Route 53 is a global DNS service. IAM identities and policies are generally account-wide rather than created separately in each Region.

### 7.3 Comparison

| Question | Regional service | Global service |
|---|---|---|
| Is a Region selected for the resource? | Usually yes | Often no |
| Can resources be separate by Region? | Commonly | Depends on the service |
| Example | EC2, RDS, VPC | IAM, Route 53, CloudFront |
| What should you check? | Region availability, quotas, and configuration | Global scope, supported features, and any regional dependencies |

## 8. High Availability, Fault Tolerance, and Disaster Recovery

These concepts are related, but they are not identical.

### 8.1 High Availability (HA)

High Availability means designing a system to remain accessible with minimal interruption.

Typical techniques:

- Deploy application instances across multiple AZs.
- Put a load balancer in front of application instances.
- Use health checks to stop sending traffic to unhealthy instances.
- Use managed database configurations that support failover.
- Monitor the system and respond to failures.

### 8.2 Fault Tolerance

Fault tolerance means a system can continue operating when a component fails, ideally without interruption to the service.

Fault tolerance usually requires more deliberate redundancy and application design than simply adding another instance.

### 8.3 Disaster Recovery (DR)

Disaster Recovery is the plan and technical capability to restore service after a major disruption.

A DR plan may use another AZ, another Region, backups, replicated data, or a combination.

### 8.4 RTO and RPO

Two important disaster recovery terms:

- **RTO (Recovery Time Objective):** The target maximum time to restore a service after a disruption.
- **RPO (Recovery Point Objective):** The target maximum amount of data loss measured in time.

Example:

A business sets:
- RTO = 2 hours
- RPO = 15 minutes

This means it aims to restore the service within two hours and to limit data loss to no more than approximately 15 minutes of changes, subject to the actual backup and replication design.

### 8.5 Simple comparison

| Concept | Main question | Example |
|---|---|---|
| High Availability | How do we keep the service available? | Run application instances in two AZs |
| Fault Tolerance | Can the system continue through a component failure? | Redundant components and automatic recovery |
| Disaster Recovery | How do we restore service after a major incident? | Recover the workload in another Region |

## 9. Designing a Highly Available Spring Boot Application

### 9.1 Requirements

Imagine an online shopping application with these requirements:

- Customers can browse products and place orders.
- The API should remain available if one AZ has a problem.
- Product images should load efficiently for users in different locations.
- The database must support a recovery strategy.

### 9.2 Example architecture

```text
                         Internet users
                               |
                               v
                         Amazon Route 53
                               |
                               v
                    Application Load Balancer
                               |
                 +-------------+-------------+
                 |                           |
                 v                           v
               AZ-A                         AZ-B
                 |                           |
          Spring Boot EC2              Spring Boot EC2
          application                  application
                 |                           |
                 +-------------+-------------+
                               |
                               v
                       Amazon RDS Multi-AZ
                               |
                               v
                       Order and product data

       Product images ---> Amazon CloudFront ---> Amazon S3
```

### 9.3 How the architecture works

1. Route 53 resolves the application's domain name.
2. The Application Load Balancer receives HTTP or HTTPS traffic.
3. The load balancer sends requests to healthy application instances.
4. Spring Boot instances run in separate Availability Zones.
5. The application connects to an RDS database configured for Multi-AZ availability.
6. Product images are stored in S3 and delivered through CloudFront.
7. CloudWatch can collect metrics and logs for monitoring.

### 9.4 Important implementation considerations

- Deploy application instances in private subnets when appropriate.
- Use security groups to allow only required network traffic.
- Configure load balancer health checks using an application health endpoint.
- Store database credentials in a managed secret store rather than source code.
- Use connection pools and handle database failover events.
- Make order-processing operations safe to retry; consider idempotency keys.
- Back up important data and test restoration procedures.
- Define RTO and RPO based on business requirements.
- Monitor application errors, latency, and infrastructure health.

### 9.5 Multi-AZ vs Multi-Region design

| Design | Typical purpose | Complexity |
|---|---|---|
| Single AZ | Development or workloads that accept AZ-level risk | Low |
| Multi-AZ | High availability within one Region | Medium |
| Multi-Region | Geographic disaster recovery or global application needs | High |

Multi-Region designs introduce additional decisions about data replication, consistency, DNS routing, failover, deployment, and cost. They are not automatically necessary for every application.

## 10. AWS CLI — Working with Regions

### 10.1 Check your current AWS CLI Region

```bash
aws configure get region
```

### 10.2 List enabled Regions for your account

```bash
aws ec2 describe-regions --all-regions \
  --query "Regions[].{Name:RegionName,Status:OptInStatus}" \
  --output table
```

The `--all-regions` option includes Regions with different opt-in statuses. Not every Region is necessarily enabled for use in your account.

### 10.3 List Availability Zones in a Region

```bash
aws ec2 describe-availability-zones \
  --region ap-southeast-1 \
  --query "AvailabilityZones[].{Name:ZoneName,State:State}" \
  --output table
```

This queries the Availability Zones visible to your account in the selected Region.

### 10.4 Run a command in a specific Region

```bash
aws ec2 describe-instances --region ap-southeast-1
```

The `--region` option overrides the default Region for that command.

### 10.5 Set a default Region

```bash
aws configure set region ap-southeast-1
```

This changes the default Region in your local AWS CLI configuration for the selected profile. It does not move existing AWS resources.

### 10.6 Check the configured identity

```bash
aws sts get-caller-identity
```

This helps verify which AWS account and identity your CLI credentials are using.

**Safety note:** These inspection commands do not launch EC2 instances. AWS CLI access still depends on valid credentials and IAM permissions.

### Exercise 2 — Choose the right architecture

**Question:** Your application must remain available if one Availability Zone becomes unavailable. What is a suitable starting design?

**Answer:** Deploy application instances across at least two AZs, use a load balancer with health checks, and ensure the database and other dependencies also have an appropriate availability design.

**Explanation:** Adding a second application instance is not enough if both instances depend on a single-AZ database or another single point of failure.

### Exercise 3 — Understand CloudFront

**Question:** A website stores product images in Amazon S3. Customers in different countries report slow image loading. Which AWS service could help deliver these images closer to users?

**Answer:** Amazon CloudFront.

**Explanation:** CloudFront can cache and deliver content through its global edge network. Correct cache configuration is important.

### Exercise 4 — RTO and RPO

**Question:** A business requires a service to be restored within 30 minutes and wants to lose no more than five minutes of data.

**Answer:**
- RTO = 30 minutes
- RPO = 5 minutes

**Explanation:** RTO describes the recovery-time target. RPO describes the acceptable data-loss window.

### Exercise 5 — Region selection

**Question:** A company based in Vietnam wants to deploy an application for customers in Southeast Asia. Is Singapore automatically the correct Region?

**Answer:** No. Singapore may be a candidate, but the company should test latency, verify service availability, compare costs, and review data-residency and compliance requirements before choosing.

### Exercise 6 — AWS CLI

**Question:** Which command lists Availability Zones in Singapore?

**Answer:**

```bash
aws ec2 describe-availability-zones --region ap-southeast-1
```

## 14. AWS Interview Questions and Answers

### Q1. What is an AWS Region?

**Answer:** An AWS Region is a separate geographic area where AWS operates infrastructure. Customers choose Regions based on factors such as latency, cost, service availability, and compliance.

### Q2. What is an Availability Zone?

**Answer:** An Availability Zone is an isolated location within an AWS Region. It consists of one or more discrete data centres with redundant power, networking, and connectivity.

### Q3. What is the difference between a Region and an Availability Zone?

**Answer:** A Region is a geographic area. An Availability Zone is an isolated location inside a Region. A Region contains multiple AZs.

### Q4. What is an Edge Location?

**Answer:** An Edge Location is a site in AWS's edge network used by services such as CloudFront to deliver content closer to users.

### Q5. What is the purpose of Amazon CloudFront?

**Answer:** CloudFront is a content delivery network that delivers content through AWS's global edge network. It can cache content closer to users and reduce latency for suitable workloads.

### Q6. What is Multi-AZ deployment?

**Answer:** Multi-AZ deployment distributes resources across multiple Availability Zones to improve availability and resilience against certain AZ-level failures.

### Q7. Does Multi-AZ mean that an application can never go down?

**Answer:** No. Multi-AZ improves availability, but failover, application bugs, regional failures, and other dependencies can still cause interruptions. Monitoring, testing, and resilient application design are still required.

### Q8. What is the difference between high availability and disaster recovery?

**Answer:** High availability aims to keep a service running with minimal interruption. Disaster recovery focuses on restoring service after a major disruption.

### Q9. What do RTO and RPO mean?

**Answer:** RTO is the target time to restore service. RPO is the target maximum data-loss window measured in time.

### Q10. Why might a company deploy an application in multiple Regions?

**Answer:** It may need geographic disaster recovery, lower latency for users in different parts of the world, or regional separation for business and compliance requirements.

## 15. Lesson Summary

- **Region:** A separate geographic AWS area.
- **Availability Zone:** An isolated location within a Region.
- **Edge Location:** A location in AWS's edge network used to deliver content closer to users.
- **CloudFront:** A CDN that can cache and deliver content globally.
- **Multi-AZ:** A common design approach for improving availability within a Region.
- **Multi-Region:** A design approach that can support geographic resilience or global workloads, but adds complexity.
- **RTO:** Target time to restore service.
- **RPO:** Target maximum data-loss window.

### Quick memory rule

```text
Region = Geographic area
AZ = Isolated location inside a Region
Edge Location = Deliver content closer to users
Multi-AZ = Improve availability within a Region
Multi-Region = Geographic resilience / global deployment
```
