## 2. S3 Presigned URLs

A **presigned URL** grants temporary access to a specific S3 operation on an object. It is signed using credentials belonging to an AWS principal that has the required permissions.

Common use cases:

- Allow a browser to upload a file directly to S3.
- Allow a customer to download a private document.
- Avoid routing large file bodies through a Spring Boot server.
- Share temporary access without making a bucket public.

### 2.1 Architecture

```text
Browser / Mobile App
        |
        | 1. Request upload permission
        v
   Spring Boot API
        |
        | 2. Authorize user and create presigned URL
        v
   AWS SDK / S3
        |
        | 3. Return short-lived URL
        v
Browser / Mobile App
        |
        | 4. Upload directly to S3
        v
   Private S3 Bucket
```

The backend should authenticate the user and authorize the exact object operation before creating the URL.

### 2.2 Important security properties

- A presigned URL is a bearer capability: anyone who obtains it may use it while it remains valid and the underlying authorization permits the operation.
- Set a short expiration appropriate to the workflow.
- Generate a unique object key on the server.
- Do not log full presigned URLs.
- Do not send presigned URLs through public channels.
- A presigned URL does not make the entire bucket public.
- A URL cannot grant more permission than the signing principal has.
- Temporary credentials can cause a URL to expire earlier than its configured expiration.
- Changing or revoking the signing principal's credentials or permissions can affect access.

### 2.3 Generate a presigned download URL with AWS CLI

The AWS CLI supports presigning an object URL:

```bash
aws s3 presign \
  s3://YOUR-BUCKET-NAME/private/report.pdf \
  --region ap-southeast-1 \
  --expires-in 600
```

This example requests a URL valid for ten minutes, subject to the signing credentials' lifetime and permissions.

### 2.4 Generate a presigned URL with Java SDK v2

Add the S3 presigner dependency alongside the AWS SDK S3 dependency:

```xml
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>s3-presigner</artifactId>
</dependency>
```

Use the same AWS SDK BOM version for all SDK modules.

Example service:

```java
package com.example.storage.service;

import java.time.Duration;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;

import software.amazon.awssdk.regions.Region;
import software.amazon.awssdk.services.s3.model.GetObjectRequest;
import software.amazon.awssdk.services.s3.model.PutObjectRequest;
import software.amazon.awssdk.services.s3.presigner.S3Presigner;
import software.amazon.awssdk.services.s3.presigner.model.GetObjectPresignRequest;
import software.amazon.awssdk.services.s3.presigner.model.PutObjectPresignRequest;

@Service
public class S3PresignService {

    private final String bucket;
    private final S3Presigner presigner;

    public S3PresignService(
            @Value("${app.aws.region}") String region,
            @Value("${app.aws.s3.bucket}") String bucket) {

        this.bucket = bucket;

        this.presigner = S3Presigner.builder()
                .region(Region.of(region))
                .build();
    }

    public String createUploadUrl(String objectKey, String contentType) {
        PutObjectRequest putRequest = PutObjectRequest.builder()
                .bucket(bucket)
                .key(objectKey)
                .contentType(contentType)
                .build();

        PutObjectPresignRequest presignRequest =
                PutObjectPresignRequest.builder()
                        .signatureDuration(Duration.ofMinutes(10))
                        .putObjectRequest(putRequest)
                        .build();

        return presigner.presignPutObject(presignRequest)
                .url()
                .toString();
    }

    public String createDownloadUrl(String objectKey) {
        GetObjectRequest getRequest = GetObjectRequest.builder()
                .bucket(bucket)
                .key(objectKey)
                .build();

        GetObjectPresignRequest presignRequest =
                GetObjectPresignRequest.builder()
                        .signatureDuration(Duration.ofMinutes(5))
                        .getObjectRequest(getRequest)
                        .build();

        return presigner.presignGetObject(presignRequest)
                .url()
                .toString();
    }
}
```

In a production service, manage the presigner as a Spring bean and close it during application shutdown. Validate the requested object against the authenticated user's authorization before generating a URL. If you sign a `Content-Type` header, the client must send the matching header.

### 2.5 Browser upload example

The browser can use the returned URL:

```javascript
async function uploadFile(presignedUrl, file) {
  const response = await fetch(presignedUrl, {
    method: "PUT",
    headers: {
      "Content-Type": file.type
    },
    body: file
  });

  if (!response.ok) {
    throw new Error(`Upload failed: ${response.status}`);
  }
}
```

The browser's origin must be allowed by the bucket's CORS configuration for browser-based cross-origin requests. CORS is not an authorization mechanism; S3 permissions still control access.

## 3. Multipart Upload

Multipart upload allows a large object to be uploaded as separate parts.

The process:

1. Initiate a multipart upload.
2. Upload each part.
3. Collect each part's part number and ETag.
4. Complete the multipart upload.
5. Or abort the upload if it should not be kept.

```text
                 Large File
                     |
          +----------+----------+
          |          |          |
        Part 1     Part 2     Part 3
          |          |          |
          v          v          v
        Upload     Upload     Upload
          |          |          |
          +----------+----------+
                     |
               Complete upload
                     |
                     v
                S3 Object
```

### 3.1 Benefits

- Parts can be uploaded in parallel.
- Failed parts can be retried independently.
- Large uploads can be more resilient to network interruptions.
- The application can control upload concurrency.

Multipart upload is particularly useful for large files and unreliable networks. The S3 service has minimum part-size and maximum part-count constraints; consult current S3 limits when implementing a production uploader. The final part has different minimum-size handling from other parts.

### 3.2 AWS CLI

The high-level `aws s3 cp` command automatically uses multipart upload for sufficiently large files according to CLI behavior and configuration.

```bash
aws s3 cp ./large-video.mp4 \
  s3://YOUR-BUCKET-NAME/videos/large-video.mp4
```

For tuning multipart behavior, inspect the AWS CLI S3 configuration options supported by your installed CLI version.

### 3.3 Incomplete multipart uploads

If an upload is initiated but never completed or aborted, uploaded parts can remain and incur storage charges.

Configure a lifecycle rule to abort incomplete multipart uploads after an appropriate number of days.

## 4. S3 Event Notifications

S3 event notifications allow other services to react when objects are created, deleted, restored, or otherwise changed through supported event types.

Common destinations include:

- Amazon SQS.
- Amazon SNS.
- AWS Lambda.
- Amazon EventBridge, when enabled/configured for the bucket.

### 4.1 Example architecture: image processing

```text
User uploads image
        |
        v
   S3 input bucket
        |
        | ObjectCreated event
        v
      Lambda
        |
        | Resize / generate thumbnail
        v
   S3 output prefix
```

Other examples:

- A CSV upload triggers data validation.
- A PDF upload triggers text extraction.
- A video upload triggers a transcoding workflow.
- A new backup object triggers a verification job.

### 4.2 Event notification considerations

- Event notifications are delivered at least once in common S3 notification flows; design consumers to tolerate duplicates.
- Event delivery and processing are asynchronous.
- Do not assume notifications arrive in the same order as object operations.
- A consumer should be idempotent.
- Avoid writing processed output into the same triggering prefix unless recursion is intentionally prevented.
- Use event keys and version IDs where relevant to identify the correct object state.

### 4.3 Idempotency

An idempotent processor can handle the same event more than once without creating duplicate side effects.

Possible techniques:

- Record processed event identifiers or object versions.
- Use a deterministic output key.
- Check whether the intended output already exists.
- Use a database transaction or deduplication table for business operations.

### 4.4 Configure event notifications

A bucket notification configuration can route selected object events to a supported destination. Destination permissions must allow S3 to invoke or publish to that destination.

For example, a Lambda function's resource-based policy must allow invocation by the relevant S3 bucket. The bucket and Lambda destination must meet the service's Region requirements.

In production, use the console, infrastructure as code, or the documented API to configure notification destinations and permissions together. Avoid replacing an existing bucket notification configuration without first reviewing it: a `put-bucket-notification-configuration` operation can replace the bucket's current notification configuration.

Inspect notifications:

```bash
aws s3api get-bucket-notification-configuration \
  --bucket YOUR-BUCKET-NAME
```

## 5. Event-Driven Processing with Lambda

AWS Lambda runs code in response to events without requiring you to manage EC2 servers.

Example flow:

```text
S3 ObjectCreated
       |
       v
Lambda function
       |
       +---- Read uploaded object
       |
       +---- Validate file
       |
       +---- Generate thumbnail
       |
       +---- Write output to S3
       |
       +---- Store processing status
```

### 5.1 Lambda execution role

The Lambda function needs an execution role with only the permissions it requires.

For example:
- `s3:GetObject` for the input prefix.
- `s3:PutObject` for the output prefix.
- Logging permissions for CloudWatch Logs.

If the bucket uses SSE-KMS, the function may also need appropriate KMS permissions.

### 5.2 Avoid recursive triggers

A common error:

```text
S3 upload
   |
   v
Lambda
   |
   v
Write result to same triggering prefix
   |
   v
S3 upload event
   |
   v
Lambda again
```

Safer design:

```text
Input bucket/prefix:  incoming/
Output bucket/prefix: processed/
```

Configure the notification to trigger only for the `incoming/` prefix, or use separate buckets.

### 5.3 Reliability

For reliable processing:
- Make handlers idempotent.
- Configure retries and failure handling appropriate to the invocation model.
- Use a dead-letter or failure destination where supported and useful.
- Monitor errors, throttles, duration, and concurrency.
- Keep processing within Lambda's execution and payload limits.
- For long-running or complex workflows, consider SQS, Step Functions, or container-based processing.

## 6. S3 Replication: SRR and CRR

Replication automatically copies eligible objects from a source bucket to a destination bucket.

Two common types:

- **Same-Region Replication (SRR):** Source and destination buckets are in the same Region.
- **Cross-Region Replication (CRR):** Source and destination buckets are in different Regions.

### 6.1 Use cases

| Use case | Possible approach |
|---|---|
| Keep a second copy in the same Region | SRR |
| Disaster recovery in another Region | CRR |
| Meet data locality or processing requirements | SRR or CRR, based on policy |
| Aggregate data into a central bucket | SRR or CRR |
| Reduce latency for users in another Region | CRR plus an appropriate delivery architecture |

### 6.2 Replication architecture

```text
Source bucket
Region A
    |
    | Replication rule
    v
Destination bucket
Region B
```

### 6.3 Requirements and considerations

Replication setup commonly requires:

- Versioning enabled on both source and destination buckets.
- A replication IAM role that S3 can assume.
- A replication rule selecting eligible objects.
- Appropriate destination permissions.
- KMS permissions when replicating objects encrypted with customer-managed KMS keys.
- A plan for existing objects, because enabling a rule does not automatically mean every pre-existing object is replicated retroactively.

S3 Replication Time Control is an optional feature for customers who need a predictable replication time objective for eligible objects. Standard replication is asynchronous and should not be treated as synchronous replication.

### 6.4 Replication is not a complete backup strategy

Replication can also copy unwanted changes or deletions, depending on configuration and the operation. Consider versioning, Object Lock, separate account boundaries, and recovery testing for stronger protection.

## 7. S3 Object Lock

S3 Object Lock helps prevent objects from being deleted or overwritten for a specified retention period or indefinitely under a legal hold.

It supports a WORM model:

**Write Once, Read Many.**

Typical use cases:
- Regulatory retention.
- Financial records.
- Audit logs.
- Compliance archives.
- Evidence preservation.

### 7.1 Retention modes

| Mode | Protection | Typical use |
|---|---|---|
| Governance mode | Authorized principals with special permissions may bypass retention | Controlled internal retention |
| Compliance mode | Protected versions cannot be overwritten or deleted before retention expires, including by the account root user | Strict regulatory retention |

### 7.2 Legal hold

A legal hold can keep an object version protected until the hold is removed by an authorized principal. It does not require a fixed retention end date.

### 7.3 Important planning notes

- Object Lock must be enabled for the bucket according to S3's supported setup requirements.
- Versioning is required.
- Retention applies to object versions.
- Compliance mode is very restrictive; mistakes can make data unavailable for deletion until the retention period ends.
- Object Lock is not a replacement for IAM least privilege, monitoring, or a tested recovery plan.

Do not enable compliance retention casually on a training bucket containing data you may need to delete.

## 8. S3 Access Points

An S3 Access Point provides a named network endpoint and access policy for accessing objects in a bucket.

It can simplify access management for applications, teams, and datasets that need different permissions.

### 8.1 Concept

```text
                  S3 Bucket
                      |
           +----------+----------+
           |                     |
     Access Point A         Access Point B
     Analytics team         Application team
           |                     |
      Read dataset          Read/write uploads
```

Access Points do not create separate storage. They provide controlled access paths to the same underlying bucket.

Access Points can have network-origin restrictions and their own policies. They work alongside bucket policies and IAM policies; they do not bypass them.

### 8.2 When to use them

- Many applications access one bucket.
- Different teams need different access policies.
- You want separate network access constraints.
- A large data lake needs multiple controlled access paths.

## 9. CORS for Browser-Based S3 Uploads

**Cross-Origin Resource Sharing (CORS)** is a browser security mechanism that controls whether a web page from one origin can make certain cross-origin requests.

Example:
- Frontend: `https://app.example.com`
- S3 request: `https://bucket.s3.ap-southeast-1.amazonaws.com`

The browser may send a preflight `OPTIONS` request before a `PUT` request.

### 9.1 Example CORS configuration

This is an illustrative configuration. Replace the allowed origin and headers with the exact values required by your application.

```json
[
  {
    "AllowedOrigins": [
      "https://app.example.com"
    ],
    "AllowedMethods": [
      "GET",
      "PUT",
      "HEAD"
    ],
    "AllowedHeaders": [
      "content-type",
      "x-amz-*"
    ],
    "ExposeHeaders": [
      "ETag"
    ],
    "MaxAgeSeconds": 3000
  }
]
```

Apply it:

```bash
aws s3api put-bucket-cors \
  --bucket YOUR-BUCKET-NAME \
  --cors-configuration file://cors.json
```

Inspect it:

```bash
aws s3api get-bucket-cors \
  --bucket YOUR-BUCKET-NAME
```

### 9.2 CORS is not authorization

CORS does not grant S3 permissions. A request can pass CORS checks but still receive `AccessDenied` because IAM, bucket policy, KMS, or another authorization layer denies it.

Avoid using `*` for allowed origins in production when a specific frontend origin is known.

## 10. Spring Boot Advanced S3 Upload Design

A robust design separates authorization, metadata, and binary file transfer.

### 10.1 Recommended architecture

```text
Browser
   |
   | 1. Request upload
   v
Spring Boot API
   |
   +---- Authenticate user
   |
   +---- Validate file metadata and business rules
   |
   +---- Generate unique object key
   |
   +---- Create upload record in database
   |
   +---- Generate presigned PUT URL
   |
   v
Browser
   |
   | 2. PUT file directly
   v
Private S3 bucket
   |
   | 3. ObjectCreated event
   v
Processing service / Lambda
   |
   +---- Validate actual object
   +---- Scan or process file
   +---- Update database status
```

### 10.2 Why keep file metadata in a database?

S3 stores the object bytes and object metadata. A relational database can store application-specific information such as:

- Owner user ID.
- Original filename.
- Generated object key.
- Upload status.
- File size.
- Detected content type.
- Creation time.
- Business entity association.

Example table:

```sql
CREATE TABLE uploaded_files (
    id BIGINT PRIMARY KEY,
    owner_id BIGINT NOT NULL,
    object_key VARCHAR(1024) NOT NULL UNIQUE,
    original_filename VARCHAR(255),
    content_type VARCHAR(255),
    file_size BIGINT,
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

The schema is illustrative. Choose database-specific types and indexing based on your system.

### 10.3 Upload status workflow

```text
PENDING_UPLOAD
      |
      | Client uploads to S3
      v
UPLOADED
      |
      | Validation / scanning
      v
PROCESSING
      |
      +------> AVAILABLE
      |
      +------> REJECTED
```

Do not mark a file as available merely because a presigned URL was issued. Confirm that the object exists and has passed required validation.

### 10.4 Security checklist

- Authenticate the user before issuing a presigned URL.
- Verify the user can upload to the intended business record.
- Generate the object key on the server.
- Limit upload size and allowed file types.
- Sign required content-type or checksum headers where appropriate.
- Keep the bucket private.
- Use least-privilege IAM roles.
- Validate the object after upload.
- Consider malware scanning for untrusted files.
- Do not trust filenames or client-supplied MIME types.
- Avoid logging presigned URLs.
- Use encryption and suitable retention controls.
- Apply rate limits and quotas to upload requests.

## 12. Hands-on Lab — Direct Browser Upload with a Presigned URL

### Goal

Build a workflow where Spring Boot authorizes an upload, the browser sends the file directly to S3, and an event-driven process verifies the result.

### Step 1 — Prepare a private bucket

1. Create a bucket in `ap-southeast-1`.
2. Keep Block Public Access enabled.
3. Enable versioning for the lab.
4. Configure default encryption.
5. Create an `incoming/` prefix for uploads.

### Step 2 — Create an application IAM role

Allow only the required operations on the intended prefix. For a presigned upload, the signing principal needs permission to perform the signed `PutObject` operation.

Avoid granting broad `s3:*` permissions.

### Step 3 — Build the presigned URL endpoint

Create a Spring Boot endpoint that:
1. Authenticates the user.
2. Validates the requested upload.
3. Generates a unique object key.
4. Creates a short-lived presigned PUT URL.
5. Returns the URL and object key.

Do not accept an arbitrary bucket name or unrestricted object key from the client.

### Step 4 — Configure CORS

Allow only the frontend origin and methods required by the upload flow. Include the headers that the browser must send.

### Step 5 — Upload from the browser

Use `fetch()` with `PUT` and the presigned URL. Send any headers that were included in the signature.

### Step 6 — Verify the object

Use:

```bash
aws s3api head-object \
  --bucket YOUR-BUCKET-NAME \
  --key "incoming/YOUR-GENERATED-KEY"
```

The application should verify object ownership and metadata before marking the upload available.

### Step 7 — Configure an event notification

Configure an `ObjectCreated` event for the `incoming/` prefix to trigger a processing destination.

Ensure the destination's resource policy allows the event source.

### Step 8 — Process idempotently

The processing function should:
- Validate the object.
- Avoid processing the same object version twice.
- Write output to a different prefix, such as `processed/`.
- Record success or failure.
- Send failed work to a suitable retry or failure-handling path.

### Step 9 — Test failure cases

Test:
- Expired URL.
- Wrong content type when signed.
- Unauthorized user.
- Duplicate event.
- Missing object.
- Processing failure.
- Large upload interruption.

### Step 10 — Clean up

Delete lab objects and all object versions if versioning is enabled. Remove event configurations, functions, roles, and other resources that are no longer needed. Review S3 storage, requests, Lambda invocations, CloudWatch Logs, KMS usage, and data transfer for charges.

## 13. Troubleshooting

| Problem | Possible cause | What to inspect |
|---|---|---|
| Presigned URL returns AccessDenied | Signing role lacks permission or a policy denies access | IAM, bucket policy, KMS policy |
| Presigned URL expires early | Signing credentials expired or URL expired | Credential lifetime and URL expiration |
| Browser upload fails before reaching S3 | CORS preflight rejected | Origin, method, allowed headers |
| Browser gets 403 | Signature mismatch or authorization denial | Signed headers, Region, clock, permissions |
| Multipart upload remains incomplete | Client failed before completion | Multipart upload list and lifecycle cleanup |
| Lambda is not invoked | Notification or destination permission is wrong | Bucket notification and Lambda resource policy |
| Lambda processes an object repeatedly | Duplicate event or recursive output trigger | Idempotency and prefix filters |
| Replication does not occur | Versioning, IAM role, rule, KMS, or destination issue | Replication metrics and configuration |
| Object cannot be deleted | Object Lock retention or legal hold | Object version retention and legal hold |
| Browser can call API but cannot upload to S3 | S3 CORS or presigned request mismatch | CORS configuration and request headers |

### Debugging order

1. Identify the signing or application principal.
2. Check the exact bucket and object key.
3. Verify IAM identity permissions.
4. Review bucket policy and explicit Deny statements.
5. Check KMS permissions if SSE-KMS is used.
6. For browser requests, inspect preflight and actual request headers.
7. For event processing, inspect notification configuration and destination permissions.
8. Check CloudWatch Logs and metrics for the consumer.
9. Confirm that retries and duplicate events are handled safely.

## 14. Exercises with Answers

### Exercise 1 — Presigned URL

What is a presigned URL?

**Answer:** It is a time-limited URL that authorizes a specific S3 operation using a signature created by an AWS principal with the required permissions.

### Exercise 2 — Presigned URL security

Why should a presigned URL be treated like a secret?

**Answer:** Anyone who obtains it may be able to perform the signed operation while the URL is valid and the underlying authorization remains effective.

### Exercise 3 — Multipart upload

Why is multipart upload useful for large files?

**Answer:** It splits the file into parts that can be uploaded independently, often in parallel, and failed parts can be retried without restarting the entire upload.

### Exercise 4 — Event notifications

Why should an S3 event consumer be idempotent?

**Answer:** Events may be delivered more than once, and processing can be retried. Idempotency prevents duplicate business side effects.

### Exercise 5 — Replication

What is the difference between SRR and CRR?

**Answer:** SRR replicates objects between buckets in the same Region. CRR replicates objects between buckets in different Regions.

### Exercise 6 — Object Lock

What is the difference between Governance and Compliance mode?

**Answer:** Governance mode can be bypassed by specially authorized principals. Compliance mode prevents deletion or overwrite of protected versions before retention expires, even by the account root user.

### Exercise 7 — CORS

Does CORS grant permission to read or write an S3 object?

**Answer:** No. CORS controls browser cross-origin behavior. IAM and S3 resource policies determine authorization.

### Exercise 8 — Recursive Lambda

How can you prevent a Lambda function from repeatedly triggering itself after writing a processed object?

**Answer:** Use separate input and output prefixes or buckets, and configure event filters to match only the input location.

### Exercise 9 — Direct upload

Why might a browser upload directly to S3 rather than send the file through Spring Boot?

**Answer:** It reduces backend bandwidth and memory usage and allows S3 to handle the file transfer. The backend still authorizes the upload and verifies the result.

### Exercise 10 — Object retention

Why should Object Lock Compliance mode be planned carefully?

**Answer:** Protected versions cannot be deleted before the retention period ends, even by the account root user. An incorrect retention period can make data impossible to remove for a long time.

## 17. AWS Interview Questions and Answers

### 1. What is a presigned URL?

**Answer:** A presigned URL is a time-limited URL that grants access to a specific S3 operation using a signature created by an authorized AWS principal.

### 2. Is a presigned URL safe to share publicly?

**Answer:** No. Treat it as a bearer capability. Anyone who obtains it may use it while it is valid and authorized.

### 3. What is multipart upload?

**Answer:** Multipart upload divides an object into parts, uploads the parts separately, and completes the upload to assemble the final object.

### 4. What happens to incomplete multipart uploads?

**Answer:** Uploaded parts can remain stored and incur charges until the upload is completed or aborted. A lifecycle rule can abort incomplete multipart uploads after a configured period.

### 5. How does S3 trigger Lambda?

**Answer:** An S3 event notification can invoke a Lambda function when a configured object event occurs, provided the required destination permissions are configured.

### 6. Why should an S3-triggered Lambda be idempotent?

**Answer:** Event delivery can be duplicated or retried. Idempotency prevents duplicate side effects.

### 7. What is the difference between SRR and CRR?

**Answer:** SRR copies eligible objects to a destination bucket in the same Region. CRR copies eligible objects to a destination bucket in another Region.

### 8. Does replication copy existing objects automatically?

**Answer:** Enabling a replication rule generally applies to eligible new objects. Existing objects require a separate approach, such as S3 Batch Replication, where appropriate.

### 9. What is S3 Object Lock?

**Answer:** It provides WORM-style protection for object versions through retention periods and legal holds.

### 10. What is the difference between Governance and Compliance retention modes?

**Answer:** Governance mode permits specially authorized bypass. Compliance mode does not permit protected versions to be deleted or overwritten before the retention period ends.

### 11. What is an S3 Access Point?

**Answer:** It is a named endpoint with an access policy that provides a controlled way to access a bucket, often for different applications or teams.

### 12. What is the purpose of CORS?

**Answer:** CORS controls which browser origins can make cross-origin requests to a resource. It does not grant AWS authorization.

### 13. How would you design a secure file-upload service?

**Answer:** I would authenticate the user in Spring Boot, authorize the upload, generate a unique object key, create a short-lived presigned URL, and let the browser upload directly to a private S3 bucket. I would then validate the uploaded object and update its status in the database.

### 14. How do you avoid recursive S3-to-Lambda triggers?

**Answer:** I would write processed files to a separate prefix or bucket and configure the event notification to match only the input prefix.
