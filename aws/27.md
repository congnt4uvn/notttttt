## 2. What Is a Relational Database?

A relational database stores structured data in tables. Tables contain rows and columns, and relationships can be represented using keys.

Example: an online store.

```text
customers
+----+-----------+----------------------+
| id | name      | email                |
+----+-----------+----------------------+
|  1 | Alex      | alex@example.com     |
|  2 | Maria     | maria@example.com    |
+----+-----------+----------------------+

orders
+----+-------------+--------+------------+
| id | customer_id | total  | status     |
+----+-------------+--------+------------+
| 10 |           1 | 120.00 | PAID       |
| 11 |           2 |  75.00 | PENDING    |
+----+-------------+--------+------------+
```

The `customer_id` column in `orders` can reference the `id` column in `customers`.

### 2.1 Important database concepts

| Concept | Meaning |
|---|---|
| Table | A structure containing related records |
| Row | One record |
| Column | One attribute of a record |
| Primary key | Uniquely identifies a row |
| Foreign key | References a key in another table |
| Index | Helps find rows efficiently |
| Transaction | A logical unit of database work |
| SQL | Language used to query and manage relational data |

### 2.2 ACID properties

Relational database transactions are commonly described using ACID:

- **Atomicity:** A transaction succeeds as a whole or is rolled back.
- **Consistency:** A transaction preserves defined database rules and constraints.
- **Isolation:** Concurrent transactions are controlled according to the isolation level.
- **Durability:** Committed changes are persisted according to the database's durability guarantees.

Example: transferring money between two accounts should debit one account and credit the other as one transaction.

## 3. What Is Amazon RDS?

**Amazon Relational Database Service (Amazon RDS)** is a managed relational database service.

AWS manages many operational tasks, such as:
- Provisioning database infrastructure.
- Operating system and database maintenance tasks supported by the service.
- Automated backups.
- Monitoring integration.
- Configurable maintenance windows.
- High-availability deployment options.

You remain responsible for:
- Database schema and query design.
- User and privilege management.
- Application connection management.
- Data classification and access controls.
- Performance tuning and capacity planning.
- Backup and recovery testing.
- Choosing appropriate maintenance and failover behavior.

RDS reduces database administration work, but it does not eliminate the need for database engineering.

### 3.1 RDS architecture

```text
                 Application Users
                        |
                        v
                 Spring Boot API
                        |
                 Private Network
                        |
                        v
                  Amazon RDS
                        |
              +---------+---------+
              |                   |
          Database            Automated
           storage              backups
```

The application normally connects to RDS through a private network path rather than exposing the database to the public internet.

## 4. RDS Database Engines

RDS supports several relational database engines. Availability and supported versions vary by Region and change over time.

| Engine | Typical use case |
|---|---|
| Amazon RDS for MySQL | Web applications and general relational workloads |
| Amazon RDS for PostgreSQL | Advanced SQL features and extensibility |
| Amazon RDS for MariaDB | Applications using the MariaDB ecosystem |
| Amazon RDS for Oracle | Applications requiring Oracle compatibility |
| Amazon RDS for SQL Server | Applications built around Microsoft SQL Server |
| Amazon Aurora | AWS-built relational database compatible with MySQL or PostgreSQL |

Aurora is part of the RDS family but has a different architecture and pricing model from standard RDS database engines. It uses a distributed storage design and has its own cluster and instance concepts.

### 4.1 Choosing an engine

Consider:

1. Existing application compatibility.
2. SQL dialect and database-specific features.
3. Licensing costs.
4. Team experience.
5. Extension and tooling requirements.
6. Performance and scaling requirements.
7. Migration complexity.
8. Availability in the intended Region.

For a typical Spring Boot learning project, MySQL or PostgreSQL is a practical starting point.

## 5. RDS Core Components

### 5.1 DB instance

A DB instance is the compute environment running a database engine.

It is configured with:
- DB instance class.
- Engine and engine version.
- Allocated storage.
- Network settings.
- Credentials and authentication configuration.
- Backup and maintenance settings.

### 5.2 DB instance class

The DB instance class determines compute and memory capacity.

Examples of broad instance families include:
- General purpose.
- Memory optimized.
- Burstable performance.

Choose a class based on measured workload, memory use, connection count, and query performance. Do not choose solely by the number of application users.

### 5.3 Storage

RDS storage options depend on engine, instance configuration, and Region. Common storage types include General Purpose SSD and Provisioned IOPS SSD options.

Consider:
- Allocated storage.
- IOPS and throughput.
- Storage autoscaling, where supported.
- Expected growth.
- Backup retention.
- Storage performance during peak load.

Storage autoscaling can increase allocated storage when configured thresholds are reached, but it does not automatically shrink allocated storage later.

### 5.4 DB subnet group

A DB subnet group identifies subnets in a VPC that RDS can use.

For a Multi-AZ design, include subnets in at least two Availability Zones.

```text
                    VPC
                     |
              DB Subnet Group
                 /       \
              AZ-a       AZ-b
               |           |
          Private subnet  Private subnet
               \           /
                \         /
                 Amazon RDS
```

A DB subnet group is not a security group. It determines eligible network locations; security groups control traffic.

### 5.5 Parameter group

A DB parameter group controls supported database engine settings.

Examples may include:
- Connection limits.
- Logging settings.
- Memory-related parameters.
- Time zone behavior.
- Engine-specific configuration.

Some parameters are dynamic and apply immediately; others require a reboot. The exact behavior depends on the engine and parameter.

### 5.6 Option group

For engines that support option groups, an option group enables additional engine features. Availability and behavior depend on the database engine.

## 6. Network Security for RDS

A common production pattern is to place the database in private subnets and allow application access only from the application security group.

```text
Internet
   |
   v
Application Load Balancer
   |
   v
Spring Boot EC2 / ECS
Security Group: app-sg
   |
   | Database port allowed from app-sg
   v
Amazon RDS
Security Group: db-sg
```

### 6.1 Security group rules

Example for MySQL:

**Application security group**
- Inbound: application traffic from the ALB security group.
- Outbound: required database traffic to the RDS security group.

**Database security group**
- Inbound TCP 3306 from the application security group only.
- Avoid allowing database access from `0.0.0.0/0`.

For PostgreSQL, the default port is commonly TCP 5432.

Use the actual configured database port if it differs.

### 6.2 Public accessibility

For most application databases, set public accessibility to `No`.

Public accessibility does not by itself guarantee that a database can be reached; routing, security groups, network ACLs, and other controls still matter. Nevertheless, private placement is the safer default for an application database.

### 6.3 Encryption in transit

Use TLS for application-to-database connections where supported and required. Configure the client to validate the database server certificate rather than simply disabling certificate checks.

### 6.4 Encryption at rest

RDS supports encryption at rest using AWS KMS. Encryption should be selected during database creation or planned carefully for migration because enabling encryption on an existing unencrypted DB instance generally requires a snapshot-copy or migration workflow.

## 7. Create an RDS Database

You can create an RDS DB instance using the AWS Console, CLI, or infrastructure as code.

Before creation, decide:
- Engine and engine version.
- DB instance class.
- Storage type and size.
- VPC and DB subnet group.
- Security group.
- Public accessibility.
- Master credentials or supported authentication method.
- Backup retention.
- Encryption and KMS key.
- Multi-AZ requirements.
- Deletion protection.

### 7.1 Example CLI command

The following is an illustrative MySQL example. Replace all placeholders and choose a supported engine version and instance class for your Region.

```bash
aws rds create-db-instance \
  --region ap-southeast-1 \
  --db-instance-identifier app-mysql-db \
  --engine mysql \
  --db-instance-class db.t3.micro \
  --allocated-storage 20 \
  --storage-type gp3 \
  --master-username appadmin \
  --manage-master-user-password \
  --vpc-security-group-ids sg-REPLACE_ME \
  --db-subnet-group-name app-db-subnet-group \
  --backup-retention-period 7 \
  --no-publicly-accessible \
  --storage-encrypted
```

Notes:
- Confirm that the selected instance class is supported for the chosen engine and Region.
- `--manage-master-user-password` asks RDS to manage the master password using AWS Secrets Manager, subject to engine and configuration support.
- This command is a learning example; production configurations should also consider deletion protection, maintenance windows, monitoring, and appropriate availability settings.
- Do not place database passwords directly in shell history or source control.

### 7.2 Check creation status

```bash
aws rds describe-db-instances \
  --region ap-southeast-1 \
  --db-instance-identifier app-mysql-db
```

Wait until the DB instance status is `available` before connecting.

### 7.3 Get the endpoint

```bash
aws rds describe-db-instances \
  --region ap-southeast-1 \
  --db-instance-identifier app-mysql-db \
  --query "DBInstances[0].Endpoint"
```

The endpoint is a DNS name, not a fixed IP address to hard-code into application logic.

## 8. Multi-AZ Deployments

Multi-AZ is an availability and failover feature.

In a traditional RDS Multi-AZ DB instance deployment, RDS maintains a standby in another Availability Zone and uses synchronous replication for the supported configuration. The standby is not normally used for read traffic.

```text
                 Application
                      |
                      v
                RDS endpoint
                      |
                +-----+-----+
                |           |
              AZ-a        AZ-b
                |           |
             Primary      Standby
                |           |
                +--- sync --+
                 replication
```

If a supported failure occurs, RDS can fail over to the standby. The endpoint is designed to redirect clients to the new primary.

### 8.1 Benefits

- Higher availability.
- Managed failover for supported failure scenarios.
- Reduced operational burden for maintaining a standby.

### 8.2 Important limitations

- Failover causes a connection interruption.
- Applications must reconnect.
- Failover does not protect against every application-level error.
- Multi-AZ is not a read-scaling solution in the traditional standby configuration.
- Costs are higher than a single-AZ deployment.

Some RDS engines also offer Multi-AZ DB cluster deployment options with different architecture and read behavior. Check the specific engine and deployment type rather than assuming all Multi-AZ options work identically.

## 9. Read Replicas

A read replica is a separate database instance that receives replicated changes from a source database and can serve read queries.

```text
                 Application
                      |
              +-------+-------+
              |               |
           Writes           Reads
              |               |
              v               v
         Primary DB       Read Replica
              |               ^
              +-- replication-+
```

### 9.1 Common use cases

- Reporting workloads.
- Read-heavy applications.
- Offloading read queries.
- Some cross-Region read architectures, where supported.

### 9.2 Read replica vs. Multi-AZ standby

| Feature | Multi-AZ standby (traditional DB instance deployment) | Read replica |
|---|---|---|
| Main purpose | High availability | Read scaling |
| Normally serves application reads | No | Yes |
| Replication behavior | Synchronous for supported traditional Multi-AZ setup | Typically asynchronous |
| Failover role | Managed standby promotion | Can be promoted through supported operations |
| Read lag | Not applicable as a read endpoint | Replication lag can occur |

Do not assume a read replica always contains the latest committed write. Applications may need to tolerate replication lag or route consistency-sensitive reads to the primary.

## 10. Automated Backups and Snapshots

RDS provides automated backups and manual snapshots.

### 10.1 Automated backups

Automated backups support point-in-time recovery within the configured retention period, subject to engine and service behavior.

They include database storage backups and transaction logs needed for recovery.

Important settings:
- Backup retention period.
- Preferred backup window.
- Maintenance window.
- Backup storage and retention costs.

### 10.2 Manual snapshots

Manual snapshots are created on demand and retained until you delete them.

Use cases:
- Before a major database change.
- Before a migration.
- Before testing an upgrade.
- Long-term retention of a known database state.

### 10.3 Point-in-time recovery

Point-in-time recovery creates a new DB instance restored to a selected time within the available backup window.

This is useful when:
- A table was accidentally modified.
- Data was deleted.
- A bad application release wrote incorrect data.

A point-in-time restore normally creates a new DB instance rather than rewinding the existing instance in place.

### 10.4 Create a manual snapshot

```bash
aws rds create-db-snapshot \
  --region ap-southeast-1 \
  --db-instance-identifier app-mysql-db \
  --db-snapshot-identifier app-mysql-before-change
```

Inspect snapshots:

```bash
aws rds describe-db-snapshots \
  --region ap-southeast-1 \
  --db-instance-identifier app-mysql-db
```

### 10.5 Backup strategy

A robust plan should define:
- Recovery Point Objective (RPO): how much data loss is acceptable.
- Recovery Time Objective (RTO): how long recovery may take.
- Backup retention.
- Snapshot retention and ownership.
- Cross-Region or cross-account copy needs.
- Restore testing frequency.
- Who can delete backups.

A backup is not proven until restoration has been tested.

## 11. Spring Boot Integration with RDS

A Spring Boot application commonly connects to RDS using JDBC and a connection pool such as HikariCP.

### 11.1 Architecture

```text
                 Users
                   |
                   v
             Application ALB
                   |
                   v
             Spring Boot API
                   |
             JDBC / HikariCP
                   |
                   v
              Amazon RDS
```

### 11.2 Maven dependencies

Example for MySQL:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>
```

Use dependency versions managed by your Spring Boot parent or BOM rather than manually mixing incompatible versions.

### 11.3 application.yml

```yaml
spring:
  datasource:
    url: jdbc:mysql://${DB_HOST}:3306/appdb
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver

    hikari:
      maximum-pool-size: 10
      minimum-idle: 2
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000

  jpa:
    hibernate:
      ddl-auto: validate
    properties:
      hibernate:
        dialect: org.hibernate.dialect.MySQLDialect
```

For production:
- Supply credentials through a secure configuration mechanism.
- Prefer Secrets Manager integration or another approved secret-delivery pattern.
- Do not commit credentials to Git.
- Use schema migration tools such as Flyway or Liquibase.
- Avoid using `ddl-auto: update` as a substitute for controlled database migrations.

### 11.4 Connection pool sizing

HikariCP manages reusable database connections.

Suppose:
- Maximum application instances: 6.
- Hikari maximum pool size per instance: 10.

The theoretical application connection maximum is:

```text
6 instances × 10 connections = 60 connections
```

This excludes administration, monitoring, migrations, and other services.

The database must be sized for total connections and query workload. Increasing the pool size is not automatically a performance improvement.

### 11.5 Database migrations

Use Flyway or Liquibase to manage schema changes.

Example Flyway migration:

`V1__create_customers.sql`

```sql
CREATE TABLE customers (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Migrations should be reviewed, tested, and compatible with the deployment sequence. For rolling deployments, prefer backward-compatible schema changes.

## 12. RDS Monitoring and Performance

Useful monitoring signals include:

- CPU utilization.
- Freeable memory.
- Free storage space.
- Database connections.
- Read and write IOPS.
- Read and write latency.
- Network throughput.
- Replica lag.
- Deadlocks and slow queries.

CloudWatch provides RDS metrics. Enhanced Monitoring and Performance Insights or the currently available database performance tools can provide deeper insight, depending on engine and configuration.

### 12.1 Query performance

A slow application may be caused by:
- Missing indexes.
- Full table scans.
- Inefficient joins.
- N+1 ORM queries.
- Lock contention.
- Too many concurrent connections.
- Insufficient memory or I/O capacity.

Use query plans and database performance tools rather than simply increasing instance size.

### 12.2 Connection management

Applications should:
- Reuse connections through a pool.
- Close connections and statements correctly.
- Use transaction boundaries deliberately.
- Set reasonable connection and query timeouts.
- Retry only transient failures and do so carefully.
- Avoid retrying non-idempotent transactions blindly.

## 14. Hands-on Lab — Spring Boot with a Private RDS Database

### Goal

Create a private MySQL RDS instance and connect to it from a Spring Boot application running in the same VPC.

### Step 1 — Prepare the VPC

1. Choose a VPC.
2. Select private subnets in at least two AZs for the DB subnet group.
3. Confirm the application compute environment can route to the database subnets.
4. Do not expose the database directly to the internet.

### Step 2 — Create security groups

Application security group:
- Allow inbound application traffic from the ALB security group.
- Allow outbound MySQL traffic to the DB security group.

Database security group:
- Allow inbound TCP 3306 from the application security group only.

### Step 3 — Create the DB subnet group

Select private subnets in at least two AZs.

### Step 4 — Create RDS

For a learning environment:
- Engine: MySQL.
- Instance class: a low-cost class supported in your Region.
- Storage: suitable small lab allocation.
- Public accessibility: No.
- Encryption: Enabled.
- Backup retention: choose an appropriate short lab period.
- Deletion protection: consider enabling it until you are ready to clean up.

The exact options and cost depend on the selected engine, class, storage, and Region.

### Step 5 — Wait for availability

Use the RDS console or:

```bash
aws rds describe-db-instances \
  --region ap-southeast-1 \
  --db-instance-identifier YOUR-DB-IDENTIFIER
```

### Step 6 — Configure Spring Boot

Set environment variables:

```text
DB_HOST=your-rds-endpoint
DB_USERNAME=your-app-user
DB_PASSWORD=retrieve-from-approved-secret-store
```

Use a database user for the application rather than the master user. Grant only the privileges required by the application.

### Step 7 — Connect from the application network

Test connectivity from an EC2 instance or container in the VPC. A database endpoint resolving successfully does not prove that the network path or authentication is correct.

### Step 8 — Create a table and test CRUD

Use a migration to create a table. Test:
- Insert a record.
- Read a record.
- Update a record.
- Delete a test record.

### Step 9 — Create a snapshot

Create a manual snapshot before a test schema or data change.

### Step 10 — Review Multi-AZ and read replica concepts

For the lab, you may not need to create paid additional resources. Understand the architecture and compare the deployment options before choosing them in production.

### Cleanup

RDS resources can continue to incur charges. When finished:
1. Export any data you need.
2. Create a final snapshot if required.
3. Disable deletion protection if enabled and appropriate.
4. Delete the DB instance and choose whether to retain a final snapshot.
5. Remove unused subnet groups, security groups, and secrets where appropriate.
6. Review snapshot and backup retention.

Do not delete a production database or its backups as part of this lab.

## 15. Troubleshooting

| Problem | Possible cause | What to inspect |
|---|---|---|
| Connection timeout | Security group, route, NACL, or DNS issue | Network path and DB security group |
| Access denied | Incorrect username/password or DB grants | Secret value and database user privileges |
| Unknown database | Database/schema does not exist | Database name and migration status |
| Too many connections | Pool sizes too large or leaked connections | RDS connection metrics and Hikari settings |
| Slow queries | Missing indexes or inefficient SQL | Query plan and performance metrics |
| Application fails after failover | Stale connections | Connection pool validation and retry strategy |
| Storage full | Data growth or insufficient allocation | Free storage and growth trend |
| Read replica returns old data | Replication lag | Replica lag metrics and read routing |
| TLS connection fails | Trust chain or TLS configuration mismatch | CA certificate and JDBC TLS settings |
| RDS cannot be created | Invalid subnet group or unsupported class | Subnets, AZ coverage, engine/class support, quotas |

### Debugging checklist

1. Confirm the DB instance status is `available`.
2. Confirm the endpoint and port.
3. Confirm DNS resolution from the application network.
4. Check the application and database security groups.
5. Check route tables and network ACLs.
6. Verify credentials and database grants.
7. Check database name and JDBC URL.
8. Inspect connection pool limits.
9. Review RDS and application metrics.
10. Check database logs and application exceptions.

## 16. Exercises with Answers

### Exercise 1 — Relational database

What is the purpose of a primary key?

**Answer:** A primary key uniquely identifies each row in a table.

### Exercise 2 — Foreign key

What does a foreign key do?

**Answer:** It creates a relationship by referencing a key in another table, helping enforce referential integrity.

### Exercise 3 — RDS responsibility

Does Amazon RDS mean developers no longer need to manage database security?

**Answer:** No. AWS manages parts of the underlying service, but customers remain responsible for access control, schema, queries, credentials, network rules, and data protection.

### Exercise 4 — Multi-AZ

What is the main purpose of a traditional RDS Multi-AZ DB instance deployment?

**Answer:** High availability and managed failover. Its standby is not normally used to serve read traffic.

### Exercise 5 — Read replica

What is the main purpose of a read replica?

**Answer:** To serve read queries and help scale read-heavy workloads. Replication lag may mean the replica is temporarily behind the primary.

### Exercise 6 — Backup

What is the difference between an automated backup and a manual snapshot?

**Answer:** Automated backups support point-in-time recovery within the configured retention period. A manual snapshot is created on demand and retained until deleted.

### Exercise 7 — Network security

Which source should be allowed to connect to the RDS security group?

**Answer:** Prefer the application security group, not the entire internet or an unnecessarily broad CIDR range.

### Exercise 8 — Connection pool

An application runs on four instances, each with a maximum pool size of 15. What is the theoretical maximum number of application connections?

**Answer:** 4 × 15 = 60 connections, excluding other database clients.

### Exercise 9 — Failover

Why should a Spring Boot application be prepared for database failover?

**Answer:** Failover can interrupt existing connections. The application should detect connection failures, reconnect safely, and retry suitable operations without duplicating non-idempotent work.

### Exercise 10 — Backups

Why is restore testing important?

**Answer:** A backup may exist but still be unusable or insufficient for the required recovery time. Restore testing verifies the recovery procedure and helps measure RTO and RPO.

## 18. English Speaking Practice

Read each question aloud, then practice the model answer.

### Q1. What is Amazon RDS?

**Model answer:**

Amazon RDS is a managed relational database service. It helps us create, operate, and scale relational databases in the AWS Cloud.

### Q2. Which database engines does RDS support?

**Model answer:**

RDS supports engines such as MySQL, PostgreSQL, MariaDB, Oracle, and SQL Server. Amazon Aurora is also part of the RDS family.

### Q3. What is a DB subnet group?

**Model answer:**

A DB subnet group identifies the subnets that RDS can use in a VPC. For a Multi-AZ design, it should include subnets in multiple Availability Zones.

### Q4. What is Multi-AZ?

**Model answer:**

Multi-AZ is an availability feature. RDS maintains a standby or uses a supported cluster deployment so the database can fail over when certain failures occur.

### Q5. What is a read replica?

**Model answer:**

A read replica is a separate database that receives replicated changes from the primary database. It can serve read queries and help scale read-heavy workloads.

### Q6. What is the difference between a snapshot and automated backup?

**Model answer:**

Automated backups support point-in-time recovery during the retention period. A manual snapshot is created on demand and remains until it is deleted.

### Q7. How does Spring Boot connect to RDS?

**Model answer:**

Spring Boot connects to RDS using JDBC and a connection pool such as HikariCP. The application uses the database endpoint, port, database name, and credentials.

### Q8. Why should an RDS database usually be private?

**Model answer:**

A private database reduces exposure to the public internet. I would allow database traffic only from the application security group.

## 19. AWS Interview Questions and Answers

### 1. What is Amazon RDS?

**Answer:** Amazon RDS is a managed relational database service that simplifies provisioning, backups, maintenance, monitoring, and availability options for supported database engines.

### 2. What is a DB instance?

**Answer:** A DB instance is the compute environment running a database engine, configured with a class, storage, network settings, and database configuration.

### 3. What is a DB subnet group?

**Answer:** It is a collection of subnets in a VPC that RDS can use to place database resources.

### 4. What is the difference between Multi-AZ and a read replica?

**Answer:** Traditional Multi-AZ DB instance deployments focus on high availability and failover. Read replicas focus on serving read traffic and scaling reads.

### 5. Does a traditional Multi-AZ standby serve read queries?

**Answer:** No. It is maintained for failover rather than normal read traffic. Some newer Multi-AZ cluster deployment types have different read capabilities.

### 6. What is point-in-time recovery?

**Answer:** It restores a database to a selected point within the available backup retention window, generally by creating a new DB instance.

### 7. What is a DB parameter group?

**Answer:** It is a collection of database engine configuration parameters that can be applied to DB instances.

### 8. Why use a DB subnet group across multiple AZs?

**Answer:** It provides RDS with eligible subnets in multiple Availability Zones for supported high-availability deployments.

### 9. How should an application connect securely to RDS?

**Answer:** Place the database in private subnets, allow inbound database traffic only from the application security group, use TLS where appropriate, and store credentials securely.

### 10. What is HikariCP?

**Answer:** HikariCP is a JDBC connection pool commonly used by Spring Boot. It reuses database connections and controls pool size and connection timeouts.

### 11. Why can increasing the connection pool size make performance worse?

**Answer:** Too many concurrent database connections can increase memory use, scheduling overhead, lock contention, and database load. Pool size should be based on measured capacity.

### 12. What should an application do during an RDS failover?

**Answer:** It should tolerate temporary connection interruption, discard stale connections, reconnect, and retry only safe operations with appropriate backoff.

### 13. What is the difference between RPO and RTO?

**Answer:** RPO is the maximum acceptable amount of data loss measured in time. RTO is the maximum acceptable time to restore service.

### 14. Why should database restores be tested?

**Answer:** Restore tests verify that backups are usable and that the team can meet its recovery objectives in practice.
