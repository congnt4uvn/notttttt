# DAY 11 — IAM Security Best Practices

## 1. Learning Objectives
By the end of this lesson, you should be able to:
1. Secure the AWS root user.
2. Explain MFA and phishing-resistant authentication.
3. Manage IAM users and access keys safely.
4. Apply least privilege to people and workloads.
5. Review IAM roles and trust policies.
6. Use credential reports, IAM Access Analyzer, and CloudTrail.
7. Perform basic IAM security checks with AWS CLI.
8. Secure a Spring Boot application running on EC2.

## 2. Why IAM Security Matters
IAM determines who can access AWS and what they can do. A compromised identity with excessive permissions can expose data, change security settings, create resources, or disrupt production.

Common risks include exposed access keys, weak passwords, missing MFA, broad policies, overly permissive trust relationships, unused credentials, and insufficient monitoring.

The objective is to make access intentional, limited, temporary where possible, and observable.

## 3. Secure the AWS Root User
The root user is created when an AWS account is opened. It has extensive account-level privileges and should be treated as highly sensitive.

Best practices:
- Do not use root for everyday administration.
- Enable MFA; prefer phishing-resistant methods such as FIDO2 security keys or passkeys where supported.
- Use a strong, unique password.
- Protect the email account associated with AWS.
- Do not create root access keys for routine programmatic access.
- Store recovery information securely.
- Use IAM Identity Center or controlled IAM roles for workforce access.
- Review root-user activity and account security notifications.

| Topic | Root user | Administrator role |
|---|---|---|
| Created | With the AWS account | By an authorized administrator |
| Permissions | Broad account-level privileges | Defined by policies and other controls |
| Everyday use | Avoid | Use for authorized administration |
| MFA | Strongly recommended | Strongly recommended |
| Recovery | AWS account recovery | Depends on identity setup |

An administrator role is not identical to the root user. Some account-level tasks remain root-only.

## 4. Multi-Factor Authentication (MFA)
MFA requires an additional authentication factor beyond a password.

Examples:
- Authenticator applications using TOTP.
- FIDO2/WebAuthn security keys.
- Other methods supported by the AWS sign-in flow.

MFA makes account takeover more difficult if a password is stolen. For privileged human identities, prefer phishing-resistant methods where supported.

| Identity | Recommendation |
|---|---|
| Root user | Enable MFA |
| Human administrators | Require strong MFA through the identity system |
| Developers | Use the organization's approved workforce authentication |
| EC2 applications | Use an instance role, not interactive MFA |
| CI/CD workloads | Use workload roles or federation with short-lived credentials |

Do not put a human MFA code into application source code. Human authentication and workload authentication are different.

MFA-related IAM condition keys have context-specific behavior. `aws:MultiFactorAuthPresent` is not a universal MFA enforcement switch for every service or federated sign-in flow. Configure MFA in the relevant identity provider or IAM Identity Center flow and test the complete path.

## 5. IAM Users and Access Key Management
IAM users can have long-term access keys. These are sensitive credentials and should not be the default for workloads running on AWS.

| Scenario | Preferred approach |
|---|---|
| Application on EC2 | EC2 instance role |
| Application on ECS | ECS task role |
| Application on Lambda | Lambda execution role |
| Human workforce | IAM Identity Center or federation |
| CI/CD outside AWS | OIDC federation or another supported short-lived flow |
| Local development | Approved developer profile with limited permissions |

If a legacy integration requires access keys:
1. Create a dedicated identity.
2. Grant only required permissions.
3. Never commit keys to Git.
4. Store keys in an approved secrets manager.
5. Restrict access to the secret.
6. Replace or rotate keys according to risk policy.
7. Monitor key usage.
8. Deactivate and delete unused keys.

If a key is exposed, revoke or deactivate it immediately; do not wait for scheduled rotation.

Never hardcode credentials:

```java
// INSECURE — do not use this pattern
AwsBasicCredentials credentials = AwsBasicCredentials.create(
    "AKIA_EXAMPLE_ACCESS_KEY",
    "example-secret-access-key"
);
```

Use the AWS SDK default credentials provider chain with an appropriate role or approved local profile.

## 6. Principle of Least Privilege
Least privilege means granting only the permissions required for a task.

Example: a Spring Boot application uploads invoice PDFs to `s3://company-invoices/invoices/`.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadInvoiceObjects",
      "Effect": "Allow",
      "Action": ["s3:PutObject"],
      "Resource": "arn:aws:s3:::company-invoices/invoices/*"
    }
  ]
}
```

This does not grant delete, bucket-policy administration, or IAM administration. Additional permissions may be required for specific upload features, encryption with a customer-managed KMS key, tagging, or multipart upload. Add only verified requirements.

For each policy, ask:
- Does the identity need every action?
- Does each action support resource-level permissions?
- Can the ARN be narrowed?
- Are wildcards necessary?
- Are conditions supported and safe?
- Is the policy still needed?
- Are resource policies or organization controls also involved?

Use separate roles and resources for development, testing, and production where practical.

```text
Development Account -> DevApplicationRole -> Dev bucket
Testing Account     -> TestApplicationRole -> Test bucket
Production Account  -> ProdApplicationRole -> Production bucket
```

## 7. Secure Role Trust Policies
A role trust policy controls who can assume the role. A broad trust policy can expose the permissions of that role to unintended principals.

Avoid wildcard trust as a default:

```json
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "sts:AssumeRole"
}
```

Example trust policy for EC2:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TrustEC2",
      "Effect": "Allow",
      "Principal": {"Service": "ec2.amazonaws.com"},
      "Action": "sts:AssumeRole"
    }
  ]
}
```

Example cross-account trust of a specific role:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TrustSpecificApplicationRole",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/ApplicationRole"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

Replace the sample account ID and role name with real values.

For certain third-party cross-account access patterns, an external ID can help mitigate the confused deputy problem:

```json
{
  "Condition": {
    "StringEquals": {
      "sts:ExternalId": "unique-customer-integration-id"
    }
  }
}
```

An external ID is not a password and does not replace a narrowly scoped trust policy.

## 8. IAM Credential Report
The credential report provides account-level information about IAM users and certain credentials, including password and access-key status and age, and MFA status.

It is not a complete inventory of all AWS identities. It does not replace reviewing IAM roles, federation, or workload identity.

Generate and retrieve it:

```bash
aws iam generate-credential-report
aws iam get-credential-report
```

Review:
- IAM users with unnecessary console passwords.
- MFA status for human users.
- Old or unused access keys.
- Inactive keys that should be removed.
- Identities that should migrate to federation.

## 9. IAM Access Analyzer
IAM Access Analyzer helps identify and review certain external access paths and validate IAM policies. Capabilities depend on analyzer type, service, and Region.

Common uses:
- Find supported resources shared with external principals.
- Validate policy grammar and receive security findings.
- Review policy changes before deployment.
- Generate policy suggestions from CloudTrail activity in supported workflows.

Before deploying a policy:
1. Validate JSON syntax.
2. Run policy validation.
3. Review errors, warnings, and security findings.
4. Confirm actions and resources match application needs.
5. Test in a controlled environment.
6. Review after deployment.

A syntactically valid policy can still be too broad or fail to support the application workflow. Validation does not replace testing.

## 10. CloudTrail for IAM Monitoring
CloudTrail records AWS account activity and API events. It helps investigate who performed an action, when it happened, and which request was made.

Important IAM-related events include:
- Creating or deleting IAM users.
- Creating or deleting access keys.
- Attaching or detaching policies.
- Updating role trust policies.
- Creating roles.
- Assuming roles through STS.
- Changing account security settings.

```text
IAM User / Role / AWS Service
          |
          | AWS API request
          v
       AWS Service
          |
          v
       CloudTrail
          +--> Event History
          +--> Trail to S3
          +--> CloudTrail Lake (if configured)
```

Search CloudTrail Event history for:
- Event name: `AssumeRole`
- Event source: `sts.amazonaws.com`

Review the caller, target role, time, source IP when recorded, request parameters, and result.

AWS CLI example:

```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=AssumeRole \
  --max-results 20
```

Event History has a limited retention window. Configure a trail or another collection mechanism for longer-term retention.

## 11. AWS CLI Security Review
The caller needs permission to run these commands.

Check current identity:

```bash
aws sts get-caller-identity
```

List IAM users:

```bash
aws iam list-users
```

List a user's access keys:

```bash
aws iam list-access-keys --user-name LegacyIntegrationUser
```

List a user's MFA devices:

```bash
aws iam list-mfa-devices --user-name DeveloperUser
```

Generate and retrieve credential report:

```bash
aws iam generate-credential-report
aws iam get-credential-report
```

List roles:

```bash
aws iam list-roles
```

Inspect role and trust policy:

```bash
aws iam get-role --role-name InvoiceApplicationRole
```

List managed policies attached to a role:

```bash
aws iam list-attached-role-policies \
  --role-name InvoiceApplicationRole
```

List a user's attached managed policies:

```bash
aws iam list-attached-user-policies \
  --user-name DeveloperUser
```

These are inspection commands. Do not change production identities without understanding the impact and following an approved change process.

## 12. Secure Spring Boot Workloads on AWS
Scenario: a production Spring Boot application runs on EC2 and uploads customer invoices to S3.

```text
Internet
   |
Load Balancer
   |
Spring Boot API
   |
EC2 Instance
   |
Instance Profile / IAM Role
   |
Temporary Role Credentials
   |
Amazon S3: company-invoices/invoices/
```

Security controls:
1. Attach a dedicated IAM role to EC2.
2. Grant only `s3:PutObject` on the required prefix and verified supporting permissions.
3. Require IMDSv2 where supported.
4. Do not store long-term keys in source code, environment files, or images.
5. Store application secrets in an appropriate secrets manager.
6. Use TLS in transit.
7. Enable S3 Block Public Access unless public access is explicitly required.
8. Configure S3 encryption and appropriate KMS permissions if using a customer-managed key.
9. Enable and review CloudTrail management events.
10. Monitor application errors and AWS API activity.
11. Separate development and production roles and resources.
12. Review permissions when application features change.

Example AWS SDK for Java 2.x configuration:

```java
@Configuration
public class AwsConfig {

    @Bean
    public S3Client s3Client() {
        return S3Client.builder()
                .region(Region.AP_SOUTHEAST_1)
                .build();
    }
}
```

The SDK default credentials provider chain can retrieve role credentials from EC2 metadata when the instance has an appropriate role. Let the SDK handle credential retrieval and refresh; do not manually store metadata credentials.

IAM does not replace application-level authorization. The API must still verify that a customer is allowed to upload or retrieve a particular invoice.

## 13. Practical Exercises with Answers

### Exercise 1 — Root user
Should you use the root user for everyday EC2 administration?

**Answer:** No. Use a controlled workforce identity and an appropriately scoped role. Keep root credentials for tasks that specifically require root.

### Exercise 2 — Access key in Git
A developer commits an AWS key to a public repository. What should happen?

**Answer:**
1. Treat it as compromised.
2. Immediately deactivate or revoke it.
3. Investigate usage with CloudTrail and other logs.
4. Remove it from repository history where practical, but do not assume that makes it safe.
5. Replace the integration with a safer credential method.
6. Review permissions and affected resources.

### Exercise 3 — Credentials for EC2
Should a Spring Boot application on EC2 store an IAM user's key in `application.yml`?

**Answer:** No. Attach a dedicated role to EC2 and use the SDK default credentials provider chain.

### Exercise 4 — Trust policy
Is `Principal: "*"` a safe default for `sts:AssumeRole`?

**Answer:** No. Trust only the specific service, account, role, or identity required, with suitable conditions where appropriate.

### Exercise 5 — CloudTrail
Which service helps identify who changed a role trust policy?

**Answer:** CloudTrail. Search for the relevant IAM management event, such as `UpdateAssumeRolePolicy`.

### Exercise 6 — Credential report
What can it reveal?

**Answer:** Credential properties for IAM users, such as access-key status and age, console-password status, and MFA status.

### Exercise 7 — Least privilege
An application only uploads to `invoices/`. Should it receive `s3:*` on every bucket?

**Answer:** No. Grant only the required upload action on the specific object prefix and add supporting permissions only when required.

### Exercise 8 — MFA for applications
Should an EC2 application ask a developer for an MFA code every time it calls S3?

**Answer:** No. Use a workload role and temporary credentials. MFA is primarily part of human authentication flows.

## 15. English Speaking Practice

### Question 1: How do you secure an AWS root user?
**Model answer:**

I protect the root user with a strong, unique password and MFA. I do not use it for everyday administration. I also avoid creating root access keys and protect the email account associated with the AWS account.

### Question 2: Why is MFA important?
**Model answer:**

MFA adds another authentication factor. If someone steals a password, MFA can make it more difficult for that person to access the account. For privileged users, phishing-resistant methods are a good choice when supported.

### Question 3: How should an EC2 application access S3?
**Model answer:**

I attach a dedicated IAM role to the EC2 instance. The role has only the S3 permissions the application needs. The AWS SDK obtains temporary credentials, so I do not need to store permanent access keys in the source code.

### Question 4: What is AWS CloudTrail used for?
**Model answer:**

CloudTrail records AWS account activity and API events. I can use it to investigate who performed an action, when it happened, and which API request was made.

### Question 5: What is IAM Access Analyzer?
**Model answer:**

IAM Access Analyzer helps identify certain external access paths and validate policies. It helps us review security risks before and after deploying IAM policies.

### Five-minute speaking script

Today, I learned about AWS IAM security best practices.

First, we should protect the AWS root user. We should enable MFA and avoid using the root user for daily administration.

Second, we should manage access keys carefully. We should never commit access keys to Git or put them directly in application source code.

For applications running on AWS, we should prefer IAM roles and temporary credentials.

We should also follow the principle of least privilege. Each user or application should receive only the permissions it needs.

IAM Access Analyzer can help us review policies and identify certain external access risks. CloudTrail records AWS API activity and helps us investigate security events.

Finally, we should review IAM permissions regularly and remove access that is no longer needed.

These practices help us build a more secure AWS environment.

## 16. AWS Interview Questions and Answers

### Q1. How do you secure the AWS root user?
Enable MFA, use a strong unique password, protect the associated email account, avoid daily use, and do not create root access keys for routine programmatic access.

### Q2. What is MFA?
Multi-factor authentication requires additional proof of identity beyond a password. Examples include TOTP authenticator applications and FIDO2 security keys.

### Q3. Why should applications use IAM roles instead of access keys?
Roles provide temporary credentials and centrally managed permissions. This reduces the need to store long-term secrets in application code or configuration.

### Q4. What should you do if an access key is exposed?
Deactivate or revoke it immediately, investigate usage, review possible impact, replace the credential path, and remove the secret from source control history where practical.

### Q5. What is IAM Access Analyzer?
It helps identify supported external access paths and validate IAM policies. Some workflows can also generate policy suggestions based on activity.

### Q6. What is an IAM credential report?
It is an account-level report about IAM users and certain credential properties, such as password and access-key status and age.

### Q7. What is CloudTrail?
CloudTrail records AWS account activity and API events. It supports auditing and incident investigation.

### Q8. What is the principle of least privilege?
Grant only the permissions required for a specific job or workload, and remove unnecessary permissions.

### Q9. Why should role trust policies be reviewed?
A trust policy determines who can assume a role. An overly broad trust relationship can let an unintended principal obtain the role's permissions.

### Q10. Does IAM replace application-level authorization?
No. IAM controls what the workload can do with AWS resources. The application must still verify what each end user is allowed to access.
