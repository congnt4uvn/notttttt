## 2. What Is the AWS Shared Responsibility Model?

The AWS Shared Responsibility Model explains how security and compliance responsibilities are divided between AWS and its customers.

AWS operates the cloud infrastructure, but customers are responsible for securely configuring and using the services they consume.

There are two main areas:

1. **Security of the cloud** — AWS is responsible for protecting the infrastructure that runs AWS services.
2. **Security in the cloud** — customers are responsible for protecting their data, identities, applications, and configurations in AWS.

A simple way to remember it:

```text
AWS Shared Responsibility Model
|
+-- AWS: Security OF the cloud
|   |
|   +-- Physical data centres
|   +-- Physical servers and storage
|   +-- Physical networking
|   +-- Virtualization infrastructure
|   +-- Infrastructure supporting AWS services
|
+-- Customer: Security IN the cloud
    |
    +-- Data and encryption choices
    +-- IAM identities and permissions
    +-- Network and service configuration
    +-- Application code and dependencies
    +-- Operating system on customer-managed instances
    +-- Workload monitoring and security response
```

The exact boundary depends on the AWS service and the way it is configured.

## 3. AWS Responsibilities — Security OF the Cloud

AWS is responsible for protecting the infrastructure that supports AWS cloud services.

### 3.1 Physical security

AWS is responsible for security controls at its data centres, including:

- Physical access controls.
- Facility monitoring.
- Environmental controls.
- Power and cooling infrastructure.
- Physical protection of hardware.

Customers do not manage the physical security of AWS data centres.

### 3.2 Hardware and infrastructure

AWS manages the underlying infrastructure, including:

- Physical servers.
- Physical storage devices.
- Physical network equipment.
- Data-centre infrastructure.
- The virtualization layer used by services such as EC2.

### 3.3 Infrastructure supporting managed services

For managed services, AWS operates more of the underlying technology.

For example, with Amazon RDS, AWS manages much of the underlying database infrastructure and service operations. The customer still manages database users, permissions, data, schemas, and workload configuration.

### 3.4 Example

If a physical server in an AWS data centre has a hardware failure, AWS is responsible for maintaining and replacing that hardware.

The customer is responsible for designing the application so that it can tolerate relevant infrastructure failures, using appropriate AWS architecture and recovery mechanisms.

---

## 4. Customer Responsibilities — Security IN the Cloud

Customers are responsible for securing the resources and workloads they configure in AWS.

The exact responsibilities vary by service.

### 4.1 Data security

Customers are responsible for decisions about:

- What data is stored in AWS.
- How data is classified.
- Who can access the data.
- Whether data should be encrypted.
- How data is backed up and retained.
- How data is deleted when no longer needed.

Example: If a company stores customer information in S3, it must configure access appropriately and protect the data according to its business and compliance requirements.

### 4.2 Identity and access management

Customers must manage:

- IAM users, roles, and groups where used.
- IAM policies and permissions.
- Authentication and MFA.
- Trust policies for roles.
- Access keys and other credentials.
- Least-privilege access.

Example: An application role should receive only the S3 permissions it needs, not unrestricted access to every bucket in the account.

### 4.3 Operating system and patching

For Amazon EC2, the customer is responsible for the guest operating system, including:

- OS security updates.
- Package updates.
- Host-level configuration.
- Installed software.
- Runtime configuration.
- Host firewall configuration where applicable.

This differs from many managed services, where AWS manages more of the underlying operating environment.

### 4.4 Network security

Customers are responsible for configuring network controls in their AWS environments, including:

- VPC design.
- Public and private subnet design.
- Route tables.
- Security groups.
- Network ACLs.
- Network exposure and connectivity.
- Secure access paths to workloads.

AWS provides the networking infrastructure, but customers must configure their virtual networks securely.

### 4.5 Application security

Customers are responsible for application-level security, including:

- Secure coding.
- Input validation.
- Authentication and authorization logic.
- Dependency management.
- API protection.
- Secure session handling.
- Application logging and error handling.
- Secrets management.

### 4.6 Monitoring and response

Customers should monitor their workloads and respond to security events.

Common AWS services include:

| AWS service | Security or operational purpose |
|---|---|
| AWS CloudTrail | Records account activity and API events |
| Amazon CloudWatch | Collects metrics, logs, and alarms |
| AWS Config | Records resource configuration and evaluates rules |
| Amazon GuardDuty | Helps detect threats and suspicious activity |
| AWS Security Hub | Provides a consolidated view of security findings |
| AWS Systems Manager | Helps manage and operate supported resources |

The availability and exact capabilities of these services depend on Region, configuration, and account setup.

## 5. How Responsibilities Change by AWS Service

The most important lesson is that the responsibility boundary changes depending on the service.

### 5.1 Amazon EC2

EC2 is an Infrastructure as a Service (IaaS) offering.

AWS manages:

- Physical data centres.
- Physical servers and networking.
- Virtualization infrastructure.

Customer manages:

- Guest operating system.
- OS patching.
- Installed software and Java runtime.
- Application code.
- Application data.
- Security group and network configuration.
- IAM permissions and credentials used by the workload.

Example:

```text
AWS manages
|
+-- Data centre
+-- Physical server
+-- Physical network
+-- Virtualization
       |
       v
Customer manages
|
+-- Guest Linux operating system
+-- OS updates
+-- Java runtime
+-- Spring Boot application
+-- Application data
+-- Security configuration
```

### 5.2 Amazon RDS

Amazon RDS is a managed relational database service.

AWS manages more of the underlying infrastructure and database service operations, such as:

- Physical infrastructure.
- Underlying host operating environment.
- Managed database service infrastructure.
- Many routine service-maintenance tasks, depending on configuration.

Customer manages:

- Database users and permissions.
- Database schema.
- Data and data classification.
- Query and application design.
- Network access configuration.
- Encryption and key configuration choices.
- Backup retention and recovery requirements, as configured.
- Database settings exposed to the customer.

Do not assume that RDS removes every database-administration or security responsibility.

### 5.3 Amazon S3

Amazon S3 is managed object storage.

AWS manages:

- Physical storage infrastructure.
- Underlying service infrastructure.
- Service durability and availability mechanisms according to the service design.

Customer manages:

- Bucket and object access configuration.
- IAM and bucket policies.
- Data classification.
- Encryption choices and key permissions.
- Versioning and lifecycle configuration.
- Data retention and deletion requirements.
- Application access patterns.

Example: A bucket can be misconfigured to allow unintended access. AWS operates S3, but the customer is responsible for configuring access to their data securely.

### 5.4 AWS Lambda

Lambda is serverless compute.

AWS manages:

- Physical infrastructure.
- Compute infrastructure and service platform.
- Underlying operating environment used to run functions.

Customer manages:

- Function code.
- Dependencies and application logic.
- Execution role and permissions.
- Event source and trigger configuration.
- Environment configuration and secrets.
- Data access and application security.
- Logging and error handling.

Serverless does not mean security is fully managed by AWS.

### 5.5 Comparison table

| Responsibility | EC2 | RDS | S3 | Lambda |
|---|---|---|---|---|
| Physical data centre | AWS | AWS | AWS | AWS |
| Physical hardware | AWS | AWS | AWS | AWS |
| Underlying service infrastructure | AWS | AWS | AWS | AWS |
| Guest OS management | Customer | AWS manages underlying service OS | AWS | AWS |
| Application code | Customer | Customer's application | Customer's application | Customer |
| Data and data access decisions | Customer | Customer | Customer | Customer |
| IAM permissions | Customer configures | Customer configures | Customer configures | Customer configures |
| Service/network configuration | Shared by service boundary | Shared by service boundary | Shared by service boundary | Shared by service boundary |

This is a learning summary, not a complete contractual responsibility matrix. Consult the current AWS Shared Responsibility Model and service-specific documentation for a production design.

## 6. Security of the Cloud vs Security in the Cloud

| Question | Security OF the cloud | Security IN the cloud |
|---|---|---|
| Main responsible party | AWS | Customer |
| Physical data-centre security | AWS | Not managed directly by customer |
| Physical hardware | AWS | Not managed directly by customer |
| Guest OS on EC2 | Not the customer's responsibility for the underlying host OS; customer manages the guest OS | Customer |
| IAM permissions | AWS provides IAM infrastructure | Customer configures identities and permissions |
| Application code | AWS secures supporting infrastructure | Customer secures application code |
| Data access | AWS operates the service | Customer configures access to their data |

### Important principle

AWS provides secure cloud infrastructure, but customers must use and configure that infrastructure securely.

For example, AWS can provide S3 with strong security capabilities, but a customer can still create an overly permissive bucket policy.

## 7. Data Protection and Encryption

Encryption is an important part of customer data protection.

### 7.1 Encryption at rest

Encryption at rest protects stored data.

Examples:

- S3 objects encrypted at rest.
- EBS volumes encrypted at rest.
- RDS database storage encrypted at rest.

AWS services provide encryption options, but customers must understand and configure the relevant settings and permissions.

### 7.2 Encryption in transit

Encryption in transit protects data while it moves between systems.

Examples:

- HTTPS using TLS for web application traffic.
- TLS connections between application services and databases when configured.
- Secure API communication.

### 7.3 AWS Key Management Service (AWS KMS)

AWS KMS is a managed service for creating and controlling cryptographic keys used by supported AWS services and applications.

Customers remain responsible for decisions such as:

- Which keys are used.
- Who can use or administer keys.
- Key policies and IAM permissions.
- Key rotation settings where applicable.
- Data-access design.

### 7.4 Example: Protecting an S3 bucket

A secure design may include:

- S3 Block Public Access settings.
- A restrictive bucket policy.
- IAM permissions for approved application roles.
- Encryption at rest.
- TLS for data in transit.
- Versioning or other recovery controls where appropriate.
- Logging and monitoring based on requirements.

Encryption alone does not prevent unauthorized access if permissions are too broad.

## 8. Network Security Responsibilities

AWS provides network capabilities, but customers configure their virtual network.

### 8.1 Security groups

A security group acts as a virtual firewall for supported resources. It controls inbound and outbound traffic using rules.

Example:

```text
Internet
   |
   v
Application Load Balancer
   |
   | HTTPS 443
   v
Spring Boot EC2
   |
   | Database port, only from app security group
   v
Amazon RDS
```

A good design avoids exposing the database directly to the public internet.

### 8.2 Example security-group design

| Resource | Example inbound rule | Reason |
|---|---|---|
| Application Load Balancer | HTTPS 443 from approved client ranges or internet, as required | Receive web traffic |
| Spring Boot EC2 | Application port only from the load balancer security group | Prevent direct public access |
| RDS database | Database port only from the application security group | Restrict database access |

The exact ports and rules depend on the application. Do not copy a broad rule such as `0.0.0.0/0` for SSH or a database port into production.

### 8.3 Network ACLs

Network ACLs are stateless network access controls associated with subnets. Security groups are stateful controls associated with supported resources.

| Feature | Security group | Network ACL |
|---|---|---|
| Scope | Resource/network interface level | Subnet level |
| State | Stateful | Stateless |
| Rule evaluation | Allow rules | Allow and deny rules |
| Return traffic | Automatically allowed for established connections | Must be explicitly allowed by rules |

This is an introductory comparison. Detailed VPC security design will be covered in a later networking lesson.

## 9. Practical Scenario — Secure a Spring Boot E-commerce Application

### 9.1 Requirements

A company deploys a Spring Boot e-commerce application on AWS.

The system uses:

- EC2 for the application.
- RDS for order and customer data.
- S3 for product images.
- IAM roles for application access.
- CloudWatch for logs and metrics.

### 9.2 Architecture

```text
                         Internet
                            |
                            v
                    Application Load Balancer
                            |
                            v
                 Spring Boot EC2 instances
                            |
              +-------------+-------------+
              |                           |
              v                           v
          Amazon RDS                 Amazon S3
       Order/customer data          Product images
              ^                           ^
              |                           |
              +-------------+-------------+
                            |
                      IAM role
                 (limited permissions)

Monitoring:
EC2 / Application / RDS
          |
          v
    Amazon CloudWatch

Account activity:
AWS API events
          |
          v
      AWS CloudTrail
```

### 9.3 Responsibility breakdown

| Security task | Main responsibility |
|---|---|
| Physical data-centre security | AWS |
| Physical server maintenance | AWS |
| EC2 guest OS patching | Customer |
| Spring Boot secure coding | Customer |
| IAM role permissions | Customer |
| RDS database user permissions | Customer |
| S3 bucket policy | Customer |
| Application monitoring configuration | Customer configures and operates it |
| Underlying managed-service infrastructure | AWS |

### 9.4 Recommended controls

1. Use an IAM role for the EC2 application.
2. Give the role only the required S3 permissions.
3. Keep RDS in private subnets where appropriate.
4. Allow database connections only from the application security group.
5. Require HTTPS for public application traffic.
6. Protect application secrets using a suitable secrets-management service.
7. Enable appropriate encryption settings.
8. Monitor application and infrastructure behavior.
9. Record account API activity with CloudTrail.
10. Back up important data and test restoration.

## 10. Practical AWS CLI Exercises

These commands are intended for inspection. They do not create paid resources.

### 10.1 Verify the AWS CLI installation

```bash
aws --version
```

### 10.2 Check the active identity

```bash
aws sts get-caller-identity
```

### 10.3 Check the active Region

```bash
aws configure get region
```

### 10.4 List configured profiles

```bash
aws configure list-profiles
```

### 10.5 List S3 buckets

```bash
aws s3 ls
```

Your identity needs the relevant permissions to list buckets.

### 10.6 Inspect EC2 instances

```bash
aws ec2 describe-instances \
  --region ap-southeast-1 \
  --output table
```

### 10.7 Use a named profile

```bash
aws sts get-caller-identity --profile dev
```

This verifies which identity the `dev` profile uses.

## 11. Common Mistakes to Avoid

| Mistake | Why it is risky | Better approach |
|---|---|---|
| Using the root user every day | Exposes a highly privileged identity to routine risk | Use authorized IAM roles or federated access |
| Storing access keys in source code | Keys can leak through repositories or logs | Use temporary credentials and roles |
| Giving every user AdministratorAccess | Violates least privilege | Grant only required actions and resources |
| Making an S3 bucket public without a requirement | Can expose sensitive data | Keep public access blocked unless explicitly required |
| Opening SSH to the entire internet | Increases attack surface | Use controlled administration paths and restricted access |
| Ignoring the active CLI profile | Commands may target the wrong account | Check identity before important operations |
| Assuming AWS manages all security | Customer configuration remains critical | Review the responsibility boundary for each service |

## 12. Practical Exercises (Answers Included)

### Exercise 1 — Identify the identity

| Scenario | Your answer | Correct answer |
|---|---|---|
| The original identity created with an AWS account | ______ | **Root user** |
| An identity with permissions that can be assumed by an EC2 workload | ______ | **IAM role** |
| An account identity that can have a console password or access keys | ______ | **IAM user** |
| A human employee signs in through a corporate identity provider | ______ | **Federated access / IAM Identity Center** |

### Exercise 2 — Choose the correct tool

| Scenario | Correct answer |
|---|---|
| Create an S3 bucket using a graphical interface | AWS Management Console |
| List S3 buckets from a terminal | AWS CLI |
| Upload a file to S3 from a Spring Boot application | AWS SDK |
| Run commands in a browser-based terminal | AWS CloudShell |

### Exercise 3 — Secure an EC2 application

**Question:** A Spring Boot application running on EC2 needs to read objects from one S3 bucket. What is the recommended access method?

**Answer:** Attach an IAM role to the EC2 instance through an instance profile. Grant the role only the required S3 actions on the required bucket or object resources. Use the AWS SDK's default credential provider chain.

### Exercise 4 — Explain the CLI command

**Question:** What does this command show?

```bash
aws sts get-caller-identity
```

**Answer:** It shows the AWS account and identity associated with the credentials used by the current CLI invocation.

### Exercise 5 — Diagnose a permission issue

**Question:** A developer can sign in to AWS but receives `AccessDenied` when listing an S3 bucket. Does successful sign-in mean the developer has permission to list the bucket?

**Answer:** No. Authentication proves the identity, but authorization determines which actions that identity can perform. Review the relevant identity policy, bucket policy, and other applicable controls.

### Exercise 6 — Root-user security

**Question:** Name three practices for protecting the AWS root user.

**Answer:**

1. Enable MFA.
2. Use a strong, unique password and secure the associated email account.
3. Avoid using the root user for daily work and do not create root access keys for routine programmatic access.

## 14. English Speaking Practice

Read each question aloud and practise answering with the model answer.

### Question 1: What is the AWS root user?

**Model answer:**

The AWS root user is the original identity created when an AWS account is opened. It has unrestricted access to the account, so I should protect it carefully and avoid using it for everyday tasks.

### Question 2: What is an IAM role?

**Model answer:**

An IAM role is an identity that can be assumed by a trusted user or service. It provides temporary credentials and permissions. For example, an EC2 instance can use an IAM role to access an S3 bucket.

### Question 3: What is the AWS Management Console?

**Model answer:**

The AWS Management Console is a web-based interface. I can use it to create, configure, and monitor AWS resources.

### Question 4: What is the difference between AWS CLI and AWS SDK?

**Model answer:**

The AWS CLI is used from a terminal, while the AWS SDK is used inside application code. For example, I can use the AWS SDK for Java in a Spring Boot application to upload files to S3.

### Question 5: Why should we avoid hard-coded access keys?

**Model answer:**

Hard-coded access keys can leak through source code, logs, or configuration files. It is safer to use IAM roles and temporary credentials whenever possible.

### Question 6: What does least privilege mean?

**Model answer:**

Least privilege means giving an identity only the permissions it needs to perform its tasks. It helps reduce security risks if an identity is misused or compromised.

### Useful speaking patterns

| Pattern | Example |
|---|---|
| X is responsible for... | The customer is responsible for IAM permissions. |
| X allows us to... | AWS CLI allows us to manage resources from a terminal. |
| We should avoid... | We should avoid storing access keys in source code. |
| Instead of..., we can... | Instead of long-lived keys, we can use an IAM role. |
| The purpose of X is... | The purpose of MFA is to add another verification step. |
| For example,... | For example, EC2 can assume a role to access S3. |

## 15. AWS Interview Questions and Answers

### Q1. What is the AWS root user?

**Answer:** It is the original identity created when an AWS account is established. It has unrestricted access to the account and should be protected with MFA and used only when required.

### Q2. Why should we avoid using the root user for daily tasks?

**Answer:** Because it has unrestricted account access. Using it routinely increases the risk and impact of credential compromise or accidental changes.

### Q3. What is the difference between authentication and authorization?

**Answer:** Authentication verifies who an identity is. Authorization determines what that identity is allowed to do.

### Q4. What is an IAM role?

**Answer:** An IAM role is an identity with permissions that can be assumed by a trusted principal. It commonly provides temporary credentials for users or workloads.

### Q5. Why are IAM roles recommended for EC2 applications?

**Answer:** They provide temporary credentials to the application without requiring long-lived access keys to be stored in code or configuration files.

### Q6. What is AWS CLI?

**Answer:** AWS CLI is a command-line tool for managing AWS services and resources through commands and scripts.

### Q7. What is AWS SDK?

**Answer:** AWS SDK is a collection of programming-language libraries that allow application code to call AWS APIs. For example, the AWS SDK for Java can be used in Spring Boot.

### Q8. What is AWS CloudShell?

**Answer:** CloudShell is a browser-based shell environment available through the AWS Management Console. It can be used to run AWS CLI commands.

### Q9. What is the principle of least privilege?

**Answer:** It means granting only the permissions necessary for an identity to perform its required tasks.

### Q10. What is the difference between authentication and an IAM policy?

**Answer:** Authentication establishes the identity. IAM policies are one of the mechanisms AWS uses to evaluate what actions that identity is allowed or denied to perform.

## 16. Lesson Summary

- An AWS account is a boundary for resources, identities, permissions, and billing.
- The root user is highly privileged and should be protected with MFA.
- IAM users are account identities; IAM roles are assumable identities that commonly provide temporary credentials.
- The AWS Management Console is a visual web interface.
- AWS CLI is used from a terminal.
- AWS SDK is used by application code.
- AWS CloudShell provides a browser-based shell.
- Authentication and authorization are different.
- Least privilege reduces unnecessary access.
- Applications should prefer IAM roles and temporary credentials instead of hard-coded access keys.

### Quick memory rule

```text
Authentication = Who are you?
Authorization  = What can you do?

Root user = Protect carefully
IAM user  = Account identity
IAM role  = Assumable identity with permissions

Console = Browser
CLI     = Terminal
SDK     = Application code
CloudShell = Browser-based terminal
```
