## 2. What is the AWS Shared Responsibility Model?

The AWS Shared Responsibility Model defines how security responsibilities are divided between AWS and its customers.

AWS does not manage every aspect of your application. Customers also have responsibilities for securing their applications, data, configurations, and access permissions.

There are two main categories:

- Security OF the Cloud: AWS is responsible.
- Security IN the Cloud: Customers are responsible.

### 2.1 Security of the Cloud

AWS is responsible for protecting the infrastructure that runs AWS services.

Examples:

- Physical data centers.
- Physical servers.
- Networking infrastructure.
- Hardware.
- Physical security.
- Infrastructure supporting AWS services.
- Virtualization infrastructure.

For example, when you launch an EC2 instance, AWS manages the physical server and the underlying infrastructure.

### 2.2 Security in the Cloud

Customers are responsible for securing what they deploy and configure in AWS.

Examples:

- Application code.
- Data.
- IAM permissions.
- Security group rules.
- Operating system configuration, depending on the service.
- Encryption configuration.
- Application authentication.
- Network access configuration.

For example, if you deploy a Spring Boot application on EC2, you are responsible for securing the application and configuring the instance appropriately.

### 2.3 Architecture overview

```
             AWS Cloud
                 |
       Shared Responsibility
                 |
       +---------+---------+
       |                   |
       v                   v
  AWS Responsibility   Customer Responsibility
  Security OF Cloud    Security IN Cloud
       |                   |
       v                   v
  Physical Data       Application Code
  Centers             Customer Data
  Hardware            IAM Permissions
  Network             Security Groups
  Infrastructure      Encryption Settings
  Virtualization      OS Configuration*
```

\*Operating system responsibility depends on the AWS service and deployment model.

Important: AWS secures the cloud infrastructure, but customers must correctly configure and secure their workloads.

## 3. AWS responsibilities vs Customer responsibilities

| Security area                   | AWS                              | Customer                                |
| ------------------------------- | -------------------------------- | --------------------------------------- |
| Physical data center            | Responsible                      | Not responsible                         |
| Physical servers                | Responsible                      | Not responsible                         |
| Physical network infrastructure | Responsible                      | Not responsible                         |
| Hardware maintenance            | Responsible                      | Not responsible                         |
| Application code                | Not responsible                  | Responsible                             |
| Customer data                   | Infrastructure protection        | Data protection and access              |
| IAM policies                    | Provides IAM service             | Configures policies                     |
| Security groups                 | Provides capability              | Configures rules                        |
| Application authentication      | Provides supporting services     | Implements and configures               |
| Data encryption settings        | Provides encryption capabilities | Selects and configures where applicable |
| OS patching on EC2              | Underlying infrastructure        | Guest OS                                |
| S3 infrastructure               | Responsible                      | Bucket access and data configuration    |

The key idea is that AWS provides secure services and tools, but customers must use them correctly.

## 4. How responsibilities differ between AWS services

This is one of the most important parts of the lesson.

The amount of responsibility you have depends on the AWS service you choose.

### 4.1 Amazon EC2 — Infrastructure as a Service

More customer responsibility

When you use EC2, AWS provides a virtual machine, but you manage much of its software environment.

Example:

You deploy a Spring Boot application on an Ubuntu EC2 instance.

| Responsibility                  | Owner    |
| ------------------------------- | -------- |
| Physical server                 | AWS      |
| Data center                     | AWS      |
| Virtualization infrastructure   | AWS      |
| Ubuntu operating system updates | Customer |
| Java installation               | Customer |
| Spring Boot application         | Customer |
| Application security            | Customer |
| IAM role configuration          | Customer |
| Security group configuration    | Customer |

Example architecture:

```
AWS Data Center
      |
      v
Physical Server (AWS)
      |
      v
EC2 Virtual Machine
      |
      +-- Ubuntu OS       Customer
      |
      +-- Java Runtime   Customer
      |
      +-- Spring Boot    Customer
      |
      +-- Application Data
```

Real-world scenario:

Your EC2 instance runs an old version of Ubuntu with unpatched security vulnerabilities.

Who must update Ubuntu?

Answer: The customer.

AWS manages the underlying infrastructure, not the guest operating system running inside your EC2 instance.

### 4.2 Amazon RDS — Managed Database

Shared operational responsibilities

Amazon RDS is a managed relational database service.

AWS manages many database infrastructure operations, including supported automated backups, infrastructure maintenance, and managed database software patching according to the service configuration.

Customers remain responsible for database access, data, permissions, and appropriate security configuration.

| Responsibility                        | Owner    |
| ------------------------------------- | -------- |
| Physical database infrastructure      | AWS      |
| Database host infrastructure          | AWS      |
| Managed database software maintenance | AWS      |
| Database username and password        | Customer |
| Database access permissions           | Customer |
| Database network access               | Customer |
| Data classification                   | Customer |
| Application SQL queries               | Customer |
| Backup retention configuration        | Customer |
| Database encryption configuration     | Customer |

Example:

You create an Amazon RDS PostgreSQL database.

You must:

- Configure database credentials securely.
- Restrict network access.
- Use appropriate database permissions.
- Enable encryption where required.
- Configure backup retention.
- Protect sensitive data.

AWS operates the managed database service, but you still control how your database is accessed and used.

### 4.3 Amazon S3 — Object Storage

Amazon S3 is a managed object storage service.

AWS manages the underlying storage infrastructure.

Customers are responsible for configuring access to their buckets and protecting their data.

| Responsibility                  | Owner    |
| ------------------------------- | -------- |
| Physical storage infrastructure | AWS      |
| Storage hardware                | AWS      |
| S3 service infrastructure       | AWS      |
| Bucket policies                 | Customer |
| IAM permissions                 | Customer |
| Public access configuration     | Customer |
| Data classification             | Customer |
| Encryption configuration        | Customer |
| Object access permissions       | Customer |

Real-world scenario:

You upload customer identity documents to an S3 bucket.

You accidentally configure the bucket to allow public access.

Who is responsible?

Answer: The customer.

AWS provides security controls, but customers must configure those controls correctly.

### 4.4 AWS Lambda — Serverless Computing

Less infrastructure management

AWS Lambda lets you execute code without managing servers directly.

AWS manages:

- Physical servers.
- Server infrastructure.
- Operating system maintenance.
- Runtime execution infrastructure.
- Infrastructure scaling.

Customers manage:

- Function code.
- Function permissions.
- Application dependencies.
- Environment variables.
- Data access.
- Application-level security.
- Trigger and event configuration.

| Responsibility                 | Owner    |
| ------------------------------ | -------- |
| Physical infrastructure        | AWS      |
| Server operating system        | AWS      |
| Infrastructure scaling         | AWS      |
| Lambda function code           | Customer |
| Function execution permissions | Customer |
| Data access permissions        | Customer |
| Application logic              | Customer |

Example:

You create a Lambda function that processes uploaded images from S3.

AWS manages the execution infrastructure.

You must ensure that the Lambda execution role has only the permissions it needs.

## 5. Comparing EC2, RDS, S3, and Lambda

| Responsibility         | EC2                 | RDS                 | S3          | Lambda      |
| ---------------------- | ------------------- | ------------------- | ----------- | ----------- |
| Physical hardware      | AWS                 | AWS                 | AWS         | AWS         |
| Physical data center   | AWS                 | AWS                 | AWS         | AWS         |
| Guest OS management    | Customer            | AWS                 | AWS         | AWS         |
| Application code       | Customer            | Customer            | N/A         | Customer    |
| Data access control    | Customer            | Customer            | Customer    | Customer    |
| Service infrastructure | AWS                 | AWS                 | AWS         | AWS         |
| Infrastructure scaling | Customer-configured | AWS-managed options | AWS-managed | AWS-managed |

The exact responsibility boundaries can vary by service configuration and deployment model.

Key takeaway:

The more managed the AWS service is, the less infrastructure you manage. However, application security, data protection, and access control remain important customer responsibilities.

## 6. Shared Responsibility across IaaS, PaaS, and SaaS

Let's connect today's topic with DAY 3.

### 6.1 IaaS — Infrastructure as a Service

Example: Amazon EC2.

The customer manages:

- Operating system.
- Runtime.
- Middleware.
- Application.
- Data.
- Network and access configurations.

AWS manages the underlying infrastructure.

### 6.2 PaaS — Platform as a Service

Example: AWS Elastic Beanstalk.

AWS manages more of the infrastructure and platform operations.

Customers still manage:

- Application code.
- Data.
- Application dependencies.
- Access permissions.
- Application security settings.

The exact operating system and platform responsibilities depend on the deployment option and configuration.

### 6.3 SaaS — Software as a Service

Example: Amazon QuickSight (a managed business intelligence service).

The provider manages the application infrastructure and software operations.

Customers still manage:

- User access.
- Data permissions.
- Data classification.
- Configuration of their own environment.

### Comparison

| Layer                   | IaaS     | PaaS                       | SaaS                                    |
| ----------------------- | -------- | -------------------------- | --------------------------------------- |
| Physical infrastructure | AWS      | AWS                        | Provider                                |
| Virtualization          | AWS      | AWS                        | Provider                                |
| Operating system        | Customer | Generally provider-managed | Provider                                |
| Runtime                 | Customer | Generally provider-managed | Provider                                |
| Application             | Customer | Shared by service model    | Provider                                |
| Customer data           | Customer | Customer                   | Customer's data responsibilities remain |

## 7. Practical Security Example — Spring Boot on AWS

Imagine you are developing an e-commerce application.

Your architecture:

```
                  Internet
                     |
                     v
                Route 53
                     |
                     v
               Load Balancer
                     |
                     v
               EC2 Instance
                     |
                     v
             Spring Boot API
                     |
          +----------+----------+
          |                     |
          v                     v
       Amazon RDS             Amazon S3
       PostgreSQL             Product Images
```

Let's identify the responsibilities.

| Component     | AWS responsibility                | Customer responsibility                 |
| ------------- | --------------------------------- | --------------------------------------- |
| Route 53      | DNS infrastructure                | DNS records and configuration           |
| Load Balancer | Managed infrastructure            | Listener and security configuration     |
| EC2           | Physical host and virtualization  | OS, Java, application                   |
| Spring Boot   | No application management         | Code, dependencies, authentication      |
| RDS           | Managed database infrastructure   | Credentials, data, access configuration |
| S3            | Storage infrastructure            | Bucket policies, object access          |
| IAM           | IAM service infrastructure        | Roles and permissions                   |
| CloudWatch    | Monitoring service infrastructure | Logs, alarms, monitoring configuration  |

### 7.1 Security checklist for this application

EC2 security

- Use a supported operating system.
- Regularly patch the operating system.
- Restrict SSH access.
- Use IAM roles instead of hardcoded AWS credentials.
- Monitor application logs.

RDS security

- Do not expose the database publicly unless there is a justified requirement.
- Allow database access only from the application security group.
- Use strong credentials.
- Enable encryption where required.
- Configure backups.

S3 security

- Enable Block Public Access unless public access is explicitly required.
- Use IAM policies and bucket policies.
- Enable encryption.
- Consider versioning for important objects.
- Monitor access.

Spring Boot security

- Validate user input.
- Use authentication and authorization.
- Protect API endpoints.
- Store secrets securely.
- Avoid logging passwords and sensitive data.
- Keep dependencies updated.

## 8. Important AWS security services

These services help customers fulfill their security responsibilities.

| AWS Service         | Purpose                                             |
| ------------------- | --------------------------------------------------- |
| AWS IAM             | Manage identities and permissions                   |
| AWS KMS             | Manage encryption keys                              |
| AWS Secrets Manager | Store database passwords and API secrets            |
| Amazon GuardDuty    | Detect suspicious activity and threats              |
| AWS CloudTrail      | Record account activity and API calls               |
| AWS Config          | Track resource configurations and compliance        |
| Amazon CloudWatch   | Monitor metrics, logs, and alarms                   |
| AWS Security Hub    | Centralize security findings and posture management |

### Example security workflow

```
       AWS Account
            |
            v
       CloudTrail
            |
            v
     Record API Activity
            |
            v
       GuardDuty
            |
            v
    Detect Suspicious Events
            |

            |
            v

            |
```

Note that these services have different purposes. CloudTrail records activity, GuardDuty analyzes signals for threats, and Security Hub helps centralize security findings.

## 9. Real-world security scenarios

### Scenario 1 — EC2 operating system vulnerability

Your application runs on EC2. A security vulnerability is discovered in the Ubuntu operating system.

Who is responsible for patching it?

Answer: The customer.

### Scenario 2 — Physical data center failure

An AWS data center experiences a physical hardware failure.

Who is responsible for the physical infrastructure?

Answer: AWS.

Your architecture should still account for availability and recovery requirements.

### Scenario 3 — Public S3 bucket

A developer accidentally makes a private S3 bucket publicly accessible.

Who is responsible?

Answer: The customer.

The customer must configure bucket access correctly.

### Scenario 4 — RDS database credentials leaked

A developer accidentally commits database credentials to GitHub.

Who is responsible?

Answer: The customer.

AWS provides services such as Secrets Manager, but the customer must use them appropriately and respond to credential exposure.

### Scenario 5 — Lambda infrastructure failure

An underlying Lambda execution server experiences a hardware issue.

Who manages the underlying infrastructure?

Answer: AWS.

Customers still need to design their application to handle failures and retries appropriately.

## 12. Interview questions and answers

Q1. What is the AWS Shared Responsibility Model?

Answer:

The AWS Shared Responsibility Model defines how security responsibilities are divided between AWS and its customers. AWS is responsible for security of the cloud, while customers are responsible for security in the cloud.

Q2. What is the difference between Security of the Cloud and Security in the Cloud?

Answer:

Security of the Cloud refers to AWS responsibilities, such as physical data centers, hardware, and infrastructure. Security in the Cloud refers to customer responsibilities, such as application code, data protection, and access permissions.

Q3. Who is responsible for patching an EC2 operating system?

Answer:

The customer is responsible for patching and maintaining the guest operating system on EC2.

Q4. Who is responsible for Amazon S3 infrastructure security?

Answer:

AWS is responsible for the underlying storage infrastructure. Customers are responsible for configuring bucket policies, access permissions, and data protection.

Q5. Why does AWS Lambda require less infrastructure management than EC2?

Answer:

AWS manages the underlying servers, operating systems, and execution infrastructure for Lambda. Customers mainly focus on function code, permissions, and application logic.

Q6. Does using a managed AWS service mean customers have no security responsibilities?

Answer:

No. Customers remain responsible for their data, access permissions, application code, and service configurations.

Q7. How can a Spring Boot application securely access S3?

Answer:

The application can use an IAM role attached to its EC2 instance or an appropriate workload identity. AWS SDK retrieves temporary credentials, avoiding hardcoded access keys.

Q8. What is the purpose of AWS KMS?

Answer:

AWS Key Management Service helps create and manage cryptographic keys used to protect data through encryption.
