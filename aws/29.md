## 2. What Is Amazon DynamoDB?

Amazon DynamoDB is a fully managed, serverless NoSQL database service. It supports key-value and document data models and is designed for applications that need predictable, low-latency access at scale.

Typical use cases include:

- Shopping carts and order metadata.
- User profiles and preferences.
- Gaming leaderboards and player state.
- IoT device state and telemetry indexes.
- Session storage.
- Event metadata and high-volume application workloads.

### DynamoDB vs. relational databases

| Topic | Relational database (for example, RDS) | DynamoDB |
|---|---|---|
| Data model | Tables, rows, columns, relationships | Tables, items, attributes |
| Schema | Defined table schema | Flexible attributes; key schema is defined |
| Relationships | Joins and foreign keys | Usually modeled into access patterns |
| Scaling | Vertical and read-replica options; engine-dependent | Managed horizontal partitioning |
| Query style | SQL | Key-based API operations and PartiQL |
| Transactions | ACID transactions | ACID transactions across supported items |
| Best fit | Complex relational queries and joins | High-scale key-value/document access |

**Important:** NoSQL does not mean “no structure.” DynamoDB design requires deliberate key and access-pattern planning.

### When should you choose DynamoDB?

Choose DynamoDB when:

- Your application has known access patterns.
- You need low-latency reads and writes at high request rates.
- You want managed scaling without managing database servers.
- Your data can be modeled around partition and sort keys.

Consider RDS when:

- You need complex joins and ad hoc SQL queries.
- Your data has many relational constraints.
- You frequently need flexible reporting across many dimensions.

## 3. Core DynamoDB Concepts

A DynamoDB table contains items. Each item contains attributes.

```text
Table: Customers
|
+-- Item 1
|   +-- customerId: "C1001"
|   +-- name: "Anna"
|   +-- email: "anna@example.com"
|
+-- Item 2
    +-- customerId: "C1002"
    +-- name: "David"
    +-- email: "david@example.com"
```

| DynamoDB term | Meaning | Relational comparison |
|---|---|---|
| Table | Collection of items | Table |
| Item | One record | Row |
| Attribute | A value associated with an item | Column/value |
| Partition key | Attribute used to determine item partition | No direct equivalent |
| Sort key | Optional key used to order related items | No direct equivalent |

An item's attributes do not all need to be identical. However, every item must contain the attributes required by the table's primary key schema.

### Supported data types

Common DynamoDB types include:

- String (`S`)
- Number (`N`)
- Binary (`B`)
- Boolean (`BOOL`)
- Null (`NULL`)
- String, number, and binary sets (`SS`, `NS`, `BS`)
- List (`L`)
- Map (`M`)

Example document-style item:

```json
{
  "customerId": {"S": "C1001"},
  "name": {"S": "Anna"},
  "age": {"N": "29"},
  "active": {"BOOL": true},
  "address": {
    "M": {
      "city": {"S": "Seoul"},
      "country": {"S": "Korea"}
    }
  },
  "tags": {
    "L": [
      {"S": "premium"},
      {"S": "newsletter"}
    ]
  }
}
```

## 4. Primary Keys: The Most Important Design Decision

DynamoDB supports two primary-key designs.

### 4.1 Simple primary key

A simple primary key contains only a partition key.

Example: `Products`

| productId (partition key) | name | price |
|---|---|---:|
| P100 | Keyboard | 50 |
| P101 | Mouse | 25 |
| P102 | Monitor | 220 |

Each item must have a unique `productId`.

### 4.2 Composite primary key

A composite primary key contains:

- Partition key: groups related items.
- Sort key: distinguishes and orders items within that partition-key value.

Example: `Orders`

| customerId (PK) | orderDate#orderId (SK) | status |
|---|---|---|
| C1001 | 2026-10-01#O501 | PAID |
| C1001 | 2026-10-08#O520 | SHIPPED |
| C1002 | 2026-10-03#O507 | PAID |

This design makes it efficient to retrieve all orders for one customer and to query a range of sort-key values.

### 4.3 Design keys from access patterns

Start by writing down the questions your application must answer.

| Access pattern | Possible key design |
|---|---|
| Get a product by ID | PK = `PRODUCT#P100` |
| Get all orders for a customer | PK = `CUSTOMER#C1001`, SK begins with `ORDER#` |
| Get one order | PK = `CUSTOMER#C1001`, SK = `ORDER#O501` |
| Get all items in an order | PK = `ORDER#O501`, SK = `ITEM#...` |
| Find an order by order ID regardless of customer | Add a suitable GSI |

A key should support the operations your application performs frequently. Do not select keys only because they resemble relational primary keys.

### 4.4 Single-table design introduction

DynamoDB can store multiple logical entity types in one physical table.

```text
Table: ApplicationData

PK                  SK                    Entity
-------------------------------------------------------
CUSTOMER#C1001      PROFILE               Customer
CUSTOMER#C1001      ORDER#2026-10-01#O501 Order
CUSTOMER#C1001      ORDER#2026-10-08#O520 Order
ORDER#O501          ITEM#P100             OrderItem
ORDER#O501          ITEM#P101             OrderItem
```

This is one possible design, not a rule that every DynamoDB application must use one table. A multi-table design can be easier to understand for smaller applications or teams new to DynamoDB.

## 5. Partitioning and Hot Keys

DynamoDB distributes table data across partitions. The partition key value is used as part of the process that determines where an item is stored.

A good partition key distributes traffic and storage across many key values.

### Risk: hot partition key

Suppose every request reads and writes this item:

```text
PK = "GLOBAL_COUNTER"
```

A large share of traffic targets one key. That key can become a hot spot and cause throttling.

Better approaches depend on the access pattern:

- Use high-cardinality partition keys where possible.
- Distribute writes across multiple key values.
- Consider write sharding for very high-volume counters.
- Avoid putting all users or all events under one extremely popular partition key.
- Monitor throttling and consumed capacity.

Example of write sharding:

```text
COUNTER#00
COUNTER#01
COUNTER#02
...
COUNTER#09
```

The application can distribute writes among shards and aggregate values when reading. This adds read complexity, so use it only when justified by measured traffic.

## 6. Capacity Modes and Read/Write Capacity

DynamoDB offers two main capacity modes.

| Mode | How it works | Typical fit |
|---|---|---|
| On-demand | Automatically accommodates workload changes; billed by requests | Unpredictable or variable traffic |
| Provisioned | You configure read and write capacity; can use auto scaling | Predictable workloads and capacity planning |

Do not assume on-demand is always cheaper or provisioned is always cheaper. Compare the workload pattern and current regional pricing before choosing.

### 6.1 Read capacity units (RCUs)

A simplified reference model:

- 1 RCU supports one strongly consistent read per second for an item up to 4 KB.
- An eventually consistent read uses half the capacity of a strongly consistent read.
- A transactional read uses twice the capacity of a normal strongly consistent read.
- Larger items consume proportionally more capacity, rounded up in capacity units.

### 6.2 Write capacity units (WCUs)

A simplified reference model:

- 1 WCU supports one write per second for an item up to 1 KB.
- Larger items consume proportionally more write capacity, rounded up in capacity units.
- Transactional writes use twice the write capacity of standard writes.

These are foundational planning rules. Actual capacity consumption depends on the operation, item size, consistency, and service behavior. Check consumed-capacity metrics for real workloads.

### 6.3 Example capacity estimate

Assume an application performs:

- 100 strongly consistent reads per second.
- Each item is 2 KB.
- 50 writes per second.
- Each item is 0.8 KB.

Simplified estimate:

```text
Read:
2 KB item -> 1 RCU per strongly consistent read
100 reads/second -> about 100 RCUs

Write:
0.8 KB item -> 1 WCU per write
50 writes/second -> about 50 WCUs
```

Add headroom for traffic bursts and workload variation. This estimate is educational, not a production capacity recommendation.

### 6.4 Consistency models

| Read type | Meaning |
|---|---|
| Eventually consistent | A read may briefly return an earlier value after a successful write |
| Strongly consistent | Returns the latest successful prior writes, subject to service guarantees |
| Transactional | Reads as part of a transaction with transactional guarantees |

Strongly consistent reads are supported on tables and LSIs, but not on GSIs or streams. Choose consistency based on business requirements rather than enabling the strongest option everywhere.

## 7. Query vs. Scan

### Query

Use `Query` when you know the partition-key value.

Example question:

> Get all orders belonging to customer C1001.

A Query can also use supported sort-key conditions such as equality, ranges, and prefix matching.

### Scan

A `Scan` reads items across a table or index. It can be useful for small tables, administrative jobs, or carefully controlled batch work, but it is usually not the right way to implement a frequently used application lookup.

| Feature | Query | Scan |
|---|---|---|
| Partition key value required | Yes | No |
| Reads a targeted key range | Yes | No, reads across the table/index |
| Typical efficiency | Better for known access patterns | Can be expensive on large datasets |
| Common application use | Get a customer's orders | Occasional audit or migration |

### FilterExpression

A filter is applied after DynamoDB reads the items for the operation. It does not reduce the read capacity consumed by the items that were evaluated.

Therefore, do not use a Scan plus FilterExpression as a substitute for a good key or index design.

## 8. Secondary Indexes: GSI and LSI

Indexes support additional access patterns that the base table's primary key cannot efficiently answer.

### 8.1 Global Secondary Index (GSI)

A GSI can have a different partition key and optional sort key from the base table.

Example base table:

```text
PK = CUSTOMER#C1001
SK = ORDER#O501
```

A GSI could use:

```text
GSI1PK = ORDER#O501
GSI1SK = CUSTOMER#C1001
```

This can support lookups by order ID.

Key characteristics:

- Can use a different partition key and sort key.
- Can be added after table creation.
- Supports eventually consistent reads only.
- Has its own read/write capacity considerations in provisioned mode.
- Index projection determines which attributes are copied into the index.

### 8.2 Local Secondary Index (LSI)

An LSI:

- Uses the same partition key as the base table.
- Uses a different sort key.
- Must be created when the table is created.
- Supports strongly consistent reads.
- Shares the base table's partition-key distribution.

### 8.3 GSI vs. LSI

| Feature | GSI | LSI |
|---|---|---|
| Partition key | Can be different | Same as base table |
| Sort key | Optional/different | Different |
| Creation | At table creation or later | At table creation only |
| Strongly consistent read | No | Yes |
| Capacity | Separate capacity in provisioned mode | Uses base-table capacity model |
| Main purpose | New access pattern | Alternate sort order within same partition |

### 8.4 Index projection

Projection controls which attributes are stored in an index:

- `KEYS_ONLY`: key attributes only.
- `INCLUDE`: key attributes plus selected attributes.
- `ALL`: all attributes.

Project only what your access pattern needs. Larger indexes require more storage and can increase write and cost overhead.

## 9. Conditional Writes and Transactions

### 9.1 Conditional writes

A condition expression makes an operation succeed only when a condition is true.

Use cases:

- Create an item only if it does not already exist.
- Update a record only if its version is unchanged.
- Prevent an inventory quantity from becoming negative.
- Avoid overwriting a newer state with stale data.

Conceptual example:

```text
Update inventory
SET quantity = quantity - 1
ONLY IF quantity >= 1
```

Conditional writes are useful for concurrency control and avoiding lost updates.

### 9.2 Optimistic locking

Store a `version` attribute:

```json
{
  "productId": "P100",
  "price": 50,
  "version": 3
}
```

An update can require `version = 3` and then write `version = 4`. If another request has already updated the item, the condition fails and the application can reload and retry safely.

### 9.3 Transactions

DynamoDB transactions support ACID operations across supported items and tables in a single AWS account and Region. They are useful when multiple changes must succeed or fail together.

Transactions have operation and item-size limits and consume additional capacity. Use them for genuine atomic business requirements, not for every write.

## 10. TTL and DynamoDB Streams — Introduction

### Time to Live (TTL)

TTL allows DynamoDB to remove expired items asynchronously based on a configured numeric timestamp attribute.

Common use cases:

- Expiring temporary sessions.
- Removing short-lived tokens.
- Retaining temporary application state.

TTL deletion is not an exact-time scheduler. An expired item may remain visible for some time before it is deleted.

### DynamoDB Streams

Streams capture item-level modifications, such as inserts, updates, and deletes.

Common integrations:

```text
DynamoDB Table
      |
      v
DynamoDB Streams
      |
      v
AWS Lambda
      |
      +----> Send notification
      +----> Update search index
      +----> Publish event
```

Streams are useful for event-driven processing. Design consumers to handle retries and duplicate processing safely.

## 11. Security Best Practices

1. Use IAM roles for applications running on AWS.
2. Apply least-privilege IAM policies to specific tables and indexes.
3. Do not hardcode AWS access keys in source code.
4. Encryption at rest is enabled by default; choose a customer-managed AWS KMS key when your governance requirements need it.
5. Use TLS for requests in transit.
6. Consider a DynamoDB gateway VPC endpoint for private connectivity from a VPC.
7. Avoid exposing application credentials or sensitive attributes in logs.
8. Enable backups or point-in-time recovery when required by recovery objectives.
9. Review CloudTrail data events and other audit settings where appropriate.
10. Use separate IAM roles and tables or environments for development and production.

Example IAM policy concept (replace the account, Region, and table name):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:DeleteItem",
        "dynamodb:Query"
      ],
      "Resource": [
        "arn:aws:dynamodb:ap-southeast-1:123456789012:table/Orders",
        "arn:aws:dynamodb:ap-southeast-1:123456789012:table/Orders/index/*"
      ]
    }
  ]
}
```

Do not grant `dynamodb:*` to an application role unless there is a narrowly justified administrative requirement.

## 12. AWS CLI: Create and Work with a Table

### 12.1 Configure the CLI

```bash
aws configure
aws sts get-caller-identity
aws configure get region
```

Use `ap-southeast-1` in the examples. Prefer IAM Identity Center, role-based credentials, or another approved temporary-credential method over long-lived access keys.

### 12.2 Create an on-demand table

```bash
aws dynamodb create-table \
  --table-name Orders \
  --attribute-definitions \
    AttributeName=customerId,AttributeType=S \
    AttributeName=orderKey,AttributeType=S \
  --key-schema \
    AttributeName=customerId,KeyType=HASH \
    AttributeName=orderKey,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST \
  --region ap-southeast-1
```

`HASH` means partition key; `RANGE` means sort key.

Wait until the table is active:

```bash
aws dynamodb wait table-exists \
  --table-name Orders \
  --region ap-southeast-1
```

Inspect it:

```bash
aws dynamodb describe-table \
  --table-name Orders \
  --region ap-southeast-1
```

### 12.3 Put an item

```bash
aws dynamodb put-item \
  --table-name Orders \
  --item '{
    "customerId": {"S": "CUSTOMER#C1001"},
    "orderKey": {"S": "ORDER#2026-11-04#O501"},
    "status": {"S": "PAID"},
    "total": {"N": "125.50"}
  }' \
  --region ap-southeast-1
```

### 12.4 Get an item

```bash
aws dynamodb get-item \
  --table-name Orders \
  --key '{
    "customerId": {"S": "CUSTOMER#C1001"},
    "orderKey": {"S": "ORDER#2026-11-04#O501"}
  }' \
  --consistent-read \
  --region ap-southeast-1
```

### 12.5 Query a customer's orders

```bash
aws dynamodb query \
  --table-name Orders \
  --key-condition-expression "customerId = :customer" \
  --expression-attribute-values '{
    ":customer": {"S": "CUSTOMER#C1001"}
  }' \
  --region ap-southeast-1
```

### 12.6 Update an item

```bash
aws dynamodb update-item \
  --table-name Orders \
  --key '{
    "customerId": {"S": "CUSTOMER#C1001"},
    "orderKey": {"S": "ORDER#2026-11-04#O501"}
  }' \
  --update-expression "SET #s = :status" \
  --expression-attribute-names '{"#s": "status"}' \
  --expression-attribute-values '{":status": {"S": "SHIPPED"}}' \
  --region ap-southeast-1
```

### 12.7 Delete an item

```bash
aws dynamodb delete-item \
  --table-name Orders \
  --key '{
    "customerId": {"S": "CUSTOMER#C1001"},
    "orderKey": {"S": "ORDER#2026-11-04#O501"}
  }' \
  --region ap-southeast-1
```

### 12.8 Scan (for learning only)

```bash
aws dynamodb scan \
  --table-name Orders \
  --max-items 20 \
  --region ap-southeast-1
```

A Scan may require pagination and can consume substantial read capacity on a large table. Do not use it for a high-frequency production lookup when Query or an index can serve the access pattern.

**Cost warning:** DynamoDB usage can incur charges for reads, writes, storage, backups, streams, exports, data transfer, and other enabled features. Review current regional pricing and clean up lab resources when finished.

## 13. Spring Boot Integration with AWS SDK for Java 2.x

This example uses the low-level `DynamoDbClient`. It keeps AWS access inside a service class rather than putting database calls directly in a controller.

### 13.1 Maven dependencies

Use the AWS SDK for Java 2.x BOM to keep SDK module versions aligned. Replace the placeholder with an approved current SDK version in your project.

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>software.amazon.awssdk</groupId>
            <artifactId>bom</artifactId>
            <version>${aws.sdk.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>software.amazon.awssdk</groupId>
        <artifactId>dynamodb</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
</dependencies>
```

### 13.2 Configuration

```yaml
app:
  aws:
    region: ap-southeast-1
  dynamodb:
    table-name: Orders
```

```java
@Configuration
public class DynamoDbConfig {

    @Bean
    DynamoDbClient dynamoDbClient(
            @Value("${app.aws.region}") String region) {

        return DynamoDbClient.builder()
                .region(Region.of(region))
                .credentialsProvider(
                    DefaultCredentialsProvider.create()
                )
                .build();
    }
}
```

The default credentials provider chain can obtain credentials from supported sources, including an attached IAM role when the application runs on AWS. Do not place access keys in application properties.

### 13.3 Service class: create and read an order

```java
@Service
public class OrderService {

    private final DynamoDbClient dynamoDb;
    private final String tableName;

    public OrderService(
            DynamoDbClient dynamoDb,
            @Value("${app.dynamodb.table-name}") String tableName) {
        this.dynamoDb = dynamoDb;
        this.tableName = tableName;
    }

    public void createOrder(
            String customerId,
            String orderKey,
            String status,
            String total) {

        Map<String, AttributeValue> item = new HashMap<>();
        item.put("customerId", AttributeValue.builder()
                .s(customerId).build());
        item.put("orderKey", AttributeValue.builder()
                .s(orderKey).build());
        item.put("status", AttributeValue.builder()
                .s(status).build());
        item.put("total", AttributeValue.builder()
                .n(total).build());

        PutItemRequest request = PutItemRequest.builder()
                .tableName(tableName)
                .item(item)
                .conditionExpression(
                    "attribute_not_exists(customerId) " +
                    "AND attribute_not_exists(orderKey)"
                )
                .build();

        dynamoDb.putItem(request);
    }

    public Map<String, AttributeValue> getOrder(
            String customerId,
            String orderKey) {

        Map<String, AttributeValue> key = Map.of(
            "customerId", AttributeValue.builder()
                    .s(customerId).build(),
            "orderKey", AttributeValue.builder()
                    .s(orderKey).build()
        );

        GetItemResponse response = dynamoDb.getItem(
            GetItemRequest.builder()
                .tableName(tableName)
                .key(key)
                .consistentRead(true)
                .build()
        );

        return response.item();
    }
}
```

### 13.4 Controller

```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping
    public ResponseEntity<Void> create(
            @RequestParam String customerId,
            @RequestParam String orderKey,
            @RequestParam String status,
            @RequestParam String total) {

        orderService.createOrder(
            customerId, orderKey, status, total
        );
        return ResponseEntity.status(HttpStatus.CREATED).build();
    }

    @GetMapping
    public Map<String, AttributeValue> get(
            @RequestParam String customerId,
            @RequestParam String orderKey) {

        return orderService.getOrder(customerId, orderKey);
    }
}
```

For production, prefer validated request/response DTOs instead of exposing AWS SDK `AttributeValue` objects directly. Add exception mapping, structured logging, timeouts, retries appropriate to the workload, and tests. Consider the DynamoDB Enhanced Client for a more object-oriented mapping approach.

## 15. Troubleshooting

| Error or symptom | Likely cause | What to check |
|---|---|---|
| `ResourceNotFoundException` | Table or index does not exist in the selected Region | Table name, Region, account, table status |
| `AccessDeniedException` | IAM role lacks permission | Action, resource ARN, identity and resource policies |
| `ValidationException` | Invalid key, expression, or data type | Key schema, attribute names, expression syntax |
| `ConditionalCheckFailedException` | Condition evaluated to false | Current item state and condition logic |
| `ProvisionedThroughputExceededException` | Provisioned capacity exceeded | Capacity, traffic spikes, hot keys, auto scaling |
| `ThrottlingException` | Request was throttled | CloudWatch metrics, retry behavior, key distribution |
| Query returns no items | Partition key or sort-key condition does not match | Exact key values and data types |
| Scan is slow or expensive | Table is large or Scan is used frequently | Redesign around Query and indexes |
| GSI results appear behind | GSI reads are eventually consistent | Allow for propagation; avoid assuming immediate consistency |

Use exponential backoff with jitter for retryable throttling errors. Do not retry validation or authorization errors without correcting the underlying issue.

## 16. Practical Exercises with Answers

### Exercise 1 — Choose the database

An application needs complex joins across customers, invoices, and accounting records. Which database family is usually a better starting point?

**Answer:** A relational database such as Amazon RDS is usually a better starting point because joins and relational constraints are central to the workload.

### Exercise 2 — Choose a primary key

You need to retrieve all messages for a conversation in time order. Propose a composite key.

**Answer:**

```text
PK = CONVERSATION#<conversationId>
SK = MESSAGE#<timestamp>#<messageId>
```

This groups messages by conversation and orders them by the sort key.

### Exercise 3 — Query or Scan?

You know `customerId` and need all orders for that customer. Which operation should you use?

**Answer:** Use `Query` because the partition-key value is known.

### Exercise 4 — GSI or LSI?

You need to find orders by `orderId`, independently of the base table's customer partition key. Which index is appropriate?

**Answer:** A GSI is appropriate because it can use a different partition key.

### Exercise 5 — Strong consistency

Your application needs a strongly consistent read from a GSI. Is that supported?

**Answer:** No. GSI reads are eventually consistent. If strong consistency is required, reconsider the access pattern and whether the base table or an LSI can serve it.

### Exercise 6 — Prevent duplicate creation

You want to create an order only if its key does not already exist. What should you use?

**Answer:** A conditional `PutItem` with an `attribute_not_exists` condition on the key attributes.

### Exercise 7 — Diagnose throttling

A table receives heavy traffic for one partition-key value. What design issue might be present?

**Answer:** A hot key or hot partition. Review traffic distribution and consider a higher-cardinality key or write sharding if appropriate.

### Exercise 8 — TTL behavior

An item has an expiration timestamp that has passed. Must it disappear at that exact second?

**Answer:** No. TTL deletion is asynchronous; the item can remain for a period after expiration.

## 18. English Speaking Practice

Read each question aloud, then practice the model answer. Try to explain the idea again without reading.

### Question 1: What is Amazon DynamoDB?

**Model answer:**

Amazon DynamoDB is a fully managed NoSQL database service. It supports key-value and document data models. It is useful for applications that need low-latency access and can scale to a large number of requests.

### Question 2: What is the difference between a partition key and a sort key?

**Model answer:**

The partition key determines how DynamoDB distributes and locates items. The sort key organizes related items within the same partition-key value. Together, they form a composite primary key.

### Question 3: What is the difference between Query and Scan?

**Model answer:**

Query retrieves items using a partition-key value and optional sort-key conditions. Scan reads items across a table or index. Query is usually more efficient for normal application access patterns.

### Question 4: What is a Global Secondary Index?

**Model answer:**

A Global Secondary Index is an index with a different key schema from the base table. It allows an application to query data using another access pattern. GSI reads are eventually consistent.

### Question 5: How do you secure a DynamoDB application?

**Model answer:**

I use an IAM role with least-privilege permissions. I enable encryption at rest, use TLS in transit, and avoid hardcoding access keys. I also consider a VPC endpoint for private connectivity.

### Question 6: How can you prevent duplicate orders?

**Model answer:**

I can use a conditional write. The condition checks that the key does not already exist. If another request has already created the order, the condition fails and the application can handle the conflict.

## 19. AWS Interview Questions and Answers

**Q1. Is DynamoDB a relational database?**

No. It is a managed NoSQL database supporting key-value and document data models.

**Q2. What is the difference between a simple and composite primary key?**

A simple primary key contains only a partition key. A composite primary key contains a partition key and a sort key.

**Q3. Can a DynamoDB table have multiple partition-key values?**

Yes. Each item has a partition-key value, and many different values are normally used to distribute data and traffic.

**Q4. What is a hot key?**

A hot key is a key value that receives a disproportionate amount of traffic, potentially creating a throughput bottleneck.

**Q5. What is the difference between GSI and LSI?**

A GSI can have a different partition key and can be added after table creation. An LSI shares the base table's partition key, has a different sort key, and must be created with the table.

**Q6. Does FilterExpression reduce read capacity consumption?**

No. Filtering is applied after the items for the operation have been read.

**Q7. When should you use Query instead of Scan?**

Use Query when the access pattern can be served by a known partition-key value and optional sort-key condition.

**Q8. What is DynamoDB TTL?**

TTL is an asynchronous expiration mechanism that removes items after a configured expiration timestamp.

**Q9. What is DynamoDB Streams?**

Streams capture item-level changes and can trigger event-driven processing, often through AWS Lambda.

**Q10. How can an application authenticate to DynamoDB on EC2 or ECS?**

Use an attached IAM role and the AWS SDK default credentials provider chain. Avoid static access keys in application code.

**Q11. Can a GSI support strongly consistent reads?**

No. GSI reads are eventually consistent.

**Q12. How do you reduce throttling?**

Review capacity mode and metrics, distribute traffic across partition keys, avoid hot keys, and implement appropriate retry behavior with exponential backoff and jitter.
