## 2. Why Advanced VPC Networking Matters

A small application may run in one VPC. As an organization grows, it may have separate VPCs for:

- Production workloads.
- Development and testing.
- Shared services.
- Data analytics.
- Security and inspection.
- Applications owned by different teams.

An organization may also need to connect AWS to an office or data center.

Advanced networking services provide different ways to connect these environments.

### Example: Multiple VPCs

```text
                   AWS Region
                       |
       +---------------+----------------+
       |               |                |
       v               v                v
   Production VPC   Development VPC   Shared Services VPC
       |               |                |
   Spring Boot      Test APIs         DNS / Logging
   Services         and Workers       Shared Tools
```

The key design question is:

**How should these networks communicate while remaining secure, scalable, and manageable?**

## 3. VPC Peering

**VPC Peering** creates a network connection between two VPCs so that resources can communicate using private IP addresses.

A peering connection can connect:

- Two VPCs in the same Region.
- VPCs in different Regions.
- VPCs owned by the same AWS account.
- VPCs owned by different AWS accounts, subject to acceptance and configuration requirements.

### Basic architecture

```text
             VPC A                         VPC B
         10.0.0.0/16                   10.1.0.0/16
              |                             |
              v                             v
        EC2 / Services  <--- Peering ---> EC2 / Services
```

Traffic uses private IP addresses and the peering connection, provided that routes and security rules allow it.

### Route table configuration

Suppose:

- VPC A: `10.0.0.0/16`
- VPC B: `10.1.0.0/16`
- Peering connection: `pcx-abc123`

VPC A route table:

| Destination | Target |
|---|---|
| `10.0.0.0/16` | local |
| `10.1.0.0/16` | `pcx-abc123` |

VPC B route table:

| Destination | Target |
|---|---|
| `10.1.0.0/16` | local |
| `10.0.0.0/16` | `pcx-abc123` |

You must configure routes on both sides for the intended bidirectional communication.

### VPC Peering requirements

1. The VPC CIDR ranges must not overlap for the peering connection.
2. The peering connection must be created.
3. The accepter must accept the request when required.
4. Route tables must contain routes to the peer CIDR.
5. Security Groups and NACLs must allow the traffic.
6. DNS resolution options may need configuration if private DNS names are used.

### Important limitation: non-transitive routing

VPC Peering does not provide transitive routing.

Consider:

```text
       VPC A
          |
       Peering
          |
       VPC B
          |
       Peering
          |
       VPC C
```

VPC A cannot use VPC B as a router to reach VPC C through the two peering connections.

If A needs to communicate with C, you need a direct peering connection between A and C or a different network architecture such as Transit Gateway.

### When should you use VPC Peering?

- A small number of VPCs need direct communication.
- The network topology is simple.
- You do not need transitive routing.
- You want a direct VPC-to-VPC connection.

### When can peering become difficult?

If many VPCs need to communicate with one another, the number of peer connections and route-table entries can grow quickly.

For a full mesh of \(n\) VPCs, the number of pairwise connections is:

\[
\frac{n(n-1)}{2}
\]

For example, 6 VPCs in a full mesh require 15 pairwise connections.

## 4. AWS Transit Gateway

**AWS Transit Gateway** acts as a central network hub. It can connect multiple VPCs and supported network attachments.

### Hub-and-spoke architecture

```text
                  Production VPC
                        |
                        |
Development VPC --- Transit Gateway --- Shared Services VPC
                        |
                        |
                  Analytics VPC
                        |
                        |
                 VPN / Data Center
```

Each connected network is commonly called a spoke. The Transit Gateway is the hub.

### Why use Transit Gateway?

- Connect many VPCs through a central service.
- Support transitive routing through the hub, when route tables and attachments are configured appropriately.
- Connect VPCs and supported on-premises network links.
- Centralize network segmentation and routing.
- Reduce the operational complexity of large peering meshes.

### Transit Gateway attachments

Common attachment types include:

- VPC attachments.
- Site-to-Site VPN attachments.
- Direct Connect gateway associations through supported Transit Gateway integration.
- Transit Gateway peering attachments.

Exact supported attachment types and constraints depend on the service configuration and Region.

### Transit Gateway route tables

Transit Gateway has its own route tables, separate from VPC subnet route tables.

A route table determines which attachment receives traffic for a destination CIDR.

A typical packet path needs both:

1. A VPC subnet route pointing to the Transit Gateway.
2. A Transit Gateway route pointing to the destination attachment.

The destination VPC also needs a return route.

### Example

VPC A: `10.0.0.0/16`

VPC B: `10.1.0.0/16`

VPC A subnet route table:

| Destination | Target |
|---|---|
| `10.1.0.0/16` | Transit Gateway |

Transit Gateway route table:

| Destination | Attachment |
|---|---|
| `10.1.0.0/16` | VPC B attachment |

VPC B must also have a route back to `10.0.0.0/16` through the Transit Gateway.

### Network segmentation

Transit Gateway route tables can help separate environments.

Example:

```text
                  Transit Gateway
                         |
             +-----------+-----------+
             |                       |
             v                       v
       Production RT             Development RT
             |                       |
        Prod VPCs               Dev VPCs
             |                       |
       Approved shared services routes
```

A central hub does not automatically mean every VPC can communicate with every other VPC. Route-table associations and propagations determine reachability.

### Transit Gateway vs VPC Peering

| Feature | VPC Peering | Transit Gateway |
|---|---|---|
| Architecture | Direct connection | Central hub |
| Transitive routing | No | Supported through configured routing |
| Many VPCs | Can become complex | Designed for larger connected networks |
| Central routing | No central routing hub | Central route tables |
| On-premises integration | Not a general VPN hub | Supports VPN and Direct Connect integration patterns |
| Cost | Peering and data transfer charges may apply | Attachment, data processing, and data transfer charges may apply |
| Best fit | Simple direct connections | Larger networks and hub-and-spoke designs |

Choose based on topology, routing requirements, security boundaries, and cost—not simply because one service is newer.

## 5. Site-to-Site VPN

AWS Site-to-Site VPN creates an encrypted connection between an on-premises network and an AWS network.

It commonly uses IPsec tunnels over the Internet.

### Architecture

```text
       On-Premises Data Center
        192.168.0.0/16
                |
                v
       Customer Gateway Device
                |
          IPsec Tunnels
                |
                v
          AWS VPN Gateway
                |
                v
             AWS VPC
             10.0.0.0/16
```

A Site-to-Site VPN connection commonly provides two tunnels for availability. Configure and monitor both tunnels according to AWS guidance and your network-device capabilities.

### Main components

**Customer Gateway device**

The physical or software VPN device on the customer side.

**Customer Gateway resource**

An AWS resource representing the customer gateway device and its public IP address or supported configuration.

**Virtual Private Gateway (VGW)**

An AWS VPN endpoint attached to a VPC for supported Site-to-Site VPN architectures.

**Transit Gateway**

Can also be used as the AWS-side endpoint for Site-to-Site VPN connections in supported designs.

### Static vs dynamic routing

| Routing type | Description |
|---|---|
| Static | Routes are configured explicitly |
| Dynamic | Routes are exchanged using BGP |

Dynamic routing with BGP is useful for networks that need to exchange routes automatically and adapt to route changes.

### VPN characteristics

- Encrypted tunnels.
- Uses the public Internet as the underlying transport in the common Site-to-Site VPN model.
- Can be deployed faster than a dedicated physical connection.
- Performance depends on tunnel configuration, traffic, and service characteristics.
- Useful for hybrid connectivity and backup paths.

### VPN vs Direct Connect

A VPN is encrypted over the Internet. Direct Connect provides a dedicated network connection to AWS but is not automatically encrypted at the physical connection layer. You can use additional encryption, such as VPN over Direct Connect, when required.

## 6. AWS Direct Connect

**AWS Direct Connect** provides a dedicated network connection from an organization’s data center, office, or colocation facility to AWS.

### Architecture

```text
          Company Data Center
                  |
                  v
          Customer Router
                  |
                  v
        Direct Connect Location
                  |
                  v
             AWS Network
                  |
          +-------+-------+
          |               |
          v               v
       VPC A           VPC B
```

### Benefits

- More consistent network performance than Internet-based connectivity in many use cases.
- Private connectivity to AWS through a supported Direct Connect design.
- Can support higher bandwidth requirements.
- Can reduce reliance on the public Internet for hybrid network traffic.

### Important considerations

- Direct Connect is not automatically encrypted.
- It requires planning with a Direct Connect location or partner.
- Provisioning may take longer than creating a VPN.
- Resilience requires a deliberate design, often using multiple connections and locations.
- A VPN can be used as a backup or additional encrypted path.
- Direct Connect does not automatically give every VPC connectivity; routing and gateway associations still need to be configured.

### Virtual interfaces

Common virtual interface types include:

| Type | Purpose |
|---|---|
| Private virtual interface | Access private resources in a VPC through supported gateway designs |
| Public virtual interface | Access supported AWS public service endpoints |
| Transit virtual interface | Connect to a Transit Gateway through a Direct Connect gateway |

Exact options depend on the Direct Connect gateway and network architecture.

### Direct Connect vs Site-to-Site VPN

| Feature | Site-to-Site VPN | Direct Connect |
|---|---|---|
| Transport | Commonly IPsec over Internet | Dedicated network connection |
| Encryption | IPsec encryption | Not encrypted by default |
| Provisioning | Often faster | May take longer |
| Performance | Depends on Internet and tunnel conditions | More consistent network path in many cases |
| Cost | VPN and data transfer charges | Port, connection, provider, and data transfer charges |
| Typical use | Hybrid connectivity and backup | Consistent private connectivity and higher throughput needs |

## 7. AWS PrivateLink

**AWS PrivateLink** enables private connectivity to supported services without exposing traffic to the public Internet.

It is commonly used through interface VPC endpoints.

### Service consumer and provider

A service provider exposes a service through a supported endpoint service. A consumer creates an interface endpoint in its VPC to connect privately.

```text
             Consumer VPC
                  |
                  v
         Interface VPC Endpoint
                  |
             AWS PrivateLink
                  |
                  v
            Provider Service
               (VPC)
```

### Why use PrivateLink?

- Private access to services across VPC boundaries.
- Service-provider and service-consumer separation.
- Avoids requiring broad VPC-to-VPC network connectivity.
- Useful for SaaS providers and internal shared services.

### PrivateLink vs VPC Peering

| Feature | PrivateLink | VPC Peering |
|---|---|---|
| Connectivity | Access to a specific service through an endpoint | Network connectivity between VPC CIDR ranges |
| Consumer access | Limited to exposed service | Can reach routed resources in peer VPC |
| Transitive routing | Not a general network-routing solution | No |
| CIDR overlap | Can support service access without general CIDR routing; check endpoint-service constraints | Overlapping CIDRs prevent peering |
| Common use | Publish an internal API to consumers | Connect two networks |

PrivateLink is service-oriented. It is not a replacement for general-purpose network connectivity.

## 8. Choosing a Connectivity Architecture

| Requirement | Possible AWS solution |
|---|---|
| Connect two VPCs directly | VPC Peering |
| Connect many VPCs through a hub | Transit Gateway |
| Connect an office to one VPC | Site-to-Site VPN with a VGW |
| Connect an office to multiple VPCs | Site-to-Site VPN with Transit Gateway |
| Dedicated hybrid connectivity | Direct Connect |
| Private access to a specific service | AWS PrivateLink |
| Private access to S3 from a VPC | S3 Gateway VPC Endpoint |
| Backup hybrid connectivity | VPN alongside Direct Connect, where appropriate |

### Decision guide

```text
Need to connect two VPCs?
        |
        +---- Simple direct connection?
        |           |
        |           v
        |       VPC Peering
        |
        +---- Many VPCs / central routing?
                    |
                    v
              Transit Gateway

Need to connect on-premises?
        |
        +---- Fast encrypted connection over Internet?
        |           |
        |           v
        |       Site-to-Site VPN
        |
        +---- Dedicated network connection?
                    |
                    v
                Direct Connect

Need access to one provider service privately?
        |
        v
     PrivateLink
```

## 9. CIDR Overlap and Network Planning

Overlapping CIDR ranges are a common cause of network integration problems.

Example:

```text
VPC A: 10.0.0.0/16
VPC B: 10.0.0.0/16
```

Both networks use the same IP range. This prevents ordinary VPC Peering between them and complicates routing through other connectivity designs.

### Better planning

Example:

```text
Production VPC:    10.10.0.0/16
Development VPC:   10.20.0.0/16
Shared Services:   10.30.0.0/16
Analytics VPC:     10.40.0.0/16
On-Premises:       172.20.0.0/16
```

Plan address space before creating VPCs, especially when future connectivity to other accounts, Regions, or data centers is likely.

### If CIDRs already overlap

Possible strategies depend on the service and use case:

- Renumber one network, if feasible.
- Use application-level connectivity instead of general IP routing.
- Publish a service through PrivateLink where suitable.
- Use a proxy or translation architecture when appropriate and supported.
- Avoid assuming Transit Gateway will automatically solve overlapping CIDRs.

A network design should be reviewed before implementation.

Set the Region and confirm the account:

```bash
aws configure set region ap-southeast-1
aws sts get-caller-identity
```

```bash
aws ec2 describe-vpc-peering-connections \
  --query "VpcPeeringConnections[].[VpcPeeringConnectionId,Status.Code,RequesterVpcInfo.VpcId,AccepterVpcInfo.VpcId]" \
  --output table
```

```bash
aws ec2 describe-vpc-peering-connections \
  --vpc-peering-connection-ids pcx-REPLACE_ME
```

```bash
aws ec2 describe-transit-gateways \
  --query "TransitGateways[].[TransitGatewayId,State,OwnerId]" \
  --output table
```

```bash
aws ec2 describe-transit-gateway-attachments \
  --query "TransitGatewayAttachments[].[TransitGatewayAttachmentId,TransitGatewayId,ResourceType,ResourceId,State]" \
  --output table
```

```bash
aws ec2 describe-transit-gateway-route-tables \
  --query "TransitGatewayRouteTables[].[TransitGatewayRouteTableId,State]" \
  --output table
```

```bash
aws ec2 describe-vpn-connections \
  --query "VpnConnections[].[VpnConnectionId,State,Type,TransitGatewayId,VpnGatewayId]" \
  --output table
```

### 10.7 List Virtual Private Gateways

```bash
aws ec2 describe-vpn-gateways \
  --query "VpnGateways[].[VpnGatewayId,State,Type]" \
  --output table
```

### 10.8 List Customer Gateways

```bash
aws ec2 describe-customer-gateways \
  --query "CustomerGateways[].[CustomerGatewayId,State,Type,IpAddress]" \
  --output table
```

### 10.9 List VPC endpoints

```bash
aws ec2 describe-vpc-endpoints \
  --query "VpcEndpoints[].[VpcEndpointId,VpcId,ServiceName,VpcEndpointType,State]" \
  --output table
```

### 10.10 List Direct Connect connections

Direct Connect resources are managed through the Direct Connect API:

```bash
aws directconnect describe-connections \
  --query "connections[].[connectionId,connectionName,connectionState,bandwidth]" \
  --output table
```

These commands inspect resources. They do not create connectivity or prove that an end-to-end application connection works.

## 11. Hands-on Lab: Design a Multi-VPC Architecture

### Lab objective

Design a network for a company with three VPCs and an on-premises data center.

Requirements:

- Production VPC hosts customer-facing Spring Boot services.
- Development VPC hosts test services.
- Shared Services VPC hosts internal DNS, logging, and common tools.
- On-premises network needs access to approved private services.
- Production and development must be isolated except for explicitly approved shared services.

### Step 1 — Allocate CIDR ranges

| Network | CIDR |
|---|---|
| Production VPC | `10.10.0.0/16` |
| Development VPC | `10.20.0.0/16` |
| Shared Services VPC | `10.30.0.0/16` |
| On-premises | `172.20.0.0/16` |

Confirm that these ranges do not overlap with any existing networks.

### Step 2 — Choose a hub-and-spoke design

Use Transit Gateway as the central routing hub.

```text
                    On-Premises Network
                       172.20.0.0/16
                              |
                         Site-to-Site VPN
                              |
                              v
                       Transit Gateway
                       /      |      \
                      /       |       \
                     v        v        v
               Production  Development Shared Services
                  VPC         VPC          VPC
              10.10/16     10.20/16      10.30/16
```

### Step 3 — Define traffic requirements

| Source | Destination | Allow? | Reason |
|---|---|---|---|
| Production | Shared DNS | Yes | Name resolution |
| Production | Shared logging | Yes | Centralized monitoring |
| Development | Shared DNS | Yes | Name resolution |
| Development | Production database | No | Environment isolation |
| On-premises admin network | Approved management endpoints | Yes | Operations |
| Internet | Private database | No | Protect database |

These are example requirements. Real rules should be approved by the network and security owners.

### Step 4 — Design Transit Gateway route tables

Create separate route-table associations or policies to enforce environment segmentation.

For example:

- Production attachment associates with a production route table.
- Development attachment associates with a development route table.
- Shared Services attachment is reachable only from approved networks.
- On-premises routes are propagated or configured only where needed.

Do not associate every attachment with one permissive route table unless full connectivity is intended.

### Step 5 — Design VPC routes

Each VPC subnet route table needs routes to the intended remote CIDRs through the Transit Gateway.

Example for Production VPC:

| Destination | Target |
|---|---|
| `10.10.0.0/16` | local |
| `10.30.0.0/16` | Transit Gateway |
| `172.20.0.0/16` | Transit Gateway |

Do not add a route to Development unless the approved architecture requires it.

### Step 6 — Apply workload security

Even when routing exists, Security Groups and NACLs should restrict application traffic.

For example:

- Spring Boot API accepts HTTPS from the intended ALB.
- Application instances accept the application port from the ALB security group.
- Database accepts connections only from the application security group.
- Management access uses approved private paths or Systems Manager.

### Step 7 — Validate connectivity

Test each approved flow:

1. Production to shared DNS.
2. Production to shared logging.
3. Development to shared DNS.
4. On-premises to approved management endpoints.
5. Development to production database should fail.
6. Public Internet to private database should fail.

Use application-level tests, route inspection, security review, and Flow Logs where appropriate.

### Step 8 — Review resilience and cost

Check:

- Transit Gateway attachment placement.
- VPN tunnel health and routing.
- Whether Direct Connect is required.
- Whether a backup VPN is appropriate.
- Data processing and transfer costs.
- Route-table segmentation.
- Monitoring and alerting.

### Step 9 — Clean up

This is a design exercise unless you intentionally deploy resources. If you deploy a live Transit Gateway, VPN, or Direct Connect-related resource, review dependencies and charges before deleting anything.

## 12. Troubleshooting Advanced Connectivity

When two networks cannot communicate, check the complete path.

### Troubleshooting checklist

1. Are the source and destination CIDR ranges overlapping?
2. Is the connection or attachment in an available state?
3. Is the source subnet route table configured?
4. Is the Transit Gateway route table configured, if used?
5. Is the destination VPC route table configured?
6. Is the return route present?
7. Do Security Groups permit the traffic?
8. Do NACLs permit both directions?
9. Are DNS settings and private hosted-zone associations correct?
10. Are VPN tunnels up?
11. Are BGP routes being exchanged as expected?
12. Are operating-system firewalls and application listeners configured?
13. Do Flow Logs or service monitoring show rejected traffic?

### Symptom comparison

| Symptom | Possible causes |
|---|---|
| VPC A cannot reach VPC B | Missing route, peering not active, security rule, overlapping CIDR |
| Peered VPC can reach one subnet but not another | Route-table association or security differences |
| Transit Gateway attachment is available but traffic fails | Missing TGW route, missing VPC route, return path |
| VPN tunnel is down | Customer gateway configuration, routing, IPsec parameters, network issue |
| VPN is up but application fails | Missing routes, security rules, DNS, host firewall |
| PrivateLink endpoint cannot connect | Endpoint state, endpoint SG, provider acceptance or service configuration, DNS |
| DNS name fails but IP works | DNS resolution or private DNS configuration |

### Useful diagnostic tools

- `describe-route-tables`
- `describe-security-groups`
- `describe-network-acls`
- `describe-vpc-peering-connections`
- `describe-transit-gateway-route-tables`
- `describe-vpn-connections`
- VPC Flow Logs
- Reachability Analyzer
- Application logs and connection tests

Reachability Analyzer can help analyze supported network paths and identify configuration blockers. It is not a live packet capture and does not replace application testing.

## 13. Common Advanced Networking Mistakes

1. Creating VPC Peering and assuming it provides transitive routing.
2. Forgetting to configure routes on both sides of a peering connection.
3. Using overlapping CIDRs across networks that need ordinary IP connectivity.
4. Creating a Transit Gateway but forgetting its route-table configuration.
5. Adding a route in the VPC but forgetting the return route.
6. Assuming Transit Gateway automatically allows all attached VPCs to communicate.
7. Treating a Site-to-Site VPN as a dedicated private physical circuit.
8. Assuming Direct Connect encrypts traffic by default.
9. Forgetting that Direct Connect still needs routing and gateway configuration.
10. Using PrivateLink when general network routing is required.
11. Exposing a provider service more broadly than intended.
12. Ignoring cross-AZ, data processing, and data transfer charges.
13. Failing to monitor VPN tunnels and BGP route changes.
14. Testing only one direction of a network flow.

## 14. Practical Exercises

### Exercise 1 — VPC Peering

**Question:** What does VPC Peering do?

**Answer:** It creates a private network connection between two VPCs so resources can communicate using private IP addresses when routes and security rules permit.

### Exercise 2 — Non-transitive routing

**Question:** VPC A peers with VPC B, and VPC B peers with VPC C. Can A automatically reach C through B?

**Answer:** No. VPC Peering does not provide transitive routing.

### Exercise 3 — Transit Gateway

**Question:** What problem does Transit Gateway solve?

**Answer:** It provides a central hub for connecting many VPCs and supported network attachments, reducing the complexity of large peering meshes.

### Exercise 4 — Transit Gateway routing

**Question:** Is creating a VPC attachment enough to make two VPCs communicate?

**Answer:** No. VPC route tables, Transit Gateway route tables, return routes, and security controls must all be configured.

### Exercise 5 — Site-to-Site VPN

**Question:** What is the common transport for AWS Site-to-Site VPN?

**Answer:** IPsec tunnels over the public Internet in the common Site-to-Site VPN architecture.

### Exercise 6 — VPN tunnels

**Question:** Why does a Site-to-Site VPN commonly provide two tunnels?

**Answer:** To support availability and resilient connectivity. Both tunnels should be configured and monitored according to the design.

### Exercise 7 — Direct Connect

**Question:** Is Direct Connect encrypted by default?

**Answer:** No. Direct Connect provides a dedicated network connection, but encryption is not automatic. Use an additional encryption solution when required.

### Exercise 8 — PrivateLink

**Question:** What is the main difference between PrivateLink and VPC Peering?

**Answer:** PrivateLink provides private access to a specific service. VPC Peering provides network connectivity between VPC CIDR ranges.

### Exercise 9 — CIDR overlap

**Question:** Why is overlapping CIDR a problem?

**Answer:** Routing becomes ambiguous, and services such as ordinary VPC Peering cannot connect VPCs with overlapping IPv4 CIDR ranges.

### Exercise 10 — Hybrid connectivity

**Question:** Which AWS service would you evaluate for a dedicated connection from a data center to AWS?

**Answer:** AWS Direct Connect. A Site-to-Site VPN may be used as an additional or backup path.

### Exercise 11 — Route troubleshooting

**Question:** A route exists from VPC A to VPC B, but the connection still fails. What else should you check?

**Answer:** Check the destination return route, Transit Gateway routes if applicable, Security Groups, NACLs, DNS, host firewall, application listener, and Flow Logs.

### Exercise 12 — Architecture

**Question:** A company has 20 VPCs and wants central routing. Which service should it evaluate?

**Answer:** AWS Transit Gateway is a strong candidate for a hub-and-spoke architecture, subject to routing, segmentation, scale, and cost requirements.

## 17. AWS Interview Questions and Answers

### Q1. What is VPC Peering?

VPC Peering is a network connection between two VPCs that allows private IP communication when routing and security settings permit.

### Q2. Does VPC Peering support transitive routing?

No. If A peers with B and B peers with C, A cannot automatically route through B to reach C.

### Q3. What is AWS Transit Gateway?

Transit Gateway is a managed network hub that connects VPCs and supported network attachments through centralized routing.

### Q4. What is the difference between VPC Peering and Transit Gateway?

VPC Peering provides direct connectivity between two VPCs. Transit Gateway provides a hub-and-spoke model for connecting many networks and supports transitive routing through configured route tables.

### Q5. What is a Transit Gateway attachment?

An attachment connects a supported network resource, such as a VPC or VPN, to a Transit Gateway.

### Q6. What are Transit Gateway route tables?

They control how traffic entering the Transit Gateway is forwarded to attachments based on destination routes.

### Q7. What is AWS Site-to-Site VPN?

It creates encrypted IPsec connectivity between an on-premises network and AWS through a supported VPN gateway architecture.

### Q8. Why are there two VPN tunnels?

The two tunnels support availability. Both should be configured and monitored for the intended resilient design.

### Q9. What is the difference between static and dynamic VPN routing?

Static routing uses manually configured routes. Dynamic routing uses BGP to exchange routes between the customer gateway and AWS.

### Q10. What is AWS Direct Connect?

Direct Connect provides a dedicated network connection from a customer network to AWS through supported Direct Connect locations and configurations.

### Q11. Is Direct Connect encrypted?

Not by default. Use additional encryption, such as VPN over Direct Connect, when required by the security design.

### Q12. What is AWS PrivateLink?

PrivateLink provides private connectivity to supported services through endpoint-based access, commonly using interface VPC endpoints.

### Q13. Does PrivateLink provide general VPC-to-VPC routing?

No. It provides access to a specific service, not general network connectivity between all resources in two VPCs.

### Q14. Why should CIDR ranges not overlap?

Overlapping ranges create ambiguous routing and prevent some network connectivity options, including ordinary VPC Peering.

### Q15. How would you troubleshoot Transit Gateway connectivity?

Check VPC subnet routes, Transit Gateway attachment state, Transit Gateway route-table association and propagation, destination routes, return routes, Security Groups, NACLs, DNS, and application settings.

### Q16. How would you design hybrid connectivity for a company?

I would evaluate Site-to-Site VPN for encrypted connectivity over the Internet and Direct Connect for dedicated connectivity. For multiple VPCs, I would evaluate Transit Gateway as the central routing hub. I would design route segmentation, redundant paths, monitoring, and security controls.
